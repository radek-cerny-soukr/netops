# Documentation map

This directory is mostly a signpost. Documentation lives with the component it describes, so it is released, versioned, and reviewed together with the code it documents; the one exception is a page that is about more than one component and therefore belongs to none of them.

| Component | Documentation |
|---|---|
| `netops-helper` | [`components/netops-helper/docs/`](../components/netops-helper/docs/) — security model, egress control, installation, onboarding, configuration, read-only accounts, tools, query catalogue, vendor CLI references, releasing, known vulnerabilities |
| `netops-auditor` | [`components/netops-auditor/docs/`](../components/netops-auditor/docs/) — collection channels, configuration, inventory, releasing and their documented limits |
| `netops-core` | [`components/netops-core/docs/`](../components/netops-core/docs/) — inventory and credential schemas, the SSH transport, the audit record, shared FortiOS parser and measured schemas, releasing |
| `netops-admin` | [`components/netops-admin/docs/`](../components/netops-admin/docs/) — planning rules, value limits, execution with the rollback safeguard, journal, limits, undo, MCP, audit export, installation, release process, measured scenarios and known limits |

Cross-component: [`verified-support.md`](verified-support.md) — per platform, what firmware, transport, authentication and account privilege the family has actually measured against a device, versus catalogue only; [`lab-measurements-2026-09-25.md`](lab-measurements-2026-09-25.md) — the combined 25 September 2026 catalogue and T-067 functional measurements: device preparation, per-query results, actual traffic, faults, recovery and coverage limits.

Repository-level policy is in [`../SECURITY.md`](../SECURITY.md) and [`../CONTRIBUTING.md`](../CONTRIBUTING.md); the release shape of the family is described [below](#releases), including how earlier versions are kept. Use the current release links in the root README for downloads, and verify every download as described [below](#verifying-a-release). Documentation inside a published archive is fixed at the moment that archive was signed; the documentation in this tree is the current one.

## Releases

Every component has its own version, its own tag prefix `netops-<component>/vX.Y.Z`, and its own release page with its own assets.

**Published versions stay published.** A new version gets its own release page, assets and tag; those of earlier versions remain, and a published tag is never moved. The component table in the root README links the current version of each component. Removing an earlier release is a separate, explicit decision taken only after its assets have been archived.

**PyPI is a delayed, secondary channel.** The release pages are authoritative, and the installation guides of the components install from their assets. PyPI publication is a separate workflow after GitHub; check exact-version availability before installing there. Historically, on 1 October 2026 PyPI carries `netops-core` 0.2.4, `netops-auditor` 0.2.7 and `netops-admin` 0.2.2, each older than the current release of its component, and Helper was absent on that date. Each upload is a source distribution and a wheel built from the release tag by [`publish-pypi.yml`](../.github/workflows/publish-pypi.yml), uploaded through trusted publishing, optionally via TestPyPI or directly to PyPI with the required approval; those files are not assets of the release page and are not covered by its Sigstore bundle. An uploaded `netops-auditor` or `netops-admin` pins the exact versions of the other components it needs. For `netops-helper` an upload would carry the client side only, the stdio proxy an MCP client launches; its server runs as an image built from the release archive, and its runtime dependencies are installed there from a hash lock that `pip install` would not apply.

Three of the earliest versions - `netops-auditor` 0.2.2, `netops-core` 0.2.1 and `netops-helper` 0.3.2 - were removed under an earlier one-version-per-component rule. The tag `netops-helper/v0.3.4` has no release page: its CI failed and 0.3.5 replaced it before publication. Every release is also one signed commit on `main`; checking out that commit recovers its source, not the original image, SBOM, scan or artifact signature, which are the assets of its release page. Changelog entries describe source history, including the removed versions.

A component release archive is self-contained: it carries the component tree, its own `LICENSE`, and its own changelog. Self-contained does not mean identical in shape: the `netops-helper` archive additionally vendors `src/netops_core`, the `netops-auditor` archive pins one exact `netops-core` version and needs that core archive installed beside it, the `netops-admin` archive pins both, and the `netops-helper` archive pins one exact `netops-core` version and needs that core archive too, because its vendored copy of `netops_core` is there for the image build and does not satisfy the pin for `pip`, and `netops-core` is a library archive with no image of its own. The released `netops-auditor` 0.2.8, `netops-admin` 0.2.4 and `netops-helper` 0.3.7 pin `netops-core==0.2.5`, `netops-auditor` 0.2.9, `netops-admin` 0.2.5 and `netops-helper` 0.3.8 pin `netops-core==0.2.6`, and `netops-auditor` 0.2.10, `netops-admin` 0.2.6 and `netops-helper` 0.3.9 pin `netops-core==0.2.7`; the current versions in this tree, `netops-auditor` 0.2.11, `netops-admin` 0.2.7 and `netops-helper` 0.3.10, pin `netops-core==0.2.8`. Repository-level files (this page, `SECURITY.md`, `CONTRIBUTING.md`, CI) live here and are not part of a component archive.

## Verifying a release

Each release page carries `<component>-<version>-release-SHA256SUMS`, the SHA-256 of every other asset of that page, and `<component>-<version>-release-SHA256SUMS.sigstore.json`, a Sigstore bundle that signs that manifest. The signing identity is the maintainer's GitHub account: certificate identity `325383355+radek-cerny-soukr@users.noreply.github.com`, OIDC issuer `https://github.com/login/oauth`. Verify the manifest first, then every asset against it, and use nothing that fails either step. With [cosign](https://github.com/sigstore/cosign), for the source archive of `netops-helper` 0.3.10:

```sh
component=netops-helper
version=0.3.10
base="https://github.com/radek-cerny-soukr/netops/releases/download/${component}%2Fv${version}"
for name in source.tar.gz release-SHA256SUMS release-SHA256SUMS.sigstore.json; do
  curl -fsSLO "${base}/${component}-${version}-${name}"
done
cosign verify-blob \
  --bundle "${component}-${version}-release-SHA256SUMS.sigstore.json" \
  --certificate-identity 325383355+radek-cerny-soukr@users.noreply.github.com \
  --certificate-oidc-issuer https://github.com/login/oauth \
  "${component}-${version}-release-SHA256SUMS"
sha256sum --check --ignore-missing "${component}-${version}-release-SHA256SUMS"
```

`cosign` prints `Verified OK`, and `sha256sum` prints `OK` for every downloaded asset. `--ignore-missing` skips the assets you did not download, so confirm that every file you use is listed. Add further asset names to the loop as needed, such as `linux-arm64.oci.tar` and `image-digest.txt` of a `netops-helper` release (`linux-amd64.oci.tar` and `linux-amd64-image-digest.txt` for its AMD64 image from 0.3.10) or `source.cdx.json`. The unpacked source archive carries its own `SHA256SUMS` and `release-manifest.json` for the files inside it; `sha256sum -c SHA256SUMS` in that directory checks them. Run on 2 October 2026 with cosign 3.1.3 against the published `netops-helper` 0.3.7 assets: both commands succeeded, and the same `cosign` call with a different `--certificate-identity` was refused.

## Repository gate

A tag run of CI tests the component that tag names, plus the repository gate; the jobs of the other three components are skipped, and a skipped job is not a test that passed. The state of the whole tree at that commit is what the `main` run of the same commit reports.

`scripts/check_release.py` is the gate for the tree as a whole. It fails closed when a tracked file belongs to no component release and to no reviewed repository file, when a component has no release selector or no gate of its own, when a component `LICENSE` differs from the repository one, when CI does not cover a component, or when any tracked file carries a private address, host name, path, or credential-shaped string. Each component then runs its own gate over its own tree: `components/netops-helper/scripts/check_public_release.py`, `components/netops-auditor/scripts/check_gates.py`, `components/netops-core/scripts/check_gates.py`, and `components/netops-admin/scripts/check_gates.py`.

```sh
python3 scripts/check_release.py                                    # whole repository
python3 tests/test_release_gate.py                                  # tests of this gate
```
