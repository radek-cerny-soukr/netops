# Verified platform support

Qualification uses local Docker state volumes; network-backed state storage, including NFS, is not qualified.

Compatibility is scoped to the exact platform, firmware build, model, account policy and operation documented by each component. Catalogue presence does not qualify every deployment. Software-image or synthetic results do not establish hardware forwarding, sensor or every timing path. Each target must satisfy its component's enrollment requirements.

## Host operating system

NetOps deployment hosts run Linux with Docker Engine and Compose. NetOps 1.0.7 was qualified on Debian 13 (amd64, arm64) and Fedora 44 (amd64 Server, arm64 Cloud Edition), with local state volumes. Fedora requires Docker SELinux support with the host enforcing. The 1.0.7 quickstart procedure was also exercised with the released 1.0.7 image on Ubuntu 26.04.1 LTS and 24.04.5 LTS (amd64, Docker Engine), on rootless Docker (Ubuntu 24.04.5 and Debian 13, amd64), on Raspberry Pi OS Lite 64-bit (arm64, a virtual machine with a Debian kernel) and on physical arm64 hardware, a single-board computer, with Raspberry Pi OS 64-bit (Docker 29.8.0, vendor kernel 6.12, 4 KiB pages); every run passed, and the Ubuntu 26.04.1 and Debian 13 rootless runs include a restart of the host. Not verified: kernels with 16 KiB pages, 32-bit Raspberry Pi OS and the Docker installation steps on physical hardware. The virtual-machine runs replaced `cat .env` with `grep`. On the physical Pi, Docker was already installed, Compose and cosign were placed in a private directory, and an isolated directory and Compose project were used; restart meant Compose `down`/`up`, not a host reboot. The Pi had an initial transient healthcheck failure and became healthy within about a minute. All runs used the 1.0.7 quickstart text and image and were not performed by an independent tester; qualification of the 1.0.8 image requires its own release acceptance. A newer acceptance of the 1.0.9 quickstart is documented for Debian 13 arm64: a blind installation by a tester who followed only the quickstart text, together with blind installations on Debian 13 and Fedora 44 (amd64), used the 1.0.9 pre-publication release-candidate files and passed functionally, with a test signature instead of the signature of the published release; it found no blocking defect in the product or in the installation procedure and left only documentation remarks. Debian 13 arm64 is therefore verified for 1.0.9 in that scope and no longer only for 1.0.7, while the other statements above stay dated as written. The minimum requirements are in the [README](../README.md#minimum-requirements). macOS and Windows are MCP client hosts only: Claude Code was tested there for 1.0.1; Codex was tested on Linux only. They are not supported or tested as NetOps servers. The [single-product quickstart](quickstart-1.0.md) is the only installation path. Engines are not separately installed. Support is bounded by the exact current release qualification; no platform inherits PASS from an older build.

### Admin safeguard on FortiOS 7.6 and 8.0

Referenced service delete/port changes and protected predefined-service changes were refused before writes. Not measured for this table: safeguard firing a POST inverse, SIGKILL with recovery, loss of the whole management path and comment/port-range length limits ([admin configuration](admin-configuration.md#opt-in-table-firewall-service-custom-measured-end-to-end)).

- FortiOS 8.0.1 and later: the `cli-script` safeguard is not used, because Fortinet changed the behaviour of auto-script. This is a FortiOS behaviour change, not a NetOps fault. The CLI script action runs on auto-script: "The CLI script action utilizes the auto-script feature to perform the execution of the script commands." (FortiOS Administration Guide, CLI script action, same text in [7.6.8](https://docs.fortinet.com/document/fortigate/7.6.8/administration-guide/639044/cli-script-action) and [8.0.2](https://docs.fortinet.com/document/fortigate/8.0.2/administration-guide/639044/cli-script-action)). ## Other platforms

Helper catalogues distinguish Arista EOS 4.36.1F, Cisco NX-OS 9.3(12), IOS-XE 17.18.2, IOS 15.9(3)M12 and IOS 15.2(20200924), and Junos 26.2R1.7 scope. Arista EOS container images (cEOS), virtual EOS images, Cisco virtual images and virtual Junos images do not establish corresponding physical hardware support. A CLI answer with a nonzero transport status differs from a device CLI error; neither extends compatibility to another build or command.

Linux read and diagnostic paths retain their documented distribution, architecture and permission requirements. Ruckus Unleashed retains the explicit administrator-bounded role and catalogue boundary; the catalogue does not reduce the device credential's privileges. A read catalogue or native timer on another platform does not imply Admin execution support there.

## Clock and state boundaries

FortiOS and ExtremeXOS safeguards can follow device-clock changes. Admin requires verified removal or return evidence tied to its own safeguard. Incomplete listings or missing proof do not establish success; unverified return leaves the operation unknown and the device blocked. FortiOS gives Admin no device proof that its stitch ran: when the state after the fire time and grace differs from the state before the change, Admin keeps a still installed stitch and reports unknown with the device blocked; only when the stitch is no longer installed does the operation end as revert-failed. A person removes a kept stitch after checking the device; a new change is refused while it is installed. A forward clock jump before a FortiOS safeguard is loaded can therefore leave an unreturned change as unknown, with a stitch that may never run.

Host-side elapsed budgets use monotonic time within one boot; across reboot, trusted elapsed time is not guaranteed. Shared admission locks and the journal preserve request identity, but separate journal/index files do not imply filesystem atomicity between those files.

## Operator responsibility

Verify the exact model, full firmware build, credential permissions, egress, catalogue scope, safeguard behavior and result interpretation before use. Unsupported or unspecified paths remain unsupported or unspecified. Full configuration collectors may need administrator credentials; fixed collector commands and the pinned device identity define that channel's read boundary. Keep collector credentials separate from Helper accounts and from the Auditor MCP surface.

Local-file auditing needs no device credential or connection, while workflow setup and result upload may use the network. Compatibility does not certify complete corpus recall, all hardware variants, every account grant or production exploitability. [Compatibility boundaries](compatibility-boundaries.md) describe the evidence classes and limits.

IOSv 15.9(3)M12 and IOL XE 17.18.2 route fallback is tested against anonymized lab lookup and routing table captures.
