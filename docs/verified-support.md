# Verified platform support

Qualification uses local Docker state volumes; network-backed state storage, including NFS, is not qualified.

Compatibility is scoped to the exact platform, firmware build, model, account policy and operation documented by each component. Catalogue presence does not qualify every deployment. Software-image or synthetic results do not establish hardware forwarding, sensor or every timing path. Each target must satisfy its component's enrollment requirements.

## Host operating system

NetOps deployment hosts run Linux with Docker Engine and Compose. Supported host families are Ubuntu, Debian and Fedora Server on amd64 and arm64, and Raspberry Pi OS 64-bit on arm64. Fedora requires Docker SELinux support with the host enforcing. Docker Engine runs as root or in rootless mode. macOS and Windows are supported only as MCP client hosts (Claude Code, Codex); they are not supported or tested as NetOps servers. The [single-product quickstart](quickstart-1.0.md) is the only installation path. Engines are not separately installed. Support is bounded by the exact current release qualification; no platform inherits PASS from an older candidate.

## FortiOS bounds

Documented FortiOS contracts distinguish 7.6.7 build3704, 7.6.8 build3744, 8.0.0 build0167 and 8.0.2 build0251. Current measurements cover only 7.6.8 build3744 and 8.0.2 build0251; the 7.6.7 build3704 and 8.0.0 build0167 contracts come from earlier measurements. FortiGate 60F, FortiGate 80F and FortiGate-VM64-KVM model scopes remain separate; software-image coverage does not establish physical forwarding or every firmware variant. Preserve the exact schema's model/build, reference semantics, conditionals, nested configuration, protected objects and restart requirements.

Helper reads use their documented catalogue and account policy. The opt-in FortiOS `managed_switch_stacking` and `managed_switch_poe` queries have no positive result: the tested switch is neither stacking- nor PoE-capable, so behavior on such hardware is unverified (see the [FortiOS reference](../components/netops-helper/docs/vendor-cli-references/fortinet-fortios.md)). Auditor SSH and REST collection require the [collector channel](../components/netops-auditor/docs/channels.md) permissions. Admin supports enrolled address, address-group, DHCP-reservation and explicitly bounded schema operations only; in NetOps 1.0 schema operations have no supported way to receive their binding files (see [Admin MCP tools](admin-configuration.md#mcp-tools)). Safeguard installation, readback, prediction and return proof remain mandatory.

### Admin safeguard on FortiOS 7.6 and 8.0

Admin writes (`firewall address`, `firewall addrgrp`, `system dhcp server/reserved-address`, `firewall policy`) need the device-side safeguard: a one-shot automation stitch whose `cli-script` action holds the inverse configuration commands.

- FortiOS 7.6: verified, works. On FortiGate 60F with FortiOS 7.6.8 build3744 the stitch reverted the change (enrollment self-test `reverted` on 2026-10-31, full `admin apply` runs on 2026-11-01).
- FortiOS 8.0.1 and later: the `cli-script` safeguard is not used, because Fortinet changed the behaviour of auto-script. This is a FortiOS behaviour change, not a NetOps fault. The CLI script action runs on auto-script: "The CLI script action utilizes the auto-script feature to perform the execution of the script commands." (FortiOS Administration Guide, CLI script action, same text in [7.6.8](https://docs.fortinet.com/document/fortigate/7.6.8/administration-guide/639044/cli-script-action) and [8.0.2](https://docs.fortinet.com/document/fortigate/8.0.2/administration-guide/639044/cli-script-action)). The Fortinet Community knowledge base article [Technical Tip: Automated scripts (auto-script). Execution, testing and verification explained with examples](https://community.fortinet.com/t5/FortiGate/Technical-Tip-Automated-script-execution/ta-p/193685) (a Technical Tip, not Release Notes) states: "Starting from FortiOS v8.0.1-build 0185, the auto-script engine only allows information-gathering commands (get, diagnose); 'execute' commands are not permitted in auto-script. Thus, backup using the auto-script feature will fail with the message 'unknown action or command is unavailable in auto-script'." On FortiGate 80F with FortiOS 8.0.2 build0251 (2026-11-01) the stitch fired, but the `cli-script` action refused every configuration line with `Unknown action or command is unavailable in auto-script`, also with `accprofile super_admin`, and the change stayed.
- From FortiOS 8.0.1 Admin uses a webhook safeguard instead: the one-shot stitch runs a `webhook` action that calls the REST API of the same FortiGate with a temporary API user (access profile with `fwgrp read-write` only, trusthost the device address /32) and sends the inverse request (`DELETE`, `PUT` or `POST`). The mechanism follows the snapshot firmware; there is nothing to configure. Measured on 2026-11-01 on a FortiGate 80F active-passive HA pair with FortiOS 8.0.2 build0251: the webhook removed a new address and a new policy (`DELETE`) and restored a changed policy attribute (`PUT`) after the administrator session had ended, 4 to 5 seconds after `trigger-datetime`, without traffic loss and with the HA pair in sync. On 2026-11-02 the full `admin apply` path was measured on the same pair with a `super_admin` write account: enrollment self-test `reverted`, policy create, update and undo `confirmed`, `PUT`, `DELETE` and `POST` inverses `reverted` after loss of the check account, SIGKILL with `admin recover` `reverted`, API key generated by Admin after the device password prompt, configuration unchanged after cleanup. Preflight, token life cycle and residual risk: [webhook safeguard contract](fortios-webhook-safeguard-contract.md) and [Admin configuration](admin-configuration.md#webhook-safeguard-on-fortios-801-and-later).
- Admin refuses every FortiOS 8.0.x build that a profile does not list, before any device write; the refusal names this change and that Admin uses the webhook safeguard from 8.0.1 and the `cli-script` safeguard on 8.0.0, once the build is measured. 8.0.0 build0167 stays listed for `firewall address`, `firewall addrgrp` and `system dhcp server/reserved-address`: there the stitch restored the change on 2026-09-23, on a build older than the one Fortinet names. It is no longer measured.
- The FortiOS 8.0.0, 8.0.1 and 8.0.2 Release Notes and the CLI Reference do not describe the change: `config system automation-action` and `config system auto-script` have the same fields in 7.6.8 and 8.0.2, and the 8.0.2 Administration Guide still shows CLI script examples with configuration commands (CLI script action, FortiGate Rugged digital I/O trigger logging enhancement). The Technical Tip is the Fortinet document that states it.

## EXOS bounds

ExtremeXOS contracts distinguish 33.7.1.6, 33.7.1.6-patch1-11 and the 33.6.1.14 virtual-image scope. Generic hardware model identifiers include Extreme X435-8P-4S, X440-G2-12p and X440-G2-12p-10G4; a model contract does not imply support for every firmware or device in the family. Virtual-image behavior does not establish physical forwarding, sensor or save behavior.

Helper catalogues keep their platform-specific diagnostic exclusions. Auditor full configuration collection requires administrator privilege. Admin supports only enrolled VLAN, port display-string and port-membership profiles. Safeguard confirmation requires its own identity and a complete count-and-row listing. A count without rows never proves absence.

The account fingerprint covers explicit create/configure configuration rows; implicit accounts and changes outside those rows are outside that fingerprint. It is not a complete account or privilege inventory.

## FortiADC bounds

FortiADC-KVM 7.6.7 build0676 (virtual image, standalone) is the only FortiADC scope. The current Helper catalogue contains thirty-three queries (`system_status` and eighteen further views, three installed inactive-state BGP/OSPF reads, six further source-qualified reads, two installed TLS statistics queries and three DoS block-count reads); exact command scope and qualification are in the [FortiADC reference](../components/netops-helper/docs/vendor-cli-references/fortinet-fortiadc.md). NetOps 1.0.4 had only `system_status` (`get system status`); NetOps 1.0.5 adds the other thirty-two queries, among them eighteen further read-only views (`system_performance`, `vm_license`, `interface_state`, `interface_counters`, `routing_table`, `arp_table`, `firewall_timeouts`, `slb_load`, `slb_vs_stat`, `waf_signature_status`, `cpu_info`, `slb_sessions`, `persistence_sessions`, `nic_detail`, `waf_block_ip`, `log_list_traffic`, `log_list_attack`, `autoupdate_contract`); before returning a result, the Helper confirms that the live device identifies itself as FortiADC and removes the CLI prompt that frames the exec answer. Verified on 2026-10-27 against FortiADC-KVM v7.6.7 build0676 with a read-only account: the positive read returns rc 0 with the prompt removed; a query outside the catalogue, another platform name, a wrong host key pin and an unknown alias are refused; a FortiADC enrolled as FortiOS is refused before any query output is returned. Repeated with the final NetOps 1.0.4 image on 2026-10-28: `system_status` returned rc 0 with the FortiADC-KVM v7.6.7 build0676 identity, and the same refusals held, together with the refusal of a raw `command` argument. The eighteen later queries have reference runs of 2026-10-30 on the same VM image (three batches), made with a system administrator account (`is-system-admin yes`, as the built-in `admin`); in the three access profiles tested, the seven `diagnose` and `get router` queries among the first eleven were refused wherever tried with `Command fail. Return code is -284 (CLI parsing error.)` while the system-admin control succeeded, so the account for them is enrolled as `admin-bounded` with `role_boundary: "catalogue"`, which is not a device-read-only account and the read-only status result does not establish permission for those commands; it covers the device commands, not every Helper path, and `slb_vs_stat` was observed only for a virtual server in the state `DEAD`. The Auditor audits an exported FortiADC-KVM 7.6.7 build 0676 configuration text with its identity metadata (`auditor run --platform fortiadc`); `auditor collect` refuses FortiADC. The Admin `pool-member` operation was verified live only as described in the 1.0.5 measurements above (one member of a two-member pool disabled and re-enabled, the last healthy member refused; standalone, development build), and for `pool-member-add` and `pool-member-remove` as follows. On 2026-10-31, `pool-member-add` created a disabled member with a confirmed readback and `pool-member-remove` removed that disabled member with a confirmed readback; the pool equalled its initial state afterwards. On 2026-11-01, with a failure injected after the real deletion of a disabled member, `pool-member-remove` wrote the inverse create, the device accepted it, the result was `rolled_back` with the member present, the pool readback equalled the state before the removal, and the final removal and cleanup left the pool equal to its initial state. Both runs used a development build of the 1.0.5 source, not the final image; refusal of an enabled member, of the last member and of a member with settings that cannot be restored is covered by tests only, not by a live run; other operations and the final 1.0.5 image are not covered.

The 2026-10-30 installed Helper measurement on this same standalone model/build returned explicit inactive BGP and disabled OSPF states through the three routing reads, five successful ping replies, a DNS CNAME and three IPv4 addresses, HTTP 200 with the health endpoint body, and one UP/status-200 health-check result. The bounded traceroute returned three unresponsive hops and was interrupted at its 60-second deadline with `complete=false`; it did not establish target reachability. ## Other platforms

Helper catalogues distinguish Arista EOS 4.36.1F, Cisco NX-OS 9.3(12), IOS-XE 17.18.2, IOS 15.9(3)M12 and IOS 15.2(20200924), and Junos 26.2R1.7 scope. Arista EOS container images (cEOS), virtual EOS images, Cisco virtual images and virtual Junos images do not establish corresponding physical hardware support. A CLI answer with a nonzero transport status differs from a device CLI error; neither extends compatibility to another build or command.

Linux read and diagnostic paths retain their documented distribution, architecture and permission requirements. Ruckus Unleashed retains the explicit administrator-bounded role and catalogue boundary; the catalogue does not reduce the device credential's privileges. A read catalogue or native timer on another platform does not imply Admin execution support there.

## Clock and state boundaries

FortiOS and ExtremeXOS safeguards can follow device-clock changes. Admin requires verified removal or return evidence tied to its own safeguard. Incomplete listings or missing proof do not establish success; unverified return leaves the operation unknown and the device blocked. FortiOS gives Admin no device proof that its stitch ran: when the state after the fire time and grace differs from the state before the change, Admin keeps a still installed stitch and reports unknown with the device blocked; only when the stitch is no longer installed does the operation end as revert-failed. A person removes a kept stitch after checking the device; a new change is refused while it is installed. A forward clock jump before a FortiOS safeguard is loaded can therefore leave an unreturned change as unknown, with a stitch that may never run.

Host-side elapsed budgets use monotonic time within one boot; across reboot, trusted elapsed time is not guaranteed. Shared admission locks and the journal preserve request identity, but separate journal/index files do not imply filesystem atomicity between those files.

## Operator responsibility

Verify the exact model, full firmware build, credential permissions, egress, catalogue scope, safeguard behavior and result interpretation before use. Unsupported or unspecified paths remain unsupported or unspecified. Full configuration collectors may need administrator credentials; fixed collector commands and the pinned device identity define that channel's read boundary. Keep collector credentials separate from Helper accounts and from the Auditor MCP surface.

Local-file auditing needs no device credential or connection, while workflow setup and result upload may use the network. Compatibility does not certify complete corpus recall, all hardware variants, every account grant or production exploitability. [Compatibility boundaries](compatibility-boundaries.md) describe the evidence classes and limits.
