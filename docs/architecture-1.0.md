# NetOps 1.0 architecture

One product and one container contain Core, Helper, Auditor and Admin. Their existing engines and measured device contracts are retained. All roles share the hashed production closure in `requirements.lock`, initially FastMCP 4.0.5 and MCP 2.2.0. Every change to dependency versions must resolve and test the entire closure again.

The image uses a pinned multiarch Python 3.14.8 / Alpine 3.24 base. Gateway, Helper, Auditor and Admin have distinct UID/GID pairs 51000 through 51003. A short bootstrap prepares only declared directories, starts role processes, removes all bounding capabilities and becomes the unprivileged gateway. The long-running gateway and role processes have empty supplementary groups, zero effective/permitted/inheritable/ambient/bounding capabilities and no-new-privileges. The Docker healthcheck (`netops health`) and one-off operator commands run with `docker compose run` start briefly as root with the capability set declared in Compose: the healthcheck, `configure`, `ca rotate`, `audit recover` and the `admin`/`auditor` commands drop to the gateway or role UID before their work, while `init`, `ca` export, `token`, `connection` and the other `audit` reads run as root until they exit. IPC authenticates peer UID in both directions. A process holding the state instance lock prevents a second instance from starting against the same data. The runtime and role configuration workflows reject a different product version or state schema before starting workers or installing inputs; no automatic migration or downgrade is attempted. The runtime never mounts the Docker socket or uses host networking.

The native image entrypoint preserves a pending SIGTERM across exec before Python startup. The Python launcher installs its stop handler and unblocks the signal before importing the CLI or starting role workers. The native entrypoint execs Python directly and leaves no supervisor process; it blocks SIGTERM only for serve, while other commands keep their normal startup. Startup cancellation joins its owned role-list RPC before exit; once gateway startup owns the stop signal, normal audit shutdown applies.

The HTTPS gateway uses the existing FastMCP Streamable HTTP implementation with stateless JSON responses. Every supported request, notification, response and connection boundary is audited. Requests are durable before dispatch; responses are durable before delivery. A failed response audit reports that the operation may have completed and forbids automatic retry. An incomplete final local audit record, for example after power loss during a write, blocks following operations: the gateway refuses to start and the healthcheck reports it. `netops audit recover`, run while the instance is stopped, moves only the incomplete trailing bytes of each segment to a private quarantine file in the audit directory, records the recovery in the audit and changes nothing when a complete record is invalid JSON. A syslog queue is bounded and durable before dispatch; TLS/TCP transmission does not prove receiver persistence. The forwarder sends queued records in batches of up to 512 records or 16 MiB over one TLS connection, outside the audit write lock, removes them only after the transport hand-over of the complete batch described under [Syslog delivery](#syslog-delivery), retries with backoff and reports a failing receiver once in the gateway log. Stateless HTTP does not offer server-originated long-lived SSE sessions or automatic replay of writes.

For local audit, the writer holds an exclusive segment lock through the complete write and fsync. The live health check uses a nonblocking shared lock: a locked segment is being written and is not classified as a crashed incomplete record. An unlocked incomplete record still fails health and startup; offline recovery remains explicit. A writer stuck while holding its lock is not detected by this check; health still separately verifies TLS readiness of the gateway and readiness of the role workers.

Cancellation does not abandon an audit commit: the handler waits for redaction and the durable write before propagating cancellation. A request cancelled after its audit begins records an interrupted outcome and connection end when audit storage remains available. A connection_end with delivery committed-before-send records the boundary before network delivery; if sending is then cancelled, the same correlation may also have an interrupted connection_end. Neither record proves client receipt. An interrupted dispatched operation may have completed and must never be retried automatically.

At the gateway, an authenticated request uses a single shared lane if it has a Transfer-Encoding header; duplicate, empty, non-decimal or oversized Content-Length values (more than 10 bytes); a declared body above 65536 bytes; or no Content-Length unless it is GET, HEAD or OPTIONS over HTTP/1.0 or HTTP/1.1. The lane covers receiving, auditing and dispatch. All admitted requests, including that lane, share 16 operation slots; connections waiting for the lane do not hold a slot. A large request can therefore wait behind another large request across roles while smaller correctly framed requests can use the remaining slots.

An authenticated connection cancelled while waiting for admission records admission_cancelled and connection_end with delivery not_started. If it is cancelled while its body is still being read, request_body_cancelled records that the body is incomplete, the received byte count and that no operation executed, followed by connection_end. These cancellation records contain method and path but no headers, body fragments or inferred MCP parameters. They do not claim that a complete request was received.

After a complete authenticated large MCP request is durably audited, the gateway checks for an already observable client disconnect before tool validation or dispatch. The observation has a fifty-millisecond timeout; any cancelled receive call remains owned until it finishes, before dispatch or release of the admission slot. An observed disconnect retains the full redacted request, then records client_disconnect with phase before_dispatch, complete_body true, the received byte count and operation_executed false, followed by connection_end with delivery not_started. Cancellation during this check follows the existing request/interrupted/connection_end path and reports that no operation was dispatched. This check does not prove eventual client receipt.

Shutdown waits for admitted handlers, cancelled admission waiters and their audit records before recording instance_stop. After the server shutdown grace period, cleanup has an additional twenty-second budget. If cleanup fails or that budget expires, the process reports incomplete audit shutdown and exits with status 1; this is a crash, not proof of completed operations. Inspect the durable audit and actual device state before any retry, and use the stopped-instance audit recovery procedure if a local record is incomplete. A stop record does not itself prove client delivery or a later successful filesystem sync. In syslog mode a batch delivery in progress at stop counts toward that budget; its records stay queued until delivery completes and may be delivered again after restart. The final instance_stop record is appended after the forwarder stops and remains in the durable syslog queue until forwarding resumes on a subsequent start.

Audit JSON contains parsed protocol content, explicit redaction paths and a representation label. It is not a raw byte transcript. Known token values, secret-bearing fields, private-key blocks and documented password forms are redacted. Worker-side credential values are removed before crossing into the gateway. Device output remains sensitive. Audit output escapes terminal controls. Local retention defaults to seven days within a 256 MiB budget and 16 MiB segments; the syslog queue blocks new operations when its budget is exhausted. Disk budgets must be checked against measured workload before deployment.

The Helper bridge retains enrollment, device host-key checks, per-target authorization, rate limits and output sanitization. Credentials are loaded only by the Helper worker. The old host firewall/egress setup is absent. SNMPv2c and FTP/FTPS operations are explicitly refused in the SSH/HTTPS-only default profile. ICMP uses unprivileged datagram sockets. Admin and Auditor use their existing engines and protected role data. No network device is enrolled implicitly.

Each role uses its private state directory as its home. The Helper keeps its existing bounded operation-summary recorder in its own private operations.jsonl (2 MB segments, five retained segments); it cannot read or alter the gateway transport audit. These summaries supplement the mandatory gateway request/response records and do not replace them. Operator workflows use the same role-owned home and permissions. Offline Admin workflows run with the gateway stopped: an allowlisted workflow name is durably recorded by a short gateway-UID preflight process, then the Admin engine uses its private operation log and change journal. Role configuration and Auditor snapshot/policy imports also require this gateway-UID intent before reading their input. Only allowlisted workflow names are recorded, without file names, command arguments or input values. This intent record is not a gateway MCP response or a completion receipt. Audit preflight and private-log write failures refuse device writes. Local preflight detects an incomplete final record but does not revalidate complete historical JSONL records or prove freedom from privileged tampering.

The instance CA is private, constrained to the configured DNS subtree, with all IPv4/IPv6 names explicitly excluded and stored outside the image. The server leaf lasts seven days and renews with the existing server key, avoiding a partially replaced key/certificate pair. The instance CA is valid for 730 days from init or its last rotation. Renewal of the server certificate is attempted when it has two days or less left; once the CA expires within seven days, that renewal is refused and the instance stops, and with `restart: unless-stopped` every restart fails the same way. `connection` and the gateway log warn from 30 days before expiry, and the healthcheck reports the instance unhealthy from 14 days. `netops ca rotate`, run while the instance is stopped, records its start in the mandatory audit before any change, issues a new CA under the same name constraints and a new server key and certificate, keeps the previous pair in a private retired directory of the state volume and records completion; the token and role data are unchanged. The gateway and the healthcheck verify that the CA and server key and certificate files match before serving, so an interrupted rotation stops the instance with guidance to rotate again. Clients must then trust the new CA; clients that trust only the previous CA refuse the connection. Token rotation is an operator action; authorization is rechecked before response delivery. Init never prints the token and preserves existing identities on repeat.

Functional qualification must use the actual image on every supported platform, including real MCP clients, device operations, restart and documented upgrades. Import or SDK smoke tests are only their stated evidence scope. Confirmed relevant vulnerabilities, missing tests and failed installation paths block release.

## Unauthenticated request rejection

The gateway checks the bearer token and HTTPS before reading any request body or acquiring an operation slot. Rejected clients cannot consume the durable operation-audit budget or rotate its history. Bodies, headers and paths are intentionally not retained. Denials of requests that reach the gateway application are aggregated into a separate fixed-size private rejection summary (rejections.json), exposed by netops audit stats: `authentication_required` counts a missing or wrong token and `https_required` an authenticated request that did not arrive over HTTPS. A connection that fails before the application is not counted: plain HTTP sent to the HTTPS port fails in the TLS layer and leaves no line in `docker compose logs netops`, and an invalid HTTP request sent inside TLS is logged there as `WARNING:  Invalid HTTP request received.`. In the summary, the first denial is persisted immediately, later counts at most once per 60 seconds and on graceful shutdown. A crash can lose the latest 60 seconds of denial counts. The summary is local and does not claim a complete per-request transcript or independent syslog protection. Supported authenticated MCP messages continue to receive complete redacted request/response audit with durable ordering.

## Syslog delivery

A syslog batch counts as handed over when the TLS handshake verifies the receiver certificate, every frame of the batch is passed to TLS without an error and NetOps then attempts an orderly TLS closure by sending close_notify. A TCP EOF from the receiver without its own close_notify is tolerated (RFC 5425 section 4.4); rsyslog with the gtls network stream driver closes this way. The hand-over is a transport result, not an application or durable acknowledgement. A batch can be removed from the queue although the receiver application did not take all of it: when the receiver closes the connection without reading the batch or after reading only part of it, when it half-closes the connection, or when its FIN arrives before a reset. An error after the receiver has read a batch produces duplicates. A failed connection or certificate verification, a send error, a reset or a timeout keeps the complete batch queued for retry. The receiver must handle the configured maximum record size (up to 8 MiB plus framing). The verified receiver is rsyslog 8.2512 with the gtls driver (package rsyslog-gnutls); with the ossl driver (rsyslog-openssl) the receiver lost records in testing, so that driver is not supported. A receiver that silently discards accepted application data remains outside this guarantee.

NetOps 1.0.0 sends audit records of up to 8 MiB plus framing. This exceeds the interoperability baseline in RFC 5425 section 4.3.1: a TLS receiver MUST process 2048 octets and SHOULD process 8192 octets. These are minimum receiver requirements, not a universal upper size limit. RFC 5424 section 6.1 allows a receiver to truncate or discard messages larger than it supports. Default receiver settings therefore do not guarantee complete NetOps audit records. For 1.0.0, the supported receiver is explicitly configured rsyslog 8.2512 with gtls and both limits below. NetOps retains complete queued records until transport hand-over; it cannot detect later receiver truncation or discard. Verify receiver configuration and retained full records before relying on external audit protection.

The verified receiver ran on Ubuntu with packages rsyslog and rsyslog-gnutls 8.2512.0-1ubuntu4.2 and this `/etc/rsyslog.d/60-netops-tls.conf`; it writes each record unchanged as one line to its own file:

~~~
global(DefaultNetstreamDriver="gtls"
       DefaultNetstreamDriverCAFile="/etc/rsyslog.d/netops-tls/ca.pem"
       DefaultNetstreamDriverCertFile="/etc/rsyslog.d/netops-tls/srv.pem"
       DefaultNetstreamDriverKeyFile="/etc/rsyslog.d/netops-tls/srv.key"
       maxMessageSize="9m")
module(load="imtcp" MaxFrameSize="9437184" StreamDriver.Name="gtls" StreamDriver.Mode="1" StreamDriver.AuthMode="anon")
template(name="netopsraw" type="string" string="%rawmsg%\n")
ruleset(name="netops") { action(type="omfile" file="/var/log/netops-audit.log" template="netopsraw" fileCreateMode="0640") }
input(type="imtcp" port="6514" ruleset="netops")
~~~

`maxMessageSize="9m"` bounds the message buffer; `MaxFrameSize="9437184"` separately bounds octet-counted frames and covers the 8 MiB maximum record plus its syslog header. Both limits are required; the default frame ceiling is smaller. These limits were checked with rsyslog 8.2512.0 using gtls. The receiver certificate must name the `host` given to NetOps; for a private CA, that CA certificate is the `ca_pem` of `configure syslog`. On Ubuntu the rsyslogd AppArmor profile read the certificate files under `/etc/rsyslog.d/netops-tls/`; under `/etc/rsyslog-netops/` rsyslog reported that they `could not be accessed: Permission denied`.

## Operation outcomes

The common MCP boundary preserves structured results and marks refused/failed operations with `isError: true`. Helper `ok: false`, Admin rejected/unknown/reverted/revert-failed execution outcomes, failed readiness and unknown operation lookups are errors. Successful `admin_status` reads of previously failed operations and Auditor queries with findings remain successful queries. Unknown writes must be investigated using request/change identity and actual device state, never retried automatically.

Only root metadata declares the netops distribution/version and production dependency closure. Component directories are internal engines with regression tests and API references; their test support fixtures are not deployable components. Historical standalone metadata, installation procedures, images and SBOMs are archived.

## Helper operation summaries

These private engine records supplement the mandatory gateway audit; they cannot replace or modify it. A device operation records `status: "started"` before execution, then `status: "ok"` on normal completion. After an exception, a `status: "failed"` record carries `detail` with the exception type, never its credential-bearing text. An operation_id correlates the two records. The bounded recorder rotates mode-0600 segments inside the Helper private directory. A logical diagnostic refusal returned as data can complete the internal call; its explicit failure is still marked as an error at the public MCP boundary.
