# Admin configuration in NetOps 1.0

Configure the stopped instance using a private JSON file (mode 0600) outside the source checkout. Input requires `config` and `vault`. The optional `notification_topic` is required on the first notification setup: 8–64 ASCII letters, digits, underscores or hyphens. Never send this file, topic or credentials to MCP or logs.

The adapter validates input, fixes state/audit/topic/device-vault paths inside the Admin private directory and stores the topic in mode 0600. An arbitrary path does not import host files. Reconfiguration preserves the topic when omitted. Credentials remain separate from Helper and Auditor.

## Complete input example

The document is a template with the structure of the schema; every address, pin, public key, account, credential and notification endpoint/topic is a placeholder. Validation refuses it as shown, because `host_key` must be an OpenSSH public key whose SHA-256 equals `host_key_fingerprint`. Replace the placeholders using trusted device identity and reviewed permissions before `configure admin` and enrollment. Validation does not contact a device or send a notification.

```json
{
  "config": {
    "version": 1,
    "mcp_undo": false,
    "notify": {
      "server": "https://ntfy.example.invalid",
      "timeout_seconds": 10
    },
    "limits": {
      "changes_per_device_per_hour": 6,
      "changes_per_day": 40
    },
    "devices": {
      "firewall-a": {
        "platform": "fortios",
        "address": "192.0.2.10",
        "host_key_fingerprint": "SHA256:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
        "host_key": "<verified OpenSSH public key: type and base64, required for Fortinet SSH>",
        "credential": "firewall-write",
        "check_credential": "firewall-check",
        "accounts": [
          "example-write",
          "example-check"
        ],
        "safeguard_seconds": 180,
        "confirm_margin_seconds": 45,
        "protected": {
          "firewall address": [
            "all",
            "none"
          ]
        }
      }
    }
  },
  "vault": {
    "version": 2,
    "credentials": {
      "firewall-write": {
        "kind": "password",
        "login": "example-write",
        "value": "replace-with-write-secret"
      },
      "firewall-check": {
        "kind": "password",
        "login": "example-check",
        "value": "replace-with-check-secret"
      }
    }
  },
  "notification_topic": "replace_with_private_topic"
}
```

```sh
docker compose stop
docker compose run -T --rm netops configure admin < admin-private.json
docker compose up -d --wait
```

Until this configuration is saved, the MCP Admin tools return `admin_not_configured`, whose hint means this `configure admin` command with the private JSON on standard input, and an offline command such as `admin status` refuses with `configuration: devices must be a non-empty object`, because init stores an Admin configuration without devices.

## Enroll the device and verify readiness

Configuration alone does not authorize changes. First verify the configured device host-key fingerprint through a trusted device console, the write/check account permissions and successful trusted-HTTPS notification delivery. Subscribe to the private notification topic before testing.

Enrollment performs a real temporary device change and deliberately lets the on-device safeguard return it; the exceptions are FortiADC and Ruckus Unleashed, which have no on-device safeguard and return the probe by compensation in the same run (see [FortiADC pool member](#fortiadc-pool-member) and [Ruckus Unleashed](#ruckus-unleashed-wlan-and-dhcp-relay)). Reserve a genuinely unused subnet for the FortiOS probe; the documentation subnet below is only an example and must be reviewed for the target. Enrollment can take the full safeguard interval and verification time. Keep this operator command running until it reports a final outcome.

~~~sh
docker compose stop
docker compose run --rm netops admin enroll --device firewall-a --probe 192.0.2.252/30
docker compose run --rm netops admin doctor --device firewall-a
docker compose up -d --wait
~~~

Successful enrollment reports `"enrollment": "valid"` with `"result": "reverted"` and reason `"enrollment self-test"`: the probe must be gone, the safeguard absent and notification sent. Doctor then reports `"ready": true`. An exit code alone is insufficient; inspect the structured result. If enrollment is not valid or doctor is not ready, stop and resolve the reported cause before requesting a change. Re-enroll after changing the bound device configuration, firmware, account identities, profiles or notification settings.

Doctor also checks whether the write and check accounts have more rights than their role needs. Each account reads only its own entry with `show system admin "<login>"` and, for the check account, its own profile with `show system accprofile "<profile>"`; doctor keeps only the profile fields and never reports password, `ENC` or certificate lines. The checks `write account rights` and `check account rights` report `warning` for a FortiOS `super_admin` or `prof_admin` write account before 8.0.1 (on 8.0.1 and later the webhook safeguard needs `super_admin`), for a FortiOS check account with `super_admin`, `prof_admin`, a `read-write` group or `cli-config enable`, and for a FortiADC check account with `is-system-admin yes` or a `read-write` area; a FortiADC write account may be a system administrator, which the health precheck of a pool member status change (`diagnose server-load-balance vs_stat`) and `pool-member` need. The warning names the row of [Accounts and least privilege](../components/netops-helper/docs/read-only-accounts.md) that lists the rights of that role; the FortiADC row `Admin check` there is not measured, so for a FortiADC check account the warning rests only on the entry and profile the account reads. They report `cannot verify` with the reason or the exact device answer when the entry or the profile cannot be read, for example a wildcard, RADIUS, TACACS+ or VDOM administrator without a local profile (an entry that is not found), a check account without `cli-show` (`Unknown action 0`), a `custom` group, or a profile the account does not see; a refusal line that may hold a secret is reported without the rest of the line. Neither status changes `ready` or the exit code. Since 1.0.10 doctor runs the full report on FortiADC too (before, it refused with `platform 'fortiadc' has no plan and apply adapter` and listed only the credentials and the two rights checks); its `audit policy` check is `cannot verify` there, because Admin runs no auditor rules on FortiADC (see [FortiADC pool member](#fortiadc-pool-member)). The `warning` and `cannot verify` results are verified by tests against simulated devices; on real devices (FortiOS 7.6.8, FortiOS 8.0.2, FortiADC 7.6.7) only the result `ok` was verified.

## Preview and make one explicit change

Use the authenticated HTTPS MCP connection from the [quickstart](quickstart-1.0.md). The request below creates an address object only; it does not add a traffic policy. Use a new object name and a reviewed unused subnet on an isolated test device for the first operation. Replace `user_request` with the actual words of the person authorizing that change, and choose a unique `request_id` (8–64 supported characters).

Call `admin_preview` with these arguments:

~~~json
{
  "device": "firewall-a",
  "table": "firewall address",
  "op": "create",
  "key": "netops-example-address",
  "changes": {
    "subnet": "192.0.2.248/30"
  },
  "reason": "Verify an explicitly authorized address object",
  "user_request": "Create this test address object on firewall-a.",
  "request_id": "example-address-create-0001"
}
~~~

Preview reads the device and returns the proposed commands, prediction and refusal reasons without making a change. Continue only when `result` is `ready` and the person has reviewed the plan. Then call `admin_apply` with the same arguments; for an operation that requires approval ([MCP tools](#mcp-tools)), also pass the approved preview's `plan_sha256` as `expected_plan_sha256`. Apply plans again from a fresh snapshot and uses the independent check account; a configuration change also uses the device safeguard (a clear or save is a standalone operation without one); preview is not a stored executable plan. On FortiADC and Ruckus Unleashed, and for ExtremeXOS ACL policy files and the IOS and IOS XE VLAN database, there is no device safeguard: preview names the `return_mechanism`, apply returns an unverified change by compensation in the same run, and after a loss of the Admin process, the host or the management path nothing on the device returns it; run `admin recover` (see [FortiADC pool member](#fortiadc-pool-member)).

`admin_doctor`, `admin_preview`, `admin_apply` and the operator commands `admin doctor` and `admin enroll` read the device configuration over SSH with a 180-second limit that includes the host-key check (later SSH queries are limited to 60 seconds and interactive logins to 30 seconds). When the device does not answer, these calls return their refusal only after about 180 seconds. Set the request timeout of the MCP client above 180 seconds. A client timeout does not prove that the call was cancelled: the operation can still complete, and the audit can hold its response or an interrupted or pending record. Inspect `admin_status` and the actual device first, and never repeat a write automatically. The Admin worker handles one MCP request at a time; further Admin calls wait until the running one ends. While a long operator command such as `admin enroll` runs, `docker ps` can show its `docker compose run` container as `unhealthy`: the service healthcheck also runs in that container, which has no gateway (see the [quickstart](quickstart-1.0.md)). This does not affect the command; judge it by its final structured result.

A completed change must report `result: confirmed`, successful notification and no blocking reason. Retain the returned `change_id` and read it through `admin_status` using `{"change_id": "CHANGE_ID_FROM_RESPONSE"}`. Inspect the actual object through the independent read-only account. Repeating an already used `request_id` returns its existing operation; it does not authorize another write. For an unknown or interrupted result, inspect status and the actual device before any operator recovery.

## Return the test change as an operator

Undo is an explicit operator action. The MCP tool `admin_undo` is listed but off by default (`mcp_undo_disabled`); since 1.0.12 the top-level `mcp_undo` setting enables it, and it runs an undo only with the `plan_sha256` of the `admin_undo_preview` the person approved. The MCP tool `admin_undo_preview` and the operator command `admin undo --preview` only show what the undo would do and change nothing on the device (see [MCP tools](#mcp-tools)). Use the actual change ID from the confirmed operation:

~~~sh
docker compose stop
docker compose run --rm netops admin undo --change-id CHANGE_ID_FROM_RESPONSE --reason "Remove the verified test object"
docker compose run --rm netops admin status --change-id CHANGE_ID_FROM_UNDO_RESPONSE
docker compose up -d --wait
~~~

Undo creates a new safeguarded operation with its own change ID. Require its confirmed result, notification and independent verification that the object returned to its original state. Keep both operation records and the gateway audit. Never delete the state volume to clear a refusal or an unknown operation.

## Interrupted or unknown Admin operation

Stopping or restarting NetOps does not prove that an in-flight change was cancelled. The on-device safeguard can continue after the container exits. Do not repeat an unknown write automatically or delete its journal to remove a refusal.

Retain the original business request_id and change_id. Inspect admin_status and the actual device through the independent read-only account. The gateway audit pending command identifies requests without a trustworthy completed response; a pending entry alone does not tell you whether the device changed.

For explicit operator recovery, stop the instance and use the original request ID and configured device alias:

~~~sh
docker compose stop
docker compose run --rm netops audit pending
docker compose run --rm netops admin status --request-id REQUEST_ID_FROM_ORIGINAL_ARGUMENTS
docker compose run --rm netops admin recover --device firewall-a
~~~

Recovery can inspect and settle the existing operation using its saved safeguard and original state. Inspect every returned settled record, notification result and the actual device; an exit code alone is insufficient. A still-running or blocked operation requires investigation before any new write. After the original operation is settled, start the instance with docker compose up -d --wait. A subsequent write requires a new explicit request and a new request_id.

Available operator recovery commands and flags can be inspected while the instance is stopped:

~~~sh
docker compose stop
docker compose run --rm netops admin --help
docker compose up -d --wait
~~~

Admin write and independent check accounts must differ (see the [device account model](account-model.md); the measured access profiles are in [Accounts and least privilege](../components/netops-helper/docs/read-only-accounts.md)). The check account verifies device identity and readback independently. FortiOS administrator visibility is bounded by the enrolled accounts. ExtremeXOS also needs exact `firmware` and the explicit create/configure account fingerprint; implicit accounts are not proven.

## Blocked device or undelivered notification

Admin blocks a device when an operation ends with result `unknown` or `revert-failed`, or with a blocking reason: `administrator table`, `foreign change`, `not persisted`, `foreign change during save`, `saved configuration unverified`, `postcheck rejected`, `snapshot incomplete`, `snapshot scope unsupported`, `snapshot unreadable` or `snapshot firmware mismatch`. Every further preview, apply or enrollment for that device is then refused with `the device is blocked (REASON, operation CHANGE_ID); a person must investigate and unblock it`, and doctor reports the device state as refused. A finished operation whose notification is still `pending`, `failed` or `sending` also refuses new operations on its device: `the notification of operation CHANGE_ID was not delivered; run notify-retry, or a person unblocks the device after checking the notification channel`.

Since 1.0.12, with `mcp_undo` enabled ([MCP tools](#mcp-tools)), MCP can lift the block of an eligible profile operation that ended `unknown`, whatever its blocking reason, only after both accounts verify the planned state after, with no installed safeguard or unfinished operation and an unchanged administrator-account baseline. Pass the `unblock_sha256` of the latest `admin_unblock_preview` the person approved as `expected_unblock_sha256` of `admin_unblock`; the hash is accepted once. The operation stays `unknown`. Other results (such as `revert-failed`), schema transactions, profile batches, a verified state before and a changed account baseline are refused with `unblock_operator_only`, an unfinished operation with `operation_unfinished`, and an unverified state or a remaining safeguard with `unblock_state_unverified`; they need the operator command below.

These operator commands run with the instance stopped, like `recover` above:

- `admin notify-retry --change-id CHANGE_ID` sends the notification of that finished operation again unless it was already sent; it needs a configured notification.
- `admin unblock --device firewall-a --reason "TEXT"` is for a person who has inspected the operation record and the actual device. It lifts the block, clears the stored administrator-account baseline of the device and marks its undelivered notifications as `waived`. The private Admin operation log records only the length of the reason, not its text. The command prints a JSON object with `device` and `unblocked`, which is `false` when there was nothing to lift or waive.

On FortiOS, a result `unknown` whose `steps` in `admin_status` end with `safeguard_kept` means that NetOps could prove neither that its timed safeguard fired nor that it was disarmed, so it left the safeguard on the device. The safeguard is three automation objects named after the first 12 characters of the change ID: the stitch `netops-sg-ID12-s`, the trigger `netops-sg-ID12-t` and the action `netops-sg-ID12-a`, where the action holds the inverse CLI script and the trigger is scheduled once at `safeguard.fire_at`. A stitch that fires late can still restore the previous object after you inspected it, so before `unblock` check for these objects through an administrator account (`show system automation-stitch netops-sg-ID12-s`, and likewise `automation-trigger` and `automation-action`) and remove them before you judge the object. Delete the stitch first, because it refers to the trigger and the action; on a device with VDOMs, run the commands inside `config global`:

~~~
config system automation-stitch
delete "netops-sg-ID12-s"
end
config system automation-trigger
delete "netops-sg-ID12-t"
end
config system automation-action
delete "netops-sg-ID12-a"
end
~~~

Then read the object again, compare it with the operation record and unblock the device only after that.

NetOps 1.0 reads no firing record from FortiOS. After an expired safeguard it waits until `safeguard.fire_at` plus 20 seconds, reads the configuration and ends with `unknown` and `safeguard_kept` when the object is not the previous one and the stitch `netops-sg-ID12-s` still exists. A once trigger stays configured after it has fired, so `safeguard_kept` does not mean that the stitch did not fire. The device itself shows whether it fired, through an administrator account:

~~~
diagnose test application autod 3
~~~

lists every stitch; for `netops-sg-ID12-s`, a stitch that fired shows `local hit` of at least 1, the time in `last trigger` and `next scheduled trigger:trigger expired`. The event log records each firing:

~~~
execute log filter reset
execute log filter category event
execute log filter field logid 0100046600
execute log display
~~~

Each firing is one line with `logid="0100046600"`, `logdesc="Automation stitch triggered"` and `stitch="netops-sg-ID12-s"`. Such a line proves that the stitch was triggered, not that its inverse script restored the object; compare the object as above either way. In a measurement of 21 once triggers, 10 on a FortiGate 80F with FortiOS 8.0.2 build0251 and 11 on a FortiGate 60F with FortiOS 7.6.7 build3704, each trigger fired between 0.1 and 5 seconds after its `trigger-datetime`, within the 20 seconds that NetOps waits.

Inside NetOps, the operator commands `apply`, `preview`, `doctor`, `enroll`, `status`, `recover`, `notify-retry`, `unblock`, `undo`, `pool-member`, `pool-member-add` and `pool-member-remove` receive `--config` with the private Admin configuration automatically; `admin enroll --help` and the other subcommand help pages still list `--config` as required, but the documented commands omit it. `plan`, `verify`, `schema-plan` and `schema-verify` are offline engine commands that take explicit file paths readable by the Admin UID, and `apply` and `preview` also need a `--request` file. NetOps 1.0 places Admin operator files only through `configure admin` (JSON on standard input), so these engine commands have no supported way to receive their input files and are not a supported operator workflow in NetOps 1.0; preview and apply changes with the MCP tools `admin_preview` and `admin_apply`.

## Webhook safeguard on FortiOS 8.0.1 and later

A Fortinet Technical Tip states that from FortiOS 8.0.1 build0185 the auto-script engine allows only `get` and `diagnose` commands, and on 8.0.2 build0251 the `cli-script` safeguard was observed to refuse every configuration line, so Admin does not use it to restore configuration from 8.0.1 ([verified support](verified-support.md#admin-safeguard-on-fortios-76-and-80)). On those builds Admin installs a webhook safeguard instead; the choice follows the snapshot firmware and needs no setting. The stitch calls the REST API of the same FortiGate with a temporary API user and sends the inverse request: `DELETE` for a create, `PUT` with the previous values for an update, `POST` with the previous object for a delete (for a policy, also the undo of a policy create, only when it was the last policy), and `PUT` with the validated position for a policy move. Runtime clears have no inverse and no timed safeguard. The full design is in the [webhook safeguard contract](fortios-webhook-safeguard-contract.md).

`admin doctor` reports these conditions, except the table and the request body, in its check `webhook safeguard` with the same texts; on firmware before 8.0.1 the check reports that the webhook is not used. Before any device write Admin refuses the request, naming the missing condition, unless:

- the device `address` in the Admin configuration is an IPv4 address, held by an interface in the snapshot, and that interface has `https` in `allowaccess` (the webhook calls this address on the `admin-sport` of `system global`, read with `show system global` before the API user is created, 443 when the answer omits it; a port that cannot be read refuses the request);
- the write credential is a password credential, because `execute api-user generate-key` asks for the administrator password;
- the write account has the access profile `super_admin` (read from its `system admin` entry in the snapshot), because only `super_admin` may create the API user of the safeguard;
- no `system api-user` or `system accprofile` named `netops-sg-…` is left from an earlier operation;
- the table has a REST inverse and the request body fits 1023 bytes. Since 1.0.12 the REST inverses cover `firewall policy`, `firewall address`, `firewall addrgrp`, `firewall service custom`, `system dhcp server/reserved-address`, `system dns-database/dns-entry`, `vpn ipsec phase2-interface`, `firewall vip` and `firewall ippool`; `system interface`, `router static` and the FortiSwitch port tables have none and are refused with `safeguard_no_rest_inverse`, and a profile batch is refused, on these builds. The REST inverses of `system dhcp server/reserved-address` and `system dns-database/dns-entry` are implemented and covered by automated tests, but on FortiOS 8.0.2 only their REST paths were read; a live write through them is not verified.

On these builds the write account must therefore be a `super_admin` account; see [what to check](#write-account-for-the-webhook-safeguard-what-to-check). Schema transactions are not available on these builds.

The Auditor reports each of these objects left on a device as `fortios.mgmt.netops-safeguard-leftover` (severity high, remediation `admin recover`); during its own operation Admin ignores only its own safeguard. The safeguard is five objects named after the first 12 characters of the change ID: the access profile `netops-sg-ID12-p` (`fwgrp read-write`, everything else `none`; for a DNS entry `sysgrp read-write` and for a Phase 2 selector `vpngrp read-write` instead of `fwgrp`), the API user `netops-sg-ID12-u` (that profile, trusthost the device address /32), the action `netops-sg-ID12-a` (`webhook`), the trigger `netops-sg-ID12-t` and the stitch `netops-sg-ID12-s`. Admin removes all five after confirmation and after expiry and proves their absence by reading back. When firing is not proven (`safeguard_kept`), Admin still deletes the API user and the access profile, so the token is revoked (step `safeguard_token_revoked`, or `safeguard_token_revoke_unverified` when the readback does not prove it), and leaves the stitch, trigger and action for the investigation above. `admin recover` deletes the API user and the access profile as well.

Cleanup after a partial installation: when the device refuses or ends the installation part-way, Admin removes what it created in the same operation and ends `reverted` with `safeguard not verified`. When that removal is not proven by the readback, the operation ends `unknown` with `safeguard not verified`, blocks the device and leaves objects such as the access profile `netops-sg-ID12-p`; `admin doctor` then names them (`a safeguard of an earlier operation is still installed: netops-sg-ID12-p`). Stop the instance and run `admin recover --device firewall-a`: for the operation that blocks the device, if it ended this way before `change_start`, recover deletes the remaining `netops-sg-ID12-…` objects of its change ID, reads them back and appends the step `safeguard_removed` (`safeguard_removal_unverified` when an object is still found; run `admin recover` again after the cause is fixed). The result stays `unknown` and the device stays blocked; read the steps with `admin status`, then run `admin unblock`. No manual CLI is needed for this case.

If NetOps stops during the window and is not recovered, remove the objects through an administrator account, the stitch first; on a device with VDOMs inside `config global` (on FortiOS 8.0.2 `delete` of the API user asks `Please enter current administrator password:`; enter the password of the signed-in administrator):

~~~
config system automation-stitch
delete "netops-sg-ID12-s"
end
config system automation-trigger
delete "netops-sg-ID12-t"
end
config system automation-action
delete "netops-sg-ID12-a"
end
config system api-user
delete "netops-sg-ID12-u"
end
config system accprofile
delete "netops-sg-ID12-p"
end
~~~

Residual risk: FortiOS keeps the `Authorization` header of the automation action in clear text in the configuration while the safeguard exists, so configuration backups taken during the window hold the API token. FortiOS also writes the header into the event log when the action is created (log ID 0100044547); the token therefore reaches syslog and FortiAnalyzer when logs are forwarded. Deleting the action does not remove it from those logs; NetOps neither disables logging nor deletes logs. The token is limited: it is accepted only from the device's own management address (trusthost /32), it carries `fwgrp read-write` and nothing else (for a DNS entry `sysgrp`, for a Phase 2 selector `vpngrp`), and it is revoked when NetOps deletes the API user after confirmation, after expiry or in `admin recover`. `fwgrp read-write` is the whole firewall permission group, not one policy: whoever holds the token on the device itself can change any firewall object until it is revoked; the same holds for the system and VPN groups. If NetOps stops during the window, the token stays valid until `admin recover` or the manual cleanup above. NetOps never writes the token into the plan, the preview, the operation record, the Admin audit log, a notification or an error text, and Helper `config_read` hides the header value.

### Write account for the webhook safeguard: what to check

Measured on 2026-11-01 on FortiOS 8.0.2 build0251 (FortiGate 80F, active-passive HA). The device behaviour below is what the device answered; where it differs from a Fortinet document, the device is right.

- **Access profile `super_admin`.** Only `super_admin` may create the API user of the safeguard. Signed in with any other access profile, `config system api-user` answers `command parse error before 'api-user'` and `Command fail. Return code 1`; this stays so with `sysgrp read-write`, with every permission group `read-write` and with `cli-exec enable`. A restricted account also cannot create an access profile with more rights than its own: the safeguard profile (`fwgrp read-write`) is refused at its `next` with `object set operator error, -672 discard the setting` and `Command fail. Return code -672`. On FortiOS 8.0.1 and later the write account therefore needs the `super_admin` profile. `super_admin` has full rights on the device, so use a dedicated account for NetOps only, limit it with a trusted host /32 to the address the Admin host connects from, and keep its password only in the Admin credential store.

  1. An administrator with the `super_admin` profile creates or changes the account:

     ~~~
     config system admin
         edit "<write account>"
             set accprofile "super_admin"
             set trusthost1 <Admin host address> 255.255.255.255
             set password <password>
         next
     end
     ~~~

     `set password` is needed when the account is new (`edit` answers `new entry '<write account>' added`); leave it out for an existing account. On FortiOS 8.0.2 the device asks `Please enter current administrator password:` after `set password` and again after `next`; enter the password of the administrator who is signed in.
  2. Check it with `show system admin | grep "edit \|set accprofile\|set trusthost"`; under `edit "<write account>"` the answer lists `set trusthost1 <address> <mask>` and `set accprofile "super_admin"`.
  3. Run `admin doctor`. Until the account has `super_admin`, it reports the check `webhook safeguard` as `refused` with `the webhook safeguard needs the write account <login> with access profile super_admin on FortiOS 8.0.1 and later (only super_admin may create the API user of the safeguard); <login> has access profile <profile>`, and `admin preview`, `admin apply` and `admin enroll` refuse with the same text before any device write. When the device refuses a line while the safeguard is installed, the step `safeguard_not_verified` names the line, the object and the device answer, for example `safeguard installation failed (AccessError: line 13 (config system accprofile, edit "netops-sg-ID12-p") was refused by the device: object set operator error, -672 discard the setting | Command fail. Return code -672)`.
- **All administrators in `accounts`.** A `super_admin` write account sees every administrator of the device, so `accounts` in the device section must list all of them, as `show system admin | grep edit` lists them through a `super_admin` account. Otherwise the `admin doctor` check `administrator accounts` is `refused` and `admin preview`, `admin apply` and `admin enroll` refuse before any device write with a text that names the administrators the write account sees but `accounts` does not list (`not configured`) and the ones `accounts` lists but the device does not show (`not visible`), for example `the write account sees other administrators than the configured ones: not configured: admin, operator-1, netops-ro; not visible: netops-missing`. The built-in profile `super_admin` is not listed in `show system accprofile`; Admin accepts it without its profile text. Every other access profile of a visible administrator must be in the snapshot, otherwise the refusal names it: `an administrator access profile is not visible in the snapshot: <profile>`.
- **Password credential.** A write credential with an SSH key only is refused on 8.0.1 and later with `the webhook safeguard needs a password write credential: FortiOS asks for the administrator password when it generates the API key`, in the `admin doctor` check `webhook safeguard` and before any device write in `admin preview`, `admin apply` and `admin enroll`. Store a password credential for the write account. This is an accepted limitation of NetOps 1.0.5. FortiOS 7.6 with the `cli-script` safeguard is not affected.
- **What a restricted account sees.** A profile that is not `super_admin` does not list `super_admin` in `show system accprofile`, and in `system admin` and `system api-user` it lists only the entries its profile covers; the output does not say that anything is left out ([account model](account-model.md)). On 8.0.2 build0251 a read-only account listed in `show system accprofile` its own profile and one other read-only profile, but not the profiles with write rights, and in `show system admin` only itself (measured on 2026-11-02).
- **Password prompt for the API user.** On FortiOS 8.0.2 build0251 with a `super_admin` write account the device asks `Please enter current administrator password:` after the `next` that saves `system api-user "netops-sg-ID12-u"` and after `delete "netops-sg-ID12-u"`; the other lines of the installation and removal (access profile, trusthost entry, action, trigger, stitch) are answered with the prompt. Admin answers this prompt with the password of the write credential, and only when the device asks. Measured on 2026-11-02 without an answer: the device ends the SSH session about 9 seconds after the prompt, and the API user is saved all the same (`show system api-user netops-sg-ID12-u` lists it afterwards). A development build that did not answer it ended `admin enroll --probe` with `unknown` and `safeguard installation failed (AccessError: interactive session failed after 23 lines: the session to <address> ended before any of the 2 awaited pattern(s) matched, 86 byte(s) seen)` and left the access profile `netops-sg-ID12-p`.

## Opt-in table `firewall policy`

`firewall policy` is off unless the device lists it: `"opt_in": ["firewall policy"]` in the device section (FortiOS only, `protected["system interface"]` must be non-empty). The change is bound into the enrollment, so run `admin enroll` again after changing `opt_in` and after upgrading.

For a delete or its undo, live planning reads whether the VDOM allows manual UUID assignment. Restoration keeps the original policy ID, attributes and order. If manual assignment is enabled, restoration also keeps the original UUID. Otherwise, FortiOS assigns the UUID, and the result reports a verified change in `warnings`.

| Warning | Fields |
| --- | --- |
| `uuid_changed` | `original_uuid` and `new_uuid` record the old and verified replacement UUID after undo or a timed return. |

- Without a position, `create` places the new policy after all existing policies. An `update` of `status` is accepted only alone. Since 1.0.12 `create` may also name a position and `status enable`, and `delete` and `move` exist ([Firewall policy: delete, order and staged creation](#firewall-policy-delete-order-and-staged-creation)). Apply of every policy change requires `expected_plan_sha256` (`fortios_policy_preview_required`), and a change of an active policy that affects traffic requires `endpoint_impact` naming the policy ID.
- `action deny` needs `logtraffic` in the same request: FortiOS 7.6.8 sets `logtraffic disable` with `action deny`, which the postcheck would find as a difference and the audit reports as `fortios.policy.logging-disabled`; send `logtraffic all`. `undo` of such an update brings `logtraffic` back as well.
- `update` of anything else uses the normal path; `undo` of a create deletes the policy, `undo` of an update restores the previous values (default values for attributes that were unset).
- The plan is refused when the policy id exceeds the limit, names an interface, address, service or schedule missing from the snapshot, touches the management path of a protected interface (also through `any`, zones or SD-WAN zones), or the inverse would not fit the safeguard script. Undo keeps the policy order: it is refused when the original order of the policies changed (`fortios_policy_order_changed`); policies appended later do not block it. With the webhook safeguard a recreation is one `POST` that appends the policy at the end, so there a delete, also the undo of a create, is refused when the policy is not the last one.
- The profile lists FortiOS 7.6.8 build3744 with the `cli-script` safeguard and 8.0.2 build0251 with the webhook safeguard ([Webhook safeguard on FortiOS 8.0.1 and later](#webhook-safeguard-on-fortios-801-and-later)) as tested builds. Since 1.0.12 another build, also 8.0.0 build0167 or 7.6.7 build3704, is not refused: the plan carries `firmware_support` with status `untested`. Delete, move, positions, an enabled create and the attributes added in 1.0.12 are tested on 7.6.8 build3744 only. The defaults of FortiOS 7.6.8 are `status enable`, `logtraffic utm` and `action deny`, and `unset status` returns `enable`; the id limit 4294967294 and the script limit 1023 come from the FortiOS 7.6.8 CLI Reference. On 8.0.2 build0251 with a `super_admin` write account the full `admin apply` path was measured on 2026-11-02 on a FortiGate 80F active-passive HA pair with the webhook safeguard: `admin enroll --probe` ended `reverted`; create, update and undo of a policy ended `confirmed`; loss of the check account after the change ended `reverted` for an update (`PUT`), a create (`DELETE`) and an undo of a create (`POST`), each after `trigger-datetime`; SIGKILL after `change_applied` followed by `admin recover` ended `reverted`; the precheck refused a policy on the protected interface. No `netops-sg-` object stayed, the HA pair was in sync and the configuration after cleanup equalled the configuration before. A policy that names a member of an aggregate interface (for example `a` or `b` of the FortiLink aggregate `fortilink`) passes the precheck, because the member is an interface in the snapshot, but the device refuses the line `set dstintf`; Admin then ends `reverted` with `change failed` (step `change_failed`, detail `AccessError after 4 lines`) and the configuration stays unchanged. Name the aggregate, a VLAN or a zone instead. Zone members were not measured; a policy line that the device refuses ends the same way, with the configuration unchanged.
- **Undo limits.** `admin undo` runs once per change, under the fixed request ID `undo-CHANGE_ID`, so repeating it never repeats the write. Repeating exactly the same undo request (same reason) returns the stored result of the first undo. An undo of the same change with a different request (another reason) is refused with exit code 3 (rejected, like every refused request) and the text `undo of this change has already been performed; after a reverted change remove the object with regular administration`; nothing is sent to the device. Development builds printed `request_id was already used for a different request`, which says nothing about the cause. When the undo ended `reverted` (the safeguard restored the object), the object is still there and cannot be undone again; remove such a policy with a new `delete` request or through the normal administration. A genuine reuse of a request ID by another request keeps the text `request_id was already used for a different request`. `admin undo --preview` (MCP `admin_undo_preview`) runs the planning checks of the undo, including the `delete` of an undo of a create, without a device change; the undo checks the current state again. MCP `admin_undo` and the CLI undo of a profile batch require the approved plan hash; for other CLI undo operations pass `--expect-plan-sha256` to bind the undo to the preview; after an undo has run, also one with the same reason, it refuses with `undo_already_done`.
- **Provisional profile.** The profile `firewall policy` is provisional. Create and undo of a policy were measured on FortiOS 7.6.8 build3744 and 8.0.2 build0251, and the cleanup was verified (configuration equal to the configuration before, HA pair in sync, `admin recover` found nothing). On 8.0.2 the run with the whole management path blocked was recorded only once, with NetOps reaching the device through a translated (DNAT) address, and its repeat was not completed.
- **What was measured and what was only tested.** Measured live: on FortiOS 8.0.2 build0251 (FortiGate 80F active-passive HA pair, 2026-11-02) the main path `admin apply` with confirmation and revert, the attacks that remove the check account (`PUT`, `DELETE` and `POST` inverses), SIGKILL after `change_applied` followed by `admin recover`, and the precheck refusal; on FortiOS 7.6.8 build3744 (FortiGate 60F, `cli-script` safeguard) enrollment, a create and its undo. Verified only by automated tests against a simulated device, not on a real device: recovery after a partial installation of the safeguard (status `finished` with result `unknown` and `safeguard not verified`) through `admin recover`. Treat this recovery as untested on hardware and read the steps of `admin status` and the device afterwards.
- When the check account loses the device after the change, the safeguard restores the previous policy at `trigger-datetime` and the result is `reverted`; after a crash of NetOps after `change_applied`, `admin recover` ends `reverted`; when the whole management path is lost after the change, the result is `unknown` and the device stays blocked until the `netops-sg-` objects are removed and `admin unblock` runs. The measurements are in [verified support](verified-support.md#fortios-bounds).
- A Fortinet Technical Tip states that from FortiOS 8.0.1 build0185 auto-script, which the safeguard's `cli-script` action runs, allows only information-gathering commands (get, diagnose), while the 8.0.2 Administration Guide still shows CLI script examples with configuration commands. On a FortiGate 80F with 8.0.2 build0251 the stitch fired, but every configuration line was refused with `Unknown action or command is unavailable in auto-script`, and the probe address was still present after `trigger-datetime`. This is an observed refusal on the measured build and the statement of the Technical Tip, not a measurement of every 8.0.x build, so Admin does not rely on the `cli-script` safeguard from 8.0.1; on these builds Admin uses the webhook safeguard ([Admin safeguard on FortiOS 7.6 and 8.0](verified-support.md#admin-safeguard-on-fortios-76-and-80), with the Fortinet sources).

## Opt-in table `firewall service custom` (measured end-to-end)

**Measured end-to-end on FortiOS 7.6.8 build3744 and 8.0.2 build0251 (2026-11-14).** The profile has `provisional: false`, `measured: true` and `exact_versions: true`; preview, apply and undo are available with the table enabled in `opt_in`.

`firewall service custom` holds custom TCP/UDP services, for example `TCP-8443` with `tcp-portrange 8443`. It is off unless the device lists it: `"opt_in": ["firewall service custom"]` in the device section (FortiOS only). The change is bound into the enrollment, so run `admin enroll` again after changing `opt_in`. Turning a policy on or off is not part of this table; it stays an `update` of `status` in [`firewall policy`](#opt-in-table-firewall-policy).

- Operations `create`, `update` and `delete`; `undo` of a create deletes the service, `undo` of a delete recreates it (with a new `uuid`), `undo` of an update restores the previous values. Attributes: `tcp-portrange`, `udp-portrange` (each one range `low[-high][:low[-high]]`, ports 1–65535, low ≤ high; a list of several ranges is refused) and `comment` (at most 255 characters). A service needs `tcp-portrange` or `udp-portrange`. The protocol stays `TCP/UDP/UDP-Lite/SCTP`. Shared defaults measured on both builds (empty category/fqdn, helper auto, check-reset-range default, color and timers 0, fabric-object disable, iprange 0.0.0.0, unset UDP-Lite/SCTP ranges) are normalized; nondefault fixed values and unsupported attributes are refused. Missing and empty `comment` are equivalent; CLI `unset comment` and REST `PUT {"comment":""}` restore that default. `visibility` and `proxy` are not shared fixed defaults.
- A service referenced in the configuration (for example by the `service` of a policy or by a service group) cannot be deleted, and its port ranges cannot change; its `comment` can. The predefined FortiOS services (`ALL`, `ALL_TCP`, `ALL_UDP`, `ALL_ICMP`, `HTTP`, `HTTPS`, `SSH`, `DNS`, `PING` and the other predefined names) are protected keys; names listed in `protected["firewall service custom"]` are protected as well.
- On FortiOS 8.0.1 and later the webhook safeguard calls `api/v2/cmdb/firewall.service/custom[/<name>]` (`DELETE` for a create, `PUT` for an update, `POST` with `name` for a delete); the earlier tables keep their REST paths `firewall/policy`, `firewall/address` and `firewall/addrgrp`.
- **Measured on the two exact builds above** (2026-11-14, CLI/REST and end-to-end Admin measurements). Preview/apply/undo succeeded with cli-script on 7.6.8 and webhook on 8.0.2 HA; loss of the check account reverted create and update. Referenced service delete/port changes and protected HTTPS changes were refused before writes. Not measured: safeguard firing a POST inverse, SIGKILL with admin recover, loss of the whole management path for this table, and comment/port-range length limits.

## FortiOS operations added in 1.0.12

These operations use the MCP tools `admin_preview` and `admin_apply` (operator undo: `admin undo`, preview: `admin_undo_preview`) unless stated otherwise. Each table lists its tested FortiOS builds; a build outside that list is not refused: the plan carries `firmware_support` with status `untested` and the preview names it, while every other check stays. The one technical limit is the safeguard: from FortiOS 8.0.1 Admin returns a change through the [webhook safeguard](#webhook-safeguard-on-fortios-801-and-later), which needs a REST inverse. `system interface`, `router static`, `switch-controller managed-switch/ports`, `port-bounce`, `poe-cycle` and profile batches have none and are refused on 8.0.1 and later before any write (`safeguard_no_rest_inverse` or `action_unsupported`). "Measured" below means a live run on a lab FortiGate-60F with FortiOS 7.6.8 build3744 (November 2026), compared with an independent CLI read of the check account; everything else is covered by automated tests only. For addresses, address groups, DHCP reservations, DNS entries, and policy move and staged creation, the live run sent the planned commands and inverses separately. Admin apply with undo ran for the creation and disablement of one A record, the creation and the deletion of a disabled policy, and all three steps of one batch of an address, a group and a policy; in a separate development run the device refused the policy step, and after the session closed the timed safeguard restored the changes made before the refusal. The other Admin apply and unattended safeguard-expiry scenarios of these tables are covered by automated tests only. The lease release and the other sections ran through Admin.

Tables that change the network path are off unless the device lists them in `opt_in`: `firewall policy`, `system interface`, `router static`, `vpn ipsec phase2-interface`, `ipsec-tunnel`, `firewall vip`, `firewall ippool` (and `firewall service custom`). `firewall policy`, `system interface` and `router static` need a non-empty `protected["system interface"]`; the IPsec and NAT tables accept `protected["system interface"]` or `protected["interface"]`. Re-enroll after changing `opt_in`.

`endpoint_impact` is an optional request field that must repeat the request key exactly; it records that the person accepted the interruption of clients. `expected_plan_sha256` (see [MCP tools](#mcp-tools)) binds the apply to the approved preview. Where a row below names them as required, apply without them is refused before any write.

Flow of every change: `admin_preview` → approve its `plan_sha256` → `admin_apply` with `expected_plan_sha256` → readback by the check account → `admin undo` with the hash of `admin_undo_preview`. A clear, a recovery and a cycle have no undo.

| Profile tables, policy, NAT, IPsec, batch | before FortiOS 8.0.1 (7.6 and 8.0.0): the Admin write profile in [Accounts and least privilege](../components/netops-helper/docs/read-only-accounts.md); 8.0.1 and later: `super_admin` with a password credential (webhook) | a second login with the Helper read profile (never the write credential) |

### Fortinet SSH sessions

A FortiOS or FortiADC device entry needs `host_key`, the verified OpenSSH public key (`<type> <base64>`) whose SHA-256 is `host_key_fingerprint`. Admin builds the known-hosts line from these two values and never scans the host key from the network; without `host_key` every operation stops with `host key check failed: missing Fortinet public host key; add host_key at enrollment`. During one operation (preview, apply, undo, enrollment, doctor or recover) Admin opens at most one SSH session per account, one for the write and one for the check account, and sends every command through it. A login that failed is not repeated in the same operation (`Fortinet SSH login already failed in this operation`). This was measured on the lab FortiGate-60F and on FortiADC-KVM 7.6.7 build0676: one session per operation and account, no host-key scan.

### Private global backup

`admin backup` (operator command, not MCP) exports the global configuration of a FortiGate over HTTPS (`POST /api/v2/monitor/system/config/backup?scope=global`, `GET` after a `405` answer) and stores it encrypted (AES-256-GCM) in a private directory. Without `--confirm` it only prints the plan and its `plan_sha256`; with `--confirm PLAN_SHA256` it exports. Arguments: `--host`, `--port` (default 443), `--login` (or omit it and set `NETOPS_BACKUP_TOKEN` to an API token), `--tls-sha256` (SHA-256 of the device leaf certificate, checked before the credential is sent), `--directory` and `--keep` (1–365, default 7 per host and port). The environment of the command holds `NETOPS_BACKUP_KEY` (32 bytes in hexadecimal) and `NETOPS_BACKUP_PASSWORD` for `--login`. The directory must exist, belong to the user that runs Admin, have mode 0700 and lie outside any Git worktree. `admin backup-unseal --input FILE --output FILE` authenticates an archive with the same key and writes the native configuration file for a restore into a private directory.

The export is refused when it is masked (`FortinetPasswordMask`), incomplete, misses `system global`, `system interface`, `system admin` or `firewall address`, or misses sections that the newest archive readable with the current key holds; refusals use the `backup_*` codes and `plan_changed`. A VDOM export must end with its `vdom` block and hold `firewall address` in at least one VDOM. Admin checks the framing and the presence of sections; missing lines inside a section can escape that check. Nothing changes on the device and nothing is restored by Admin. Measured: an export with an account and `POST` (FortiGate-60F, 7.6.8 build3744); a token and the `GET` fallback are covered by automated tests only, and a restore was not run.

### FortiSwitch ports through FortiLink

Table `switch-controller managed-switch/ports`, `op` `update`, key `SERIAL:portN` (for example `S108ENTF00000000:port5`). Attributes: `description` (63 characters), `status` (`up` or `down`), `vlan` (native VLAN: the name of a VLAN interface on the FortiLink), `allowed-vlans` and `untagged-vlans` (lists of such names), `allowed-vlans-all` and `poe-status` (`enable` or `disable`). Apply requires `expected_plan_sha256`. The write account needs Read/Write for WiFi & Switch Controller in its access profile (`fortiswitch_write_permission_required`).

- Refused before any write (`port_protected`): a port in `protected["interface"]` (by name or key), a FortiLink, stacking, point-to-point or MCLAG ICL port, a trunk member, a port controlled by a port policy (VLAN change), and a port whose LLDP neighbor is a bridge or network device. Admin checks the link and the learned MACs, and checks power only for a `poe-status` change or a PoE cycle; an active port (link up, a learned MAC, or power delivered in those two cases) needs `endpoint_impact` (`endpoint_impact_required`). A port with link up also needs a readable LLDP answer, with or without `endpoint_impact`.
- VLAN changes: every VLAN that the change adds or removes must be an interface on the switch FortiLink with ID 1–4094, an untagged VLAN must also be allowed or native (`fortiswitch_vlan_invalid`), and a VLAN interface that is protected or carries administrative access is refused (`port_management_vlan`). A diagnostic that times out is `fortiswitch_read_timeout`.
- Undo restores the previous values. Measured: description, status, native VLAN and the allowed/untagged lists with one test VLAN (FortiGate-60F with a FortiSwitch 108E-series switch without PoE). `allowed-vlans-all` and `poe-status` are covered by automated tests only and always carry the `untested` warning; on the lab switch without PoE the device answered `-7622` and Admin refused with `poe_not_capable`.

**Port bounce and PoE cycle.** Table `port-bounce` with `changes` `{"status": "down"}`, or table `poe-cycle` with `changes` `{"poe-status": "disable"}`; key `SERIAL:portN`, `op` `update`; MCP `admin_apply`/`admin_preview`, or the operator commands `admin port-bounce` and `admin poe-cycle` with `--port SERIAL:portN`, `--preview` and `--expect-plan-sha256` (these two operator commands do not receive `--config` automatically). Apply requires `expected_plan_sha256`. A bounce sets the port down, waits until the check account sees software admin and link down, sets it up again and verifies that the configuration returned exactly. A PoE cycle runs `execute switch-controller poe-reset SERIAL portN` only on a port that delivers measurable power (`poe_device_not_powered` otherwise) and confirms only when no power is drawn (current zero, or lower while `Searching`) and power returned. Both run behind the timed safeguard and end `confirmed` only when the down state was proven, the return verified and the safeguard confirmed. When the down state is unproven, Admin reports `reverted` with `cycle effect unverified` only after it verified the return; otherwise the timed safeguard and its readback settle the result. Neither can be undone (`undo_not_applicable`). Measured: a bounce of an unused port (software admin up, down, up). The PoE cycle is covered by automated tests only.

### Interfaces, VLANs and static routes

Opt-in tables `system interface` (key: interface name, 15 characters) and `router static` (key: the route sequence number). `system interface` creates and deletes VLAN interfaces (`vdom` `root`, parent `interface`, `vlanid`, optional `ip`, `allowaccess` only `ping`; a new VLAN gets `role undefined`), and updates `alias`, `description`, `status` and `ip`. An update of only `alias`, `description` or `status` is also accepted on an interface with attributes outside the profile. `router static` creates, updates and deletes routes with `dst`, `device` (required), `gateway`, `distance`, `status`, `dynamic-gateway` and `comment`.

Refused before any write: an interface in `protected["system interface"]`, an interface built on it or carrying it, an interface with administrative access other than `ping`, a VLAN on a protected parent, an address that overlaps another interface subnet, a default route, a route through a protected interface or into the subnet of one or into the destination of a route that leaves through one, a route through an interface missing from the snapshot, and a delete of an object that is still referenced. Undo restores the previous object; the undo of a newly added `ip` or `gateway` (`unset`) is covered by automated tests only. Measured: alias, description and status with undo, create and delete of a VLAN with undo, create, disable and delete of a route with undo, and the refusals of the management path. `dynamic-gateway` was not measured through Admin.

### DHCP reservations, DNS entries and lease release

`system dhcp server/reserved-address` (create, update, delete): key `SERVER:ID` or `INTERFACE@MAC`, attributes `ip` and `mac` (required) and `description`. The DHCP server must exist, be enabled and of type regular, and the address must be usable in its subnet; a reservation of a server on a protected interface is refused. `endpoint_impact` naming the key and `expected_plan_sha256` are required. Tested builds: 7.6.8 build3744, 7.6.7 build3704 and 8.0.0 build0167.

`system dns-database/dns-entry` (create, update, delete): key `ZONE:ID` or `ZONE@HOSTNAME`, attributes `type` (`A` or `PTR`, not changed by update), `hostname` and `ip` (required), `ttl` and `status`. Only entries of an existing enabled primary zone; a PTR entry needs a host name with a domain; a duplicate of another entry is refused. `expected_plan_sha256` is required. Tested build: 7.6.8 build3744. On create, the `@` key takes the highest existing numeric ID plus one (1 in an empty table) and fills in the MAC or host name from the key; an update or delete needs exactly one match. Use the numeric key to change the MAC or host name of an existing entry.

**Lease release.** Table `dhcp-lease`, `op` `clear`, key one IPv4 address, empty `changes`, `endpoint_impact` naming the address and `expected_plan_sha256`. Admin reads `execute dhcp lease-list` with the check account, refuses an address without a lease (`clear_no_entry`), a lease on a protected interface (`clear_protected_target`), `all`, ranges and lists (`clear_invalid_target`), and sends `execute dhcp lease-clear ADDRESS`. Because the device answers with nothing either way, the result is proven only by the row leaving the list while the other leases stay; an incomplete list is `clear_readback_unreadable`. A released lease cannot be undone; the client requests a new one. The write account needs `execute`.

Measured: for a reservation and for A and PTR entries, the planned create, update and delete commands and their inverses, sent separately and read back by the check account as predicted (of these, only the A record named above ran through Admin, with apply and undo; the remaining `admin apply` scenarios and the unattended expiry of the timed safeguard of these tables are covered by automated tests only), and the release of one lease through Admin. Known limits: the device accepts `lease-clear` by address without a MAC condition, so another client can take the address between the check and the release (a window of seconds); the binding between `SERVER-ID` and the interface comes only from the section of the lease list.

### Addresses and address groups

`firewall address` (create, update, delete) accepts the types `ipmask` (`subnet`), `fqdn`, `iprange` (`start-ip`, `end-ip`), `mac` (`macaddr`), `geography` (`country`) and `interface-subnet` (`interface`; Admin derives the subnet from the static IPv4 address of the interface), each with `comment`; the type is set at create. `firewall addrgrp` creates, updates and deletes static groups with `member` and `comment`; a group must keep at least one member, must not contain itself and may name only visible objects. Changing the members of a group that an active policy uses needs `endpoint_impact` (`fortios_policy_impact_required`); a group used by a protected policy is refused. Measured: create, update, delete and undo of every address type and of groups, and the refusal to delete a referenced object. Only `ipmask` addresses are tested on 8.0.2 build0251; the other address types and the create, delete and comment changes of groups are tested on 7.6.8 build3744 only, and their webhook inverse is covered by automated tests only. Known limit: the undo of a deleted `interface-subnet` address after the interface address changed is refused.

### Firewall policy: delete, order and staged creation

These extend the opt-in table [`firewall policy`](#opt-in-table-firewall-policy). Apply of any policy change requires `expected_plan_sha256` (`fortios_policy_preview_required`), and a change of an active policy that affects traffic requires `endpoint_impact` naming the policy ID (`fortios_policy_impact_required`).

- `op` `move` with `changes` `{"before": "ID"}` or `{"after": "ID"}` moves a policy; `create` may name the same position. A create with `status enable` and a position is written disabled, moved and then enabled.
- `op` `delete` removes a policy. Undo recreates it at its original position. When the VDOM allows manual UUID assignment, the original UUID is kept; otherwise FortiOS assigns a new one and the result reports `uuid_changed`.
- The plan reads the whole policy order (`fortios_policy_order_unreadable` if incomplete) and refuses a position anchor that is missing, a new order that moves an enabled policy across a protected policy, and an undo after the original order of the policies changed (`fortios_policy_order_changed`). With the webhook safeguard an undo of a move is one REST request; a delete whose undo must recreate and reposition the policy is refused.

Measured: move and undo, delete and recreation at the original position with a new UUID, undo after more policies were appended, and staged creation before enabling. Known limit: undo identifies a policy by ID and attributes, not by UUID; a policy replaced by hand with the same ID and attributes is treated as the original.

### VIP, IP pools and policy NAT and security attributes

Opt-in tables `firewall vip` (create, update, delete; `extintf`, `extip`, `mappedip` required; `portforward` with `protocol`, `extport` and `mappedport` as single ports; `arp-reply`; `comment`) and `firewall ippool` (create, update, delete; `startip`, `endip` required; `associated-interface`, `arp-reply`, `comments`). Apply requires `expected_plan_sha256` (`fortios_nat_preview_required`); a change of an object with ARP reply enabled, other than its comment, requires `endpoint_impact` (`fortios_nat_impact_required`). Both tables refuse a protected interface binding (`fortios_nat_protected`). A VIP also refuses an external or mapped management address, including secondary addresses and addresses of interfaces with administrative access; an IP pool refuses a range that contains the primary IPv4 address of a protected interface.

`firewall policy` also accepts `nat`, `ippool` with `poolname`, `utm-status` with `ssl-ssh-profile`, `webfilter-profile`, `av-profile`, `ips-sensor`, `application-list` and `dnsfilter-profile`, `internet-service` with `internet-service-name`, `-group`, `-custom` and `-custom-group`, `groups`, `users`, `srcaddr6` and `dstaddr6`. The plan refuses policy NAT under central NAT, `ippool` without `nat` and `poolname`, UTM, NAT or users without `action accept`, a security profile without `utm-status enable`, an Internet Service policy with destination addresses or service, a missing referenced object, and a destination VIP that maps to a management address. These attributes are tested on 7.6.8 build3744 only. Measured: create, update and undo of a VIP, an IP pool and a policy with these attributes, the refusals, and one TCP flow through the port forward. A VIP group as destination is covered by automated tests only. The VIP and IP pool profiles are provisional.

### Related changes in one batch

Table `batch`, `op` `update`, key `batch`, `changes` a list of 2–32 steps, each with `table`, `op`, `key`, `changes` and optional `endpoint_impact`; the steps are addresses, address groups and at most one firewall policy, each object at most once. The preview plans each step against the predicted result of the previous ones and returns one `plan_sha256`; pass it to `admin_apply` as `expected_plan_sha256`. Steps are `create`, `update` or `delete` (no `move`). One cli-script safeguard holds the inverse of all steps (the escaped script at most 1023 UTF-8 bytes), and each step is checked again on the device just before it writes. When a step fails, Admin returns the steps already written. Undo: `admin undo --change-id ID --expect-plan-sha256 HASH` with the hash of `admin undo --preview`. Batches are refused on 8.0.1 and later. Measured: an address, a group and a policy in one batch with undo, and a failure in the middle that returned the earlier steps. Known limits (timing windows): the safeguard holds the inverses of all steps from the start, so when the Admin process is lost during a batch it also runs the inverses of steps that were never sent; and when the read of the safeguard is delayed past its fire time, a step can still write after the safeguard has fired, so that step is not returned by it.

### Targeted session clear

Table `sessions`, `op` `clear`, key `src:IPv4` or `dst:IPv4`, `changes` with the optional opposite address (`src` or `dst`), `sport`, `dport` and `proto` (6 or 17 when ports are named), `endpoint_impact` naming the key and `expected_plan_sha256` (`clear_preview_required`). Admin needs a single-VDOM device (`clear_scope_unverified` otherwise), an empty session filter at the start, and the same configuration checksum for both accounts. It sets `diagnose sys session filter` (VDOM 0, forwarded sessions only), lists the matching sessions with the check account, refuses an empty match (`clear_no_entry`) and a session that crosses a protected policy or interface (`clear_protected_target`), clears, resets the filter and verifies the reset (`fortios_clear_cleanup_unverified`). A read that times out is `fortios_clear_read_timeout`. Cleared sessions cannot be undone; clients open new sessions. Tested on FortiGate-60F 7.6.8 build3744. Measured: one session cleared while a control session stayed, filters reset, configuration checksum unchanged.

### IPsec Phase 2 and tunnel recovery

Opt-in table `vpn ipsec phase2-interface`, `op` `create` only (undo deletes it): key the Phase 2 name (35 characters), `phase1name`, `src-subnet`, `dst-subnet` and `proposal` required, `dhgrp`, `pfs`, `auto-negotiate` and `keylifeseconds`; `copy-from` names an existing IPv4 Phase 2 whose settings are copied. `endpoint_impact` naming the selector and `expected_plan_sha256` are required (`fortios_ipsec_impact_required`, `fortios_ipsec_preview_required`). The Phase 1 and its tunnel interface must exist; a protected selector, Phase 1 or tunnel interface, a tunnel interface with `ssh` or `https` access, a DH group without PFS and a duplicate selector pair are refused (`fortios_ipsec_protected`, `fortios_ipsec_target_invalid`).

Tunnel recovery: table `ipsec-tunnel`, `op` `clear`, key the Phase 2 name, `changes` `{"phase1name": "NAME"}` of a static Phase 1, `endpoint_impact` and `expected_plan_sha256`. Admin sends `diagnose vpn tunnel down` and `up` for a selector that is up (only `up` for one that is down) and verifies through the check account that the selector went down, or that its SAs were replaced, and that it came up again. It changes runtime state only and cannot be undone. Tested on 7.6.8 build3744. Measured: create, copy and undo of a Phase 2, recovery of a selector with a strongSwan peer that confirmed the new SA, and the refusals without hash or impact. Known limit: a management path that runs through the tunnel without local administrative access on the tunnel interface is not detected as protected; recovery still requires `endpoint_impact`.

## ExtremeXOS port admin state and PoE cycle

Both operations were measured on 33.7.1.6-patch1-11 on X435-8P-4S/X440G2-12p-10G4 (write account with the R/W role; 2026-11-14). The `ports` table lists 33.7.1.6 and EXOS-VM 33.6.1.14 as tested, the PoE tables 33.7.1.6. Since 1.0.12 another firmware is not refused: the plan carries `firmware_support` with status `untested`.

**Port admin state.** The `ports` table has the attribute `admin-state` (`enabled` or `disabled`, default `enabled`). `admin preview`/`admin apply` (CLI and MCP `admin_preview`/`admin_apply`) with `{"table": "ports", "op": "update", "key": "8", "changes": {"admin-state": "disabled"}}` sends `disable ports 8`; `enabled` sends `enable ports 8`. The timed UPM safeguard holds the inverse after `configure cli mode persistent` (without it the switch restored the port, but `show configuration` kept `disable port 8`). The read-back is `show configuration` (a disabled port is the line `disable port 8` in module vlan) and, with the check account, `Admin state` of `show ports 8 information detail`; preview also shows the port and link state of `show ports 8 configuration no-refresh`. `admin undo` returns the previous state. A snapshot with `disable port N` was earlier a line outside the port object; it is now the `admin-state` of that port, also for display-string changes.

Before the admin state of a port is changed (disabled or enabled) Admin refuses, before any write (since 1.0.12 `port_uplink`, `port_lag_member`, `port_lldp_neighbor` and `port_learned_mac` apply only without `endpoint_impact`, and `port_uplink` also covers a port with an active link; see below):

| Code | Refused port |
|---|---|
| `port_protected` | listed in `protected["ports"]` of the device |
| `port_management_vlan` | member of a VLAN named in `management_vlans` of the device audit policy |
| `port_uplink` | carries tagged VLANs (a trunk is treated as an uplink) |
| `port_lag_member` | member of a link aggregation (`enable sharing`) |
| `port_lldp_neighbor` | has a neighbor in `show lldp neighbors` |
| `port_learned_mac` | has a learned address in `show fdb` |
| `port_usage_unreadable` | the LLDP or FDB answer is not recognised or incomplete (the FDB row count must match its `Total` line) |

Enabling a port gets the same checks and reads LLDP and FDB as disabling it does (since 1.0.10: enabling a disabled uplink or LAG member can bring back a loop); a display string change does not. The out-of-band management port is not a numbered port and cannot be named.

Since 1.0.12 a request with `endpoint_impact` naming the port accepts a trunk, a LAG member (the whole aggregation is the scope), an active link, an LLDP neighbor and learned MAC addresses. Admin then checks that the SSH session of Admin does not return through an affected port or VLAN (`port_management_interface` otherwise), and the plan reports `port_impact` with the tagged VLANs, the LAG ports, the link state, the LLDP ports and the ports with learned MAC addresses. Apply with `endpoint_impact` requires `expected_plan_sha256`. `port_protected` and `port_management_vlan` stay refusals; a protected port anywhere in the aggregation refuses the change.

**PoE cycle.** With the instance stopped, `docker compose run --rm netops admin poe-cycle --config /var/lib/netops/admin/config.json --device sw-x435 --port 3 --reason "..." --user-request "..." --request-id ...` (with `--preview` it only checks) power-cycles one port: `disable inline-power ports 3`, then `enable inline-power ports 3`. `poe-cycle` is not among the operator commands that receive `--config` automatically, so the command names the private Admin configuration of the default state path itself. Since 1.0.12 the same cycle runs through MCP: `admin_preview`/`admin_apply` with `{"table": "poe-cycle", "op": "update", "key": "3", "changes": {"admin-state": "disabled"}}`; MCP apply requires `expected_plan_sha256`. It runs through the same admission as `admin apply` (enrollment, budgets, blocking, operations log, notification) as one operation of kind `poe-cycle` on the table `inline-power`, behind the safeguard `enable inline-power ports 3`. Since 1.0.12 the table `inline-power` also takes a permanent `update` of `admin-state` (`disable inline-power ports 3` or `enable inline-power ports 3`) with undo. Whenever inline power is disabled, also in a cycle, a port in a LAG is refused (`port_lag_member`) and the SSH management path of Admin must not use the port. The cycle:

1. reads `show inline-power info ports 3` (write account) and `show inline-power info detail ports 3` (check account);
2. reads the switch clock and checks that the time left until the safeguard fires is more than the cycle budget plus `confirm_margin_seconds` (see **Safeguard margin** below); otherwise it removes the safeguard, saves the configuration and ends `rejected` with `safeguard_margin_insufficient` without touching inline power;
3. disables inline power and verifies `show configuration` (the line `disable inline-power ports 3` in module poe) and the audit;
4. reads the check account every 2 s until it sees `Configured Admin State: disabled` and `Inline Power State: disabled`, for at most 15 s of pauses between the reads; it stops at the first read that shows both; when the pauses run out, the time of each read (up to 60 s) comes on top, so the wait can exceed 15 s (measured on 2026-11-14: about 1 s of `searching` first);
5. enables inline power and verifies that `show configuration` equals the state before;
6. reads the check account in the same way, for at most 60 s of pauses plus the time of the reads (with 31 reads of 2 s each about 122 s), until it sees `enabled` and a state other than `disabled`; when the port was `delivering` before, it waits for `delivering`;
7. removes the safeguard and saves the configuration.

The result is `confirmed`; when a powered device that was `delivering` is not `delivering` again by the end of the wait in step 6, it is `confirmed` with the reason `powered device not delivering after the cycle` (CLI exit code 4). The record holds `poe.before`, `poe.off` and `poe.after`. A cycle that fails or loses a read-back is settled by the safeguard as any other change (`reverted`, `unknown` or `revert-failed`). A PoE cycle has no undo (`undo_not_applicable`).

**Safeguard margin.** From the clock check in step 2 until the safeguard is removed in step 7 a cycle can take up to 175 s. This is a budget, not a measured duration: three writes (disable, enable, safeguard removal), two `show configuration` reads, the off wait (15 s of pauses and 9 reads) and the on wait (60 s of pauses and 31 reads). A read is budgeted at 2 s and `show configuration` at 4 s, the longest measured durations (ssh exec, 1 s resolution). An interactive write was not timed on its own and is budgeted as two reads (4 s). A cycle without a powered device usually ends much sooner. The budget counts with response times as measured; a device that answers far slower than that (reads close to their timeouts) can exceed it, and then the safeguard decides: it restores the inline power configuration at its time, and the result is `unknown` or `reverted`, not an unsafe state. The cycle and `confirm_margin_seconds` must fit inside `safeguard_seconds`. When `175 + confirm_margin_seconds >= safeguard_seconds`, preview and apply refuse the PoE cycle with `safeguard_margin_insufficient` before any device read or write, without an operation record. `reason_details` gives `cycle_seconds`, `confirm_margin_seconds`, `available_seconds` and `required_safeguard_seconds`. With the default `safeguard_seconds` 180 and `confirm_margin_seconds` 45 a PoE cycle is refused: set `safeguard_seconds` of a switch used for PoE cycles to at least 221 (with the margin 45). Step 2 repeats the comparison against the switch clock after the safeguard is installed, because the installation itself takes time. When that check refuses, the operation ends `rejected` with the same code (CLI exit code 4) and inline power was not touched. When the clock cannot be read there, the code is `device_clock_unreadable`. In both cases the safeguard is removed and the configuration saved; if the removal is not proven the result is `unknown`, and if the save fails the reason is `not persisted` and the device is blocked.

**Interrupted cycle.** `admin recover` settles a cycle interrupted before `confirm_start` through the safeguard like any other change (`reverted` with the reason `interrupted`). After `confirm_start`, power was already seen on again. If the safeguard is already absent, recover ends `confirmed` with `confirmed before the interruption`, as in 1.0.9. If the safeguard is still installed, recover reports the cycle as done only on proof, which needs all three of these:

- the journal holds `poe_off_observed`, `poe_enable_verified`, `poe_on_observed` and `confirm_start` in this order, with `poe.off` showing `disabled`/`disabled` and `poe.after` showing `enabled` and a state other than `disabled`;
- a fresh `show configuration` equals the state before;
- the check account sees `Configured Admin State: enabled` and a state other than `disabled`.

With that proof recover records the step `cycle_proven` and the record field `poe.recovered`, removes the safeguard, verifies the configuration again and saves it. The result is `confirmed` with the reason `cycle confirmed before the interruption; safeguard removed by recover`, or `powered device not delivering after the cycle` when the port was `delivering` before and is not now. Without the proof recover records `cycle_unproven` with the cause and lets the safeguard fire, which runs `enable inline-power ports N`. The result is then settled like any expiry, normally `reverted` with the reason `interrupted; PoE cycle not proven`. It never reports a cycle that was not proven.

`reset inline-power ports N` is not used: on a port without PoE it is silent (empty output, exit status 0) and its off time varied from 3 s to 40 s (measured on 2026-11-14), so neither a refusal nor the cycle itself would be observable.

| Code | Refused PoE cycle |
|---|---|
| `poe_not_capable` | `Port N is not inline-power capable` |
| `poe_unsupported` | the switch gives no inline-power table (a platform without PoE) |
| `poe_disabled` | inline power of the port is configured disabled or its state is `disabled` |
| `poe_state_unreadable` | the inline-power answer is not recognised or names another port |
| `safeguard_margin_insufficient` | `safeguard_seconds` leaves less than the cycle budget (175 s) plus `confirm_margin_seconds`; checked from the configuration before any read and again on the switch clock after the safeguard is installed |
| `port_protected` | listed in `protected["ports"]` or `protected["inline-power"]` |

**Not measured.** The state `delivering` with a real powered device and the time until such a device is powered again (no powered device was connected; all ports were `searching`). The operation does not depend on it: the configuration and `Configured Admin State` are verified as measured, and the observed power state is reported. The read-only check account read `show inline-power info detail` in the Admin runs on the two switches (2026-11-14). The safeguard margin check and the recover classification of 1.0.10 change only decisions in Admin, not the commands or waits of the cycle on the switch: they add one read, `show switch`, for the clock, and recover decides without waiting for the safeguard timer. They are verified by automated tests against the simulated switch, with measured `show inline-power info detail` outputs. They were not run on a switch.

### Ports, PoE and bounce

- `ports` also takes `description-string` (up to 255 characters of letters, digits, spaces and `._()/+-`); a key may be `slot:port` for a stack. Measured: a long description and its undo on X440 and EXOS-VM; stack keys are covered by automated tests only (no stack in the lab).
- `vlan-membership` takes `op` `update`, a port key (also `slot:port`) and the `tagged` (list of VLAN names) or `untagged` VLAN of the port. The check account reads the port membership back, and undo restores the previous membership. Stack port keys are covered by automated tests only.
- `inline-power` `update` of `admin-state` sets the PoE state of a port permanently, with undo (tested on 33.7.1.6). Measured on X440: disable, readback, undo, and the refusal `poe_not_capable` of a port without PoE.
- `port-bounce`: MCP table `port-bounce` or operator `admin port-bounce --port N`, `changes` `{"admin-state": "disabled"}`, `expected_plan_sha256` required. ### VLANs: ports, rename and IP interfaces

The `vlan` table (key the VLAN name; `Default` and `Mgmt` are protected) creates, updates and deletes VLANs with `tag`, `description`, `tagged-ports` and `untagged-ports` (lists of port numbers), `name` (rename: `configure vlan OLD name NEW`, undo renames back), `ipaddress`, `ipforwarding`, `ipv6-address` and `ipforwarding-ipv6`. ### Ingress ACLs

- `acl-policy` (key the policy name, create, update, delete): `policy-content` is the text of a `.pol` file made only of entries `entry NAME { if { MATCHES } then { permit|deny; [count NAME;] } }`, where the matches are `source-address` and `destination-address` (with a prefix length), `protocol` (`tcp`, `udp`, `icmp`), `source-port` and `destination-port`; anything else is refused (`exos_acl_policy_invalid`). Entry names must be unique and every statement ends with `;`; the file is printable ASCII of at most 8192 bytes. Admin transfers the file over SFTP with the pinned host key, runs `check policy NAME access-list` and refuses a change of a file that a client uses. A policy file has no on-switch timer: an unverified file change is returned by Admin in the same run (`return_mechanism` `pinned-sftp-compensation`), and after a loss of the Admin process by `admin recover`.
- `acl-attachment` (key `port:N` or `vlan:NAME`, `policy` required, create and delete): refused for `Default`, `Mgmt`, management or protected VLANs, tagged, aggregated, protected or unavailable ports, a protected policy, an overlap with another ingress ACL and a policy already attached elsewhere (`exos_acl_unsafe_scope`); an active target needs `endpoint_impact`, and the SSH management path must not use it. Unreadable answers are `exos_acl_unreadable`.

Measured: policy create, update and delete and port and VLAN attachments with undo on two EXOS-VM nodes and X440. No packet test of a client was run. Known limits: apart from the attachment to an active target, no ACL change asks for `endpoint_impact`; a refused preview without enrollment can return the text of the existing policy file; a staging file with the name that Admin derives from the operation is removed by the compensation even if someone else created it.

### DHCP relay and DHCP server

Both tables take only `op` `update`, which also adds or removes the service (`null` removes an attribute; a kept `dhcp-server` needs both range ends, and adding or removing its `lease-seconds` is refused with `exos_dhcp_inverse_unsupported`).

- `bootprelay` (key a VLAN in VR-Default, `server-ip`): one IPv4 relay target; the VLAN needs IPv4 forwarding, and a VR-wide relay target is refused.
- `dhcp-server` (key the VLAN): `range-start`, `range-end`, `default-gateway`, `primary-dns`, `secondary-dns`, `lease-seconds` and `ports`. The range must lie in the VLAN subnet without the VLAN address, the gateway in the subnet outside the range, and the ports must be standalone ports of the VLAN. A new server needs a VLAN without active ports, so that no other DHCP server can be present on it.

Both refuse a VLAN that already has the other service or a setting outside the profile (`exos_dhcp_conflict`), a protected VLAN or port, and an unreadable answer (`exos_dhcp_readback_unreadable`). A change of an existing configuration, the VLANs `Default` and `Mgmt`, a management VLAN of the audit policy and an active VLAN that may carry the SSH management path need `endpoint_impact` naming the VLAN. Tested on 33.6.1.14 and 33.7.1.6. Measured: relay and pool with undo on EXOS-VM and X440, refusals without hash and of a pool on a relay VLAN. Known limit: undo does not check whether the VLAN has meanwhile become a management VLAN.

### Save the configuration explicitly

`op` `save`, `table` and `key` `startup-config`, empty `changes`, `expected_plan_sha256` required (`exos_save_preview_required`). The preview shows the selected configuration file and up to 100 lines of `show configuration difference` with credential lines redacted; the check account must read the same file and difference (`exos_save_check_denied`). Apply runs `save configuration` only when no other session is open (`exos_save_sessions`) and nothing changed since the preview (`plan_changed`), then verifies a clean prompt and an empty difference (`exos_save_diff_mismatch`). Saving also stores changes made by others that the preview showed. The previous saved configuration cannot be restored by Admin: a save cannot be undone. Measured on EXOS-VM and X440 with an empty difference (a nonempty difference only in the preview); saving a nonempty difference is covered by automated tests only.

### Targeted clear

`op` `clear`, `expected_plan_sha256` required (`clear_preview_required`): `port-counters` (key one port), `fdb` (one MAC address, `port:N` or `vlan:NAME`), `iparp` (one IPv4 address) and `neighbor-discovery` (one IPv6 address), with `changes` `{}` or `{"vr": "NAME"}` for an address. Admin sends one bounded command (`clear counters ports`, `clear fdb`, `clear iparp ADDRESS vr VR`, `clear neighbor-discovery cache ipv6 ADDRESS vr VR`) and refuses a scope without learned entries (`clear_no_entry`), an address with several entries (`clear_ambiguous_entry`), and a protected port, a system VR, a management or protected VLAN or a port with an LLDP neighbor (`clear_protected_target`). The readback accepts an entry that is gone or learned again; static entries stay. A clear cannot be undone (`undo_not_applicable`). Tested on 33.6.1.14. Measured on EXOS-VM under traffic: the counters of the port fell while a control port kept them, the cleared FDB and ARP entries were learned again, the ND entry was read back empty and learned again, static and protected targets were refused, and the configuration stayed unchanged.

### Private backup of a saved configuration

`admin backup-exos` (operator command) reads a saved configuration file (`--file`, for example `primary.cfg`) over SFTP after checking the host key against `--ssh-sha256`, and stores it encrypted like the [FortiOS backup](#private-global-backup) (`--host`, `--port`, `--login`, `--identity` with a private key file or `NETOPS_BACKUP_PASSWORD`, `--legacy-ssh`, `--directory`, `--keep`, `--confirm`; `NETOPS_BACKUP_KEY`). The file must be complete XML with the aaa, cfgmgr, devmgr and vlan modules (`backup_incomplete`). Without `--confirm` the command only returns the plan hash and does not contact the switch. `admin backup-exos-unseal --input FILE --output NAME.cfg` writes the native file to a local private directory for a restore. Nothing changes on the switch. Measured on EXOS-VM and X440: the extracted bytes equal an independent SFTP copy; an upload of the restored file under an inactive name was measured separately on EXOS-VM, a boot from it was not run.

## Arista EOS interface description, admin state and access VLAN

Platform `eos`, measured only on cEOSLab 4.36.1F (GNS3 lab, 2026-11-15/16); the profiles list `4.36.1F` as the tested version. Since 1.0.12 another EOS release is not refused: preview, apply and status carry `firmware_support` with status `untested` ([MCP tools](#mcp-tools)). Tables (`update` only, CLI and MCP `admin_preview`/`admin_apply`/`admin_undo_preview`, operator `admin undo`):

| Table | Attribute | Device lines | Read-back of the check account |
|---|---|---|---|
| `interface` | `description` (at most 240 printable characters since 1.0.12, see [below](#arista-eos-vlans-ports-routing-services-and-operational-actions)) | `description TEXT` / `no description` | `show interfaces N description` |
| `interface` | `admin-state` (`enabled`/`disabled`) | `no shutdown` / `shutdown` | `show interfaces N status` (`disabled`) |
| `vlan-membership` | `access-vlan` (1–4094, default 1) | `switchport access vlan N` / `no switchport access vlan` | `show interfaces N switchport` (`Access Mode VLAN`) |

The key is the full interface name, for example `Ethernet10`. Example: `{"table": "interface", "op": "update", "key": "Ethernet10", "changes": {"description": "netops-test"}}`.

**Accounts and roles.** The write account must log in with privilege 15 (`aaa authorization exec default local` and `username <write> privilege 15 role network-admin`); Admin reads the running configuration with one SSH exec command and never sends `enable` or an enable secret. A write account that logs in with another privilege is refused (`write_account_privilege`). The check account (for example role `network-operator`, privilege 1) only reads `show interfaces N status|description|switchport`. Without command authorization any account reaches privilege 15 with `enable` when no enable secret is set, so the check account is then not really read-only; the measured lab therefore also has `aaa authorization commands all default local`, under which `network-operator` is refused `configure terminal` and `configure session` (`% Authorization denied`). The device entry needs `accounts` (the `username` lines of the running configuration); `audit_policy` is not supported, because the Auditor holds no EOS rules (the audit gate reports 0 rules).

**Safeguard and return.** Before the change Admin commits an empty configuration session `netops-<12 hex>` with `commit timer` of `safeguard_seconds`; its checkpoint is the configuration before the change. The change then runs line by line through `configure terminal` in an interactive session (an SSH exec batch continues after an error, so it is never used for configuration). Confirmation is `configure session netops-<id> commit` followed by `no configure session netops-<id>`; `write memory` runs only after it, because during the pending timer it would save the unconfirmed state. When the timer expires, EOS returns the **whole** running configuration to the checkpoint of the session: a change of someone else made in the timer window is returned too. The session then disappears; while Admin waits for the timer of a running change it accepts the return only with the log lines `CONFIG_SESSION_COMMIT_TIMER_TIMEDOUT` and `CONFIG_SESSION_COMMIT_REVERTED` of that session (`show logging last 60 minutes`) and a snapshot equal to the state before. `admin recover` of an interrupted change is weaker: when the session is already gone and the running configuration equals the state before the change, it saves the configuration and records `reverted` without reading the log (for example after more than 60 minutes, when the log lines are out of the read window); such a `reverted` is proven by the configuration matching the state before, not by log events of the timer. While the timer is pending EOS refuses every other commit timer and the commit of other sessions. Behaviour of a pending timer across a reload was not measured.

Admin refuses, before any write:

| Code | Refused |
|---|---|
| `port_management_interface` | a `Management` interface |
| `port_unsupported_interface` | an interface that is not `EthernetN` (loopback, VLAN interface, port-channel) |
| `vlan_missing` | an access VLAN that is not in the running configuration or not in `show vlan id N` (EOS would create it silently) |
| `port_uplink` | for a change of the admin state (down **or** up): a trunk (`switchport mode trunk`, `switchport trunk ...`); for an access VLAN change: a port that is not `static access` (since 1.0.12 a change of the mode or of the trunk VLANs is planned and needs `endpoint_impact`, see [below](#arista-eos-vlans-ports-routing-services-and-operational-actions)) |
| `port_lag_member` | the same, a `channel-group` member |
| `port_routed` | the same, a routed port (`no switchport`) |
| `port_lldp_neighbor` | an admin state change (down or up) or an access VLAN change of a port with an LLDP neighbor, unless `endpoint_impact` names the port (since 1.0.12) |
| `port_learned_mac` | the same, a port with learned MAC addresses, unless `endpoint_impact` names the port (since 1.0.12) |
| `foreign_config_session` | an open (`pending`) configuration session or a pending commit timer of someone else |

An interface that is not in the running configuration is refused too (EOS would create it). Admin up gets the same checks as admin down, because enabling a disabled uplink or port-channel member can bring back a loop. A description change of a trunk port is allowed; the description alone gets none of these port checks. Unsaved changes of someone else (`show running-config diffs` not empty) and a leftover `netops-` session are refused. Enrollment (`admin enroll --device D --probe Ethernet10`) sets the description of the probe interface to `netops-enroll-<hex>` and lets the commit timer return it.

## Arista EOS VLANs, ports, routing, services and operational actions

Since 1.0.12 Admin changes the EOS tables below through the path of the previous section: the same write account (privilege 15) and check account, the empty configuration session `netops-<12 hex>` with `commit timer` as the safeguard, the change line by line in `configure terminal` under the pending timer, the readback, the confirmation and `write memory`. OSPF, prefix lists, route maps and the BGP neighbor are written inside the timer session itself. `admin undo` (MCP `admin_undo_preview`) returns a confirmed change as a new safeguarded operation. All profiles list cEOSLab 4.36.1F as their tested version; another EOS release is not refused, the plan carries `firmware_support` with status `untested` (see [MCP tools](#mcp-tools)). Every live result below was measured on cEOSLab 4.36.1F in the GNS3 lab (one switch, and a pair of switches for MLAG, ACL and the clears). The lab has no EOS switch with PoE and no physical EOS hardware.

**`endpoint_impact`.** Several checks refuse a change of an object in use unless the request names the object again in `endpoint_impact` (MCP argument of `admin_preview` and `admin_apply`, the same value in both), after the person accepted that clients, phones or access points behind it lose traffic. The value must equal the key of the request. Without it the request is refused with `endpoint_impact_required`, or with the code of the finding (`port_lldp_neighbor`, `port_learned_mac`). On EOS it is needed for a disruptive port change (admin state, speed, MTU, PoE, VLAN membership) of a port with an LLDP neighbor or learned MAC addresses, for a mode change or a membership change of a port that is or becomes a trunk, even on an idle port, for a membership change of a port that is not in static access mode (`port_uplink` otherwise), for an ACL attachment on a connected port or on any SVI, for every DHCP pool request (the pool prefix), for a relay on an SVI that already has DHCP or relay or whose subnet overlaps a DHCP pool, and for every relay while the global `dhcp relay` block names a server, for a change of an existing BGP neighbor, NTP, syslog or DNS entry (and for a new NTP or DNS server in a VRF that already has one), and for every step of a batch on an active port or SVI.

**Approved preview.** Apply of a DHCP, OSPF, prefix list, route map, BGP neighbor, service or save request, of a clear, of a port bounce or PoE cycle and of a batch needs `expected_plan_sha256` (CLI `--expect-plan-sha256`) from the approved preview (static routes and the other L3 tables do not need it); without it the request is refused (`plan_changed`, for a save `eos_save_preview_required`, for a clear `clear_preview_required`) before any write.

**Port and VLAN protections.** The checks of the previous section apply to the tables `interface` and `vlan-membership` and to the bounce and PoE cycle: management interfaces, interfaces other than `EthernetN`, port-channel members (`port_lag_member`), routed ports and a trunk for an admin state change (`port_uplink`) are refused; a description change alone gets none of the checks of a disruptive change. The LAG, STP, ACL and L3 tables have their own target checks (below). A VLAN that a change needs must exist (`vlan_missing`; a VLAN created by an earlier step of the same batch counts). A VLAN with a routed `VlanN` interface or with learned MAC addresses (`port_learned_mac`) is not deleted. A new speed must be listed in `show interfaces N hardware` and a new MTU must not exceed the Ethernet MTU of the port (`port_capability_unsupported`). On a switchport `mtu` is the IP MTU (measured: `show interfaces` keeps the Ethernet MTU 9214). A PoE change reads `show poe interface N` with the write account; a switch without PoE answers that the command is not supported, and the request is refused with `poe_not_capable`. Port-channel, MLAG and STP changes also refuse protected or management interfaces and an unreadable state (`eos_l2_readback_unreadable`, `eos_l2_read_timeout`), a channel or MLAG object other configuration still depends on (`eos_l2_dependency`), a member port that is connected (`port_lag_active`), a change of the MLAG peer settings while the domain is active or negotiating and a change that touches the peer link or its VLAN (`port_uplink`), and a VLAN priority while the switch runs MSTP (`eos_stp_mode`).

**Routing and first-hop redundancy.** Static routes, SVIs and routed ports refuse a target on the management path, a protected interface or VLAN, port-channel members and uplinks, and a VLAN that does not exist. OSPF, prefix lists, route maps and BGP refuse an interface or route on the path of the Admin SSH session (the switch reads the client address and the route to it), a protected or management VLAN, a configuration outside the profile (`eos_routing_unsupported`) and the change or removal of a prefix list or route map that a policy still uses (`eos_routing_policy_in_use`); unreadable state is `eos_routing_readback_unreadable` or `eos_routing_read_timeout`. OSPF covers OSPFv2 in the default VRF only; OSPFv3 is outside the profiles. The BGP profile refuses a neighbor that is not directly connected, a remote AS equal to the local one and a switch without `ip routing`.

**ACL.** The check account must be able to log in; the readback of the list compares the targeted `show ip access-lists NAME | json` (or `ipv6`) of the write account, because the JSON read needs privilege 15. EOS sorts the rules by sequence and shows well-known ports by name (`443` as `https`); Admin compares in that form. Refused: a change or delete of a list that is referenced outside a supported attachment or in another letter case (`eos_acl_in_use`), an attachment of a list that does not exist (`eos_acl_undefined`), the management interface or VLAN, an LLDP neighbor, a connected port without a single learned endpoint (`port_uplink`), rules outside the profile (`eos_acl_unsupported`), and unreadable answers (`eos_acl_readback_unreadable`, `eos_acl_read_timeout`).

**DHCP.** A pool is one IPv4 `dhcp server` subnet with one range, bound to one SVI of the default VRF (`dhcp server ipv4` on that SVI). A pool that overlaps another pool, a relay on the same SVI, a second VRF that already uses the DHCP server (`eos_dhcp_conflict`) and a protected or management SVI are refused; `dhcp_invalid_target`, `eos_dhcp_unsupported`, `eos_dhcp_readback_unreadable` and `eos_dhcp_read_timeout` cover the rest. Admin sees only the DHCP state of the switch: a separate DHCP server in the same VLAN is not detected. Every pool request needs `endpoint_impact` naming the pool prefix; a relay needs it when the SVI already has DHCP or relay, its subnet overlaps a pool, or the global `dhcp relay` block names a server.

**NTP, syslog, DNS.** NTP servers share one VRF on EOS; the `source` is set per server (`ntp source` does not exist on 4.36.1F) and its interface must exist in that VRF. `domain-name` is written as `dns domain`; a configuration that still uses the old `ip domain-name` is refused for a domain change (`eos_service_unsupported`). Unreadable state: `eos_service_readback_unreadable`, `eos_service_read_timeout`.

### Save of the running configuration

A save (`table` and `key` `startup-config`, `op` `save`, `changes` `{}`, plus the common arguments shown in the examples above) copies the running configuration to the startup configuration (`copy running-config startup-config`). It saves every unsaved change, also one made by someone else, and **cannot be undone** (`undo_not_applicable`). Preview shows the unified diff of `show running-config diffs` with secrets masked; `plan_sha256` binds the running configuration and the full diff before masking. Apply needs that hash (`eos_save_preview_required`), reads both again, checks that no configuration session is open, sends exactly one copy and then requires an empty diff. The check account must be permitted to run `show running-config diffs`: its view must equal the view of the write account (`eos_save_diff_mismatch`); a check account without that right is refused with `eos_save_check_denied` before any write. An unreadable diff is `eos_save_diff_unreadable` or `eos_save_read_timeout`. Live on cEOSLab 4.36.1F only the clean and the non-empty preview and the refusal of a privilege-1 check account (`eos_save_check_denied`) were measured; a successful save is covered by automated tests only. The comparison and the copy are separate device operations: a change of someone else in that interval can be saved before the final readback detects the mismatch; Admin then reports `unknown` and has no save undo. The reason is `foreign change during save` when the diff after the copy is empty but the running configuration differs from the approved one, and `save outcome unverified` when the diff is not empty or the final read fails.

### Port bounce and PoE cycle

The operator commands `admin port-bounce` and `admin poe-cycle` (with the instance stopped; they need `--config /var/lib/netops/admin/config.json`, like the ExtremeXOS PoE cycle) and the MCP tables `port-bounce` and `inline-power` (`op` `update`, `changes` `{"admin-state": "disabled"}`, key `EthernetN`) run one journaled operation behind the commit timer: `shutdown` (or `poe disabled`), the check of the off state, a pause of 5 s, `no shutdown` (or `no poe disabled`), the check against the configuration before and of the on state, the confirmation and `write memory`. Apply needs `expected_plan_sha256` (CLI `--expect-plan-sha256`); `--endpoint-impact` names the port when it has an LLDP neighbor or learned MACs.

~~~sh
docker compose stop
docker compose run --rm netops admin port-bounce --config /var/lib/netops/admin/config.json --device eos-a --port Ethernet12 --reason "..." --user-request "..." --request-id eos-bounce-e12-0001 --preview
docker compose run --rm netops admin port-bounce --config /var/lib/netops/admin/config.json --device eos-a --port Ethernet12 --reason "..." --user-request "..." --request-id eos-bounce-e12-0001 --expect-plan-sha256 PLAN_SHA256
docker compose up -d --wait
~~~

Only a static access port that does not carry a management VLAN is cycled (`port_uplink`, `port_management_vlan`); a connected port with an LLDP neighbor and learned MACs that is the only connected port is refused as the possible management path (`port_management_interface`). A bounce can take 109 s and a PoE cycle 169 s; with `confirm_margin_seconds` on top they must fit `safeguard_seconds`, otherwise the request is refused with `safeguard_margin_insufficient` and `reason_details` names `required_safeguard_seconds` (with the default margin of 45 s: at least 155 s for a bounce, 215 s for a PoE cycle). The check account reads the Status column of `show interfaces N status`: a link that was connected and is not connected again within 30 s leaves the configuration as before, and the result is `confirmed` with the reason `link not connected after the bounce`. A PoE cycle needs PoE enabled (`poe_disabled`) and a powered device (`poe_device_not_powered`); a powered device that is not powered again within 60 s ends `reverted`. Neither operation has an undo; it **cannot be undone** (`undo_not_applicable`). Measured live: the bounce of a lab port (preview, `confirmed` in 68 s, the check account saw `disabled`, then `connected`) and the refusal of a trunk; the PoE cycle and the permanent `poe` attribute only as the refusal `poe_not_capable` on cEOS. The PoE path is covered by automated tests with the output layout of the Arista EOS manual only.

### Targeted clear

`op` `clear` removes one operational entry; it changes no configuration and **cannot be undone** (`undo_not_applicable`). Apply needs the hash of the approved preview (`clear_preview_required` otherwise). The tables and the commands Admin sends (syntax of cEOSLab 4.36.1F):

| Table | Key and `changes` | Command |
|---|---|---|
| `port-counters` | `EthernetN`, `{}` | `clear counters EthernetN` |
| `mac-address-table` | one unicast MAC; `vlan` when the address is learned in several VLANs | `clear mac address-table dynamic vlan V address H.H.H` (the VLAN of the learned entry; EOS 4.36.1F has no `clear mac address-table dynamic address` without `vlan`) |
| `ip-arp` | one IPv4 address; optional `vrf` | `clear arp [vrf V] ADDRESS` |
| `ipv6-neighbor` | one IPv6 address; optional `vrf`, optional `interface` | `clear ipv6 neighbors [vrf V] INTERFACE ADDRESS` (the interface of the learned entry; EOS 4.36.1F has no form with the address alone, and without the address the command clears the whole table of the interface) |
| `bgp-refresh` | one IPv4 neighbor of the default VRF; `direction` `in` or `out` | `clear ip bgp ADDRESS soft in` or `soft out` (soft refresh, the session stays up) |

A command that would clear a whole table, `vrf` `all` and the VRF `management` are never sent (`clear_invalid_target`, `clear_protected_target`). The check account reads the target before and after (`show interfaces N`, and in JSON `show mac address-table address`, `show ip arp vrf`, `show ipv6 neighbors vrf`, `show ip bgp neighbors`). Refused before the clear: no learned dynamic entry (`clear_no_entry`, also when BGP does not run), several entries (`clear_ambiguous_entry`), and as `clear_protected_target` a protected interface or VLAN, an ARP or ND entry that is not on a VLAN interface, a management VLAN, and for counters and MAC addresses a trunk, a port with an LLDP neighbor, a port-channel or its member (so the counters of an uplink are not cleared); an unreadable read is `clear_readback_unreadable`. The result is `confirmed` only with proof: a new `Last clearing of ... counters` time; the MAC entry gone or learned again with a newer move time, while the entries of the address in other VLANs stay; the ARP or ND entry gone or younger than an untouched entry would be; for BGP the session still Established without a new transition and a higher route-refresh count (`in`), or for `out` a higher begin-of-refresh count or a higher UPDATE count with a transition to `SoftResetOut`. The running configuration must be unchanged. Without that proof the result is `unknown` and the device is blocked. Measured live on cEOSLab 4.36.1F: confirmed clears on two switches, with a third switch as the BGP peer, nine positive checks covering every table (each read a second port, entry or neighbor as unchanged) and 15 refusals.

### Related changes as one batch

A batch (`table` and `key` `batch`, `op` `update`, plus the common arguments shown in the examples above) takes as `changes` a list of 2–32 steps, each `{"table", "op", "key", "changes"}` with optional `endpoint_impact`; it is planned as one preview with one `plan_sha256` and one undo. Apply needs that hash. The steps run in order under the one commit timer; each step is checked again, written only while the own timer is pending with at least 15 s left, and read back by both accounts. When a step fails, the steps already written are returned in reverse order; when that return cannot be verified, the timer returns the configuration. The response lists each step and its result. The same object twice and the tables `ospf-process`, `ospf-network`, `ospf-interface`, `ip-prefix-list`, `route-map` and `bgp-neighbor` are refused in a batch. In a batch `endpoint_impact` is required for every step on an active port or SVI, also for a description alone (a single change needs it only for disruptive changes). Measured live on three cEOSLab 4.36.1F switches (VLAN, access membership and description; a failing second step returned the first).

### Encrypted backup

`admin backup-eos --host H --login L --ssh-host-key SHA256:... --directory DIR` (optional `--port`, `--keep`, default 7) without `--confirm` validates the target and the destination and returns a preview with `plan_sha256` without contacting the device. Repeated with `--confirm PLAN_SHA256`, it reads `NETOPS_BACKUP_KEY` and `NETOPS_BACKUP_PASSWORD` from the environment, reads the running configuration with one command of an account with privilege 15 and stores an encrypted backup in the private directory (outside a Git worktree), keeping `--keep` backups per target. `admin backup-unseal --platform eos --input FILE --output FILE` authenticates a backup and writes a private restore file. Admin does not restore an EOS backup. An empty or incomplete configuration is refused. Measured live: one backup and its readback on cEOSLab 4.36.1F.

Live on cEOSLab 4.36.1F: VLAN create, rename and delete, trunk, native, phone VLAN, 802.1X and MAB, a 240-character description with diacritics; speed and MTU; port-channel, member modes and STP port settings; MLAG IDs on a pair (inactive on empty channels); static routes (IPv4, IPv6, VRF), SVIs, routed ports, VRF routing, VRRP and VARP; OSPF process, network, passive interface and cost; prefix lists and route maps; IPv4 and IPv6 ACLs on an Ethernet ingress; DHCP pools and relays; one NTP server, syslog host and DNS server; each with apply, readback by the check account and undo, and the listed refusals. Since 1.0.12 another release is not refused because it is untested (preview, apply and status carry `firmware_support` with status `untested`, [MCP tools](#mcp-tools)); the configured `firmware` must still match the device (see **Device entry**):

| Platform | Image (lab node) | `firmware` | Tables |
|---|---|---|---|
| `ios` | IOSv `VIOS-ADVENTERPRISEK9-M` (router) | `15.9(3)M12` | `interface` |
| `ios` | IOSvL2 `vios_l2-ADVENTERPRISEK9-M`, experimental image (switch) | `15.2(20200924:215240)` | `interface`, `vlan-membership` |
| `iosxe` | IOL XE `X86_64BI_LINUX-ADVENTERPRISEK9-M` (router) | `17.18.2` | `interface` |

|---|---|---|---|

The key is the full interface name, for example `GigabitEthernet0/2` or `Ethernet0/1`. Example: `{"table": "interface", "op": "update", "key": "GigabitEthernet0/2", "changes": {"description": "netops-test"}}`. The access VLAN is set only on the switch images (the router images have no `switchport`; on the IOS XE router it is refused with `port_routed`, on IOSv the profile has no measured version for it).

**Device entry.** `platform` `ios` or `iosxe`, `firmware` (required: the running configuration names only the release train, `version 15.9` or `version 17.18`; Admin compares the stated firmware with the software version parsed from the live `show version` before any write and refuses another release, or IOS XE configured as `ios` and the reverse), `accounts` (the `username` lines of the running configuration) and the `legacy_ssh` profile the device needs (measured: `rsa-sha1-dh14` for IOSv and IOSvL2, `rsa-sha1` for IOL XE and IOL-L2 XE, whose host keys are RSA). `audit_policy` is not supported, because the Auditor holds no IOS rules (the audit gate reports 0 rules).

**Prerequisite on the device.** The configuration archive: `archive` / ` path flash:netops-archive` (IOL XE: ` path unix:netops-archive`) / ` maximum 14`. Without it `show archive` names no archive maximum and Admin refuses with `archive_not_configured`. The archive files `netops-archive-<timestamp>-N` rotate at the maximum; Admin never deletes them.

**Accounts and roles.** The write account must log in with privilege 15 (`username <write> privilege 15 secret ...`); Admin reads the running configuration with one SSH exec command and never sends `enable` or an enable secret (`write_account_privilege` otherwise). An SSH exec command of IOS has exit status 0 even when IOS refuses it (`Line has invalid autocommand "..."`) and takes one line only, so Admin treats that answer as a refusal and never uses exec for configuration. The check account (privilege 1) reads `show interfaces description` and `show interfaces N switchport`; on IOS privilege 1 it cannot read `show running-config`, `show archive` or `show logging` and is refused `configure terminal`, `configure confirm` and `write memory` (measured). The measured lab grants privilege 1 the command `show` (`privilege exec level 1 show`). `admin doctor` refuses a check account with privilege 15.

**Safeguard and return.** Before the change Admin sends `configure terminal revert timer N` and `end` in an interactive session; N is `safeguard_seconds` rounded up to whole minutes, at least 2 (2–15; the device has no finer granularity, see the minimum below). IOS saves the running configuration to a new archive file at once and starts an absolute timer when the configuration mode ends. The timer is Admin's own only with proof from its own session: the answer to its own request names the new archive (`Rollback Confirmed Change: Backing up current running config to <archive>`, not `%Rollback Confirmed Change is already activated on a config`), that archive is the new most recent one of `show archive`, and `show archive config rollback timer` then shows `Timer type: absolute timer`, `Timer value: N min` and `User:` the write account. Admin records the archive name, `Time configured` and the minutes as the identity of its safeguard (IOS gives the timer no name; `safeguard.name` `netops-<12 hex>` only names the operation in the journal and the audit log, and `safeguard.fire_at` reads `device revert timer`). A pending timer is its own only when the installation was proven this way and the timer still has the recorded time configured, minutes and user; the same account and a similar time are never enough.

**Refused or unverified installation.** When the device refuses the own request (`already activated`: another session, also of the same account, started a timer after the prechecks), the operation ends `rejected` (`rollback_timer_pending`, reason `safeguard refused by the device`) and nothing was changed. When the own session reported the archive but the timer could not be verified, the operation ends `unknown` (`safeguard not verified`) and the device is blocked. In neither case does Admin send `configure confirm`, `configure revert now` or `write memory`: a timer that is not proven its own is left to its owner or to its expiry, which returns only the empty change of the own request. `admin recover` does not confirm it either.

**Protection during the whole change.** Admin never reads the device clock (the measured IOSv clock was almost three hours behind UTC and drifted by 1.7 %; IOL XE shows CET while its log is in UTC). The time left on the own timer is counted on the monotonic clock of Admin from the moment before the timer was requested, shortened by 2 % for the drift of the device clock, so Admin's count never ends after the device's. Right before the change is written Admin reads `show archive config rollback timer` again: the own timer must still be pending and at least 40 s plus `confirm_margin_seconds` must be left (20 s for the write session and 20 s for the readback, see below). Otherwise nothing is written (step `change_not_written`) and the own timer, if still pending, is returned with `configure revert now` (else Admin waits until no own timer is pending); with the state before proven the result is `reverted` with reason `no time left to write`. During the write session every configuration line is sent only while at least 10 s are left; a line that is not sent ends the write as `change failed`. Before `configure confirm` at least `confirm_margin_seconds` must be left on the same count (`no time left to confirm` otherwise).

**Minimum timer of 2 minutes.** Measured maxima on the four lab images: `configure terminal revert timer` 5.8 s, interactive login 1.6 s (2.9 s with the IOSv banner), an SSH exec read 1.1 s, `show running-config` 6.1 s, a configuration line 1.0 s, `configure confirm` 0.2 s, `configure revert now` 11.0 s. Until the change is written Admin spends about 13 s (installation and three reads). A write session of at most five lines takes about 8 s (budget 20 s); the snapshot, the check account and the final snapshot take about 13 s (budget 20 s); then `confirm_margin_seconds` (15–45 s) must be left. One minute (58.8 s after the drift allowance) is shorter than even 13 + 20 + 20 + 15 = 68 s; two minutes (117.6 s) leave room for the default margin of 45 s (98 s). A device that answers far slower than measured makes Admin stop before the write or before a line, never write without the timer.

**Confirmation and return.** The change runs line by line through `configure terminal` (IOS accepts it while the timer is pending). Confirmation is `configure confirm`, sent only for the own timer; `write memory` runs only when no revert timer is pending, because during a pending timer it saves the unconfirmed state without a warning. When the write or the readback of a normal operation fails (a refused or unsent line, a postcheck or check-account failure or mismatch, too little time to confirm, a final check that differs, an unproven confirmation), Admin returns at once with `configure revert now` from its own session, only while its own timer is pending; the answer must name the own archive (`Rollback Confirmed Change: rolling to:<archive>`) and the timer must be gone afterwards (steps `revert_now_start`, `revert_now_done`). A fresh snapshot equal to the state before then gives `reverted` and `write memory`; another state gives `revert-failed`. Only when `configure revert now` cannot be sent or proven (step `revert_now_unverified`) Admin waits for the expiry. The enrollment self-test is left unconfirmed on purpose and returned by the expiry. `configure revert now` and the expiry replace the **whole** running configuration with the archive: a change of someone else made in the timer window is returned too. IOS XE returns at once, IOS within about 7 seconds after the expiry, during which `show archive config rollback timer` still shows the timer.

**Waiting and recover.** Waiting for the expiry and `admin recover` of an interrupted operation decide by the state of the timer, never by the clock of the device: Admin reads `show archive config rollback timer` every 10 s (a failed read counts as still pending) until the own timer is no longer pending (`%No Rollback Confirmed Change pending` or a timer without the recorded identity), limited to 980 s on the monotonic clock of Admin (the longest timer of 15 minutes plus grace and slack; then `unknown`). `admin recover` leaves an interrupted operation to the expiry and does not send `configure revert now`. Admin accepts the return only when the timer is no longer pending and a fresh snapshot equals the state before; the log lines `%ARCHIVE_DIFF-5-ROLLBK_CNFMD_CHG_ROLLBACK_START: Start rolling to: <archive>` and `..._CONFIRM` are read as additional evidence only (state `fired`/`disarmed`), because IOL keeps a log buffer of 4096 bytes that a few SSH logins overwrite. Behaviour of a pending timer across a reload was not measured.

**The timer belongs to the device.** Any privilege-15 session can confirm, extend (`configure revert timer N`) or start the return (`configure revert now`) of a pending timer, and a second `configure terminal revert timer` is refused with `%Rollback Confirmed Change is already activated on a config`. Admin therefore refuses any pending timer before the write (`rollback_timer_pending`; an own timer of an earlier operation is reported as a leftover safeguard) and sends `configure confirm` and `configure revert now` only for the timer whose installation its own session proved (see above), and only after `show archive config rollback timer` in the same interactive session, right before the command, still shows that timer (else the command is not sent). The check and the command are still not atomic: the timer is global and carries no owner, so another privilege-15 session that confirms the own timer, or starts a new one right after it expired, within that fraction of a second is not detected; nobody else should use `configure` on the device while an operation of Admin runs.

Admin refuses, before any write:

| Code | Refused |
|---|---|
| `archive_not_configured` | the configuration archive is not configured (`show archive`) |
| `rollback_timer_pending` | a pending revert timer of anyone (`show archive config rollback timer` is not `%No Rollback Confirmed Change pending`) |
| `port_management_interface` | the interface that carries the local address of an SSH session of the device (`show tcp brief` with `show ip interface brief`), or an interface in a VRF whose name contains `mgmt` or `management` |
| `port_management_vlan` | a switch port whose access VLAN is the VLAN of that management interface (an SVI `VlanN`), and an access VLAN change into it |
| `port_unsupported_interface` | an interface that is not a physical Ethernet port (subinterface, `Vlan`, `Loopback`, `Port-channel`, `Serial`) |
| `vlan_missing` | an access VLAN that `show vlan id N` does not know: IOS would create it, and a VLAN of the normal range lives in `vlan.dat`, which the rollback does not remove (measured with VLAN 333) |
| `vlan_reserved` | the access VLANs 1002–1005 |
| `port_uplink` | for a change of the admin state (down **or** up) or of the access VLAN: a trunk (`switchport mode trunk`, `switchport trunk ...`), a port that negotiates trunking, or a switch port whose `Administrative Mode` is not `static access` (since 1.0.12 a trunk change of `vlan-membership` is planned with `endpoint_impact`, see [below](#cisco-ios-and-ios-xe-switching-routing-services-and-operational-actions)) |
| `port_lag_member` | the same, a `channel-group` member |
| `port_routed` | the same, a routed switch port (`no switchport`); and an access VLAN on a router image |
| `port_ip_address` | the same, an interface that carries an IPv4 address itself or on a subinterface (on a router an addressed interface is in use) |
| `port_lldp_neighbor` | the same, a port with a neighbor in `show lldp neighbors` or `show cdp neighbors`, unless `endpoint_impact` names the port (since 1.0.12) |
| `port_learned_mac` | the same on a switch, a port with learned MAC addresses (`show mac address-table interface N`), unless `endpoint_impact` names the port (since 1.0.12) |
| `port_usage_unreadable` | an answer of these reads that is not recognised, or a management interface that cannot be identified |

An interface that is not in the running configuration is refused too (IOS answers `% Invalid input`). A description change of a trunk port is allowed; the description alone gets only the management checks. Unsaved changes of someone else (`show archive config differences nvram:startup-config system:running-config` names another difference than the permanent self-signed certificate `crypto pki certificate chain TP-self-signed-...` of IOS XE) are refused, because Admin saves the configuration after its change. Enrollment (`admin enroll --device D --probe GigabitEthernet0/2`) sets the description of the probe interface to `netops-enroll-<hex>` and lets the revert timer return it.

**End-to-end run.** On 2026-11-16 (02:08–03:12 UTC) a locally built image of the development source `3dd813e` passed the operator command line scenarios on all four lab nodes (IOSv Gi0/2, IOSvL2 Gi1/0, IOL XE Et0/2, IOL-L2 XE Et0/1; `safeguard_seconds` 120): `doctor`, enrollment self-test (`reverted` by the revert timer), description preview, apply with `--expect-plan-sha256`, undo preview and undo, `no shutdown` and `shutdown`, SIGKILL of the Admin process right after the change followed by `admin recover` (`reverted` after the timer expired), on both switches access VLAN 10 and its undo (`switchport access vlan 1`), all `confirmed` and read back by the separate privilege-1 check account; refusals without a write: VLAN 3999 (`vlan_missing`), VLAN 99 and the management port (`port_management_vlan`), the management interface of the routers (`port_management_interface`). The running configuration, the test ports, `show vlan brief`, startup = running and no pending timer were the same after the run as before. On IOL-L2 XE the management address was unreachable twice during the run for several minutes (once right after an admin up, once during reads only); Admin then recorded `unknown` (`check identity unavailable`, no confirmation) and blocked the device, the revert timer returned the port, and after the investigation and `admin unblock` the same admin up and down passed. The MCP tools were not called in this run; they use the same preview and apply path. Not measured: a pending timer across a reload, `configure terminal revert timer idle`, and other images or releases than the four above.

## Cisco IOS and IOS XE switching, routing, services and operational actions

Since 1.0.12 Admin changes the IOS and IOS XE tables below through the path of the previous section: privilege-15 write account, privilege-1 check account, `configure terminal revert timer` as the safeguard, the change line by line, readback, `configure confirm` and `write memory` (exceptions below). `admin undo` (MCP `admin_undo_preview`) returns a confirmed change. The tested versions are the four lab images of the previous section; each table lists the images it was measured on. Another release is not refused because it is untested: the plan carries `firmware_support` with status `untested` ([MCP tools](#mcp-tools)). The configured `firmware` must still equal the software version parsed from `show version`, and a device with unsaved changes of someone else is still refused (except for the IOS XE service changes and the save below).

**`endpoint_impact`.** A change of an object in use needs `endpoint_impact` naming the key of the request (MCP argument of `admin_preview` and `admin_apply`, the same value in both), after the person accepted that clients, phones or access points lose traffic. On IOS and IOS XE it is needed for an admin state or VLAN membership change of a port with an LLDP or CDP neighbor or with learned MAC addresses (otherwise `port_lldp_neighbor`, `port_learned_mac`), for every change of the port mode and every membership change of a port that is or becomes a trunk, also on an unused port (`endpoint_impact_required` otherwise), for a bounce of a connected port, for a bounce or PoE operation of an uplink or a port that is not static access (`port_uplink` otherwise), on IOS XE for a bounce or PoE change of an active port, for an existing subinterface whose parent is up/up, for an ACL change that reaches an interface that is up, for a change of an active DHCP pool or relay, for removing the last NTP, syslog or DNS target, and for every batch step on an active port. Management and port-channel protection cannot be waived.

**Approved preview.** Apply of a bounce, PoE cycle, PoE mode, ACL, DHCP, service (NTP, syslog, DNS) or save request, of a clear and of a batch needs `expected_plan_sha256` from the approved preview; otherwise it is refused (`plan_changed`, for a save `ios_save_preview_required`, for a clear `clear_preview_required`) before any write.

**VLANs and ports.** A VLAN lives in `vlan.dat`, which the archive rollback does not return; Admin therefore returns an unverified VLAN create, rename or delete by compensation in the same run, and the preview names this return mechanism. After a loss of the Admin process or the management path run `admin recover`. VLANs 1 and 1002–1005, a VLAN of the management interface, a VLAN that a port, trunk or SVI names explicitly and a VLAN with learned MAC addresses are not deleted (a trunk with `allowed vlan all` does not count). An extended VLAN in a batch needs VTP transparent mode (`action_unsupported` otherwise). A trunk keeps its management VLAN; a new allowed, native, voice or access VLAN must exist (`vlan_missing`). An EtherChannel member must be a static access port in the VLAN of the channel: a free port in the default `dynamic auto` mode is refused with `port_uplink` (set `mode` `access` first), and a member in use is refused with `port_lag_active`. Removing the last member keeps the existing port-channel; only the undo of the operation that created it removes it.

**Routing and L3 interfaces.** A new SVI (classic IOS only) needs its VLAN; a route, SVI, loopback or subinterface on the management path, an overlapping address and an SVI whose VLAN has learned MAC addresses (`port_learned_mac`) are refused. `vrf` and `encapsulation` are set only on create. The delete of an SVI is refused when its values would not be valid for a create, so its undo can restore it.

**ACL.** Rules are compared as the device stores them. IOS 15.9 renumbers IPv4 ACL rules to 10, 20, 30 when the revert timer returns the configuration (measured); the preview says so when the list uses other numbers, such a return is reported as a difference and is not saved, while `admin undo` restores the numbers exactly. A list that is still referenced is not deleted (`ios_acl_in_use`), an attachment needs an existing list (`ios_acl_undefined`), the VTY `access-class` must keep the open SSH sessions permitted, and rules outside the profile are refused (`ios_acl_unsupported`); unreadable answers are `ios_acl_readback_unreadable` and `ios_acl_read_timeout`. A change of the list contents and of its attachment by someone else between the checks and the write is not detected.

**DHCP.** Pools, reservations, exclusions and relay addresses are separate objects. A relay or pool on the management interface, a protected interface and an active pool or relay without `endpoint_impact` are refused; unreadable answers are `ios_dhcp_readback_unreadable` and `ios_dhcp_read_timeout`.

**NTP, syslog, DNS.** Removing the last NTP server, syslog host or name server needs `endpoint_impact`; a source interface must exist and must not be the management interface or protected. On IOS XE these changes, and a batch that contains them, change only the running configuration: the operation ends with the step `running_configuration_only`, unsaved changes of someone else do not refuse it, and the save below stores it. On IOS they are saved like every other change. Unreadable answers: `ios_service_read_unreadable`, `ios_service_read_timeout`.

### Save of the running configuration

A save (`table` and `key` `startup-config`, `op` `save`, `changes` `{}`, plus the common arguments shown in the examples above) saves the running configuration with `write memory`, also every unsaved change of someone else, and **cannot be undone** (`undo_not_applicable`). The preview shows a diff that Admin builds from `show startup-config` and the running configuration, with secrets masked (EEM applets are shown as opaque, because they can hold any command and secret); its `plan_sha256` binds both configurations. Apply needs that hash (`ios_save_preview_required`), compares both snapshots again and verifies the saved state. Unreadable answers: `ios_save_diff_unreadable`, `ios_save_read_timeout`. The comparison and `write memory` are separate device operations: a change of someone else in that interval can be saved before the final readback detects the mismatch; Admin then reports `unknown` and has no save undo. Measured live: preview, refusal of a stale approval and a confirmed save on IOSv 15.9(3)M12 and IOL-L2 XE 17.18.2; preview on IOL XE 17.18.2.

### Port bounce, PoE mode and PoE cycle

The operator commands `admin port-bounce` and `admin poe-cycle` (with `--config /var/lib/netops/admin/config.json`, as on EOS) and the MCP tables `port-bounce` and `poe-cycle` (`op` `update`, `changes` `{"admin-state": "disabled"}`, key the full interface name) run one journaled operation behind the revert timer: `shutdown` (or `power inline never`), the check of the off state, a pause of 5 s, `no shutdown` (or the earlier `power inline` line of the port), the check against the configuration before and of the on state, then `configure confirm`. Nothing is saved, because the operation ends on the configuration before it. Apply needs `expected_plan_sha256`; `--endpoint-impact` names an occupied or active port. A bounce can take 133 s and a PoE cycle 153 s; with `confirm_margin_seconds` they must fit the revert timer (whole minutes, counted 2 % short), otherwise `safeguard_margin_insufficient` with `required_safeguard_seconds` (with the default margin of 45 s: 240 for both). Refused: a disabled port for a bounce (`port_disabled`), without `endpoint_impact` an uplink or a port that is not static access (`port_uplink`; on IOS XE an active one is refused first with `endpoint_impact_required`), and always, whatever the consent, a port carrying a management VLAN (`port_management_vlan`; IOS XE also counts the configured `protected` `vlan` and `management_vlans` IDs), a port without PoE (`poe_not_capable`), PoE disabled (`poe_disabled`) and no powered device for a cycle (`poe_device_not_powered`). A link that does not come back leaves the configuration as before; the bounce ends `confirmed` on IOS and `reverted` on IOS XE, with the link before and after in the result; a PoE cycle without restored power ends `reverted`. Neither operation has an undo; it **cannot be undone** (`undo_not_applicable`).

The table `inline-power` sets the PoE mode permanently and has an undo. Measured live: bounces on IOSvL2 (three confirmed) and IOL-L2 XE (one confirmed) with the refusals above. The lab has no PoE switch: `inline-power` and the PoE cycle were run live only as the refusal `poe_not_capable`, the output layout of `show power inline` comes from the Cisco Catalyst documentation, and no firmware is listed as tested for them (`firmware_support` is always `untested`). The `max-milliwatts` range 4000–90000 is a conservative check before the write, not a measured limit.

### Targeted clear

`op` `clear` removes one operational entry, changes no configuration and **cannot be undone** (`undo_not_applicable`). Apply needs the approved preview hash.

| `fdb` | one dynamic MAC address, or `port:IF`; `{}` | `clear mac address-table dynamic address MAC` or `... interface IF` | IOSvL2 15.2(20200924:215240) |

An active IOS XE clear (counters of a port that is up, a learned dynamic entry) requires `endpoint_impact` set to the request key, also `port:IF`; the Catalyst 9800 deauthentication always requires it, and the IOL limits below still apply. The check account reads the entry before and after; the result is `confirmed` only with proof of the effect (a new `Last clearing` time, not one that only aged; the entry gone or learned again), otherwise `unknown`, which blocks the device; on IOS XE a complete readback that does not prove the effect, with the configuration unchanged, ends `unknown` (`clear readback mismatch`) without a block, because there is nothing to restore. Measured live: counters on IOSv and IOL XE, ARP on IOL XE, a MAC address on IOSvL2 and on IOL-L2 XE (by address; IOL-L2 XE is not listed as a tested version of `fdb`). The Catalyst 9800 deauthentication and the IPv6 neighbor clear are covered by automated tests only.

### Related changes as one batch

`table` `batch` (see [MCP tools](#mcp-tools)) runs 2–32 steps of the tables above in order under one revert timer, with one preview, one `plan_sha256` and one undo; each step is checked and read back, and when a later step fails the earlier steps are returned and the result names each step. `endpoint_impact` is needed for every step on an active port. Unreadable or slow reads of a batch are `ios_batch_read_unreadable` and `ios_batch_read_timeout`. Measured live on IOSv and IOSvL2, and on IOL XE and IOL-L2 XE 17.18.2: a confirmed batch with readback and undo, and a failing second step that returned the first.

### Exec banner after a return (classic IOS)

On classic IOS, when Admin has proved the return of its own archive (a return at once or by the timer, during an operation or the enrollment self-test) and the configuration that had a `banner exec` before has none afterwards, the result is `unknown` with the reason code `exec_banner_lost` and the device is blocked; enrollment then issues no valid enrollment. Admin writes nothing more in that case: restore the banner by hand, run `admin unblock`, then repeat the operation or the enrollment (the reason text says the same). In the lab the native timer, `configure revert now` and `configure replace` kept the banner; the loss was reproduced only by removing the banner by hand after the return (measured on IOSvL2).

### Encrypted backup

`admin backup-ios` (IOS) and `admin backup-xe` (IOS XE) take `--host`, `--login` (an account allowed to read the running configuration), `--ssh-sha256 SHA256:...`, `--directory` (private, outside a Git worktree), optional `--port`, `--legacy-ssh` (`rsa-sha1`, `rsa-sha1-dh14`) and `--keep` (default 7). Without `--confirm` they print a preview with `plan_sha256`; with `--confirm PLAN_SHA256` they read `NETOPS_BACKUP_KEY` and `NETOPS_BACKUP_PASSWORD` from the environment and store an encrypted backup. `admin backup-ios-status` and `admin backup-xe-status` (`--host`, `--directory`) authenticate and report the last backup; `admin backup-unseal --platform ios|xe --input FILE --output FILE` writes a private restore file. Admin does not restore an IOS backup.

## Cisco NX-OS interface description, admin state and access VLAN

Platform `nxos`, measured only on a Nexus 9000v (N9K-C9300v, virtual) with NX-OS 9.3(12) in the GNS3 lab (2026-11-16); the profiles list `9.3(12)` as the tested version. Since 1.0.12 another NX-OS release is not refused: preview, apply and status carry `firmware_support` with status `untested` ([MCP tools](#mcp-tools)). A physical Nexus 9000 is not verified. Tables (`update` only, CLI and MCP `admin_preview`/`admin_apply`/`admin_undo_preview`, operator `admin undo`):

| Table | Attribute | Device lines | Read-back of the check account |
|---|---|---|---|
| `interface` | `description` (text, at most 64 characters) | `description TEXT` / `no description` | `show interface description` (the row of the port) |
| `interface` | `admin-state` (`enabled`/`disabled`) | `no shutdown` / `shutdown` | `show interface N status` (`disabled`) |
| `vlan-membership` | `access-vlan` (1–4094, default 1) | `switchport access vlan N` / `no switchport access vlan` | `show interface N switchport` (`Access Mode VLAN`) |

The key is the full interface name, for example `Ethernet1/48`. Example: `{"table": "interface", "op": "update", "key": "Ethernet1/48", "changes": {"description": "netops-test"}}`.

**Accounts and roles.** The write account (measured with role `network-admin`) reads the running configuration with one SSH exec command (`show running-config`; NX-OS prints no closing `end`, so a snapshot without its header or without `interface mgmt0`, `line vty` and `boot nxos` is refused as cut off) and runs the change, the safeguard and the save in interactive sessions without `enable`. The check account (measured with role `network-operator`) is really read-only on NX-OS: it may not read `show running-config` or `show scheduler`, so Admin reads its state only from `show interface N status`, `show interface description` and `show interface N switchport`. The device entry needs `accounts` (the `username` lines of the running configuration) and the SSH profile `legacy_ssh: "rsa-sha1"` when the switch offers only an RSA host key with SHA-1 signatures (the lab node does). `audit_policy` is not supported, because the Auditor holds no NX-OS rules (the audit gate reports 0 rules). A least-privilege custom role for the write account was not measured.

**Precondition `feature scheduler`.** NX-OS 9.3(12) has neither a commit timer nor an EEM timer event; the only timed return that runs without the Admin session is a one-time job of `feature scheduler`. The administrator of the switch enables it once (`configure terminal`, `feature scheduler`, `end`, `copy running-config startup-config`) and leaves it enabled. Admin never enables or disables it: every `no feature scheduler` creates a system checkpoint and evicts the oldest of the five system checkpoints (measured). Without it every change is refused with `scheduler_feature_disabled`, and `admin doctor` reports it in `device prechecks`.

**Safeguard and return.** Before the change Admin installs, in one interactive session: `checkpoint netops-<12 hex>`, the scheduler job `netops-<id>` with `rollback running-config checkpoint netops-<id> atomic`, the scheduler schedule `netops-<id>` with `job name netops-<id>` and `time start +M`, then `no checkpoint netops-<id>` and `checkpoint netops-<id>` again (the checkpoint now holds the job and the schedule, so the rollback never has to delete the running job; a job created after its checkpoint makes the rollback fail and blocks the scheduler until `no feature scheduler`, measured), and `copy running-config bootflash:netops-<id>-pred.cfg`. Admin verifies the job, the schedule, the checkpoint (`show diff rollback-patch running-config checkpoint netops-<id>` must be empty), the file and the lead of the schedule before it writes the change. The schedule has a granularity of one minute: `time start +M` starts at the next whole minute plus M−1 minutes, so the real delay is between M−1 and M minutes; Admin takes M = ceil(`safeguard_seconds` / 60) + 1. The change runs line by line through `configure terminal` (`configure session` offers neither `description`, `shutdown` nor `switchport` under an interface on 9.3(12)). Confirmation deletes the schedule, then the job, then the checkpoint and the file; `copy running-config startup-config` runs only after it, and `show running-config diff` must then be empty. The operation records `safeguard.fire_at` as `device scheduler job`; `safeguard.device_time` is the time of the job as the switch shows it (information only).

**Own objects only.** The name `netops-<id>` must be free of every checkpoint, job, schedule and file right before the installation; otherwise nothing is installed (a foreign object of that name is left alone, the operation ends `unknown` with `safeguard not verified` and the device is blocked). An object is Admin's own only when the line that creates it was answered without an error in Admin's own session: Admin notes that line by line in `safeguard.own` (and the phase of the installation in `safeguard.phase`) and the journal saves each note at once. Every removal (confirmation, cleanup after the run, an unverified or interrupted installation, `admin recover`) touches only own objects; the name derived from the change ID is never enough. Limit: NX-OS enters an existing scheduler job of the same name without a message (not measured otherwise), so a job created by someone else in the seconds between the name check and the own `scheduler job name` line cannot be told apart.

**Protection during the whole change.** Admin never reads the device clock. The job runs at least M−1 minutes after the switch took `time start +M`; Admin counts that on its monotonic clock from the moment before the installation started, 2 % shorter for the drift of the device clock, and never longer than the lead the switch itself shows (the time of the schedule less the creation time of the checkpoint, both in `show` output of the switch; a lead that does not fit `time start +M` is `safeguard not verified`). Right before the change is written the own schedule must still be pending (`show scheduler schedule name netops-<id>`) and at least 60 s plus `confirm_margin_seconds` must be left (20 s for the write session, 40 s for the readback); otherwise nothing is written (step `change_not_written`, reason `no time left to write`) and the safeguard is removed. Every configuration line is sent only while at least 15 s are left (a line that is not sent ends the write as `change failed`), and `confirm_margin_seconds` must be left before the confirmation. With the default margin of 45 s this needs `safeguard_seconds` of at least 180 (M = 4, 176 s of protection; the installation takes about 10–20 s of it).

**Return.** When the job runs, NX-OS rolls the **whole** running configuration back to the checkpoint about 3 s after the minute (measured 6–9 s): a change of someone else made in the window is returned too. A change that Admin itself finds unverified (failed write, failed read-back of the check account, prediction mismatch, too little time to confirm) is returned at once, without waiting for the minute of the job: `configure replace bootflash:netops-<id>-pred.cfg` (measured `Success`, the access VLAN included; steps `revert_now_start`, `revert_now_done`), sent only while at least 60 s of the protection are left and never while a rollback runs. Only when the snapshot then shows the object in its state before is the safeguard removed; otherwise (and with less than 60 s left, step `revert_now_skipped`) Admin waits for the job. Waiting and `admin recover` decide by the state of the scheduler, never by the device clock: Admin reads `show scheduler schedule name netops-<id>` every 10 s until the job has run to its end (the schedule shows an execution, `show rollback log verify` shows no running rollback, and `show scheduler logfile` or `show rollback log exec` names the job) or the schedule is gone, limited to 980 s on its monotonic clock (then `unknown`). It accepts the return only with a snapshot equal to the state before; when the object is still changed after the run (a line that arrived late, or a change of someone else after the return; step `expiry_not_returned`), the same `configure replace` of the own file is tried before the result is given up. Then it removes the job, the schedule (NX-OS refuses that for a while after the run; repeated every 20 s for up to 5 minutes while the switch answers `schedule in progress`), the checkpoint and the file. The enrollment self-test and `admin recover` of an interrupted change always wait for the job. `configure replace ... commit-timeout` is not used: its automatic return left a changed access VLAN in place and always reported `Failed` (measured). Behaviour of a pending job across a reload of the switch was not measured.

**Interrupted or unverified installation.** As long as the change was not sent (no step `change_start`), the safeguard is removed at once, by the operation itself (installation not verified) or by `admin recover` (step `installation_interrupted` with the phase): a pending own schedule first, so its job can no longer start, then the own job, checkpoint and file; the result is `reverted` with reason `safeguard not verified` or `interrupted`. This also covers the dangerous phase between `time start +M` and the second `checkpoint netops-<id>`, in which the job is armed while its checkpoint does not hold it yet: run in time, recover deletes the schedule and the job before the job starts. What Admin cannot do, and reports as `unknown` (reason `interrupted safeguard installation; manual cleanup needed`, the device blocked, the objects left in the step `safeguard_removal_unverified` and the manual procedure in `safeguard.manual_cleanup` of the operation, shown by `admin status`): remove an object whose creating line was sent but whose answer never reached Admin (it is not proven own), and recover a job of that phase that has already run, because it stays `schedule in progress` and only `no feature scheduler` removes it. Admin never sends `no feature scheduler`; that is a decision of the switch administrator (it creates a system checkpoint and evicts the oldest one), after which `feature scheduler` must be enabled again. The manual procedure, after checking that the objects are not someone else's: `configure terminal` / `no scheduler schedule name netops-<id>` / `no scheduler job name netops-<id>` / `end` / `no checkpoint netops-<id>` / `delete bootflash:netops-<id>-pred.cfg no-prompt` / `copy running-config startup-config`, then `admin unblock`.

Admin refuses, before any write:

| Code | Refused |
|---|---|
| `port_management_interface` | `mgmt0` (NX-OS would accept `description` and `shutdown` there) |
| `port_unsupported_interface` | an interface that is not `EthernetX/Y` (loopback, VLAN interface, port-channel) |
| `vlan_missing` | an access VLAN that is not in the running configuration or not in `show vlan id N` (NX-OS would accept it silently and leave the port `inactive`) |
| `vlan_reserved` | an access VLAN 3968–4094 (reserved on NX-OS) |
| `port_uplink` | for a change of the admin state (down **or** up) or of the access VLAN: a trunk (`switchport mode trunk`, `switchport trunk ...` or a port listed in `show interface trunk`) or a port whose operational mode is not `access` (since 1.0.12 a mode or trunk change of an idle port is planned with `endpoint_impact`, see [below](#cisco-nx-os-vlans-ports-port-channels-vpc-routing-acl-and-services)) |
| `port_lag_member` | the same, a `channel-group` member |
| `port_routed` | the same, a routed port (`no switchport`, or `Switchport: Disabled`) |
| `port_learned_mac` | an admin state change (down or up) or an access VLAN change of a port with learned MAC addresses (`show mac address-table interface N`), unless `endpoint_impact` names the port (since 1.0.12) |
| `port_lldp_neighbor` | the same, a port with an LLDP neighbor (only an addition: the measured uplink had no LLDP neighbor, so the trunk check carries the uplink protection) |
| `scheduler_feature_disabled` | `feature scheduler` is not enabled |
| `foreign_config_session` | an open configuration session (`show configuration session summary`) |
| `rollback_in_progress` | a rollback or configure replace that has started and not ended (`show rollback log verify`) |

An interface that is not in the running configuration is refused too. Unsaved changes (`show running-config diff` not empty; the return would roll them back) and any leftover `netops-` checkpoint, scheduler job or schedule or `bootflash:netops-*` file are refused. Admin up gets the same checks as admin down; a description change of a trunk port is allowed. Enrollment (`admin enroll --device D --probe Ethernet1/48`) sets the description of the probe interface to `netops-enroll-<hex>` and lets the scheduler job return it, so it takes up to M minutes plus the cleanup after the run (up to about 3 more minutes).

## Cisco NX-OS VLANs, ports, port-channels, vPC, routing, ACL and services

Since 1.0.12 Admin changes the NX-OS tables below through the path of the previous section: the `feature scheduler` safeguard (checkpoint, one-time job and schedule `netops-<id>`), the change line by line in `configure terminal`, the return at once with `configure replace` of the own file, readback by the `network-operator` check account, confirmation and `copy running-config startup-config`. `admin undo` (MCP `admin_undo_preview`) returns a confirmed change. All profiles list NX-OS 9.3(12) as their tested version; another release is not refused, the plan carries `firmware_support` with status `untested` ([MCP tools](#mcp-tools)). Every live result below was measured on Nexus 9000v (N9K-C9300v) with NX-OS 9.3(12) in the GNS3 lab: one switch, and a vPC pair for the vPC, ACL, service and clear reads. A physical Nexus is not verified.

**`endpoint_impact`.** The request names its key again in `endpoint_impact` (MCP argument of `admin_preview` and `admin_apply`) after the person accepted that the endpoint behind the object loses traffic. On NX-OS it is needed for an admin state or VLAN membership change of a port with learned MAC addresses (otherwise `port_learned_mac`), for a change of the mode or of the trunk VLANs (otherwise `endpoint_impact_required`), for an ACL attachment on an interface in use, and for removing the last NTP, syslog or DNS target. An LLDP neighbor (`port_lldp_neighbor`), a CDP neighbor (`port_cdp_neighbor`), a connected trunk (`port_uplink`), a connected port without exactly one identifiable dynamic MAC (`port_uplink`), a protected VLAN (`port_protected`), a port-channel member and the management port cannot be waived.

**Approved preview.** Apply of every NX-OS request that supplies `endpoint_impact`, and of an ACL, service (NTP, syslog, DNS), port-channel, vPC, bounce, save, clear or batch request, needs `expected_plan_sha256`; otherwise it is refused (`plan_changed`, for a save `nxos_save_preview_required`, for a clear `clear_preview_required`) before any write.

**VLANs, ports and channels.** A VLAN that a change needs must exist (`vlan_missing`; a VLAN created by an earlier step of the same batch counts), VLANs 3968–4094 are reserved (`vlan_reserved`) and a VLAN that the configuration still references is not deleted (`vlan_in_use`). A port whose VLAN has an addressed SVI is changed only when Admin reaches the switch out of band (management through `mgmt0`). A member change needs `feature lacp` and a vPC change `feature vpc` (`nxos_link_feature_disabled`). Port-channel and vPC changes touch only idle channels and members without a neighbor or MAC entry (`port_lag_active`) and refuse a configuration outside the profile (`nxos_channel_dependency`, `nxos_vpc_dependency`): a vPC domain only with an unused keepalive scope (a local source and a remote unicast destination in the named VRF, no other domain and no vPC channels), a vPC port only on a healthy topology, a peer link only with the keepalive `peer-alive`. Removing the last member keeps the empty port-channel; the undo of its create removes it.

**Routing, DHCP relay and ACL.** Routes, SVIs, loopbacks and routed ports refuse an address that overlaps a connected subnet and a change of a connected routed port. A relay address needs the DHCP feature and the relay agent (`dhcp_feature_disabled`). ACL changes refuse an egress attachment on a Layer 2 port, an attached list for delete (`nxos_acl_in_use`), an attachment of a missing list (`nxos_acl_undefined`), entries outside the profile (`nxos_acl_unsupported`), interfaces with an LLDP or CDP neighbor and the management path; unreadable answers are `nxos_acl_readback_unreadable` and `nxos_acl_read_timeout`.

**NTP, syslog, DNS.** The transport VRF is checked in the configuration; the check account confirms an NTP server with `show ntp peers`. A VRF that does not exist, an unconfigured source interface, a syslog source without an IP address, and a change whose undo would reorder the resolvers or overwrite options outside the profile are refused (`nxos_service_unsupported`); a protected source interface is `port_protected`. Unreadable answers: `nxos_service_readback_unreadable`, `nxos_service_read_timeout`.

### Save of the running configuration

A save (`table` and `key` `startup-config`, `op` `save`, `changes` `{}`, plus the common arguments shown in the examples above) runs `copy running-config startup-config`, saves every unsaved change, also one of someone else, and **cannot be undone** (`undo_not_applicable`). The preview shows `show running-config diff` with known common statements in clear text and every sensitive or unrecognised line as `[redacted]`; `plan_sha256` binds the whole raw diff. Apply needs that hash (`nxos_save_preview_required`), refuses an open configuration session (`foreign_config_session`) or a running rollback (`rollback_in_progress`), and verifies an empty diff afterwards. Unreadable answers: `nxos_save_diff_unreadable`, `nxos_save_read_timeout`. The comparison and the copy are separate device operations: a change of someone else in that interval can be saved before the final readback detects the mismatch; Admin then reports `unknown` and has no save undo. The reason is `running and startup still differ after save` when the diff after the copy is not empty, `foreign change during save` when it is empty but the running configuration differs from the approved one, and `save outcome unverified` when a final read fails. Measured live: a confirmed save, the refusal of a stale plan and the restore of the startup configuration on one switch; the preview on the pair.

### Port bounce

The operator command `admin port-bounce` (with `--config /var/lib/netops/admin/config.json`) and the MCP table `port-bounce` (`op` `update`, `changes` `{"admin-state": "disabled"}`, key `EthernetX/Y`) send `shutdown`, hold the port down for 5 s and send `no shutdown`, behind the scheduler safeguard; apply needs the approved preview hash. The port must be enabled (`port_disabled`) and pass the port checks above; a connected port must have exactly one identifiable dynamic MAC address (`port_uplink` otherwise) and needs `endpoint_impact`. When a link that was up does not come up again, the operation is not confirmed: the safeguard settles it with the reason `link not up after the bounce`. A bounce has no undo; it **cannot be undone** (`undo_not_applicable`). Measured live on a free port (admin state up, down, up, read independently) and as the refusal of a protected port.

### Targeted clear

`op` `clear` removes one operational entry, changes no configuration and **cannot be undone** (`undo_not_applicable`). Apply needs the approved preview hash.

| Table | Key and `changes` | Command |
|---|---|---|
| `port-counters` | `EthernetX/Y`, `{}` | `clear counters interface EthernetX/Y` |
| `mac-address-table` | one dynamic MAC, or `interface:EthernetX/Y`; `{}` | `clear mac address-table dynamic address MAC` or `... dynamic interface EthernetX/Y` |
| `ip-arp` | one IPv4 address; `vrf` (default `default`) | `clear ip arp ADDRESS vrf V` |
| `ipv6-neighbor` | one IPv6 address; `vrf`, optional `interface` (Ethernet or Vlan) | `clear ipv6 neighbor ADDRESS [IF] vrf V` |

`vrf` `all` and `management` and every command that clears a whole table are never sent. The check account reads `show interface`, `show mac address-table address|interface`, `show ip arp` and `show ipv6 neighbor` before and after; `confirmed` needs proof of the effect (a new `Last clearing` time; the entry gone or learned again while the other entries stay), otherwise the result is `unknown`. Refused: uplinks, port-channels, the peer link, protected interfaces including SVIs (`clear_protected_target`), invalid or ambiguous targets (`clear_invalid_target`, `clear_ambiguous_entry`), no entry (`clear_no_entry`) and unreadable reads (`clear_readback_unreadable`). Measured live: counters, a MAC address, the MACs of a port and an ARP entry, each with the other entries kept, and the refusals. The lab has IPv6 disabled: the IPv6 neighbor clear was run live only as `clear_no_entry`, and its row layout comes from the Cisco Nexus 9000 documentation.

### Related changes as one batch

`table` `batch` (see [MCP tools](#mcp-tools)) runs 2–32 reversible steps (no bounce) in order behind one scheduler safeguard with one preview, one `plan_sha256` and one undo; each step is checked against the predicted state of the earlier steps and read back, a failing step returns the earlier ones, and the result names each step. Measured live on one switch and the pair: preview, confirmed batch, failing second step with its return, and undo.

### Encrypted backup

`admin backup-nxos --host H --login L --ssh-host-key SHA256:... --directory DIR` (an account that sees the full configuration; optional `--port`, `--keep`, default 7) prints a preview with `plan_sha256`; with `--confirm PLAN_SHA256` it reads `NETOPS_BACKUP_KEY` and `NETOPS_BACKUP_PASSWORD` and stores an encrypted backup in a private directory outside a Git worktree. `--status` checks the local retention with `NETOPS_BACKUP_KEY`. `admin backup-unseal --platform nxos --input FILE --output FILE` writes a private restore file. Admin does not restore an NX-OS backup.

## Juniper Junos interface description, admin state and access VLAN

Platform `junos`, measured only on vJunos-switch 26.2R1.7 (ELS, model ex9214; GNS3 lab, 2026-11-16); the profiles list `26.2R1.7` as the tested version. Since 1.0.12 another Junos release is not refused: preview, apply and status carry `firmware_support` with status `untested` ([MCP tools](#mcp-tools)). Physical EX switches, non-ELS Junos (`port-mode`) and routers (MX, SRX) are not measured; the SRX tables of 1.0.12 are covered by automated tests only ([below](#juniper-junos-vlans-ports-routing-filters-srx-dhcp-services-and-backup)). Tables (`update` only, CLI and MCP `admin_preview`/`admin_apply`/`admin_undo_preview`, operator `admin undo`):

| Table | Attribute | Device lines | Read-back of the check account |
|---|---|---|---|
| `interface` | `description` (since 1.0.12 up to 240 characters of UTF-8 text, see [below](#juniper-junos-vlans-ports-routing-filters-srx-dhcp-services-and-backup)) | `set interfaces IF description "TEXT"` / `delete interfaces IF description` | `show interfaces descriptions` |
| `interface` | `admin-state` (`enabled`/`disabled`) | `delete interfaces IF disable` / `set interfaces IF disable` | `show interfaces IF terse` (Admin `down`) |
| `vlan-membership` | `access-vlan` (a VLAN **name**, default `default`; since 1.0.12 also mode, trunk, native and voice VLAN, see [below](#juniper-junos-vlans-ports-routing-filters-srx-dhcp-services-and-backup)) | `delete interfaces IF unit 0 family ethernet-switching vlan members` and `set ... vlan members NAME` | `show ethernet-switching interface IF` (the one `untagged` VLAN) |

The key is the interface name, for example `ge-0/0/2`. Example: `{"table": "vlan-membership", "op": "update", "key": "ge-0/0/2", "changes": {"access-vlan": "D10"}}`. Admin always quotes the description (a text with a space is a syntax error without quotes, measured). `set ... vlan members` adds a member instead of replacing it (measured), so the old member is deleted first. An access VLAN change needs an access port (`unit 0 family ethernet-switching interface-mode access`); a port without it is refused with `port_not_access`, Admin does not create the switching family. A VLAN number in place of a name is not accepted (Junos accepts a numeric member that does not exist at commit time, measured).

**Device entry.** `safeguard_seconds` must be `600` and `confirm_margin_seconds` at least `240` (see the timing below); the entry needs `accounts` (the `set system login user` names of the configuration). `audit_policy` is not supported, because the Auditor holds no Junos rules (the audit gate reports 0 rules).

**Accounts and roles.** The write account needs the login-class permissions `configure`, `view` and `view-configuration` (`show cli authorization`; otherwise `write_account_privilege`); it reads the configuration with one SSH exec command (`show configuration | display set`; for a class with the permission `secret` the answer holds the password hashes, and Admin keeps only hashes of the snapshot and the parsed object, never its text) and changes it only in an interactive session (an SSH exec batch answers with status 0 even for an error and continues after it, measured). The measured lab uses the existing class `super-user`. A narrower class was **not created and not verified**; the measurement proposes, as a recommendation for the administrator:

```
set system login class netops-admin permissions [ configure interface interface-control view view-configuration ]
set system login class netops-admin allow-configuration-regexps "interfaces (ge|xe|et|mge)-[0-9/]+ (description .*|disable|unit 0 family ethernet-switching vlan members .*)"
set system login user <write account> class netops-admin
```

Not verified: whether such a regular expression also covers the `delete` lines and the empty `commit confirmed` of the safeguard. The check account of the built-in class `read-only` reads only operational state (`show interfaces IF terse`, `show interfaces descriptions`, `show ethernet-switching interface IF`); it cannot read the configuration or the log and has no configuration mode (measured).

**Safeguard and return.** Junos has no session timer of its own besides `commit confirmed`, and every commit (also `commit check`) confirms a pending one (measured; `commit check` leaves no trace in the commit history or the log). Admin therefore works only in `configure exclusive` (`configure private` refuses `commit confirmed`, measured) and in this order:

Every interactive session starts with `set cli screen-width 1024`, a setting of that CLI session only (not of the configuration): the terminal of Admin has no width, Junos then uses 80 columns and redraws the prompt in the middle of the echo of a longer line, which a prompt reader takes for the end of the line (measured in the lab; the first enrollment attempt ended `reverted` with `change failed` because of it, before any change was committed).

1. Before any change it enters the shared configuration mode once and leaves it again: another user in configuration mode (`Users currently editing the configuration`) or an uncommitted change of someone else (`The configuration has been changed but not committed`) is refused with `foreign_config_session`; so is a pending `commit confirmed` of someone else (a `rollback pending` row whose comment does not start with `netops-` in `show system commit`).
2. Safeguard: `configure exclusive`, an empty candidate (`show | compare` must be empty), `commit confirmed 10 comment "netops-<12 hex>"`; Admin verifies its `rollback pending` row. The answer of that `show | compare` carries the banner `# commit confirmed will be rolled back in N minutes` whenever any commit confirmed is pending (measured): when it is there, a timer of someone else appeared after the prechecks and the safeguard commit is not sent (it would confirm that timer); the operation ends `rejected` (`foreign_config_session`, reason `safeguard refused by the device`) and nothing was changed.
3. Change: `configure exclusive`, an empty candidate, the `set`/`delete` lines, `show | compare` and `commit confirmed 10 comment "netops-change"`. This commit restarts the timer from itself (measured: the expiry then returns the change too); Admin reads the new commit row, which must be the write account's pending commit right above its own safeguard row, and records it as the new head of its timer. A commit that does not answer `commit complete` is a failed change (a refused VLAN name answers `error: configuration check-out failed`).
4. Readback of the write account (snapshot) and of the check account, then confirmation `commit comment "netops-<12 hex>-ok"`, sent only while the empty candidate still shows the banner of the pending timer (a plain commit during the automatic rollback makes it fail, measured); the `rollback pending` row must be gone and the newest row must be the own `-ok`. A Junos commit is the saved configuration, so nothing else is saved.


**Own timer only.** Junos gives a pending `commit confirmed` no owner, and every commit of any session confirms it, also of the same account. The timer is Admin's own only with proof from its own session: its install session answered `commit complete`, and right after it the newest row (record 0) of `show system commit` is its own comment `netops-<12 hex>` of the write account with `rollback pending`. Admin records that row (time, user, comment) as the safeguard and the later own `commit confirmed` of the change as the head. The confirmation, the immediate return and `admin recover` send a commit only while the newest row is exactly the recorded head with `rollback pending` above the recorded safeguard row; the same account, the prefix `netops-` or the comment alone are never enough, and a timer that is not proven Admin's own is left to its owner or to its expiry. An installation that is not proven (for example the commit history cannot be read right after the safeguard commit) ends `unknown` (`safeguard not verified`, the device is blocked); `admin recover` then sends nothing while a rollback is pending and clears the record once none is. Not covered: another privileged session that commits within the seconds between Admin's last read and its commit line (Junos has no identity of the owner of a timer); Admin then sees a foreign row in place of its head and does not confirm.

**Protection during the whole change.** Admin never reads the device clock for the safeguard. The timer counts whole minutes from its commit row (written at the end of the commit) and expired 0-60 s after them, so Admin counts 600 s less 2 % for the drift of the device clock on its monotonic clock from the moment before the safeguard was requested. Right before the change session Admin reads `show system commit` again: its own timer must still be pending, and at least 240 s (the change session with its commit; 126-235 s in the end-to-end lab run, commits 15-150 s) and at least 90 s (the readback) plus `confirm_margin_seconds` plus 15 s must be left (the change commit restarts the timer with the same uncertainty of its start, so the time left after the commit is about the time left before it). Otherwise nothing is written (step `change_not_written`, reason `no time left to write`). Every line of the change session up to its commit is sent only with at least 180 s left (a line that is not sent is a failed change). After the change commit the end of the timer moves by the device time between the safeguard row and the change row (both on the device clock, shortened for the drift), never past the answer of the session; before the confirmation `confirm_margin_seconds` must be left on that count (`no time left to confirm` otherwise).

**Immediate return.** When the write or the readback of a normal operation fails (a refused or unsent line, a postcheck or check-account failure or mismatch, too little time to write or to confirm, an unproven confirmation), Admin returns at once while its own timer is pending with at least 240 s left: when no own change commit exists yet, the configuration is that of the empty safeguard and the return is its confirmation; otherwise the inverse `set`/`delete` lines of the plan are committed with the plain `commit comment "netops-<12 hex>-revert"` (steps `revert_now_start`, `revert_now_done`), which ends the own timer and keeps the inverse; the `rollback pending` row must be gone and the newest row must be that own `-revert` row right above the head. The inverse is not committed with `commit confirmed`: the expiry of a timer returns the configuration before the newest `commit confirmed`, so an inverse under a timer that is then not confirmed (the process interrupted) brings the change back (measured live). A fresh snapshot then decides: equal to the state before is `reverted`; the planned object in its state before with other differences is `reverted` with the differences; an existing blocking reason is kept, otherwise the reason is `foreign change`; otherwise `revert-failed` with the differences; an unreadable snapshot is `unknown` (step `revert_unverified`). When the return cannot be sent or proven (step `revert_now_unverified`), the timer returns the change; a `-revert` row that went through unseen ends that wait as well, and the snapshot decides. When the read of `show system commit` right after the own change commit failed, or the connection failed when leaving the configuration mode after that commit, Admin reads it again before the return (limited on its monotonic clock to the time above the 240 s) and takes as its head only the single row right above its own safeguard row with the change comment `netops-change` of this operation, of the write account and with `rollback pending` (step `change_head_adopted`); anything else (a foreign commit, more rows, none) is not taken. When the own change commit cannot be proven after a failed read even then, the timer returns the change (up to 10 minutes). The inverse lines were chosen over `rollback N`: the inverse is measured (undo in the measurement and in the end-to-end lab run) and touches only the planned object, while the index N moves with every commit (`rollback 1` is wrong after a confirmation, measured) and a rollback during a pending timer was not measured. The enrollment self-test is left unconfirmed on purpose and returned by the expiry.

**Manual check after `unknown` or `revert-failed`.** Read `show system commit | no-more` and `show configuration interfaces <port> | display set` with the write account. A `rollback pending` row means a timer is still running: wait until it is gone (its expiry returns the state before the newest `commit confirmed`). Then compare the port with the `before` side of the operation record; this comparison always decides. Only an own plain `-revert` row (its row has no `commit confirmed`; written by 1.0.11) shows that the inverse is committed for good. The `-revert` of 1.0.10 was itself a `commit confirmed`: after its expiry its row stays without `rollback pending` although the change has come back (measured live). A `root via other` row above the own rows means the timer returned the configuration to the state before the newest `commit confirmed`. When the port still differs, set it back by hand in `configure exclusive` with the inverse lines of the plan and a plain `commit comment "..."`, and check it again; never commit while someone else's `rollback pending` row is shown, because the commit would confirm it.

When the change is not confirmed, Junos rolls the configuration back by itself: the measured timer counts whole minutes from the commit row (written at the end of the commit) and expired 0-60 s after them (7-9 s in the Admin runs), and the rollback is committed 55-273 s later as `root via other` (with the broadcast `Commit was not confirmed; automatic rollback complete`). **Waiting and `admin recover` decide by `show system commit` only, never by the clock of the device**: Admin reads it every 10 s (a failed read counts as still pending) and accepts the end of the timer only with that `root via other` row or the own plain `-revert` row of an immediate return above its own safeguard row and no `rollback pending` row; a fresh snapshot then decides (equal to the state before is `reverted`); the wait is limited to 1820 s on the monotonic clock of Admin (the longest timer plus 20 s grace plus 900 s for the minute granularity, the rollback commit and a change commit that restarted the timer: `admin recover` of a change interrupted right after its commit saw the proof 530 s after the expiry of the safeguard commit). `admin recover` sends no commit for an interrupted operation: while its own timer is pending, it waits for that end (the expiry, or an own plain `-revert` row that went through unseen); when the own `-ok`, the own plain `-revert` or a `root via other` row has already ended the timer, it does not wait and a fresh snapshot decides; a timer that ended without the own `-ok`, the own `-revert` or a `root via other` row (an automatic rollback still running, or a commit of someone else that confirmed it) is not taken as removed. The rollback returns the **whole** configuration to the state before the newest `commit confirmed` (measured live: after the empty safeguard, a change and an inverse each committed with `commit confirmed` and no confirmation, the expiry brought the change back; without the inverse commit it returned the state before the change). Admin's only `commit confirmed` after the empty safeguard is the change, so the rollback returns the state before the change commit, and a commit of someone else in the timer window is returned too; a `commit confirmed` of someone else above the change would make the expiry keep the change, which Admin then reports as `revert-failed`. A confirmation that started before the expiry won the measured race (`automatic rollback failed as other commit triggered during rollback`); Admin starts it only with `confirm_margin_seconds` left before the earliest expiry. A pending timer across a reload was not measured.

**Timing.** A commit took 15-150 s on the measured lab switch (load 15-26). With `commit confirmed 10`, after the change commit Admin needs about 60-90 s for the snapshot, the check account and the final snapshot, and keeps at least 240 s for the confirmation commit, so it ends before the earliest expiry; on a slower device the change is not written or the confirmation is skipped (`no time left to write`, `no time left to confirm`) and the change is returned at once or by the timer. SSH exec reads of a Junos device may take up to 180 s (more than 60 s was seen under load in the lab). A change that is returned by the timer took 16-21 minutes in total on the lab (enrollment included), a confirmed change 6-12 minutes. The device measured an SSH outage of about one hour (banner exchange timeout); Admin then reports the operation as `unknown` or refuses before any change, and `admin recover` settles it later.

A leftover `netops-` commit confirmed is refused until it expires. Enrollment (`admin enroll --device D --probe ge-0/0/2`) sets the description of the probe interface to `netops-enroll-<hex>` and lets the timer return it.

## Juniper Junos VLANs, ports, routing, filters, SRX, DHCP, services and backup

Since 1.0.12 Admin changes the Junos tables below through the path of the previous section: `configure exclusive`, the empty safeguard `commit confirmed 10`, the change committed with `commit confirmed 10`, readback by the `read-only` check account and the confirmation `commit comment "netops-<id>-ok"`; an unverified change is returned at once with the inverse lines and a plain commit, otherwise by the timer. A commit is the saved configuration, so nothing else is saved. `admin undo` (MCP `admin_undo_preview`) returns a confirmed change. All profiles list vJunos-switch 26.2R1.7 as their tested version; another release is not refused, the plan carries `firmware_support` with status `untested` ([MCP tools](#mcp-tools)). Every live result below was measured on vJunos-switch 26.2R1.7 (ELS, model ex9214) in the GNS3 lab. The lab has no SRX, no PoE controller, no BGP licence and no physical EX switch.

**`endpoint_impact`.** The request names its key again in `endpoint_impact` (MCP argument of `admin_preview` and `admin_apply`) after the person accepted the interruption behind the object. On Junos it is needed for a port change with learned MAC addresses (`port_learned_mac`), for a VLAN membership change of a port with an LLDP neighbor, for an aggregate that carries LACP traffic, for the RSTP bridge priority (key `rstp`, `junos_rstp_impact_required`), for a default static route, for a policy change on an existing BGP group or neighbor, for a filter that is bound to an interface and for a binding change, for a DHCP pool, reservation or relay that serves clients, for a change of an existing SRX object, and for every batch step on an active target. Admin state, speed and MTU changes of a port with an LLDP neighbor, trunks, the only port with a link up, and a port carrying a VLAN whose IRB carries the management path cannot be waived.

**Approved preview.** Apply of a LAG, RSTP, firewall filter, SRX or DHCP request, of a request with `endpoint_impact` on a default route or a BGP table, of a clear, a bounce, a PoE cycle and a batch needs `expected_plan_sha256`; otherwise it is refused (`plan_changed`, for a clear `clear_preview_required`) before any write.

**VLANs and membership.** A trunk names its tagged VLANs and removes `access-vlan` and `voice-vlan` (`null`) in the same request; back to access removes `trunk-vlans` and `native-vlan`. A VLAN that the configuration still references is not deleted (`vlan_in_use`), a missing VLAN is `vlan_missing`, and a name reserved by Junos is `vlan_name_reserved`. Since 1.0.12 a VLAN statement that the port inherits from an `interface-range` or an applied configuration group is edited in that source, when the source configures no other port; otherwise the change is refused with `inherited_shared`, naming the other ports. A statement configured in two sources, `apply-groups-except`, group conditions and other inheritance forms are refused.

**Ports, aggregates and RSTP.** Speed and MTU changes are checked by the check account in `show interfaces IF`; a combination outside the profile is `junos_link_configuration_unsupported`, a slow read `junos_link_read_timeout`. On vJunos the speed is not committed (virtual ports): its syntax is the measured completion list, its effect on a physical EX or QFX port comes from the Juniper documentation. A LAG member must be a free physical port (`port_lag_member`, `port_protected`, `port_management_interface`); a global `bpdu-block-on-edge` also respects ports protected as `IF.0`. For that global flag the configuration read by the write account verifies the flag and the check account verifies the operational RSTP state (Junos shows no value of the flag in operational output). The undo of a combined speed and admin-state change can fail its readback and is then returned by the safeguard.

**Routing, IRB and VRRP.** Routes and IRB addresses refuse a change on the management path or its return route (`junos_l3_management_path`; `junos_l3_management_unreadable` when it cannot be determined) and objects outside the profile (`junos_l3_scope`); unreadable reads are `junos_l3_read_unavailable` and `junos_l3_read_timeout`. VRRP is refused when the device has no operational VRRP (`junos_vrrp_unsupported`). OSPF, prefix lists, route policies and BGP refuse the management path (`junos_routing_management`), objects outside the profile (`junos_routing_scope`), and the removal of a policy or prefix list that is still used, also by a BGP group or neighbor (`junos_routing_dependency`); unreadable reads are `junos_routing_readback_unreadable` and `junos_routing_read_timeout`.

**Firewall filters.** A term change or a new order is written as `delete term` and a new term placed with `insert ... before`. A binding on `fxp`, `em`, `me`, `vme`, `lo0.0` or a protected interface is `port_protected`; a filter on the interface that carries the management session or its return route, also by changing a filter bound there, is `junos_filter_management`. Also refused: a filter still bound for delete (`junos_filter_dependency`) and terms outside the profile (`junos_filter_scope`); unreadable reads are `junos_filter_readback_unreadable` and `junos_filter_read_timeout`. Removing a binding deletes only `input` or `output`.

**SRX zones, address book, policies and NAT.** These tables follow the Juniper SRX documentation and are covered by automated tests only. A device without `security` configuration (such as an EX switch or vJunos-switch) refuses them with `junos_srx_unsupported`. Refused: the management path and its ingress zone (`junos_srx_management`), objects outside the small profile model (`junos_srx_scope`), a referenced object (`junos_srx_dependency`) and unreadable reads (`junos_srx_readback_unreadable`, `junos_srx_read_timeout`). The undo of a NAT rule keeps its position.

**DHCP.** Admin checks a relay interface that does not exist, a network with host bits and the MAC spelling itself; Junos refuses the other errors at commit. A relay on a protected IRB is not removed or moved. Refused: objects outside the profile (`junos_dhcp_scope`), a pool or server group still used (`junos_dhcp_dependency`), unreadable reads (`junos_dhcp_readback_unreadable`, `junos_dhcp_read_timeout`).

**NTP, syslog, system.** Name servers are an ordered list: from the first difference on they are deleted and set again in the wanted order. A host name outside the attribute pattern refuses the `system` table, so the undo can always return the name read from the device.

### Port bounce, PoE and PoE cycle

The operator commands `admin port-bounce` and `admin poe-cycle` (with `--config /var/lib/netops/admin/config.json`) and the MCP tables `port-bounce` and `inline-power` (`op` `update`, `changes` `{"admin-state": "disabled"}`) commit `set interfaces IF disable` (or `set poe interface IF disable`) with `commit confirmed`, check the off state, hold 5 s and return at once with the inverse and a plain `commit comment "netops-<id>-revert"`, then check the configuration before and the on state (a link within 30 s, a powered device within 60 s). Apply needs the approved preview hash; `--endpoint-impact` names an occupied port. A link that does not come back leaves the configuration as before with the reason `link not up after the bounce`; a powered device that is not powered again ends with `powered device not powered after the cycle`. Neither has an undo; it **cannot be undone** (`undo_not_applicable`). The table `poe` disables or enables PoE permanently and has an undo. vJunos has no PoE controller and answers `show poe interface` with a warning that Admin turns into `poe_not_capable` before any write; the PoE answer layout comes from the Juniper EX documentation and no firmware is listed as tested for the PoE tables. Measured live: a bounce, an MTU change with undo, and the refusals; PoE only as the refusal `poe_not_capable`.

### Targeted clear

`op` `clear` removes one operational entry, changes no configuration, needs the approved preview hash and **cannot be undone** (`undo_not_applicable`). Commands (counters, MAC and ARP measured live on vJunos-switch 26.2R1.7; IPv6 neighbor and BGP only syntax and refusals):

| Table | Key and `changes` | Command |
|---|---|---|
| `port-counters` | physical port, `{}` | `clear interfaces statistics IF` |
| `fdb` | one MAC address, `{}` | `clear ethernet-switching table MAC` (positional; the keyword `address` is read as a MAC) |
| `arp` | one IPv4 address, `{}` | `clear arp hostname ADDRESS` |
| `neighbor-discovery` | one IPv6 address, `{}` | `clear ipv6 neighbors host ADDRESS` |
| `bgp-neighbor-refresh` | one peer address, `{"mode": "soft-inbound"}` or `{"mode": "soft"}` | `clear bgp neighbor ADDRESS soft-inbound` or `soft` |

The check account reads the target before and after; `confirmed` needs proof against the state before: counters with a new `Statistics last cleared` time, the same port and link state, and each traffic counter lower than before or at most 64 packets (64 × 1522 bytes); a MAC entry gone or learned again with a newer time; an ARP or IPv6 neighbor entry absent at readback; for `soft-inbound` an established peer with the Refresh capability, a higher count of sent Refresh messages and an unchanged flap count. Outbound `soft` needs an established peer with advertised prefixes (otherwise `clear_no_entry` before the command); it is sent, but its effect cannot be verified, so it ends `unknown`. Otherwise the result is `unknown`. Refused: protected and management interfaces, also logical interfaces and IRBs (`clear_protected_target`), invalid targets (`clear_invalid_target`), a missing port (`port_missing`), no entry (`clear_no_entry`; Junos does not clear a neighbor in the reachable state), several entries (`clear_ambiguous_entry`) and unreadable reads (`clear_readback_unreadable`). Measured live: counters, a MAC entry and an ARP entry, and the refusals; the IPv6 neighbor and BGP modes have syntax and refusal evidence only, and their readbacks are adapted from the Juniper CLI Reference and covered by automated tests only.

### Related changes as one batch

`table` `batch` (see [MCP tools](#mcp-tools)) puts 2–32 reversible steps into one candidate with one `show | compare` and one `commit confirmed`, with one preview, one `plan_sha256` and one undo. Every step is checked against the state the earlier steps predict; when the commit or the readback fails, the whole batch is returned. Measured live: preview, confirmed batch, a batch returned after a refused CLI line, and undo.

### Backup and restore

`admin backup-junos --host H --login L --ssh-sha256 SHA256:... --directory DIR` (optional `--port`, `--keep`, default 7, and `--rescue`) without `--confirm` validates the target and the destination and returns a preview with `plan_sha256` without contacting the device. With `--confirm PLAN_SHA256` it reads `NETOPS_BACKUP_KEY` and `NETOPS_BACKUP_PASSWORD`, reads `show configuration | no-more` (the hierarchical text that `load override` accepts; a `super-user` account sees the secrets, a `read-only` class gets `ACCESS-DENIED` sections and is refused) and stores the configuration sealed with AES-GCM in a private directory outside a Git worktree; the reply carries only names, counts and SHA-256 digests. With `--rescue` it first seals the previous rescue configuration in its own retention series when one exists, then runs `request system configuration rescue save` and checks the line count of the new rescue configuration. `admin backup-junos-unseal --input FILE --output FILE` writes a private `.conf` file.

`admin restore-junos --host H --login L --ssh-sha256 SHA256:... --input SEALED-BACKUP` (optional `--minutes` for the `commit confirmed` timer, 2–60, default 10) needs a login that can read the complete configuration and load and commit it in `configure exclusive`. It previews the restore without a write: it compares the normalized texts and returns the numbers of added and removed lines and `plan_sha256`, which binds the target, the backup and the current configuration. With `--confirm PLAN_SHA256` the current configuration must still have the planned digest and no `commit confirmed` may be pending (`foreign_config_session`); the current configuration is sealed first as the return artifact `undo_artifact` (restorable with the same command); then `load override terminal`, `commit confirmed MINUTES comment "netops-restore-<id>"`, a readback that must equal the backup, and `commit comment "netops-restore-<id>-ok"` while the own commit is still the newest pending one. A restore identical to the current configuration is a no-op (`confirmed`, `changed: false`). While its own commit is the newest pending one, Admin returns at once when the readback differs from the backup, when the comparison itself fails or when less than 45 s of the timer are left, by loading the saved current text with a plain `commit comment "netops-restore-<id>-revert"`. When the newest commit is no longer its own pending one, Admin sends nothing more. In both cases it reads the configuration again and ends `reverted` when it equals the saved one, otherwise `revert-failed`. When a read after the commit fails or the confirmation is not proven, the result is `unknown` with `commit_label`, `pending` (the last observed timer state, `null` when it is not proven), `rollback_minutes` and `undo_artifact`: do not rely on the device timer; inspect that commit, the pending state and the artifact. A backup of another target is refused (`backup_target_mismatch`), a refused restore is `backup_restore_refused`. Measured live: a restore of a test backup and its return, an immediate return after a readback mismatch, and the refusals of a read-only account.

### Verified live and limits

## FortiADC pool member

On FortiADC, Admin supports real servers, real-server pool members and virtual-server status. These changes use MCP `admin_preview`, `admin_apply` (with `expected_plan_sha256`), `admin_undo_preview`, `admin_doctor` and `admin_status`, and the operator commands `preview`, `apply`, `undo`, `enroll`, `doctor`, `status` and `recover`. Each change is planned from a fresh snapshot, needs a valid enrollment, is read back by the separate check account and is recorded in the journal and the Admin operation log with its `request_id`. The profiles list FortiADC-KVM 7.6.7 build0676 as their tested build; since 1.0.12 another build gets the `untested` warning in `firmware_support` instead of a refusal, and an HA primary is accepted ([HA pair](#ha-pair)).

The table `load-balance pool/pool_member` uses the key `POOL:MEMBER`, the pool name and the number of the pool member entry, for example `LAB_POOL_SMTP:2`. The real server is selected at creation. An update can change `status` (`enable`, `disable` or `maintain`), `pool-member-service-port` (default 80), `pool-member-cookie` and `pool-member-weight` (default 1). The device spells the last three with underscores (`pool_member_service_port`, ...); Admin translates them. A member created without a cookie gets the cookie `rsN` from the device (N is the member number, measured on 7.6.7 build0676); Admin treats `rsN` on member N as that default, so do not send it explicitly.

- **Status** (`op: update`, `changes: {"status": "disable"}`): before any write, every virtual server that uses the pool must keep at least one enabled member whose health check is up (`diagnose server-load-balance vs_stat`, read with the write account); otherwise the request is refused with `no_healthy_member`. A virtual server that selects pools by content routing or schedule refuses the change only when it may select this pool or its pools cannot be read (since 1.0.12).
- **Add** (`op: create`, `real-server`, optional `pool-member-service-port`, and `status` `disable` or `maintain`): a new member is never created enabled; enable it with a separate update once its health check is up. Refused before any write when the member number is used, the real server is not configured, or the same real server with the same port is already a member.
- **Remove** (`op: delete`, empty `changes`): only a member with status `disable` or `maintain`, never the last member of a pool, and never a member with settings outside the profile.

The table `load-balance real-server` supports creating a static backend and changing its IPv4 address or FQDN and status. A change that takes a backend out of service or invalidates its measured health must leave a healthy alternative for each affected active virtual server. The table `load-balance virtual-server` supports status updates for virtual servers with a statically verifiable pool. Preview reports the affected virtual server in `service_outage` when the request takes it out of service. The protections also cover related objects in the backend, pool and virtual-server configuration.

Preview example (MCP `admin_preview` arguments; `admin_apply` takes the same and `expected_plan_sha256`):

```json
{"device": "adc-a", "table": "load-balance pool/pool_member", "op": "update", "key": "POOL_WEB:2",
 "changes": {"status": "disable"}, "reason": "patching web2", "user_request": "take web2 out of the pool",
 "request_id": "adc-web2-off-0001"}
```

**Return of an unverified change (platform property, not a device safeguard).** FortiADC 7.6.7 offers Admin no on-device timed return: its CLI has no `automation-stitch`, scheduler or cron (all answer `Parsing error`, read on a standalone FortiADC-KVM 7.6.7 VM). The FortiADC documentation describes alert policies of type `schedule` with a CLI script action, which might serve as one; this was not measured, because measuring it needs device writes outside the approved test pool, so Admin does not use it and does not claim it. Admin therefore returns an unverified change itself, in the same run: when the write, the readback of the write account or the readback of the check account fails, it writes the inverse (the previous status, the delete of a new member, the create of a removed member from its read settings) and verifies the snapshot against the state before. The result is `reverted` when that holds, `revert-failed` or `unknown` (the device is blocked) otherwise; preview names this as `return_mechanism`, and the journal records `compensation_*` steps and a `safeguard` with `fire_at` `none`. **If the Admin process, the host or the management path is lost after the write, nothing on the device returns the change.** Run `admin recover`: it returns an interrupted change that was not confirmed in the same way. Enrollment uses the same mechanism: `admin enroll --device adc-a --probe POOL:MEMBER:REAL_SERVER:PORT` creates an unused member number disabled (a real server and a port that are not yet a member of that pool), lets the compensation remove it and verifies the pool before and the check account; it proves the write, readback and compensation path, not an on-device timer.

**Not covered on FortiADC:** Admin runs no auditor rules there (they need the exported full configuration and its context, `auditor run --platform fortiadc`); preview reports this under `audit_unevaluated` and doctor as `cannot verify`. Admin does not read other administrator sessions (`foreign_sessions_unreadable`). The snapshot Admin plans against is composed of `show load-balance pool`, `show load-balance virtual-server`, `show load-balance real-server` and `show system admin` (with the firmware from `get system status`), and for certificate changes the certificate groups and names; a change elsewhere in the configuration is not seen by the postcheck. The write account sees exactly the configured administrators (`accounts`, or the write and the check login); any other administrator refuses the change and blocks the device, as on FortiOS.

The write login must be a FortiADC system administrator (`is-system-admin yes`), limited by a trusted host to the Admin host; a login without it is refused by the health precheck. The check login is a second, read-only login (the Helper read profile) with the trusted host of the Admin host; it reads the pool with `show load-balance pool POOL` and its identity with `get system status`. See [Accounts and least privilege](../components/netops-helper/docs/read-only-accounts.md).

**Deprecated operator commands.** `pool-member`, `pool-member-add` and `pool-member-remove` still work unchanged (same options, JSON record and exit codes: 0 confirmed or unchanged, 3 rejected, 4 rolled_back, 7 unknown), but they are deprecated: they need no enrollment, have no preview or `plan_sha256`, and write no journal or Admin operation record; they print a deprecation line on standard error. Use `preview`, `apply` and `undo` with the table above instead. The command grammar of the old commands is in the [FortiADC contract](fortiadc-f1-contract.md#admin-pool-member-add-and-pool-member-remove), the measured scope in [FortiADC bounds](verified-support.md#fortiadc-bounds).

The return of an unverified change is the [compensation in the same run](#fortiadc-pool-member), not a device timer. ### Real servers, virtual servers and pool member settings

These extend the tables of [FortiADC pool member](#fortiadc-pool-member):

- `load-balance real-server` (key the name): `create` with `type` `ip` and `ip`, or `type` `fqdn` and `fqdn`, and `status`; `update` of the address and `status`. Undo of a create deletes the real server and is refused while it is a pool member. A status or address change that takes the backend out of service needs, for every active virtual server whose pool uses it, another enabled member whose health check is up (`no_healthy_member`).
- `load-balance virtual-server` (key the name): `update` of `status` (`enable`, `disable` or `maintain`) for a virtual server with a static pool that has members. Taking a serving virtual server to `disable` or `maintain` is reported in `service_outage` and in the preview as a service outage; enabling it needs an enabled backend.
- `load-balance pool/pool_member`: an update can also change `pool-member-weight`, `pool-member-service-port` and `pool-member-cookie`; a port change of an active member needs a healthy alternative.
- A virtual server that selects pools by content routing or schedule no longer refuses every change: Admin reads the pools it may select (its stored pool from `vs_stat` and the content-routing and schedule-pool entries) and refuses only when one of them is affected or cannot be read.

Measured: maintain and disable of a virtual server with return to enable, a real-server status change while its members served two pools, a weight, port and cookie change with undo, create and removal of IPv4 and FQDN real servers, and an IPv4 address change with undo. A change of the FQDN of an existing FQDN real server is supported by the profile and the plan, but no test covers it. A content-routing or schedule virtual server was not present in the lab; that path is covered by automated tests with measured outputs. Known limit: an undo writes `status enable` and the default cookie `rsN` explicitly where the device had omitted them; this was measured as an identical configuration hash on the lab build only.

### Certificates

- **Replace the certificate of a group member.** Table `system certificate local_cert_group/group_member`, key `GROUP:MEMBER`, `op` `update`, `changes` `{"local-cert": "NAME"}`; undo restores the previous certificate. Apply requires `expected_plan_sha256` (`fortiadc_certificate_preview_required`). The device entry needs `fortiadc_https_sha256` (the SHA-256 pin of the HTTPS certificate) and, when not 443, `fortiadc_https_port` (`fortiadc_certificate_input_invalid` otherwise). Both certificates must be installed (`fortiadc_certificate_missing`). The check account reads the reference back over CLI. The built-in groups `LOCAL_CERT_GROUP` and `HTTP2_CERT_GROUP`, protected groups, certificates and members, and a group used by a client SSL profile or virtual server listed in `protected` are refused (`fortiadc_certificate_protected`). Enrollment can use `--probe certificate/GROUP:MEMBER:REPLACEMENT` with an existing test group member.
- **Import a new certificate.** Operator command `admin certificate-import --device D --name NAME --certificate FILE --key FILE` previews; repeating it with `--confirm PLAN_SHA256` uploads. The PEM certificate (chain allowed, without a private key) and the operator-owned private PEM key must match and be valid now. The upload uses HTTPS with the pinned certificate; the write and the check account log in with password credentials. A name that exists is refused (`fortiadc_certificate_exists`). The check account verifies the installed fingerprint; an unverified upload ends `unknown`, and `admin recover` verifies the fingerprint with both accounts. An import has no undo (`undo_not_applicable`); it only stages the certificate for a later replacement.

Measured: certificate inventory, two previews and imports with fingerprint readback, enrollment with a certificate probe, a replacement and its undo, and the refusal of a missing certificate. Known limit: the Helper certificate inventory reads at most about 48 kB (roughly 90 certificates); a larger listing is reported as incomplete, not truncated.

### HA pair

On a FortiADC in an HA pair Admin writes only to the primary of a synchronized pair (`get system ha-status`): a secondary is refused (`fortiadc_ha_secondary`), a primary whose secondary is not verified in sync is refused (`fortiadc_ha_not_synchronized`), an unreadable or timed-out answer is refused (`fortiadc_ha_unreadable`, `fortiadc_ha_read_timeout`), and a role change during the operation stops it (`fortiadc_ha_role_changed`). On a primary, apply requires `expected_plan_sha256` (`fortiadc_ha_preview_required`), and after the postcheck, and again after a compensation, Admin requires the pair to report sync (with retries for about 5 s) before the check account reads back; otherwise the result is `unknown` and the device is blocked. A standalone device behaves as before. Only the standalone role was read and planned live; the HA paths are covered by automated tests with HA outputs published by Fortinet (7.4.4), because no FortiADC pair was available.

### Clear sessions, persistence and WAF blocks

`op` `clear`, key the virtual server name, `expected_plan_sha256` required (`clear_preview_required`):

| Table | `changes` | Device commands |
|---|---|---|
| `slb-session` | `{}` or `{"source-ip": "IPv4"}` | `diagnose server-load-balance session filter 'vs-name VS [source-ip IP]'`, `... clear l4`, `... filter clear` |
| `slb-persistence` | `{}` or `{"source-ip": "IPv4"}` | the same with `persistence` |
| `waf-block-ip` | `{"source-ip": "IPv4"}` (required) | `execute waf block-ip release vs-name VS ip IP` |

Session and persistence clears need a Layer 4 virtual server. The diagnostic filter is shared between logins: Admin requires an idle filter, verifies the selection immediately before the clear and resets only its own selection. Refused before any write: a virtual server that does not exist or a target that is not one name and one address (`clear_invalid_target`), a protected virtual server or source address, also any source of the selected entries (`clear_protected_target`), an empty scope (`clear_no_entry`), and an unreadable or changed listing (`clear_readback_unreadable`, `clear_scope_unverified`). A released WAF block can still be listed for some seconds; Admin reads again for up to 60 s and confirms only when the address and virtual server are gone. Cleared entries and released blocks cannot be undone. Measured: one WAF release, a session and a persistence clear, each with an untouched control client, and the refusals without hash. Known limits: a block that expires by itself while Admin waits is reported as released; after a loss of the SSH session between setting and resetting the filter, `admin recover` does not reset the diagnostic filter.

## Ruckus Unleashed WLAN and DHCP relay

Platform `ruckus` (Unleashed), tested on an R610 with Ruckus Unleashed 200.15.6.212.27 (`firmware_support.tested_versions` names the exact version string); another release gets the `untested` warning. Admin logs in interactively (`Please login:`, `enable`) with the SSH host key checked against `host_key_fingerprint`. Both accounts need a password credential and the privileged CLI (`enable`); on Unleashed the check credential may be the write account. The device entry lists in `wlans` the names Admin may write; every other key is refused before the device is contacted (`wlan_not_selected`), and the names of DHCP relay entries must be listed there too. Apply requires `expected_plan_sha256` (`plan_changed`). Unleashed has no timed return: like FortiADC, Admin attempts to return an unverified change by writing the inverse in the same run when it can verify the state (`return_mechanism`), and after a loss of the Admin process `admin recover` attempts it. Admin runs no auditor rules on Unleashed. Enrollment: `admin enroll --device D --probe WLAN` creates the selected, not yet existing WLAN of that name disabled and removes it in the same run.

**Table `wlan`** (key the WLAN name, `create`, `update`, `delete`):

| Attributes | Rules |
|---|---|
| `ssid`, `description`, `vlan` (1–4094, default 1), `service` (`enabled` or `disabled`) | A new WLAN is created with `service disabled`, WPA2 and only these attributes; enable it with a separate update. An SSID that another WLAN uses is refused. Delete accepts only a disabled Standard Usage WLAN whose settings Admin can recreate, member only of `System Default` without a VLAN override (`wlan_delete_not_restorable`). |
| `authentication` (`open` or `dot1x`), `encryption` (`wpa2` or `wpa3`), `passphrase-ref`, `auth-server` | Authentication and encryption change together. `passphrase-ref` names a vault entry `WLAN_PSK_<NAME>` of kind `api-token` in the Admin vault. A personal request names `authentication` `open`, `encryption` and `passphrase-ref`, also when it only rotates the passphrase with the current encryption. The value (8–63 printable ASCII characters without a space, or 64 hexadecimal digits) is typed only by the transport and never appears in a plan, journal, audit or response (`wlan_passphrase_reference` when it cannot be resolved). An enterprise request names `dot1x`, `encryption` and `auth-server`, without `passphrase-ref`. |
| `max-clients`, `isolation-ap`, `l2acl`, `l3acl`, `rate-perssid-uplink`, `rate-perssid-downlink`, `rate-uplink`, `rate-downlink` | The per-client rates are whole Mbps and are set or removed together; a WLAN whose rates the device shows with fractions is outside the profile and refused. |

A change of a broadcasting WLAN that can affect its clients (SSID, VLAN, service, security, limits, ACLs) needs `endpoint_impact` naming the WLAN (`endpoint_impact_required`). Admin never learns an existing passphrase: a create (WPA2 by default), an undo that returns a personal mode and the recreation of a deleted WLAN type a newly generated passphrase, and the result says so; an undo to enterprise restores `auth-server`; set the real passphrase in the Unleashed web interface before enabling the WLAN. The undo of a passphrase rotation alone is refused, because the previous passphrase cannot be restored. Renaming a WLAN and a WLAN service schedule are not available (the CLI of the tested release offers no schedule).

**Table `dhcp-relay`** (key the entry name, `create`, `update`, `delete`): `first` (required), `second` (must differ) and `description`. The tested release does not save a change of an existing entry, so an update removes the entry and writes the complete new one in the same context. An entry is not changed while a WLAN has DHCP relay enabled; Admin does not bind a WLAN to a relay.

Measured on that R610 (Ruckus Unleashed 200.15.6.212.27) through the Admin engine with an independent CLI read: enrollment, create, SSID, VLAN, service, description and delete with undo; WPA3 with a vault passphrase (the device held the vault value) and undo to WPA2; enterprise authentication and back; ACLs, isolation, client and rate limits with undo to the identical block; relay entry create, update and delete with undo; the refusal of a WLAN that is not selected. Known limits: when the Admin process stops exactly between sending an inverse and recording it, recover can report the return without the note about the new passphrase; an interrupted passphrase-only rotation can stay `unknown`; a WLAN recreated by compensation gets its visible settings back with a new passphrase and ends `revert-failed`.

Example (MCP `admin_preview` arguments; `admin_apply` adds `expected_plan_sha256`):

```json
{"device": "unleashed-a", "table": "wlan", "op": "update", "key": "guest", "changes": {"vlan": 30},
 "endpoint_impact": "guest", "reason": "move guests to VLAN 30", "user_request": "Put the guest WLAN on VLAN 30.",
 "request_id": "ruckus-guest-vlan-0001"}
```

Not available in 1.0.12: AP description, WLAN groups and radio settings, client deauthentication and AP restart, the secondary LAN port of an AP, and the management network, services and backup of Unleashed. These changes are not implemented and wait for a decision on a lab device.

## MCP tools

The HTTPS MCP endpoint lists ten Admin tools. With the default configuration, `admin_undo_preview` shows what an undo would do and `admin undo` applies it through the operator CLI.

Set the top-level `config.mcp_undo` boolean to `true` to enable `admin_undo`, `admin_unblock_preview` and `admin_unblock`. It defaults to `false`, in which case those calls return `mcp_undo_disabled`. The operator commands `admin undo`, `admin recover` and `admin unblock` work independently of this setting.

| Tool | Arguments | Current behavior |
|---|---|---|
| admin_doctor | `device`, optional `local` (default `false`) | Readiness report without a change: `ready`, and `checks` whose status is `ok`, `missing`, `refused`, `skipped`, `warning` or `cannot verify` (the last two leave `ready` unchanged); `operations` maps each table of the platform to its operations for the firmware of the parsed configuration snapshot (on IOS and IOS XE the configured `firmware` once the snapshot shows its release train; a failed or differing live `show version` makes `device prechecks` `refused` but does not empty the maps), marked `(untested on FIRMWARE)` when that firmware is not a tested version of the table, and `firmware_support` gives the comparison per table; both maps are empty when doctor has no firmware value, and tables without a JSON profile, such as the operational clears, are not listed |
| admin_preview | `device`, `table`, `op`, `key`, `changes`, `reason`, `user_request`, `request_id`, optional `endpoint_impact` | The planning checks of apply without applying the change (a FortiOS `sessions` clear preview temporarily sets the diagnostic session filter and verifies its reset; apply and undo check the current state and any required approval again before acting; a ready preview of a save records its approval ticket locally): `result` is `ready`, `rejected` with `reasons`, or `known-request` with the `change_id` of an earlier operation of the same `request_id`; `firmware_support` of a profile plan (absent when the request is refused before planning); `return_mechanism` for irreversible operations and for compensating returns (FortiADC, Ruckus Unleashed, ExtremeXOS ACL policy files and the IOS and IOS XE VLAN database) |
| admin_apply | as admin_preview, optional `expected_plan_sha256` (required for the operations listed below) | One change behind the device safeguard or compensation (a clear or save is a standalone operation without a safeguard; on FortiADC and Ruckus Unleashed, which have none, and for ExtremeXOS ACL policy files and the IOS and IOS XE VLAN database, behind the compensating return in the same run, see [FortiADC pool member](#fortiadc-pool-member)); `result` is `confirmed`, `reverted`, `rejected`, `unknown` or `revert-failed`. With `expected_plan_sha256` (the `plan_sha256` of the approved `admin_preview`) a fresh plan that differs is `rejected` with `plan_changed` before any write |
| admin_undo_preview | `change_id`, `reason` | The planning checks of the undo of a confirmed operation without a device change (with `mcp_undo` a ready preview records its approval ticket locally), as admin_preview plus `undo_of` and `request_id` (`undo-CHANGE_ID`); after an undo has run it is `rejected` with `undo_already_done` |
| admin_undo | `change_id`, `reason`, `expected_plan_sha256` | With `mcp_undo` enabled, applies the approved undo after checking the latest ready preview and freshly calculated plan. |
| admin_unblock_preview | `device` | With `mcp_undo` enabled, verifies that the operation with an unknown result reached its intended state and returns the approval hash when ready. |
| admin_unblock | `device`, `reason`, `expected_unblock_sha256` | With `mcp_undo` enabled, rechecks the approved preview and clears the journal block. It does not write to the device. |
| admin_status | `change_id` or `request_id` | The stored operation record; `unknown-operation` when nothing matches, also for a call with neither argument |
| admin_schema_preview | `device`, `operations`, `reason`, `user_request`, `request_id` | Checks of a schema transaction without a change |
| admin_schema_apply | as admin_schema_preview | A schema transaction behind the device safeguard; it has no `expected_plan_sha256` |

`op` is `create`, `update`, `delete` or, for a FortiOS `firewall policy`, `move` (`changes` holds only `before` or `after` with the policy ID of the anchor); since 1.0.12 also `clear` (an irreversible operational clear limited to the documented target or scope; a port selector such as `port:IF` can clear several dynamic entries) and `save` (table and key `startup-config`, empty `changes`) on the platforms that offer them, see the sections of each platform. `endpoint_impact`, when given, must equal `key`: it records that the person accepted the interruption of the clients, phones or access points behind the object; the platform sections name the changes that need it. `key` has at most 128 characters and `table` at most 64. `changes` maps at most 16 attribute names (32 for a FortiOS `firewall policy`; a lowercase letter followed by up to 63 lowercase letters, digits or hyphens) to a string, an integer, a list of strings or `null` to remove the attribute; for `delete` it is empty. `reason` has at most 500 characters and `user_request` at most 4000. `request_id` has 8–64 letters, digits, `.`, `_`, `:` or `-`. A schema transaction has 1–32 `operations`, each an object with exactly `path`, `scope`, `owners`, `op` and `changes`; it requires a FortiOS device with a configured operator `schema` binding and is otherwise rejected with `schema transactions require a configured operator binding`. A binding names its schema library and rollback calibration by absolute file paths inside the container, and NetOps 1.0 has no supported way to place those files, so schema transactions are not a supported workflow in NetOps 1.0.

**Profile batch.** On NX-OS, EOS, Junos, IOS, IOS XE and FortiOS, `table` `batch` with `op` `update`, `key` `batch` and `changes` as a list of 2–32 steps (each an object with `table`, `op`, `key`, `changes` and optional `endpoint_impact`; `reason`, `user_request` and `request_id` are shared) is planned as one preview with one `plan_sha256`, applied under one safeguard and undone as one operation. Apply needs `expected_plan_sha256`. The steps are written one by one; when a step fails, Admin returns the steps already written and verifies the return, and when that return is not verified the safeguard settles the operation, which can end `unknown`. Junos puts all steps into one candidate and commits and verifies it as a whole. A FortiOS batch needs the CLI-script safeguard (not the webhook safeguard of 8.0.1 and later) and holds only address objects and at most one firewall policy. The response lists each step and its result (`operations`). The platform sections name the tables a batch refuses.

**Firmware outside the tested versions.** Since 1.0.12 a firmware that is not among the tested versions of a profile is not refused; an untested firmware alone does not gate the profile. Profile plans report `firmware_support` (in preview, apply and status; a request refused before planning has none), and doctor reports it per table for the firmware of its result (see `admin_doctor` above), with `status` `untested`, `device_version`, `tested_versions` and a `message` ("... is not among the versions ... was tested on ... It may or may not work as designed and tested; check the result."). `plan_sha256` binds that warning, so the person sees it before apply. A firmware that cannot be read is `unknown` and keeps its technical refusal; technical limits keep their own reason codes. The firmware strings named in the platform sections are the tested versions, not a gate.

**Operations that need the approved preview.** Apply of an operational clear, a standalone save and a profile batch needs `expected_plan_sha256`; so do the port bounce and PoE cycle of most platforms and several tables of each platform (named in its section). Without it the request is refused before any write (`plan_changed`, or the code of the platform such as `clear_preview_required`). The flow: `admin_preview` returns `plan_sha256`; after the person approved the plan, call `admin_apply` with the same arguments and that hash as `expected_plan_sha256`. A standalone save accepts only the hash of the latest matching preview Admin issued for the device (at most 600 s old, presented once). To return a confirmed change, `admin_undo_preview` (`change_id`, `reason`) returns the `plan_sha256` of the undo; with `mcp_undo` enabled pass it to `admin_undo` as `expected_plan_sha256`, otherwise run the operator command `admin undo`.

**Binding apply to an approved preview.** `expected_plan_sha256` (MCP `admin_apply`, operator command `admin apply --expect-plan-sha256`) is 64 lowercase hexadecimal characters; any other value is `rejected`. Apply still plans again from a fresh snapshot; when the `plan_sha256` of that plan differs from the expected one, the change is refused before the operation is recorded and before any device write, with `reason_codes` `["plan_changed"]` and `reason_details` `[{"code": "plan_changed", "expected": ..., "actual": ...}]`; a refusal bound to an issued preview (a standalone save, the MCP undo) omits `actual`. The refusal counts toward the budget of rejected requests like every other refusal and creates no Admin operation record; the MCP request and response of `admin_apply` and the operator preflight record of `admin apply` are audited as for every call. The `plan_sha256` of a profile request covers the target - the device alias from the configuration, the platform and the firmware (no secrets; FortiOS and Arista EOS read the firmware from the fresh snapshot, Junos from its `set version` line (verified against the live `show version` before any write), ExtremeXOS, Cisco IOS and IOS XE use the configured version, which Admin verifies against the live `show version` before any write) - together with the commands, the inverse and the predicted object before and after, so a preview approved for one device or firmware never matches the same change on another device or after a firmware change. A plan also binds the state its operation requires, which for a batch, a clear, a save and several profiles includes configuration outside the target; for the other profiles a change elsewhere in the configuration does not break the binding. The reason of the refusal names these causes and asks for a new preview. Since 1.0.10 the target is part of the hash: a `plan_sha256` from an Admin 1.0.9 preview is refused with `plan_changed` after the upgrade (run a new preview); stored operation records of earlier versions keep their content-only hash and stay readable for verify, recovery and undo. The parameter is not part of the request identity: a repeated `request_id` with the same request and device returns the operation it started, whatever well-formed hash is sent. A malformed hash is still refused, a `request_id` reused with another request or device is refused with `request_id_reused`, and a profile batch, or a Ruckus change, an NX-OS ACL change, an IOS or IOS XE port action, ACL or DHCP change or a FortiSwitch port change other than an undo, sent without the hash is refused with `plan_changed` before the earlier operation is looked up. To check an operation that already started, use `admin_status` with its `request_id`. Without the parameter apply behaves as in 1.0.8. Schema transactions have no such binding: their `plan_sha256` depends on the snapshot and the `request_id`, so `admin_schema_apply` has no `expected_plan_sha256` and `admin apply --expect-plan-sha256` refuses a schema transaction.

## Safety and results

Safeguards last 60–900 seconds; the confirmation margin is at least 15 seconds and at most the safeguard interval minus 15 seconds. Protected objects and their references are refused. Existing per-device/hour, daily, rejection, command and journal limits remain enforced. The per-device `legacy_ssh` exception (`rsa-sha1` or `rsa-sha1-dh14`) retains normal host-key pinning.

Rejected operations, unknown outcomes and reverted/failed returns are MCP errors. Structured results, reasons, request/change IDs and device blocks are preserved. A successful status lookup may report a previously failed operation. A `change_id` or `request_id` that matches no operation is a failed lookup, not an operation with an unknown outcome, and says nothing about the device: the MCP tool `admin_status` returns `unknown-operation` with the reason `no operation matches` as an MCP error, and the operator command `admin status` prints `"result": "rejected"` with the same reason and exits with status 3. Both forms mean the same. Never automatically retry unknown writes: inspect the actual device and journal and use explicit recovery.

The mandatory gateway audit records HTTPS MCP requests before dispatch and responses before delivery. Offline Admin operator workflows run while the gateway is stopped. Before each workflow, a short process under the gateway UID durably records an operator-preflight event with an allowlisted workflow name; device aliases, reasons and other argument values are not copied into that event. The Admin engine then records the operation in its private operations.jsonl and change journal. The preflight event records intent to start, not successful completion; inspect the private operation record and actual device state for the outcome. The deprecated FortiADC commands `pool-member`, `pool-member-add` and `pool-member-remove` are the exception (FortiADC changes through `apply` are recorded like any other): the preflight event names the workflow `other`, and the commands write no operations.jsonl or change-journal entry; their only record is the JSON record they print, so keep that output.

Missing or invalid gateway audit configuration, an unwritable audit, a failed durable write or a detected incomplete final local record refuses the workflow. Existing complete JSONL records are not revalidated by this preflight, and local audit does not prove freedom from privileged tampering. The diagnostic reports only the exception type. MCP calls are refused before dispatch when their gateway audit cannot be written. Admin checks its private operation log before device writes.

Optional legacy engine export-status files are not provisioned by the product and are absent from the example. No legacy exporter is required in the unified product. A result with no legacy exporter records independent Admin-log delivery as not configured, never acknowledged. If an operator configures a legacy export-status file, unreadable, stale or blocked status still refuses changes. Notifications use trusted HTTPS; redirects and failed TLS verification are refused.


Admin refusal responses include `reason_codes` alongside the existing text. `reason_codes` is an aggregate of categories for the refusal, not a list paired by index with `reasons`; several reasons may share one code. Every preview and apply refusal (and the ready preview, where it is empty) carries `reason_details`, and so does an operation that ends `rejected` after it was recorded (MCP result and CLI record: the enrollment notification could not be sent, the device clock could not be read, a PoE cycle found too little time left before its safeguard fires, or `recover` found it interrupted before any device change). `reason_details` contains structured data when available, for example: the `budget` (`rejected_hour`, `journal_records`, `device_hour` or `global_day`) of a budget refusal; `expected` and `actual` for a `plan_changed` plan mismatch, while every `plan_changed` refusal of an undo or save applied with the hash of its issued preview (also a fresh plan that no longer matches) and `unblock_changed` report `expected` alone and some `plan_changed` refusals have no detail; the `change_id` of the undo operation for `undo_already_done`; the `virtual_server` and `service_outage` `true` for a FortiADC `no_healthy_member` service-outage refusal; and `cycle_seconds`, `confirm_margin_seconds`, `available_seconds` and `required_safeguard_seconds` for `safeguard_margin_insufficient` before a bounce or PoE cycle is recorded. "Nothing was changed" in the table describes a refusal. The same code in a failed step of a profile batch (`batch_results`) or in a check after a write (step `postcheck_failed`) can follow a device change: inspect the overall result and the rollback status before any retry. These codes never authorize an automatic retry; unknown codes also require stopping automatic action.

`admin doctor --device firewall-a --local` (or `admin_doctor` with `local: true`) performs only local checks, without contacting or changing the device. It may write locally for writability probes, audit or initialization. The response has `scope: local`, `local_ready`, `remote_readiness: unverified`, `ready: false`, `firmware: null` and empty `operations`. CLI exit 0 means local checks passed, not that remote readiness was verified. Run full doctor before relying on device readiness.
