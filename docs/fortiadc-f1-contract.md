# FortiADC F1 acceptance contract

This narrow first slice adds a distinct `fortiadc` platform and one Helper query, `system_status`, the identity probe. Eighteen further read-only queries were added later; they do not change the identity gate below. The contract does not approve configuration writes or an Auditor implementation.

Core normalization must preserve `fortiadc` and `fortios` as separate canonical names. The existing `fortinet` alias remains `fortios`.

The proposed pure platform check is `netops_core.platforms.require_identity(platform, status_output)`. It first canonicalizes the selected platform through `normalize` and supports only `fortiadc` and `fortios`; an unknown or unrelated platform raises `PlatformError`. It returns that canonical platform only when the hardware field of exactly one line beginning `Version:` agrees with it. The line must follow the grammar of the former `schema_read.STATUS`, which the implementation moved unchanged to `netops_core.platforms.VERSION_RECORD`: `Version:`, whitespace, hardware of `[A-Za-z0-9_.+-]`, whitespace, `v` with a three-part numeric version, a comma, optional whitespace, `build` with four to six digits, then a comma, whitespace or the end of the line; the rest of the line is the existing optional suffix and is not interpreted. A record never continues on the next line. A line ends only at a line feed (`\n`), as the `(?m)^` anchor of the former `schema_read.STATUS` did: a carriage return, vertical tab, form feed, `\x1c`, `\x1d`, `\x1e`, `\x85`, U+2028 or U+2029, which Python `str.splitlines` would also treat as line boundaries, belong to the line, so a `Version:` that follows one of them inside another field is not a candidate (test `test_f1_identity_lines_end_only_at_line_feed`). A line with leading whitespace before `Version:` is not a candidate, and a malformed first `Version:` is not rescued by a second `Version:` later on the same line (the record is matched from the start of the line, not searched). A carriage return that ends the line (CRLF output) is whitespace and does not invalidate a record. Missing, malformed, duplicate (including identical) or conflicting Version records raise `PlatformError`. Hardware beginning `FortiADC-` identifies `fortiadc`; `FortiGate-` and `FortiWiFi-` identify `fortios`. The prefix comparison is case-sensitive and includes the hyphen, so `FortiGatefoo`, `fortigate-VM64`, `XFortiGate-VM64` and `XFortiADC-KVM` identify nothing (the hardware field must start with the prefix; a prefix inside it is not enough). This FortiOS hardware list is intentionally narrow and evidence-based for F1: defer `FortiGateRugged-` and `FortiFirewall-` until sanitized measured Version samples establish their exact hardware strings and a follow-up fixture/contract review approves them. Until then F1 rejects both, and the tests pin that boundary. Product words in a hostname or another field never establish identity.

Before F1 the parser was `netops_helper.schema_read.STATUS`, used by `verify_status` and then `netops_core.schema.Library.require_identity(hardware, version, build)`; the implementation removed it from `schema_read`. Implementation must extract and share that Version-line parser in Core, preserving its existing identity checks, rather than introduce an independent regex/parser in `platforms`. The shared parser must first collect every line beginning exactly `Version:`, including malformed records such as `Version:` with nothing after it, `Version:malformed` without a space or `Version:` followed by a tab, then require exactly one candidate and parse the complete line with the former `STATUS` grammar. It must reject any malformed or duplicate candidate even when another candidate is valid. This intentionally tightens existing `schema_read.verify_status` and Admin `SchemaAccess`; add regressions for malformed/duplicate Version records through both paths. The shared parser is `netops_core.platforms.version_record(status_output)`, which returns the `(hardware, version, build)` tuple. It raises one neutral Core parse error, `netops_core.platforms.VersionRecordError`, which is not a subclass of `PlatformError`; callers translate it to their existing public exceptions: `PlatformError` in `platforms.require_identity`, `SchemaError` in `schema_read.verify_status`, and `Rejected` in Admin `SchemaAccess`. `fortios_diagnostics` reaches the parser only through `schema_read.verify_status` and therefore reports the existing `SchemaError`. `ssh_read` does not parse status output in this source slice: its consumption of the shared check, and the error it then reports, are specified in the section `Transport wiring of ssh_read` below; the pure platform tests do not cover them, the F1-WIRE tests do. The proposed platform check has a narrower purpose than the existing Library method: product separation does not replace exact hardware/version/build verification or the current VDOM verification. The platform check is intentionally absent from the RED baseline. An alternative boundary requires an explicit update of this contract and its tests rather than a compatibility shim in the tests.

The device paths that must consume the shared parsing/checks are `ssh_read` for both `fortiadc` and `fortinet`/`fortios`, plus existing FortiOS `schema_read`, `fortios_diagnostics`, and Admin `netops_admin.access.SchemaAccess`. They must reject the wrong live product before sending the requested query, configuration dump or diagnostic command. Existing `schema_read` and Admin `SchemaAccess` already reject an ADC hardware mismatch through `Library.require_identity`; those protections must remain. These pure tests cover parser/platform behavior, not proof of this transport wiring.

Helper uses its existing `render_read_query` boundary. In this slice `fortiadc` has the `system_status` query, with no slots, producing exactly `get system status`. The catalogue now holds thirty-three `fortiadc` queries (see the FortiADC vendor reference); `interface_state` and `nic_detail` use `interfaces`; `slb_vs_stat` uses `vdom` and `virtual_server` from `adc_vdoms` and `adc_virtual_servers`; `tls_handshake_stats` and `tls_session_reuse` use only `virtual_server` from `adc_virtual_servers` and their fixed `show virtual-server` command templates. The three DoS block-count queries `dos_access_limit`, `dos_conn_limit` and `dos_req_limit` use that same enrolled `virtual_server` slot and the fixed `execute dos get` choice belonging to the query. Their PTY output remains bounded device text: empty output is no returned counter, not counter zero; qualification of that data on an installed Helper is pending. Unknown query names, raw CLI used as a query name and supplied parameters that a query does not declare are refused. No generic CLI parameter is introduced. The public MCP route is `ssh_read` through the proxy: implementation must update `proxy.PLATFORM_MAP`, `READ_QUERY_NAMES` and expected maps in `components/netops-helper/tests/test_policy_parity.py`; the existing parity tests must remain green.

The test status strings are synthetic product-marker fixtures, not captured appliance evidence, and make no assertion about complete status formatting, licensing or firmware support. They must later be supplemented by a sanitized measured status through the actual transport. These pure tests do not prove that the installed Helper checks identity before returning a device response; the implementation must subsequently demonstrate that boundary with a matching and mismatched real device response. The tests do not perform SSH, use credentials or change a device.

## Transport wiring of `ssh_read` (F1-WIRE)

`engine.ssh_read` gates the helper platforms `fortinet` (core name `fortios`) and `fortiadc` on the live product; every other platform is unchanged. The gate runs only on a fresh read (offset 0). A continuation (offset above 0) contacts no device and returns the cached snapshot, which was verified when it was stored.

- F1-WIRE-ORDER: before the requested query the engine reads the identity command `get system status` through the same transport (`read_from_device`) and passes the cleaned output to `netops_core.platforms.require_identity` with the selected platform. The requested query is sent only afterwards and exactly once.
- F1-WIRE-PROMPT: the cleaned output of F1-WIRE-ORDER is the output after `netops_core.prompt.cleaned`, which `read_from_device` applies per platform. A FortiADC `exec -T` answer is framed by the shell prompt (measured on FortiADC-KVM 7.6.7 on 2026-10-26): the first line begins `<host> # ` followed by `Version: ...`, and the output ends with the line `<host> # ` without a final newline (a blank line may precede it). `fortiadc` therefore joins `netops_core.prompt.PREFIXES` with the same pattern as `fortios` and `exos` (`PLATFORMS` becomes `("fortios", "exos", "fortiadc")`; the `fortiadc` name has no alias). The source tests use a synthetic host name of 12 characters, drive the real `ssh_read` through the substituted OpenSSH client and cover: a prompted FortiADC answer without a final newline passes the identity check and is returned without the prompt, also with CRLF line ends; a prompted answer of the other product (FortiGate for `fortiadc`, FortiADC for `fortinet`) ends as `product_identity` without device output. A prompted answer that still carries the prompt in the Version line is not accepted by relaxing the parser: the prompt is removed before the check, never inside it.
- F1-WIRE-SINGLE: when the requested query renders to exactly `get system status` (`system_status` of both platforms), that one response is the identity probe and the query. It is verified before it is returned, classified, cached or paged; no second device read happens.
- F1-WIRE-FAIL: the identity is not established when the probe response raises `PlatformError` (wrong product, missing, malformed, duplicate or conflicting Version record), when its exit status is neither 0 nor absent, or when the platform's CLI refusal classifier matches it. The result is `ok: false` with `error_code: "product_identity"`, the fixed text `The live device did not identify itself as the selected product (<fortiadc|fortios>); no query output was returned`, and the keys `target`, `platform`, `query`, `transport` and `rc`. It carries neither device output nor the probe response. After it no further device command is sent (the probe is the only `read_from_device` call), nothing is cached, and the audit record of the operation ends `failed`.
- F1-WIRE-TRANSPORT: an exception of the probe read itself (host key, connection, client failure) is reported by the existing generic error branch; the requested query is not sent.
- F1-WIRE-CONTINUATION: a continuation performs no probe and no device read.
- Cost, accepted for F1: a fresh read of any query other than `system_status` takes one more SSH connection, paced like every other connection to the device (5 s on the FortiOS lane). Caching a verified identity per device is deferred until it is measured to matter. A source test pins it: a FortiOS query other than `system_status` opens two connections with a 5 s wait before the second, while `system_status` opens one.
- User-visible effects, documented in the Helper docs (not in `CHANGELOG.md`: the repository changes it only in release commits, so the entry belongs to the release that ships F1): the extra connection and wait above, the new `error_code` `product_identity`, the right of the read-only account to run `get system status` on FortiOS and FortiADC, and the refusal of `FortiGateRugged-` and `FortiFirewall-` hardware (F1 identifies `FortiGate-`, `FortiWiFi-` and `FortiADC-` only).
- Scope: `schema_read`, `fortios_diagnostics` and Admin `SchemaAccess` keep their own identity reads and checks described above; `read_from_device` itself carries no gate, because `schema_read` reads through it.
- Evidence still required after these source tests: a matching and a mismatched response from a real device through the exec transport (see the `Limitations` of the FortiADC vendor reference).

## CLI refusal classification of `fortiadc` (F1-REFUSAL)

`engine._CLI_REFUSALS` has a dedicated `fortiadc` entry. It recognizes a complete standalone line of the form `Command fail. Return code is <signed integer> (<description>)`, with optional surrounding horizontal whitespace and a final CR. The description must be nonempty, remain on one line and contain no parentheses. It does not copy the FortiOS classifier or match this text inside a prefixed diagnostic field such as `Last error:`.

Observed evidence (2026-10-29): a capture of FortiADC 7.6.7 build0676 CLI answers contains five standalone occurrences of `Command fail. Return code is -284 (CLI parsing error.)`. The FortiADC 7.6.7 CLI Reference index and `get system status` page checked on 2026-10-27 do not document refusal text; they are not the source of this literal.

The observed message is only `-284` with `CLI parsing error.`. Generalizing the explicit failure-line structure to other signed numeric codes and single-line descriptions is an inference. The synthetic `+1`/different-description assertion checks that intended family, not another device observation. Other FortiADC refusal formats remain outside this classifier's demonstrated coverage.

For `ssh_read`, a refusal of the identity probe is reported as `product_identity`; a refusal after a verified identity is reported as `device_cli_error` and is not cached. The targeted regression feeds the observed `-284` literal with `rc=0` after a valid ADC identity, including beyond the first output page. The original implementation failed that check; the two updated existing test methods pass after the fix, and the earlier tests remain green.

The negative regression preserves a valid ADC status containing `Last error: Command fail. Return code is -284 (CLI parsing error.)` and the foreign FortiOS literal `Command fail. Return code -61`. Neither is a standalone ADC failure marker. FortiOS behavior remains separate.

`components/netops-helper/tests/test_vendor_references.py` checks agreement between the registry and reference document; it does not read the vendor pages or establish the measured refusal.

The standalone unittest file `tests/v1/test_fortiadc_f1_contract.py` names absent functionality as assertion failures beginning `F1-MISSING-` and the intended tightening of the existing `schema_read` and Admin paths as assertion failures beginning `F1-TIGHTEN-`, without xfail/skip or a fabricated passing stub. The unsupported platform must not make negative Helper tests pass accidentally: each first requires ADC support. The alias regression and the positive `schema_read` and Admin regressions for one exact Version record may already pass before implementation; they guard against an implementation that rejects every status.

The branch holds both the contract tests and the implementation. The tests fail before the implementation and pass with it. `components/netops-helper/docs/query-catalog.md` is generated by `components/netops-helper/tests/support/render_query_catalog_docs.py` and is never edited by hand.

Release qualification of this file: like every other file in `tests/v1`, the contract test is copied into the product image (`Dockerfile`, `/opt/netops/tests`) and runs in the installed-image unit test layer (`python -B -m unittest discover -s /opt/netops/tests -v` in `ci.yml` on every push and pull request, on its single amd64 runner `ubuntu-24.04`, and in the candidate workflow `candidate.yml` from the pushed digest on both architectures, amd64 and arm64; see [Qualification](testing-1.0.md)). The engine regression (`release/engine_regression.py`) runs only `components/<role>/tests` and does not run it. Mutations of the identity grammar, the product prefixes, the `VersionRecordError` translation and the probe exit status are caught by that layer, not by the engine regression; both layers are required for a release.

Admin import gate: Admin `SchemaAccess` reads the Version record through `netops_core.platforms.version_record` (one shared Version record parser, no second regex in Admin). The Admin gate (`components/netops-admin/tests/support/check_gates.py`, `FILE_RULES`) therefore admits exactly `from netops_core import platforms` in `access.py`. It stays a name-level allow-list: the rest of `netops_core` and every other Admin module remain closed, and `platforms` is a pure parser module without device access, sockets or processes. Admin tests pin both directions (`test_access_may_import_the_core_platforms_module`, `test_the_core_platforms_module_is_admitted_only_for_access`, `test_access_stays_closed_to_the_rest_of_netops_core`). The refusal test is parametrized over every other module: each file of `src/netops_admin`, each `FILE_RULES` entry and a module that is in neither, so widening the allow-list for any module other than `access.py`, globally or through a new rule, fails it.

  python3 -B tests/v1/test_fortiadc_f1_contract.py -v

After implementing, rerun the same command and preserve both results. These tests alone do not establish release acceptance, transport integration, masking, output limits, restart or upgrade behavior.

## Admin `pool-member` health precheck

Before a member state change, `netops_admin.fortiadc.prechecks` reads `diagnose server-load-balance vs_stat vdom root vs <vs>` for every virtual server that uses the pool and refuses the change when no enabled member reported `hc_state: UP` would remain. An unreadable, refused (`Parsing error`, `Command fail`, `-284`) or unrecognised answer refuses the change before any write (fail closed). A virtual server that selects pools by content routing or schedule also refuses the change, because the pool use cannot be evaluated.

Account of the precheck: on FortiADC-KVM 7.6.7 build0676 a read account whose access profile has every area `read` and `is-system-admin no` is refused with `Parsing error at 'server-load-balance'` and `Command fail. Return code is -284 (CLI parsing error.)` (measured 2026-10-27), so a precheck through the Read check account would always refuse the change. The precheck therefore reads `vs_stat` with the same write account that performs the change, which already holds that right: no right is added, the Read account is unchanged, and a failed read still refuses.

Mapping of the `vs_stat` member `id` to the pool member number is measured only on one pool with members 1 and 2. The regression fixture `components/netops-admin/tests/fortiadc_vs_stat_767_0676.txt` is a measured `vs_stat` answer.

Transport of the `vs_stat` read (measured 2026-10-31 on FortiADC-KVM 7.6.7 build0676): over the exec channel the whole `vs_stat` answer is written to stderr, and stdout carries only the prompt lines. The precheck therefore reads it through `DeviceAccess.diagnose_query`, which joins the cleaned stdout and stderr of the write account's exec call; a non-zero exit status, an empty, refused or unrecognised answer, or a stderr answer that reaches the capture limit (`STDERR_MAX_BYTES`, 64 KiB) refuses the change. `netops_core.ssh.Result` carries the captured stderr bytes as `stderr` (empty by default). The helper's `slb_vs_stat` already reads through an interactive terminal (`pty=True`) and is not affected.

Listings longer than one screen arrive with the FortiADC pager inline: `--More-- `, a carriage return, the erasing spaces and a second carriage return, followed by the next line on the same physical line (measured on FortiADC-KVM 7.6.7 build 0676 for `show load-balance virtual-server`). The pool and virtual-server parsers remove exactly that sequence before reading; any other `--More--` text is still an unexpected line and the change is refused.

## Admin `pool-member-add` and `pool-member-remove`

`admin pool-member-add --device D --pool P --member N --real-server RS --service-port PORT` (command line in [Admin configuration](admin-configuration.md#fortiadc-pool-member)) creates one new pool member in a single configuration block and always with `set status disable`; the member is switched on only by the separate `pool-member --status enable` after its health check is UP. Grammar (attribute names as the device prints them, with underscores):

`config load-balance pool` / `edit "P"` / `config pool_member` / `edit N` / `set real-server "RS"` / `set pool_member_service_port PORT` / `set status disable` / `next` / `end` / `next` / `end`

Before the write the operation reads the pool (`show load-balance pool P`), the real servers (`show load-balance real-server`) and the virtual servers; it refuses, without any write, when the pool is not listed, the number is already used, the real server is not configured, or the same real server with the same port is already a member. The returned `preview` carries the exact commands, the existing member numbers, the virtual servers that use the pool and the `inverse` (delete of the new number). The independent postcheck re-reads the pool and confirms only when the new member shows the requested real server, the requested port and an explicit `status disable`, and every other member is identical to the state read before. Any other outcome deletes the new member and reads back again: `rolled_back` when the pool equals the state before, otherwise `unknown`. Exit codes as for `pool-member` (0 confirmed, 4 rolled_back, 7 unknown).

`pool-member-remove` is the inverse: `config pool_member` / `delete N` / `end`; it refuses a member that is neither DISABLED nor in MAINTAIN, the last member of the pool and a member with settings that cannot be restored (all before any write), and confirms only when the pool equals the state before minus that member. No health precheck is needed because neither command enables traffic. Weight and other attributes of an added member keep the device defaults; the grammar is taken from measured `show` output (`edit`/`set real-server`/`set pool_member_service_port`/`set pool_member_weight`/`set status`). Live on FortiADC-KVM 7.6.7 build 0676 (standalone, development build): add and remove with confirmed readback on 2026-10-31 (pool equal to its initial state afterwards), and the restore path of the next section on 2026-11-01.

## Admin `pool-member-remove`: rules

`pool-member-remove` removes only a member whose status is `disable` or `maintain` (`enable`, and also a status missing from the `show` output, is refused) and never the last member of a pool (refused before any write, without a device change). The delete commands are those of the previous section; the write and the restore (the inverse create after an actual delete, `rolled_back`, pool state equal to the initial state) were verified by a live run on FortiADC-KVM 7.6.7 build 0676 (development build) on 2026-11-01.

The removal preview carries `member_before` (the complete member state as `show load-balance pool P` prints it) and `inverse`: `config load-balance pool` / `edit "P"` / `config pool_member` / `edit N` / `set real-server "RS"` / `set status disable|maintain` / `set pool_member_service_port PORT` / `set pool_member_cookie "C"` / `set pool_member_weight W` / `next` / `end` / `next` / `end` (only the attributes the member has; status directly after real-server, so that a restored member is not enabled even when a later line fails). A member with another attribute, a value outside this grammar or no real server is refused before the delete (`the member has settings that cannot be restored: ...`). When after the delete the write fails or the readback differs and the member is missing from the pool (or the pool cannot be read), the `inverse` is written and the pool is read again: `rolled_back` only when it equals the state before, otherwise `unknown`; the record carries `restore` = `{"attempted": true, "write": "ok"|"write failed (...)"}`, and `{"attempted": false}` when the member is still in the pool (delete without effect).

## Bounded event/system diagnostic

The system_event_logs recipe is ADC-specific and uses the FortiADC target's catalog-bound diagnostic enrollment. It reads the current event/system view from fixed start line 0; it does not claim full historical log coverage. The waf_attack_logs recipe is the same bounded read with type attack and subtype waf: it reads the current WAF attack view only, with the same baseline, display and restoration rules below. The CLI response is returned as record text without splitting message fields. Only measured record lines beginning with the date/time prefix are selectable; the two measured display footer lines are omitted. Unknown or multiline body content is incomplete. The session_list and persistence_list recipes read the current session or persistence table of one virtual server enrolled in `diagnostic_virtual_servers`: they refuse to run when a session or persistence filter is already set (the Helper never replaces it), set `vs-name` for this read only, verify the readback, list once and clear the filter with a byte-equal readback of the original empty filter. `header_only` true means no entry for that virtual server at the moment of the read; it is not a global absence and not a promise of non-empty data. A first line other than the exact column header of that FortiADC list is reported as incomplete with `unrecognized_body`; rows are counted, columns are not parsed.

Before filtering, the helper requires the current filter display to be empty and the unfiltered display to return the measured filter-needed refusal. It applies only the recipe's fixed type and subtype (event/system or attack/waf), performs one bounded display, then clears the filter and verifies both original baseline displays. If restoration cannot be verified on the pinned appliance identity, the response is incomplete. The recipe is not qualified on an installed Helper or on hardware other than the exact identity used for its separate qualification.
