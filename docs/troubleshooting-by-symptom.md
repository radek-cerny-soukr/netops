# Troubleshooting by symptom

Step-by-step starting points for five everyday complaints, using only the Helper tools that ship in this release. Problems when building the image or running the tests from a source checkout are at the [end](#building-or-testing-from-source). Each section says what you see, which call to make first, how to read the answer, what to do next and what the tool cannot tell you.

The Helper only reads. It does not fix anything, it does not keep history and it never reports a device as healthy on its own: every answer is one snapshot taken at the time of the call. Device text is returned in `untrusted_device_output`; read it yourself, the Helper does not interpret it except where a section says so.

## Before you start

- Every call names an enrolled `target` alias. `helper_status` with `{}` lists the aliases. `target_scope(target="<alias>")` shows, without contacting the device, everything that alias allows: `enabled_queries` (the `ssh_read` queries), `read_inventory` (the allowed parameter values: `addresses`, `interfaces`, `flow_ports`, `ip_protocols`, `policy_types`, `diagnostic_recipes`, `adc_virtual_servers`, `adc_health_checks` and others) and `egress` (what the probes may use: `tcp_ports`, `allow_icmp`, `allow_dns`, `tls_server_names`). Read it before the first call to a target.
- A query, parameter value, port or server name that is not in that scope is refused before any device contact with error code `-32009`, category `policy_scope` and always the same sentence `The requested operation is outside the enrolled target scope.` The refusal does not say which value is missing; compare your arguments with `target_scope`. If the value you need is not there, ask the person who maintains the inventory to add it; see [Helper configuration](helper-configuration.md).
- A missing argument or a wrong value type is refused with code `-32602`, category `invalid_params` (`Tool arguments do not match tools/list inputSchema`, sometimes followed by `missing required fields: <name>`, or `Tool arguments do not match the exact input schema.`).
- `ssh_read` takes `platform`, `query` and `parameters`, for example `ssh_read(target="fw-branch", platform="fortinet", query="route_lookup", parameters={"address": "198.51.100.10"})`. In `ssh_read`, `platform` is the `ssh_platform` from `target_scope` (`fortinet` for a FortiGate, `fortiadc` for a FortiADC). `config_read` takes the product name instead: `fortios` or `fortiadc`. Every parameter value is a string exactly as listed in `read_inventory`: ports as `"443"`, the protocol as the number `"6"` (TCP) or `"17"` (UDP), never `"tcp"`. A target with `ssh_platform: null` and empty `enabled_queries` accepts only the probes below. The query names and their parameters are in the [query catalogue](../components/netops-helper/docs/query-catalog.md).
- `ssh_read` result: `ok: true` with `untrusted_device_output`, `next_offset` and `complete`. When `next_offset` is not null, call again with `offset` set to it and the `content_sha256` from the first page.
- `ssh_read` failures: `error_code: "device_cli_error"` means the device refused the command (missing feature or account permission); `error_code: "product_identity"` means the target is not the product you selected. Other failures carry only `error`.
- `dns_probe`, `tcp_probe`, `icmp_probe` and `tls_probe` run from the Helper host to the address of the enrolled target itself. They do not test from the firewall, from a client network or to any other address, and the path from the Helper host need not cross the firewall your users go through. `icmp_probe` needs `allow_icmp: true` and `dns_probe` needs `allow_dns: true` in the target's `egress`; otherwise they are refused as `policy_scope`.

## 1. Internet or VPN does not work

You see: users behind a FortiGate cannot reach the internet or a site behind an IPsec tunnel.

1. Route to the destination: `ssh_read(..., query="route_lookup", parameters={"address": "<destination>"})`. Every line marked `*` is a route the firewall uses; several lines (ECMP) mean it spreads the traffic over all of them. Compare the interfaces after `via` with the uplink your design uses for that destination (the internet uplinks, or the tunnel interface for a VPN subnet). The Helper does not know your design: take the intended uplink from your network documentation or from whoever owns the firewall. The Helper can only show what is configured: `config_read(target, platform="fortios", section="router static", redaction="full")` lists the static routes with `set device` and `set comment`, and the `dstintf` of the policy from step 3 shows where that policy sends the flow. No route, or a route only out of an interface that should not carry this traffic, is the answer; stop here.
2. Ingress interface: `ssh_read(..., query="route_lookup", parameters={"address": "<client>"})` with the client address (it must be in `addresses`). The interface in the answer, for example `is directly connected, PVE-MGMT`, is the interface the client's traffic enters on; it must also be in `interfaces`.
3. Policy for the failing flow: `ssh_read(..., query="policy_lookup_ipv4", parameters={"src_ip": "<client>", "src_port": "<client source port>", "dst_ip": "<destination>", "dst_port": "<port>", "protocol": "6", "device": "<ingress interface>", "pol_type": "policy"})`. All seven values are strings and must be enrolled (`addresses`, `flow_ports`, `ip_protocols`, `interfaces`, `policy_types`). The user rarely knows the source port: use the real one when you have it, otherwise any enrolled port from `flow_ports`; in the lab the same policy matched with source port `50000` and `443`. A policy whose service filters on source ports can answer differently. Read `untrusted_device_output`:
   - `firewall policy id: <n>` with `policy_action: accept` or `deny`: that policy matches the flow. The output gives the policy ID only. A `deny` here is the answer. To see what that policy is: `config_read(target, platform="fortios", section="firewall policy", redaction="full", contains="edit <n>", context=10)` (needs `config_access` `read`) returns up to `context` lines before and up to `context` lines after the line `edit <n>`, not the whole entry. `context` is 0 to 10 lines; a larger value is refused as `-32602` without naming the field. `contains` is matched literally against the printed configuration, which shows names without quotes: for a named object use `contains="edit PVE-MGMT"`, not `contains='edit "PVE-MGMT"'` (0 matched lines). For a policy the lines include `set name`, `srcintf`, `dstintf`, `srcaddr`, `dstaddr`, `service` and `comments`. The entry ends at the first `next` after `edit <n>`; when the output stops before that `next`, the policy has more lines than were shown (in the lab policy 90 had ten lines after `edit 90`, and `context=10` ended at its `comments`, without `next`). Then repeat `config_read` with the same `target`, `platform`, `section` and `redaction` but without `contains` and `context`, and read from `edit <n>` to its `next`; when `next_offset` is not null, page as described in [Pages and snapshots](../components/netops-helper/docs/tools.md#pages-and-snapshots). `set action` is not printed when the action is the default `deny`, so a missing `set action` means `deny` only when you see the entry up to its `next`. Whether the policy is intended is a question for whoever owns the rule base.
   - `No policy matched` with `sec_default_action: deny` (and `firewall policy id: 0`): no policy allows the flow from that interface, so the implicit deny drops it.
   - `Error code: err_src_route`: the firewall has no route back to the source through the interface you gave; usually the `device` is not the client's ingress interface. Check step 2.
   - `device_cli_error` with `Policy lookup could not resolve a route for the supplied flow` means the firewall has no route for that tuple; go back to step 1.
4. For VPN: `query="ipsec_summary"` lists each tunnel; then `ike_errors` and `ike_statistics` for negotiation errors, `ipsec_tunnel_statistics` for aggregate SA counters.
5. Uplink: `query="sdwan_health"` (SD-WAN health checks), `link_monitor_status` with an enrolled `monitor`, `interface_details` with an enrolled `interface`, for each interface after `via` from step 1 (with ECMP every one of them; an interface that is not in `interfaces` is refused as `policy_scope`; ask the inventory maintainer to enroll it, and until then say that interface was not checked). `SD-WAN daemon is not running.` in the output means the unit runs no SD-WAN, so the SD-WAN queries tell you nothing; use `interface_details`. A query that is not in `enabled_queries`, such as `link_monitor_status` on a target that does not list it, is refused as `policy_scope`.
6. To see whether the flow reaches the firewall at all: `fortios_diagnostics(target, recipe="sessions", address="<destination>", interface="<ingress interface>", source_address="<client>", source_port=<client source port>, destination_port=<port>, protocol=6)` (`17` for UDP). The tuple is exact, including the source port: take it from the client's connection list. If you do not know the real source port, skip this step: `total session: 0` for a guessed port says nothing about the user's flow. Both addresses must be enrolled in `addresses` and the recipe in `diagnostic_recipes`. Here ports and protocol are numbers, not strings. Read `untrusted_device_output`; `complete` and `sessions_omitted` tell you whether you saw every matching session. `total session: 0` means no session for that exact tuple existed at the time of the call. `recipe="flow"` with the same tuple shows the packet path decision only for packets that arrive while the call runs: let the client retry during the call. An empty `untrusted_device_output` with `deadline_reached: true` means no matching packet arrived in that time, not that the path is fine.

What it cannot do:

- `fortios_diagnostics` runs only on the measured units. With a tuple (`sessions`, `sniffer`, `flow`): FortiGate-VM64 8.0.2 build 0251, FortiGate-60F 7.6.8 build 3744 and FortiGate-80F 8.0.2 build 0251 (measured on the primary member of an HA pair with a read-only account). Without a tuple (`ping`, `traceroute`, `logs`): FortiGate-VM64 8.0.2 build 0251, FortiGate-80F 8.0.2 build 0251, FortiGate-VM64-KVM 7.6.7 build 3704 and FortiGate-VM64-KVM 8.0.0 build 0167. On any other unit the call is refused before the first diagnostic command, but the caller only sees the generic `bounded FortiOS diagnostic failed; the session was closed`, not the reason; so a unit that is not listed here fails this way. On those units use steps 1 to 5.
- `ipsec_tunnel_statistics` does not give per-tunnel traffic. The Helper cannot bring a tunnel up, clear a session or change a policy.
- Only TCP (`6`) and UDP (`17`) tuples are accepted; a VDOM selector is refused.

## 2. Everything is slow

You see: applications respond slowly through a FortiGate.

1. Firewall load: `ssh_read(..., query="performance")`, then `system_top` (one fixed five-line process snapshot) and `conserve_state` (memory conserve mode).
2. Session table: `query="session_stats"`.
3. Uplink quality: `sdwan_health` (`SD-WAN daemon is not running.` means the unit runs no SD-WAN; skip to step 4); for one member `sdwan_member_detail` with an enrolled `member`; history kept by the firewall with `sdwan_sla_history` (enrolled `health_check` and `member`) or `sdwan_interface_quality` (enrolled `interface`).
4. Errors and drops: `interface_details` with an enrolled `interface`, first for the clients' ingress interface and every outgoing interface from section 1 (steps 1 and 2); with ECMP that is each interface after `via`. An interface that is not in `interfaces` is refused as `policy_scope`; ask the inventory maintainer to enroll it, and until then say that interface was not checked. In the `stat:` line, `rxe` and `txe` are receive and transmit errors and `rxd` and `txd` receive and transmit drops. The counters are cumulative, not a rate: call twice a few minutes apart and compare, a value that grows is the finding. `interface_hardware` adds the physical port counters only if it is in `enabled_queries`; otherwise it is refused as `policy_scope`.
5. From the Helper host to a target: `tcp_probe(target, port=<port>)` returns `elapsed_ms` (connect time); the port must be listed in that target's `egress.tcp_ports` (or lie inside one of its `egress.tcp_port_ranges`) in `target_scope`, any other port is refused as `policy_scope`; `icmp_probe(target, count=4)` returns `packet_loss_percent`, `avg_rtt_ms` and `jitter_ms` (needs `allow_icmp` in that target's `egress`; `count` 1 to 8). When users name the slowest server and it is enrolled as its own target (often a probe-only target with `ssh_platform: null`), probe that target and, for comparison, the firewall target: a high value only towards the server points at the path or the server, not at the firewall load from steps 1 to 4. Compare the same probe on both: a firewall target usually has `allow_icmp: false`, so `icmp_probe` to it is refused and only `tcp_probe` to its SSH port can be compared. Call each probe two or three times; in the lab one first `tcp_probe` took 411 ms and the following ones about 201 ms. The Helper has no threshold for "high": judge the server value against the firewall value from the same Helper host and against what users accept. In the lab the firewall answered in about 1 ms and the server in about 201 ms; a server value close to the firewall value does not point at the path.

What it cannot do: the probes measure from the Helper host, not through the firewall and not from the users' network; a slow result says only that the path Helper host to target is slow, and a fast one does not clear the users' path. There is no trend or baseline in the Helper; compare two calls yourself. `tcp_probe` measures only the TCP connect, not the application. `system_top` is a single snapshot. For a slow service behind a FortiADC, use section 3; `slb_vs_stat` reports RTT and throughput of one virtual server.

## 3. Backend DOWN behind a FortiADC

You see: a service published by a FortiADC virtual server fails or answers only partly.

1. `triage_slb(target="<adc alias>", virtual_server="<enrolled virtual server>")` (`vdom` defaults to `root`). It reads the virtual server, its pool, members, health checks and runtime state in one fixed plan. One call took about 60 to 65 seconds in the lab (`started_at` and `finished_at` in the result); give your MCP client a call timeout of at least 90 seconds.
2. Read `verdict` first:
   - `fault_found`: at least one finding below names the fault.
   - `incomplete`: a step is listed in `missing` with `reason` (`timeout`, `truncated`, `empty`, `unsupported`, `permission_denied`, `device_cli_error`, `unparsed`, `not_applicable`); fix that cause before trusting the result.
   - `no_fault_in_checked_data`: nothing wrong was found in what was read. It does not mean the service is healthy.
3. Read `findings`; each cites the call and `content_sha256` it came from:
   - `F-VS-DISABLED` virtual server disabled; `F-VS-AVAIL` availability not `HEALTHY`.
   - `F-MEMBER-DOWN` a pool member's health check is not `UP`; `F-POOL-ALL-DOWN` no member is usable. `F-VS-AVAIL` repeats the availability the FortiADC reports in `slb_vs_stat`; in one measurement one DOWN member of two already gave `UNHEALTHY`. `F-MEMBER-DOWN` without `F-POOL-ALL-DOWN` means the other members still serve: the service answers partly.
   - `F-MISMATCH` configured members differ from the runtime view.
   - `F-TLS-FAIL` failed TLS handshakes (see section 4).
   - Informational: `F-MEMBER-DISABLED`, `F-NO-HC` (pool without health check), `F-DOS`, `F-WAF`.
   The `object` of `F-MEMBER-DOWN` names the pool and member ID, for example `WEB_POOL id 2`. The real-server name of that member is in `chain.pool.config.members` (each entry has `id` and `real_server`, for example `{"id": 2, "real_server": "WEB_RS2"}`) and in the `why` of `next_steps`.
4. Follow `next_steps`: each is a `fortios_diagnostics` call with its arguments and a `why`. Pass the arguments as given, including `"interface": ""` (the field is required and must be empty on a FortiADC). The arguments do not contain `address`: `why` names the real server (for example `WEB_RS2`), and you add `address` with that server's IPv4 from the target's `addresses`. The Helper does not return a real server's IP address: neither `triage_slb` nor `config_read` (which has no real-server view) shows it. When `addresses` lists several servers, the inventory maintainer knows which address belongs to which real server; until then, run the check against each enrolled address and treat each result as a fact about that address only.
   - `recipe="health_check_verify"`: use `count` 1 to 5 and pass `timeout` of about 5×count+5 seconds. The output ends with the appliance's verdict, for example `recv hc state is UP(check service successfully, status code 200)` or `recv hc state is DOWN(tcp connect error)`, followed by the success rate; the second means the appliance could not open a TCP connection to the server port, so look at the service on that real server.
   - `recipe="ping"`: keep `count=3` (the appliance always sends 5 packets). It also needs `allow_icmp: true` in the ADC target's `egress`; without it the call is refused as `policy_scope` even though `ping` is in `diagnostic_recipes`.
5. To check one piece by hand: `ssh_read(..., platform="fortiadc", query="slb_vs_stat", parameters={"vdom": "root", "virtual_server": ...})` or `query="slb_load"`.

What it cannot do:

- `triage_slb` runs only on FortiADC 7.6.7 build 0676; other builds answer `config_platform_not_supported: triage_slb requires FortiADC 7.6.7 build 0676`.
- It needs `config_access` `read` on the target, the queries `slb_vs_stat`, `slb_load` and `system_performance` enabled, and the virtual server and VDOM listed in `adc_virtual_servers` and `adc_vdoms`. One call counts as 17 requests against the target rate limit (default 30 per 60 seconds) and is refused as a whole when fewer remain. The 17 requests are charged when the call is accepted and leave the window `window_seconds` later; a call takes 61 to 66 seconds, longer than the default 60-second window. The helper handles calls one at a time, so a `target_scope` sent while `triage_slb` runs returns only after it finishes, when the window has already expired, and shows `used: 0`. That does not mean nothing was charged. The FortiADC read profile refuses `diagnose` and `get router` commands, so those runtime reads need the system administrator account enrolled as `admin-bounded`; see [account boundaries](../components/netops-helper/docs/read-only-accounts.md). Without it the verdict is `incomplete`.
- It does not log in to the real servers and does not change the pool, health check or virtual server.

## 4. TLS or certificate error

You see: a browser or client reports a certificate or handshake error for a published name.

1. `tls_probe(target="<alias>", port=443, server_name="<published name>")`. The name must be in the target's `tls_server_names` (or equal to the target host) and the port in its TCP ports.
2. `ok: true` gives `tls_version`, `cipher`, `subject`, `issuer`, `days_remaining` and `certificate_sha256`. A low `days_remaining` is the warning; compare `certificate_sha256` with the certificate you expect.
3. `ok: false` gives only `error`, as `<error type>: <text>`, for example a certificate verification error or a timeout. No certificate details are returned in that case.
4. Port only: `tcp_probe(target="<alias>", port=443)` (443 must be in the target's `egress.tcp_ports`, see section 2 step 5). A connect time with `ok: true` while `tls_probe` fails means the port answers and the failure is in TLS or the certificate.
5. Behind a FortiADC, first find the virtual server that serves the name. A published name usually has its own probe-only target (`ssh_platform: null`), which accepts no `ssh_read`; the counters are read on the FortiADC target. For each virtual server in the ADC target's `adc_virtual_servers`, `config_read(target="<adc alias>", platform="fortiadc", section="load-balance virtual-server <name>", redaction="full")` (needs `config_access` `read`) shows its `ip` and `client-ssl-profile`. Compare the `ip` with the address in the published target's `egress.addresses` from `target_scope`. If that address is the ADC target's own address (its `egress.addresses`), the name points at the appliance itself, not at a virtual server: there are no virtual-server counters for it, so check the appliance's own certificate outside the Helper. If no enrolled virtual server has that address, or the matching one has no `client-ssl-profile`, the Helper has no TLS counters for that name: ask the inventory maintainer to enroll the right virtual server.
6. For the matching virtual server: `ssh_read(..., platform="fortiadc", query="tls_handshake_stats", parameters={"virtual_server": ...})` shows successful and failed handshake counters per side; `triage_slb` turns failed counters into `F-TLS-FAIL`. `tls_session_reuse` shows session reuse counters.

What it cannot do:

- `tls_probe` verifies the chain against the Helper host's system certificate store, or, when the target has `tls_ca_certificate` in its helper section, against that CA only, always with hostname/SAN checking and TLS 1.2 or newer; there is no option to skip verification. The result names the trust used as `trust: "system"` or `trust: "inventory_ca"`. A certificate from a private CA fails under the system store even when your clients trust it, with the same `SSLCertVerificationError: ... unable to get local issuer certificate` that a chain without a trusted root or a missing intermediate certificate gives; the Helper cannot tell these cases apart, and with `ok: false` it returns no subject, issuer or expiry. Enroll the private CA as described in [Optional Helper fields](helper-configuration.md#optional-helper-fields) and repeat the probe; if it still fails with `trust: "inventory_ca"`, the chain is not issued by that CA, the name is not in the certificate, or the certificate has expired, and steps 4 to 6 are all the Helper can add. The factory certificate of FortiADC (`CN=FortiADCVM`, no SAN, `CA:FALSE`, issued by `fortinet-subca`, which the device does not send in the chain) fails the name check even with an enrolled CA; install a certificate with a SAN issued by your own CA.
- It does not show the full chain or the reason a particular client rejected it. Handshake counters say how many failed, not when or for which client.

## 5. A Wi-Fi client has no connectivity

You see: one wireless client connects to the SSID but gets no address or no traffic.

What the Helper can establish here is whether the client got a DHCP lease and whether the firewall has an ARP entry for it. It cannot show whether the client is associated now, its signal, or which AP it is on right now (see What it cannot do).

1. Address: `ssh_read(..., query="dhcp_leases", parameters={"interface": "<SSID interface>"})`. When `read_inventory.interfaces` lists more than one interface and you do not know which one serves the SSID, find it first with step 3. The interface must be listed in `read_inventory.interfaces` of `target_scope`; without the `interface` parameter the call is refused with the generic `-32009` scope error. A lease shows the IP, MAC and host name association; it does not prove the client is connected now. On FortiOS 8.0.2 the lease list also has `SSID` and `AP` columns (the AP serial); like the lease itself, they do not prove the client is associated now. No lease for the client's MAC: the client has no address from this interface; whether it associated and authenticated is not visible to the Helper, so continue outside the Helper as below.
2. Layer 2 on the firewall: `query="arp_table"`. Look for the leased IP on the SSID interface; `Age(min)` shows in minutes how long ago the entry was refreshed; `0` means within the last minute. The `Hardware Addr` must be the MAC from the lease. Lease plus a fresh ARP entry: the client reached the firewall at layer 2, so look at policy and routing with section 1 (step 2 onward), using the leased IP as the source and the destination and port the user tried. That needs `route_lookup` and `policy_lookup_ipv4` in the target's `enabled_queries` and the leased IP in `addresses`; a target that only lists Wi-Fi and switch queries refuses them as `policy_scope`. Then the Helper ends at "layer 2 reached": check policy and routing for that IP on the FortiGate itself, or ask the inventory maintainer to enroll those queries and the address. Lease but no ARP entry: the client does not answer on the SSID now; association and signal must be checked outside the Helper.
3. Which VLAN the SSID uses: `config_read(target, platform="fortios", section="wireless-controller vap", redaction="full")`, and `section="system interface"` with `redaction="full"` to map the interface to its VLAN ID. A VAP without a VLAN ID does not establish the client VLAN. An SSID interface with `set type vap-switch`, its own `set ip` and no `set vlanid` (as measured on FortiOS 8.0.2) is the interface to use in step 1.
4. AP uplink through a FortiSwitch: `ssh_read(..., query="managed_switch_mac", parameters={"managed_switch": "<enrolled serial>"})` and `managed_switch_lldp` with the same parameter; LLDP lists on each switch port the FortiAP model (for example `FortiAP-231K`) and, as `Port-ID`, the AP's MAC address, not its serial. The Helper cannot map the AP serial from the lease to a switch port. When the APs are of different models, the serial prefix is a hint (`FP23JK...` is a `FortiAP-23JK`); otherwise match serial to port on the FortiGate itself. If you have to mask serial numbers, keep the model prefix (the first six characters) so this hint survives. Read LLDP on every enrolled switch: an AP model from the lease that appears on no switch port (in the lab a `FP23JK` AP appeared in the lease while LLDP on both switches showed only `FortiAP-231K`, and one port was `Up` with `-` as device name) is connected where the Helper cannot see it, or does not send LLDP; locate it outside the Helper. `config_read(..., section="switch-controller managed-switch", redaction="full")` shows the port VLANs.

What it cannot do:

- The wireless controller queries `wifi_clients`, `wifi_client_detail`, `wifi_access_points`, `wifi_ap_detail` and `wifi_ssid_mapping` are refused for read-only accounts on FortiOS 7.6.8 and on FortiGate-80F 8.0.2 build 0251 (also with `wifi read` and `cli-diagnose enable` in the profile): the call returns `ok: false`, `error_code: device_cli_error` and the device output `command parse error before 'wireless-controller'` / `Command fail. Return code -61`. [Read-only accounts](../components/netops-helper/docs/read-only-accounts.md) document these queries as not supported, and a read-only account is refused even when a target lists them in `enabled_queries`. For a read-only target do not call them and do not enable them. Enrollment still accepts them for a read-only account (`configure helper` only prints a warning per query), so `target_scope` can list them; when it also shows `account_role: "read-only"`, the calls still fail as above: skip them and continue with steps 1 to 4. They can be read only through a target enrolled as `admin-bounded`/`catalogue` whose account profile has `wifi read-write` and `cli-diagnose enable` (measured on the FortiGate-80F 8.0.2 build 0251: with `wifi read-write` and `cli-diagnose enable` all five queries return data, with `wifi read` and `cli-diagnose enable` they return `-61`, and without `cli-diagnose` they return `Unknown action 0`). With a read-only target the Helper cannot show station association, signal or the AP a client is on now, and it does not tell whether the cause is the account profile or the device.
- After the Helper: check association, signal and the AP of the client's MAC on the FortiGate itself or on the client device; the Helper cannot verify which administrator profile may read these views. Bring the MAC, leased IP and AP serial from steps 1 and 2, and the switch port from step 4 if you could match it.
- `config_read` needs `config_access` `read` and FortiOS 7.6.8 build 3744 or 8.0.2 build 0251; see [Helper tools](../components/netops-helper/docs/tools.md).
- Wi-Fi passphrases stay redacted. The Helper cannot disconnect a client or change an SSID.

## Building or testing from source

- `docker build` fails with `TLS: server certificate not trusted` from `apk` or with pip `(from versions: none)` behind a proxy or firewall that decrypts TLS: pass the inspection CA as the BuildKit secret `extra_ca`; see [Build behind TLS inspection](testing-1.0.md#build-behind-tls-inspection).
- The collector seal prints `"reason": "seal-refused"` in a checkout made under `umask 0002`: see [Seal refused in a checkout made under umask 0002](testing-1.0.md#seal-refused-in-a-checkout-made-under-umask-0002).
