# NetOps changelog

## 1.0.13 - 2026-11-23

The date marks the integration of these changes.

For the release notes of NetOps 1.0.7 through 1.0.12: Editorial change after release: lab identifiers removed, no change in content. The notes of NetOps 1.0.12 also correct two items after release: the Fortinet SSH item (the Auditor evaluates FortiADC exports and does not collect FortiADC over SSH, and FortiOS and FortiADC SSH require `host_key`) and the client acceptance, which is now attributed to the NetOps 1.0.12 image instead of the release candidate.

- Update the pinned Alpine 3.24 base and CI to Python 3.15.2, with FastMCP 4.2.4, MCP 2.3.0, Starlette 1.10.0, Uvicorn 0.54.0 and PySNMP 7.1.33.
- Auditor adds rule catalogs for Cisco IOS and IOS XE (`cisco-ios`, 22 rules), Cisco NX-OS (`cisco-nxos`, 19), Arista EOS (`arista-eos`, 20) and Juniper Junos (`juniper-junos`, 19), read from a file or a pinned SSH collection, and extends FortiOS to 43 rules (37 in 1.0.12) and ExtremeXOS to 24 (9): management access, AAA, SNMP, NTP, syslog, discovery, Layer 2 controls and unused ports. A rule that depends on a default the device does not print is evaluated only when the collection proves the complete output, a readable software version and, on NX-OS, EOS and Junos, the full role of the collecting session; otherwise it stays `not-evaluated` with its reason, and `coverage.counts` reports the evaluated, not-evaluated and unsupported rules. A snapshot with an unterminated ExtremeXOS UPM profile leaves every rule `not-evaluated`. FortiOS SSH collection also reads `get system status`, `show system admin`, `show log syslogd setting` and targeted `show full-configuration <section>` in the held session and advances the pager there without changing the console settings. Site-specific checks use `audit_intent`, which `auditor import-policy` now also imports (FortiOS and EXOS policies with intent, intent-only documents for IOS, NX-OS, EOS and Junos; FortiADC is not supported by the import). `audit_status`, `list_rules`, `rule_detail` and `findings_summary` accept an optional `platform`. SNMP evidence omits community and key values. Verified live, read only, with an installed development build of the 1.0.13 source through its HTTPS MCP endpoint and a full account on a FortiGate-60F with FortiOS 7.6.8, an X440-G2 and an EXOS-VM, IOL XE 17.18.2, a Nexus 9300v with NX-OS 9.3(12), cEOSLab 4.36.1F and vJunos-switch 26.2R1.7, with findings compared against the device CLI. On the Nexus 9300v, 18 of the 19 rules were evaluated; the lockout rule stayed `not-evaluated` because the collection could not prove lockout visibility. A collection with a read-only ExtremeXOS account was refused and stored no run.
- Helper adds [`network_overview`](components/netops-helper/docs/network-overview.md) for a paginated operational snapshot of enrolled FortiGate devices (including observations of managed FortiSwitches and FortiAPs where available), ExtremeXOS, Cisco IOS, IOS XE and NX-OS, Arista EOS, Juniper Junos, Ruckus Unleashed, FortiADC and Linux targets. It reports read coverage per device and gives reasons for partial results. Calls default to a shared budget of 45 seconds (configurable from 5 to 120 seconds), with up to four targets read concurrently, at most 10 seconds per read and 30 seconds per target. Without `limit`, a page holds at most four targets and uses one parallel round under the shared 45-second default budget; if time runs out, the response reports incomplete coverage.
- Resources: `compose.yaml` takes the container memory limit from the new `NETOPS_MEMORY` (default `1g`, as before), listed in `env.example` beside `NETOPS_CPUS`. The README states the minimum of 2 vCPU, 2 GiB RAM and 2 GiB disk; the quickstart also states what to raise on a stronger host: `NETOPS_CPUS` for the container CPU quota, `NETOPS_MEMORY` for container memory and the local audit budget for a longer history.
- Security: every Admin apply requires the approved preview's `plan_sha256` (MCP `expected_plan_sha256`, CLI `--expect-plan-sha256`): every profile change on every platform and table (single change, batch, cycle and clear), a schema transaction (`admin_schema_apply` now takes `expected_plan_sha256`, the `plan_sha256` of `admin_schema_preview`; before, it refused a hash) and the deprecated FortiADC operator commands `pool-member`, `pool-member-add` and `pool-member-remove` (new `--preview` prints the hash; the write needs `--expect-plan-sha256`). Without the hash the apply is refused before the device is contacted with `plan_changed`; the operations with their own code keep it: `clear_preview_required`, `eos_save_preview_required`, `nxos_save_preview_required`, `ios_save_preview_required`, `exos_save_preview_required`, `fortios_policy_preview_required`, `fortios_nat_preview_required`, `fortios_ipsec_preview_required` and `fortiadc_certificate_preview_required`. Before, this depended on the platform and table. Undo (bound to its own undo preview) and the enrollment self-test are unchanged. The `plan_sha256` of the deprecated FortiADC commands binds the configured target (alias, address, SSH port and host key fingerprint) and every pool member with its settings, including the real server behind it; for a request that changes the member, their `--preview` refuses an HA secondary or a primary without a verified synchronized secondary, as the write does.
- Upgrade documentation: the README and the quickstart recommend one procedure, a clean installation of the new version and a restore of the backup of the immediately preceding version; the quickstart states that skipping a version and a downgrade are not supported. The upgrade guide is reduced to backup, clean installation, restore and a check; historical variants are removed.
- Admin disabled profiles: `admin doctor` lists their tables as refused with `profile_not_measured` instead of `(untested on FIRMWARE)`. A Junos PoE cycle apply without the preview hash reports `profile_not_measured` instead of `plan_changed`. The precheck of a measured profile reads `profile measured on firmware X; the measurement covers the variants documented for this profile, not every variant of the request`. The README and the Admin documentation name the disabled operations on each platform and the refused undo of an earlier change on a disabled profile, with the manual return.
- Admin FortiOS: new tables on FortiOS 7.6.8 build3744 through a shared table registry: DHCP servers and their address ranges, the system DNS servers (opt-in) and the syslog settings (`system dns` and `log syslogd setting` are update only), service groups, recurring and one-time schedules, IPv6 address objects (`firewall address6`, including prefixes, ranges and FQDNs), IPv6 address groups (`firewall addrgrp6`) and opt-in IPv6 static routes (`router static6`). Each table was measured live on a FortiGate 60F with apply under the approved preview's hash, readback by the separate check account and undo. Apply without the hash is refused before the device is contacted (`fortios_service_preview_required`, `fortios_object_preview_required`), as for every Admin apply (see Security). Enabling, disabling or changing an enabled DHCP server or one of its ranges, changing a DNS server or the target of an enabled syslog, and changing an object that an active firewall policy uses, also through a group, need `endpoint_impact` naming the key (`-` for a single-section table). Ranges stay inside the subnet of their interface and overlap no other DHCP range on the same interface, no VIP external address and no IP pool range (`fortios_dhcp_range_conflict`); DNS over TLS or HTTPS, syslog over TLS, DHCP options, dynamic DNS and VCI matching are never managed and refuse every change by name (`fortios_service_scope`); a referenced object is not deleted (`fortios_object_referenced`). Changes to IPv6 address objects and groups that affect an enabled firewall policy's IPv6 match need `endpoint_impact`; Admin follows group memberships, including nested groups, and refuses address or membership changes when it finds a reference outside group membership or the IPv6 match fields of `firewall policy`, which includes `local-in-policy6`. Admin refuses writes involving `::/0` address objects or default routes, and IPv6 route changes require IPv4 management addresses and must avoid the protected management path. Undo checks the identity of the object before it writes: undo of a create needs the UUID read back after the create (an object of the same name created again outside Admin is refused) or, for a table without UUIDs, the same key and attributes; undo of a delete creates the object again, and FortiOS assigns a new UUID. The preview also plans the undo and refuses a change whose undo could not be sent or would not restore the state before. On FortiOS 8.0.1 and later no REST inverse of these tables is verified, so they are refused before any write (`safeguard_no_rest_inverse`). The hashes and the redaction of configurations with secrets are unchanged.

Platforms named in this section: FG-60F is a FortiGate-60F with FortiOS 7.6.8 build3744 and a managed FortiSwitch 108E series (S108EN) without PoE; the FG-80F HA pair is an HA pair of FortiGate-80F with FortiOS 8.0.2 build0251 and two FortiSwitch 8.0.1; the FortiADC is a standalone FortiADC-KVM 7.6.7 build0676 VM; for ExtremeXOS an X440-G2-12P and an X435-8P-4S with 33.7.1.6-patch1-11 and two EXOS-VM 33.6.1.14, and, read only, two further ExtremeXOS 33.7.1.6-patch1-11 switches; for Cisco IOSv 15.9(3)M12, IOSvL2 15.2(20200924:215240), IOL XE 17.18.2, IOL-L2 XE 17.18.2 and three Nexus 9300v with NX-OS 9.3(12) (a single node and a two-node pair); for Ruckus an R610 on Ruckus Unleashed 200.15.6.212.27; for Arista three cEOSLab 4.36.1F (a single node and a two-node pair); for Juniper one vJunos-switch 26.2R1.7. ### Cross-cutting

- Untested OS versions warn instead of refusing. Admin no longer refuses a change only because the firmware is not among the tested versions of its profile; the former family rule (any FortiOS 7.6.x or ExtremeXOS 33.7.x build) is removed, and only the listed builds count as tested. The plan, preview, result, status and `admin doctor` carry `firmware_support` (`status`, `tested_versions`, `message`), the start audit record stores `firmware_tested` and a notification adds a warning; an untested status is part of `plan_sha256`, so the person approves the warning with the plan. The FortiOS schema-transaction workflow still requires its exact build. Helper reads and diagnostics of FortiOS and FortiADC and `config_read` of ExtremeXOS (also images without a patch level), Cisco IOS, IOS XE, NX-OS and Arista EOS return their data with the same `firmware_support` and a `firmware_untested` warning. The Auditor FortiADC catalog evaluates its rules on another FortiADC version or build and reports it with the info rule `fortiadc.scope.untested-version`; another product stays out of scope. Device identity, account rights, argument validation, device capabilities and write safeguards are still checked; on FortiOS 8.0.1 and later, the webhook safeguard refuses configuration profile changes to tables without a REST inverse (`safeguard_no_rest_inverse`), while DHCP reservations now have one. The warning was seen live with `triage_flow` on the FG-60F and `config_read` on IOSvL2 and EXOS-VM 33.6.1.14, and in further live reads with a narrowed list of tested versions; the Auditor rule is covered by automated tests only.
- Fortinet SSH: Helper and Admin open one held OpenSSH session per FortiOS or FortiADC operation and account (Admin: one for the write account and one for the check account). Auditor SSH collection uses a held session for FortiOS only. The Auditor evaluates FortiADC configuration exports. These SSH paths use enrolled host keys without scanning. FortiOS and FortiADC SSH require the public key in the device field `host_key` (`<type> <base64>`, matching `host_key_fingerprint`); a missing key (`missing Fortinet public host key; add host_key at enrollment`), a malformed key or a fingerprint mismatch is refused with its own error before the SSH connection is opened and before any credential is sent (a role can read its own vault earlier). OpenSSH failures before login are reported as `auth`, `host_key`, `negotiation` or `disconnected`. After a lost Helper diagnostic session, one fresh pinned session restores the device-side filter or option and checks the cleanup; a lost FortiADC write is returned by `admin recover` with a fresh session. Verified live on the FG-60F (Admin enrollment, apply, undo, a lost write session and `admin recover`) and on the FortiADC (Helper and Admin), with no key scan.
- Approval hashes: as in 1.0.11, an apply whose fresh plan differs from the approved one is refused with `plan_changed` before any write, with the approved (`expected`) and the fresh (`actual`) `plan_sha256` in `reason_details` for ordinary apply; MCP undo and the initial ticketed save check return only `expected`, while the later pre-write save recheck can return the code alone. Every operational clear and save, profile batches and Ruckus changes apply only with the approved `plan_sha256` (`--expect-plan-sha256`, MCP `expected_plan_sha256`) and are refused without it (`plan_changed` or a specific `*_preview_required` code); for single configuration changes this depends on the table and the impact (for example FortiOS firewall policy, NAT, DHCP reservation, DNS entry, Phase 2 and FortiSwitch ports, FortiADC certificate replacement, ACL tables, or `endpoint_impact` on ExtremeXOS, NX-OS and Junos).
- Profile batches: on NX-OS, EOS, Junos, FortiOS, IOS and IOS XE, `table=batch`, `op=update`, `key=batch` plans 2 to 32 profile changes against each preceding predicted configuration with one approval hash, writes them under one device safeguard and returns every step with its result; a failed step starts the return of the whole batch (NX-OS timed configuration return, EOS session commit timer, Junos `commit confirmed`, IOS archive revert timer, FortiOS automation stitch with the inverse of every step in reverse order); Admin verifies the return and ends `unknown` or `revert-failed` when it cannot confirm the starting state. A confirmed batch can be undone in reverse step order. A FortiOS batch holds addresses, address groups and at most one firewall policy and needs the CLI-script safeguard, so it is refused on FortiOS 8.0.1 and later (webhook safeguard). Verified live on the single Nexus 9300v, the three cEOS, vJunos, IOSvL2/IOSv, IOL XE/IOL-L2 XE and the FG-60F.
- Admin MCP undo and unblock: the new tools `admin_undo`, `admin_unblock_preview` and `admin_unblock` are off (`mcp_undo_disabled`) unless the Admin configuration sets `mcp_undo`. `admin_undo` needs the hash of the last `admin_undo_preview` this server issued for the device, once and within 600 seconds while the journal of the device is unchanged. `admin_unblock_preview` reads the device through both accounts and offers `unblock_sha256` only when the change is fully on the device; a device in the state before, a leftover safeguard, a changed account list, an unfinished or `revert-failed` operation, a schema transaction or a profile batch stays with the operator commands `admin recover` and `admin unblock`. Verified live on the FG-60F; `revert-failed` and schema transactions are covered by automated tests only.
- Private encrypted backups: the operator commands `admin backup` (FortiOS global backup over REST with a pinned certificate), `admin backup-eos`, `admin backup-nxos`, `admin backup-xe` and `admin backup-xe-status`, `admin backup-ios` and `admin backup-ios-status`, `admin backup-exos`, `admin backup-junos` (optionally saving the rescue configuration), the unseal commands `admin backup-unseal --platform fortios|eos|nxos|ios|xe`, `admin backup-exos-unseal` and `admin backup-junos-unseal`, `admin backup-nxos --status`, and `admin restore-junos`. Confirmed exports write AES-GCM files with `NETOPS_BACKUP_KEY` into a private directory on the backup host, keep the last 7 per target by default and require the `plan_sha256` of their preview; the status commands authenticate a local archive and unseal extracts it to a private file. `restore-junos` needs its own approved preview, keeps an encrypted copy of the current configuration and uses `load override` under `commit confirmed`. These commands run outside enrollment and the change journal. The contents never pass through MCP. Verified live on the lab devices; `restore-junos` on vJunos.
- Helper configuration: `config_read` keeps an approved baseline across restarts and new processes and compares later reads with it (verified live on IOSv, IOSvL2 and the X440) and keeps a local history of redacted snapshots (`recent_snapshots`); `config_diff` also compares running and startup configuration on IOS, IOS XE, NX-OS and EOS; FortiADC full reads can be kept as encrypted archives (`NETOPS_FORTIADC_BACKUP_KEY_FILE` in `compose.yaml`).
- Helper counters: pass the `counter_baseline` of a complete `interface_errors` read as `baseline` of the next read to get per-port deltas and the interval; a reset or wrap lists the affected counters in `counter_reset_or_wrap` and sets their deltas to `null`. Zero deltas were verified live on the X435, X440, IOSv and IOSvL2; nonzero deltas, resets, wraps and the managed FortiSwitch are covered by automated tests only.
- Inventory intent check: the new operator command `netops check-intent PLAN --inventory FILE --endpoint URL --ca FILE --token-file FILE` reads the expected LAG members, VLAN membership and PoE power interval of the inventory plan `helper.intent.PLAN` through the public Helper endpoint and exits with 0 (`pass`), 1 (`fail`) or 2 (`incomplete`). It is a one-time run; schedule it outside NetOps. With `--notify` and a webhook in `NETOPS_DISCORD_WEBHOOK`, an overall `fail` makes one delivery attempt to Discord, and `notification` reports its result. Verified live through the public HTTPS MCP endpoint on the two EXOS-VMs, the X440 and the FG-80F HA pair, and through the SSH transport of Helper on IOSvL2, with delivery switched off; the Discord delivery is covered by automated tests with a fake HTTP server only.
- `locate_endpoint` finds a host by name as well (DHCP lease → ARP → FDB) and follows a wireless client to its access point and the switch port of that access point; it reports an incomplete chain instead of guessing. Verified live on the FG-80F HA pair, the two EXOS-VMs and the X440.
- Classic IOS: when Admin verifies that its own revert timer restored the managed object and finds the original `banner exec` missing, Admin ends with `unknown` and `exec_banner_lost`, blocks the device and writes nothing more; restore the banner by hand, unblock the device and repeat the operation or enrollment. The enrollment self-test ends the same way and issues no enrollment. Verified live on IOSvL2 with the banner removed on purpose after the device return; the original loss of the banner could not be reproduced live.
- The qualification and CI engine tests now give the test tmpfs `/pytmp` 2 GiB instead of 512 MiB, because the Admin suite ended with `ENOSPC` in 512 MiB; the qualification documentation and the minimum requirements state it.

### Upgrade from 1.0.11

- Enrollments made with 1.0.11 are not valid in 1.0.12: an enrollment is bound to the enrollment protocol and to the SHA-256 of every Admin profile file, and 1.0.12 adds 158 profile files and changes 19, so every Admin device needs `admin enroll` again after the upgrade; until then Admin refuses its changes with `enrollment_required`.
- FortiOS and FortiADC: add `host_key` (the OpenSSH public key from a trusted known_hosts entry, matching `host_key_fingerprint`) to the device in the Helper inventory and the Admin configuration, and for FortiOS also in the Auditor collection inventory (the Auditor collects FortiADC as an export, not over SSH); NetOps no longer scans the key, and without `host_key` the operation stops.
- Admin: FortiOS firewall policy, DHCP reservation and DNS entry changes and ExtremeXOS port changes with `endpoint_impact` now need the approved `plan_sha256`; add `--expect-plan-sha256` (MCP `expected_plan_sha256`) to scripts that apply them. A preview made with 1.0.11 on a FortiOS 7.6.x or ExtremeXOS 33.7.x build that is not listed in the profile is untested now and its hash differs; run a new preview.
- Upgrade only from 1.0.11 (upgrade 1.0.10 to 1.0.11 first) by restoring its backup into a separate 1.0.12 instance, as described in the [release notes](release/notes-1.0.12.md#upgrade-from-1011). The first start converts only the recorded product version from 1.0.11 to 1.0.12 and writes an `instance_start` audit record with `upgrade` from 1.0.11 to 1.0.12; do not run `init` on the restored state.
- Rollback: stop 1.0.12, preserve its audit records written after the backup and start the unchanged 1.0.11 instance ([Rollback](docs/quickstart-1.0.md#rollback)).
