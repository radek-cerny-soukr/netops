NetOps 1.0.10 follows NetOps 1.0.9. It brings Arista EOS, FortiADC, Cisco IOS, IOS XE, NX-OS and Juniper Junos into the common Admin, makes FortiOS `config_diff` line-based, binds Admin `plan_sha256` to the device and firmware, runs the Auditor store in WAL mode, tightens the ExtremeXOS PoE cycle safeguard budget and recover, and hides typed Cisco-style hashes and whole account values in responses while keeping everything that 1.0.8 hid hidden.

Editorial change after release: lab identifiers removed, no change in content.

## Changes in 1.0.10

### Added

- Admin supports Arista EOS (cEOSLab 4.36.1F) through the shared Admin path: preview with `plan_sha256`, enrollment, journal and audit, check-account readback, undo, recover and the existing MCP tools (no new tool). Operations: interface description, admin up/down and access VLAN, written line by line through `configure terminal` under the device-side `commit timer` of an empty EOS configuration session that Admin commits before the change; the timer reverts an unconfirmed change. Admin needs privilege 15 without `enable` and a read-only check account without write rights; see [Admin configuration](../docs/admin-configuration.md). A change of the admin state of a port, in both directions, is refused on trunks/uplinks, LAG members, routed ports, management interfaces, ports with an LLDP neighbour or learned MAC addresses. Measured on one lab switch (GNS3 cEOSLab, 2026-11-15): 13 of 13 end-to-end CLI scenarios; the MCP tools were not called live. A later fix (the same port checks also for admin up) is covered by automated tests only and was not repeated live. The configuration session `commit timer` return was measured at 120 s after a missed confirmation; behaviour after a device reload, `aaa authorization` variants other than the lab one and `enable` password use are not measured.
- Admin supports FortiADC (load-balance pool member state, add and remove) through the shared Admin path: preview with `plan_sha256`, enrollment (`admin enroll --probe POOL:MEMBER:REAL_SERVER:PORT`), journal, audit, check-account readback, undo, recover and doctor. FortiADC 7.6.7 has no on-device timed return, so an unconfirmed write is reverted by Admin itself with an inverse write in the same run, or by `admin recover` after an interruption; if the Admin process or the management path is lost after a write, nothing on the device reverts the change until recover runs. A virtual server must keep a healthy enabled member (`no_healthy_member`). Measured on FortiADC-KVM 7.6.7 build0676 (standalone lab VM, 2026-11-16): 13 of 13 end-to-end scenarios including SIGKILL and recover; the configuration hash was equal before and after. A timed return through `alert-policy` was found in documentation only and was not measured. Auditor rules are not evaluated for FortiADC in Admin (`audit_unevaluated`). The older `pool-member*` CLI keeps its output and is marked deprecated.
- Admin refuses an ExtremeXOS PoE cycle whose safeguard budget is too short: the cycle needs 175 s plus `confirm_margin_seconds` below `safeguard_seconds`, checked from the configuration in preview/apply and again against the switch clock before the power is cut (`safeguard_margin_insufficient`; unreadable clock: `device_clock_unreadable`). With the defaults (180 s, margin 45) a PoE cycle is now refused; set `safeguard_seconds` to at least 221. The 175 s is a conservative budget from measured read times, not a measured duration.
- `admin recover` of an interrupted ExtremeXOS PoE cycle with the safeguard still installed confirms the cycle only when the journal and fresh reads prove it (power off, on, configuration equal to the state before); otherwise the safeguard fires and the result is `reverted` (`PoE cycle not proven`). Covered by automated tests with measured device outputs; no live cycle was run.
- Admin supports Cisco IOS 15.x and IOS XE 17.x (platforms `ios` and `iosxe`, one adapter) through the shared Admin path: preview with `plan_sha256`, enrollment, journal and audit, check-account readback, undo, recover and the existing MCP tools (no new tool). Operations: interface description and admin state, and the access VLAN on the switch images, written line by line under the device revert timer (`configure terminal revert timer`), whose expiry returns the whole running configuration; confirmation is `configure confirm`, and a failed write or readback is returned at once with `configure revert now`. The profiles list exact versions, measured on GNS3 lab images only: IOSv 15.9(3)M12, IOSvL2 15.2(20200924:215240), IOL XE 17.18.2 and IOL-L2 XE 17.18.2; no hardware platform was measured. The device needs the configuration archive (`archive_not_configured`), the write account privilege 15 at login (Admin never sends `enable`) and a separate privilege-1 check account; see [Admin configuration](../docs/admin-configuration.md#cisco-ios-and-ios-xe-interface-description-admin-state-and-access-vlan). The timer is treated as Admin's own only with proof from Admin's own session, its time left is counted on the monotonic clock of Admin (the device clock is never read), and waiting and `admin recover` read the timer state. `safeguard_seconds` is rounded up to whole minutes, at least 2 (2–15). Measured in the GNS3 lab on 2026-11-16: the operator command line scenarios on all four nodes (source `3dd813e`) and, after later fixes (source `f0e8b0d`), on IOSvL2 Gi1/0 and IOL XE Et0/2: enrollment self-test, apply with `--expect-plan-sha256` and undo, a forced readback failure returned with `configure revert now`, SIGKILL and `admin recover`; the running configuration was equal before and after. The MCP tools were not called live.
- Admin supports Cisco NX-OS 9.3(12) (platform `nxos`) through the shared Admin path: preview with `plan_sha256`, enrollment, journal and audit, check-account readback, undo, recover and the existing MCP tools (no new tool). Operations: interface description, admin state and access VLAN. NX-OS 9.3(12) has no commit timer, so the safeguard is a checkpoint with a one-time `feature scheduler` job that rolls the whole running configuration back at its minute; `feature scheduler` must be enabled once by the switch administrator (`scheduler_feature_disabled` otherwise), and Admin never enables or disables it. A change that Admin finds unverified is returned at once by `configure replace` of a copy of the running configuration saved before the change. Admin removes only objects whose creating line its own session saw accepted, removes an unverified or interrupted installation at once (the pending schedule first) and never reads the device clock. With the default margin of 45 s, `safeguard_seconds` must be at least 180. Write account measured with role `network-admin`, check account with `network-operator`; see [Admin configuration](../docs/admin-configuration.md#cisco-nx-os-interface-description-admin-state-and-access-vlan). Measured on a Nexus 9000v (N9K-C9300v, virtual) with NX-OS 9.3(12) in the GNS3 lab on 2026-11-16: the operator command line scenarios with source `a36fd05` and, after later fixes (source `7af8285`), 9 of 9 scenarios on Ethernet1/48: `doctor`, enrollment self-test, apply with `--expect-plan-sha256` and undo, a forced readback failure returned by `configure replace`, SIGKILL and `admin recover`; the normalized running and startup configurations were equal before and after. The MCP tools were not called live.
- Admin supports Juniper Junos 26.2R1.7 on ELS switches (platform `junos`) through the shared Admin path: preview with `plan_sha256`, enrollment, journal and audit, check-account readback, undo, recover and the existing MCP tools (no new tool). Operations: interface description, admin state and access VLAN by VLAN name; the profiles list `26.2R1.7` as an exact version, so every other Junos release is refused before any write. Admin changes the configuration only in `configure exclusive` under a device-side `commit confirmed 10` safeguard: an empty safeguard commit, the change committed with `commit confirmed 10` (which restarts the timer) and, after the readback of the separate check account, a confirmation commit; an unconfirmed timer returns the whole configuration, including a commit of someone else in the window. The timer is treated as Admin's own only with proof from Admin's own session (its own commit rows in `show system commit`, recorded as the head of its timer), a timer of someone else is never committed over, and its time left is counted on the monotonic clock of Admin (the device clock is never read). A failed write or readback is returned at once by the inverse lines of the plan committed under the own timer, then confirmed only when a fresh snapshot equals the state before; this holds also when the first read after the own change commit failed and a second read proves that commit. Waiting and `admin recover` decide by the commit history only; recover of an interrupted operation sends no commit and waits for the expiry. The write account needs the login-class permissions `configure`, `view` and `view-configuration` (`write_account_privilege` otherwise), the check account the built-in class `read-only`; see [Admin configuration](../docs/admin-configuration.md#juniper-junos-interface-description-admin-state-and-access-vlan). Measured on vJunos-switch 26.2R1.7 (ELS, GNS3 lab, test port ge-0/0/2) on 2026-11-16: the operator command line scenarios with sources `5cb02e9`, `2a78465` and `65dbe31` (`doctor`, enrollment self-test, description apply with `--expect-plan-sha256` and undo, admin down and up, access VLAN and its undo, SIGKILL and `admin recover`, refusals `vlan_missing` and `port_management_interface` without a write) and, after later fixes (source `4699b25`), enrollment self-test, description apply and undo, a forced readback failure returned by the immediate inverse return about 4.5 minutes before the expiry, and SIGKILL with `admin recover`; the configuration was equal before and after both runs. A later fix (source `6a39724`: taking the own change commit as the head after a failed read) is covered by automated tests only and was not run on the device. The MCP tools were not called live.

### Changed and fixed

- FortiOS `config_diff` uses the line comparison (Myers) of the other platforms with the same limits and `config_diff_limit_exceeded`, instead of positional comparison. In the full profile, adding or removing a secret line is one `+`/`-` line, and the numbering of credential markers does not create false changes; a different firmware, profile or `include_defaults` is still `config_snapshot_incomparable`. FortiADC keeps positional comparison. Verified with the public `config_read` to `config_diff` path on real FortiGate 80F 8.0.2 build0251 captures and fake transport; no device was used.
- Admin `plan_sha256` of profile plans now includes the device alias, platform and firmware, so a plan approved for one device or firmware is refused (`plan_changed`) on another. FortiOS schema transactions have their own digest and are unchanged. Journal records written by earlier versions stay readable for verify, recover and undo.
- Auditor store runs in SQLite WAL mode. The first writer open converts an existing store once, without data loss; MCP reads use one read transaction and no longer copy the whole store, so memory does not depend on the store size and a long read does not block the COMMIT of a running `collect`. The store directory may hold `store.sqlite-wal` and `-shm`; they belong to the store and to its backup. The store must be on a local file system.
- Admin ExtremeXOS port admin state: enabling a port now gets the same checks as disabling it, including the LLDP and FDB reads. An enable that 1.0.9 accepted is refused on a trunk/uplink (`port_uplink`), a link aggregation member (`port_lag_member`), a member of a management VLAN of the audit policy (`port_management_vlan`), a port with an LLDP neighbour (`port_lldp_neighbor`) or learned MAC addresses (`port_learned_mac`), and when the VLAN membership, LLDP or FDB answer cannot be read completely (`port_usage_unreadable`). Covered by automated tests only; no live run of this change is claimed.
- Auditor instance lock on btrfs: when two subvolumes show the same inode, the lock holder is accepted only if its open descriptor is confirmed, otherwise `collect` through `docker compose exec` is refused; an overmount of the same depth uses the last `mountinfo` line.
- Response redaction hides typed Cisco-style hashes and whole account values. In `enable secret|password` and `username … secret|password` lines the hidden value is the one after the type: a number, an algorithm name (Arista EOS `enable password sha512 …`, also `sha256`, `scrypt`, `pbkdf2`, `md5`, `sha1`), any word directly followed by a `$…` hash, the value after `level N` and after IOS XE `algorithm-type …`; an `enable` line without a known type hides its first two tokens. This holds in plain text, after a prompt, inside JSON string values and in the Helper's standalone redaction; a bare wrapped `secret|password <algorithm> <hash>` line is hidden by the response chain. The account rules (`username`, `enable`, `tacacs-server`/`radius-server` keys, ExtremeXOS accounts) hide the whole value, not only the part before an anchor of another rule inside it. A JSON output whose string values hold such account lines keeps its structure and its other values instead of being withheld; it is still withheld where a legacy rule takes JSON punctuation, a neighbouring value, a number or a literal, or where a hidden range would be lost inside a nested JSON document. Every character that the released 1.0.8 redaction hid stays hidden on every path to the AI client (Helper redaction, response redaction, proxy and product), also in diagnostic output cut to `max_bytes`: where the new rules would leave such a character visible, the Helper or the proxy masks it as `<REDACTED>`. Verified with automated tests, including generated comparisons against the frozen 1.0.8 and 1.0.6 redaction chains; no device was used. See [Helper tools](../components/netops-helper/docs/tools.md#what-content_sha256-and-the-offsets-describe).
- Dependencies: Authlib 1.9.6 and PyJWT 2.15.1 (hash-locked); the dated assessments of two Python CVEs were rechecked on 2026-11-15 (no fixed 3.14 release). amd64 image build, self-test, unit tests and scan gate passed with no new finding; the arm64 evidence is left to the candidate Actions.
- Release tooling: the source gate accepts a truthful deferral of client acceptance to the candidate and requires a `Result` cell (`PASS`/`FAIL`) in the tested-clients table otherwise. One Auditor test that held a read lock now holds a writer lock to match WAL; product code unchanged.
- Documentation: quickstart (health check from `NETOPS_URL`, `curl -sS`/`-fsSLO`, copied-files verification, running-image digest check, `ca` in scripts, Docker 29 wording, Compose pull output), btrfs lock and WAL backup notes, Admin PoE and FortiADC exceptions, `plan_sha256` content, JSON account-line redaction contract, `audit.directory_lock` (no exactly-once syslog delivery), Debian 13 arm64 acceptance link.
- Update version metadata, the 1.0.9 → 1.0.10 upgrade pin and the upgrade guide ([Upgrade from 1.0.9](#upgrade-from-109)).

The classifier replay baseline (`components/netops-helper/tests/fixtures/output_status_baseline.json`) holds 1057 captured texts.

The MCP API changes of these items (the changed `admin_apply` description) are declared in `release/acceptance/api-changes-1.0.9-1.0.10.json`.

## Security

The security-related changes of 1.0.10 tighten what NetOps returns and bind approvals to the device; they do not add an arbitrary command or write path. Response redaction now also hides the hash after an algorithm name or another type word in `enable` lines, for example Arista EOS `enable password sha512 <hash>`; earlier releases left that hash visible in general outputs such as `ssh_read` (configuration captures with `config_read` return only allowlisted lines and were not affected). Account values are hidden as a whole, and every character that the released 1.0.8 redaction hid stays hidden on every path to the AI client, including diagnostic output cut to `max_bytes`; where the current chain cannot keep a JSON document's structure safely, the output is withheld instead of returned. Admin EOS, FortiADC, Cisco IOS, IOS XE, NX-OS and Junos writes go through the existing preview, `plan_sha256`, enrollment, journal and audit controls; EOS, FortiADC and IOS/IOS XE test outputs were checked for secrets (0 matches) before they were recorded. `plan_sha256` now identifies the device and firmware, so an approval cannot be replayed against another device. These notes do not assert the result of the review or scan of the 1.0.10 release candidate.

### Known dependency findings

Authlib 1.9.6 and PyJWT 2.15.1 are locked by hash. A local scan of the amd64 image built from the source with these dependency updates (2026-11-15) found the same 18 findings as before (Python 3.14.10, SQLite 3.53.4, BusyBox 1.37.0) and no new package or version; the assessments of the two Python CVEs were rechecked on 2026-11-15 (Python 3.14.11 not released). A written assessment is not a repair and not a claim of zero CVEs.

The findings and their assessments are those listed in the [1.0.9 release notes](notes-1.0.9.md#known-dependency-findings) unless the release scan shows otherwise. The arm64 image is built natively and scanned in the candidate Actions; the release scan of both architectures and the assessments covered by the signed checksum list are part of the candidate acceptance, and these notes do not assert their result.

## Upgrade from 1.0.9

Follow [Upgrade from the previous release](../docs/quickstart-1.0.md#upgrade-from-the-previous-release):

1. Check the 1.0.9 instance, stop it and create its backup and state manifest.
2. Download and verify the 1.0.10 release files. Prepare a separate instance directory and a new Compose project with the same server name and port, and download the 1.0.10 image.
3. Restore the backup into an empty target volume and compare it with the source manifest before the first start. Keep the original instance and backup.
4. Start the new instance. The first start converts only the recorded product version from 1.0.9 to 1.0.10 under the instance lock and writes an `instance_start` audit record with `upgrade` from 1.0.9 to 1.0.10. A second start skips conversion. CA, keys, token, role data and connection details are unchanged. The Auditor store is converted to WAL later, on its first writer open (below).

Do not run `init` on the restored state. Only 1.0.9 is accepted as the previous release; upgrade 1.0.8 to 1.0.9 first.

For rollback, stop 1.0.10, preserve its audit records written after the backup, and start the unchanged 1.0.9 instance; see [Rollback](../docs/quickstart-1.0.md#rollback). Its Auditor store is not converted to WAL, because only the restored copy is opened by 1.0.10. A direct downgrade of a converted volume is not supported; opening an Auditor store converted to WAL with 1.0.9 was not verified.

What changes for operators:

- Approved `plan_sha256` values from a 1.0.9 preview do not pass after the upgrade: `expected_plan_sha256` is refused with `plan_changed`. Run a new preview and approve its `plan_sha256`.
- The Auditor store converts to WAL on the first writer open (`collect`, `run`, `status`); a store restored from a 1.0.9 backup stays in the old mode until then. Backups of a stopped instance must keep `store.sqlite-wal`/`-shm` with `store.sqlite`; do not copy `store.sqlite` alone.
- Admin has new platforms in the common Admin: EOS, FortiADC, Cisco IOS, IOS XE, NX-OS and Junos; enroll each device (`admin enroll`) before use. FortiADC has no device-side timed return. IOS and IOS XE need the configuration archive; NX-OS needs `feature scheduler`, enabled once by the switch administrator, and `safeguard_seconds` of at least 180 with the default margin.
- Juniper Junos (platform `junos`) is a new Admin platform, 26.2R1.7 on ELS switches only: in the device entry set `safeguard_seconds` to 600, `confirm_margin_seconds` to at least 240 and `accounts`, and no `audit_policy` (the Auditor has no Junos rules); give the write account a login class with `configure`, `view` and `view-configuration` and the check account the class `read-only`; enroll the device (`admin enroll --probe IF`) before use.
- FortiOS `config_diff` is now line-based; diff output for the same snapshots differs from 1.0.9 where positional comparison produced shifted changes.
- ExtremeXOS PoE cycle needs `safeguard_seconds` of at least 221 with the default margin 45.
- Re-enroll every Admin device (`admin enroll`), FortiOS and ExtremeXOS included, before its first change after the upgrade. An enrollment is bound to the SHA-256 of every Admin profile file, and 1.0.10 adds profiles and changes profile texts (for example the ExtremeXOS PoE profile), so every 1.0.9 enrollment is refused with `enrollment_required`.
- ExtremeXOS: enabling a port is refused where disabling it is refused (uplink, LAG member, management VLAN, LLDP neighbour, learned MAC addresses, unreadable usage); an enable that 1.0.9 accepted on such a port is refused. Enable such a port on the switch itself if it is really intended.
- Response redaction output changes where the new rules apply: `enable secret sha512 <hash>` becomes `enable secret <REDACTED> <REDACTED>`, an `enable` line without a known type hides its first two tokens, account values are hidden as a whole, and text that 1.0.8 hid only in a later layer (for example `passwd [REDACTED]` after an account value) can appear as `passwd <REDACTED>`, because the Helper or the proxy masks it earlier. JSON outputs with account lines that were withheld before (`redaction could not be verified; output withheld`) are returned with the values hidden. Diagnostic output cut to `max_bytes` can hide more than before, in rare cases also JSON punctuation or a value that stays visible in the uncut output. Nothing that the 1.0.8 redaction hid becomes visible; adjust scripts that match exact redaction markers.
- Auditor lock on btrfs: see above; no action unless `collect` through `compose exec` is refused on btrfs.

## Known limitations

- Admin EOS: only the lab cEOSLab 4.36.1F was measured, through the CLI; MCP tools, device reload during a pending timer and other AAA variants were not measured.
- Admin FortiADC: no on-device timed return (see above); the snapshot covers pool, virtual server, real server and system admin only, and foreign administrator sessions are not read (`foreign_sessions_unreadable`).
- ExtremeXOS PoE: the 175 s budget and the interrupted-cycle recover are verified by automated tests only; no live cycle was run for 1.0.10.
- The Auditor WAL conversion was tested on a lab test machine with the Auditor suite; the Auditor suite on the final tree and the upgrade of a 1.0.9 store on an installed instance belong to the candidate acceptance and are not asserted here.
- Admin Cisco IOS and IOS XE: the revert timer is global for the device and has no owner identity. Any privilege-15 session can confirm, extend or return it, and Admin cannot check the timer and send `configure confirm` or `configure revert now` as one atomic step; a concurrent configuration session on the same device within those seconds is not prevented, so do not configure the device by other means during an Admin operation. A timer of 1 minute is too short for the measured read and write times, so the minimum is 2 minutes. GNS3 lab images only; a pending timer across a reload, other images and releases, and the MCP tools were not measured live. A refused installation because of a timer of another session, slow reads before the write and the per-line guard are verified with the simulated device of the unit tests only.
- Admin Cisco NX-OS: Nexus 9000v NX-OS 9.3(12) only; a physical Nexus 9000 and a pending job across a reload were not verified. The job has a granularity of one minute (the real delay is between M−1 and M minutes) and returns the whole running configuration, including a change of someone else made in the window. `configure replace ... commit-timeout` is not used: its automatic return left a changed access VLAN in place (measured). Enrollment takes up to M minutes plus about 3 minutes of cleanup. Admin cannot remove an object whose creating line got no answer, cannot tell apart a job of the same name created by someone else in the seconds between its name check and its own line, and cannot recover a job of an interrupted installation that already ran before its checkpoint held it; these end `unknown` with a manual procedure (`admin status`), and the last case needs `no feature scheduler` by the switch administrator. The drift of the NX-OS clock was not measured (the 2 % allowance comes from IOS). Interrupted installation phases, a foreign object of the same name, a slow device and a late line are verified with the simulated device of the unit tests only; the MCP tools were not called live.
- Admin Juniper Junos: vJunos-switch 26.2R1.7 (ELS) in the GNS3 lab only; physical EX switches, non-ELS Junos and routers (MX, SRX) are not measured and not supported. A pending `commit confirmed` is global for the device and has no owner identity: every commit of any session, also of the same account, confirms it, and another privileged session that commits within the seconds between Admin's last read and its commit line is not prevented, so do not configure the device by other means during an Admin operation. The expiry returns the whole configuration, including a commit of someone else in the timer window. The lab used the class `super-user` for the write account; a narrower login class was not created or verified, and the class in the documentation is only a recommendation. On the loaded lab a commit took up to about 4 minutes, a confirmed change 6-12 minutes and a change returned by the timer 16-21 minutes. Not measured live: the MCP tools, a pending timer across a reload, the drift of the vJunos clock (the 2 % allowance comes from IOS), a loss of the whole management path, and the final wait limit for the rollback proof. An unproven installation, a timer of someone else of the same account, a foreign commit right above the safeguard and the taking of the own change commit after a failed read are verified with the simulated device of the unit tests only.
- Response redaction: the Helper's standalone redaction of a text without an account rule returns the same text as 1.0.8 and leaves the rest to the proxy and the product, as 1.0.8 did. When diagnostic output is cut to `max_bytes` inside a block that only a later layer recognizes, for example in the END line of a private key, the body of that block can stay visible; 1.0.8 returns the same with the same limit. A bare `secret|password <algorithm> <hash>` line is left by the Helper's standalone redaction as in 1.0.8 and hidden by the proxy on the way to the client. In rare cases the masking that keeps the 1.0.8 floor takes the anchor of a new rule, so the new redaction does not apply there; the 1.0.8 floor still holds. A JSON output is still withheld in the cases named under Changed and fixed.
