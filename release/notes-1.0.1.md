NetOps 1.0.1 follows NetOps 1.0.0 and upgrades the state of an instance of NetOps 1.0.0. It is the same single product: one container image that runs the Helper, Auditor and Admin roles behind one audited HTTPS MCP endpoint. The syslog audit format changes incompatibly: if you use syslog audit, change the receiver before the first start of 1.0.1, as described below.

## Breaking change: syslog audit format

NetOps 1.0.1 sends every syslog audit record, including a small one, as numbered `netops-syslog-part/1` part envelopes instead of one message that holds the whole record. Each RFC 5424 message, header included, is at most 2048 bytes; the largest is 1618 bytes. Archives and tools that expect one JSON audit record per syslog message cannot use these messages unchanged.

- Before the first start of 1.0.1, configure on the receiver a dedicated, append-only part archive that takes only messages with the RFC 5424 APP-NAME `netops` and stores each original MSG byte string followed by one LF. Keep the archive of 1.0.0 full-record messages and the messages of other applications separate.
- Verify, as the receiver's service account, that the stored bytes equal the sent MSG, without added leading spaces, truncation or reformatting, before you rely on the archive.
- Do not empty the NetOps queue before the upgrade. The first start of 1.0.1 also sends the records still queued by 1.0.0, in the new part format.
- Configure the receiver to discard an incomplete frame left by a restart or a connection reset. A partial line, or a full NetOps 1.0 message stored in the part archive by mistake, makes the reconstruction of every record that completes only after it fail with exit status 2; records completed earlier report `late_invalid` (exit status 3).
- Read records from the part archive with the offline command `netops audit reassemble` (see below), not by parsing single messages.
- The data sent to the receiver grows: about 1.6× for the measured 8277-byte record; overhead varies with record size. In that measurement an 8277-byte record was sent as nine messages of 13256 bytes in total, 13300 bytes with their RFC 5425 length prefixes.

NetOps 1.0.1 no longer requires the enlarged receiver limits (`maxMessageSize`, `MaxFrameSize`) that 1.0.0 needed.

## Changes in 1.0.1

- Support Docker Engine in rootless mode on all supported host families and architectures, including the SELinux label of the rootless Docker data on Fedora, applied before the first start of the rootless daemon. Rootless mode was not qualified in 1.0.0.
- Send every syslog audit record as consecutive 1024-byte chunks of the original record, including its final LF. Each part carries the persistent record ID (32 lowercase hexadecimal characters), its zero-based part number, the number of parts and the SHA-256 of the whole record. The maximum record size stays at 8 MiB.
- Retry a failed syslog delivery with the complete records under the same record ID, part mapping and SHA-256. Only a successful TLS transport hand-over removes a batch from the queue, so an interrupted attempt can leave duplicate parts at the receiver. A successful delivery is a transport hand-over, not an acknowledgement that the receiver stored the record.
- Add the offline command `netops audit reassemble --record-id <32-lowercase-hex>`. It reads the part archive as JSON lines from standard input, needs no initialized instance, configuration, vault or running service, and does not change the source archive.
- Read each archive line up to a fixed limit; a longer line is an invalid row, an error before the record is complete and a `late_invalid` warning after it, so no single line can exhaust memory.
- Reassemble in the line order of the receiver archive. The first complete, consistent set of parts whose whole-record SHA-256 matches is frozen at the line that completes it. Exact duplicates of its parts from a retried delivery are accepted, and parts of other records are skipped. A later conflicting part, a later alternative set with the same record ID or a later invalid row cannot change the frozen record. Before the set is complete, conflicting parts or metadata and rows that are invalid or cannot be attributed to a record are errors.
- Report the result of `netops audit reassemble` by its exit status. Exit status 0: the record was reconstructed without findings. Exit status 3: standard output carries the same frozen record and standard error carries warnings, one compact ASCII JSON line each with exactly the fields `schema`, `code` and `line_number`; the schema is `netops-syslog-reassembly-warning/1`, the code is `late_conflict` for a valid part of the selected record that is inconsistent with the frozen set or `late_invalid` for a later row that is invalid or cannot be attributed, and `line_number` is the original line in the archive. Exit status 2: no record bytes are written on an argument, validation or input read error, also after the set was complete or warnings were reported; a failed write to standard output also ends with exit status 2 and can leave partial output.
- Treat exit status 3 as evidence that the archive was changed or damaged after the record was accepted: keep the output and the diagnostic and investigate the archive. Errors include `netops: reassembly_argument_error line_0`, `netops: reassembly_validation_error line_N` (or `after_line_N` for missing parts at the end of the archive) or `netops: reassembly_read_error after_line_N`. A failed write to standard output can leave a partial output file; keep it and the archive for inspection.
- Limit password authentication in the shared Core SSH, terminal and SFTP transports to one password attempt per connection. A server that offers only keyboard-interactive authentication is refused before a password is sent.
- Refuse `init` while `NETOPS_SERVER_NAME` is still the `env.example` placeholder, before any state is written.
- Quote the complete Auditor refusal for a changed operator policy in the quickstart.
- Document the service identity of the TLS syslog receiver after its privilege drop and the owner, group and modes of the receiver certificates and of the new part archive.
- Cite the measured device refusals of the PoE and stacking controller queries and keep their causes apart: a hardware refusal for PoE and a firmware parse refusal for stacking on FortiOS 7.6.7; an SSH `rc` of 0 does not mean that the device query succeeded.
- Document the non-interactive first `helper_status` call for Claude Code and Codex, including the Codex `required`, `enabled_tools` and `approval_mode` settings, explicit tool permission and the model of each command.
- List the MCP clients and models tested for 1.0.1: Claude Code 2.1.310 on Linux, macOS and Windows and Open WebUI v0.12.3 with the local models Laguna XS 2.1 Q4 and gpt-oss-120b MXFP4 through llama.cpp `llama-server`, and add Open WebUI notes on CA trust, name resolution, a silently skipped server after an authentication failure and the size of `read_query_catalog` for small contexts.
- Name `cli_auth_credentials_store = "file"` in the Codex configuration example and explain that it stores the Codex provider sign-in in `auth.json`, separate from the NetOps token in `NETOPS_TOKEN`.
- Extend the quickstart after a blind installation test: link the official Docker Engine installation and require a new login after joining the `docker` group, install Claude Code on the host with `~/.local/bin` on `PATH` and sign in without a browser through `claude setup-token`, try each role without an enrolled device through `read_query_catalog`, `list_rules`, `audit_status` and `admin_status`, which returns `admin_not_configured`, and list the audited tool calls with their time in UTC and whether a response was recorded through a `jq` filter over `audit export`.
- Upgrade the state of NetOps 1.0.0: the first start of 1.0.1 converts its state under the instance lock and changes only the recorded product version; the `instance_start` audit record of that start, written once its roles are ready, names the previous and the new version. State of any other version is still refused and there is no downgrade.
- Refuse `init` and `token rotate` over state of another product version, including state not yet converted from 1.0.0, before any write. Repeating `init` no longer reports `Already initialized` for such state.
- Document the upgrade from the previous release in the quickstart: prerequisites, backup, verification of the new release files, restore of the backup into a new 1.0.1 instance with the same server name and port while the 1.0.0 instance stays unchanged, start and checks, explicit project names, several operators of one instance, an interrupted first start and rollback to the unchanged 1.0.0 instance.
- Check the state before the first start of 1.0.1 converts it: the audit limits, the audit directory, the rejection summary, the local audit segments, the server name, the CA and server certificate files and their renewal, the Auditor configuration and, with Admin enabled, the Admin configuration. A refused first start does not convert the state: the gateway configuration still records `1.0.0`. The quickstart lists every check that the first start makes before the conversion, in its order and with the messages it reports, including the checks of the state directories and of the instance lock that every start makes. The Auditor and the Admin configuration are checked only as files and as JSON: a private file of the role user that holds a JSON object and, for the Auditor, text values for `tenant` and `catalog`. The roles of 1.0.0 refuse such a configuration when they start, except an Auditor configuration that 1.0.0 treated as absent, such as a dangling symbolic link; the first start of 1.0.1 now refuses it already before the conversion, and not only when the role starts after it. Everything else that the roles need, for example the values of `tenant` and `catalog` such as a value with a NUL character or an unknown catalog, the Auditor store and, when the Admin configuration lists devices, the complete Admin configuration, is still checked only by the roles after the conversion; when a role refuses it as the role starts, the state is already converted, the instance does not start and no audit record names the upgrade.
- Refuse a private state file without read permission for its owner also where NetOps reads it as root: the gateway configuration on every start and the files read by `ca`, `connection`, `token show`, `token rotate`, a repeated `init`, the `audit` reads and the operator commands. NetOps 1.0.0 read such files as root; its `token rotate` did not read the gateway configuration.
- Refuse to start when the audit directory `gateway/audit` exists but is not a directory owned by the gateway user with mode 0700, for example a directory with mode 0750 or a symbolic link, with local and with syslog audit. NetOps 1.0.0 started such an instance when the gateway user could write to the directory, for example a directory of the gateway user with mode 0750 or a symbolic link to such a directory.
- Treat only a missing rejection summary `gateway/audit/rejections.json` and a missing Auditor configuration `auditor/config.json` as absent, on every start and not only on the first start of 1.0.1. A dangling symbolic link, or a path whose existence cannot be checked, now stops the start; NetOps 1.0.0 treated it as absent, counted rejections from zero and started the Auditor with the default tenant and catalog. An existing file that its user cannot read stopped the start of 1.0.0 as well.
- Stop preparing the state directories on a repeated `init` of an initialized instance: it no longer resets the owner and mode of the state and runtime directories or reports unsafe role directories and data outside the 1.x layout. Every start still does.
- Report the running product version in the `version` field of `helper_status` instead of a fixed `1.0.0`.
- Keep the FortiOS rollback safeguard installed when the state after its fire time and grace differs from the state before the change and the stitch is still installed: FortiOS gives no device proof that the stitch ran, and NetOps 1.0.0 removed it before acting on the mismatch, so a stitch dispatched late was deleted, the change stayed and the operation ended as `revert-failed`. Such an operation now ends as `unknown` with the device blocked and the safeguard installed, so a late stitch can still return the previous state; this also applies when the stitch ran but a foreign value on the object differs, which 1.0.0 reported as `revert-failed`. Before unblocking, a person checks the object and removes the safeguard, because a new change is refused while it is installed.
- Update the Python dependencies for published security advisories: certifi 2026.7.22 to 2026.10.19 (GHSA-6q48-6c7w-9gw2, Critical: the bundle trusted a root whose intermediate CAs have compromised keys), FastMCP 4.0.5 to 4.1.2 (GHSA-7xgj-8392-5q4r, GHSA-vqqp-x5qm-5qp4), OpenTelemetry API 1.44.0 to 1.45.1 (GHSA-xcq7-p3pf-p88h) and openapi-pydantic 0.5.1 to 0.6.0, which FastMCP 4.1.2 requires.
- Update the container base image to Python 3.14.9 on Alpine 3.24. It fixes a race in the cleanup of `tempfile.TemporaryDirectory` (CVE-2026-12345).
- Check a `sftp_stat` path below an enrolled `sftp_roots` entry against the target that the SFTP server resolves in the same session: when a symbolic link in an ancestor or in the final component leads outside every resolved root, the call is refused and the metadata is not returned (reported in issue #6); a link replaced between that check and the listing remains a documented race. Lines that the SSH client prints before the SFTP session starts, such as a login banner or the OpenSSH warning about a key exchange without post-quantum protection, no longer make `sftp_stat` refuse the path.
- Limit the body receipt of an admitted authenticated request to 60 seconds, so that an incomplete body no longer holds an operation slot or the large-request lane without limit: when the deadline expires, the gateway records a `rejection` with reason `body_timeout`, `complete_body` false, the received byte count and `operation_executed` false, answers HTTP 408 `request_body_timeout`, closes the connection and dispatches nothing; a 4 MiB body needs at least about 70 KB/s.

## Upgrade from 1.0.0

Follow [Upgrade from the previous release](https://github.com/radek-cerny-soukr/netops/blob/v1.0.1/docs/quickstart-1.0.md#upgrade-from-the-previous-release). The upgrade has five steps:

1. Check the 1.0.0 instance, stop it and back it up as described in [Before the upgrade](https://github.com/radek-cerny-soukr/netops/blob/v1.0.1/docs/quickstart-1.0.md#before-the-upgrade).
2. If the instance uses syslog audit, switch the receiver as described in [Breaking change: syslog audit format](#breaking-change-syslog-audit-format) and keep its 1.0.0 configuration.
3. Download and verify the 1.0.1 release files, then prepare a clean 1.0.1 instance in a new directory, with the same server name and port and a `.env` with the 1.0.1 image.
4. Restore the backup into it as described in the same section of the quickstart.
5. Start it; the restore block of the quickstart ends with the start. The first start of 1.0.1 converts the restored state of 1.0.0 under the instance lock.

State of any other product version or state schema is refused, there is no upgrade that skips a release and no downgrade. The 1.0.0 instance, its directory and its state volume stay unchanged. Rollback: stop the 1.0.1 instance, export its audit records written after the backup as described in [Rollback](https://github.com/radek-cerny-soukr/netops/blob/v1.0.1/docs/quickstart-1.0.md#rollback), return the syslog receiver to its 1.0.0 configuration, with the enlarged message size limits and the separate 1.0 archive, and start the original 1.0.0 instance; it sends its queued records again as whole records.

## Changed behavior

NetOps 1.0.1 refuses to start some instances that NetOps 1.0.0 started. On the first start of 1.0.1 it refuses them before it converts the state, and the gateway configuration still records `1.0.0`:

- an audit directory `gateway/audit` that the gateway user can write to but that is not a directory owned by the gateway user with mode 0700, for example a directory of the gateway user with mode 0750 or 0755, or a symbolic link to such a directory; the healthcheck of 1.0.0 reports such an instance `ready`;
- a gateway configuration without read permission for its owner, which 1.0.0 read as root; the healthcheck of 1.0.0 does not report such an instance `ready`;
- a rejection summary `gateway/audit/rejections.json` that is a dangling symbolic link, or a path whose existence cannot be checked, which 1.0.0 treated as absent and counted rejections from zero;
- an Auditor configuration `auditor/config.json` that is a dangling symbolic link, or a path whose existence cannot be checked, which 1.0.0 treated as absent and started the Auditor with the default tenant and catalog. NetOps 1.0.1 refuses it on every start, also on an instance that 1.0.1 initialized or already converted.

Every later start of 1.0.1 refuses them as well, and operator commands such as `ca`, `connection`, `token show` and the `audit` reads refuse a state file that its owner cannot read. State that NetOps created is not affected: only files and directories changed by hand, for example their owner, their mode or a symbolic link in their place, or state restored with other owners or modes, are refused. Correct them as described in [Refused first start](https://github.com/radek-cerny-soukr/netops/blob/v1.0.1/docs/quickstart-1.0.md#refused-first-start) and start 1.0.1 again.

The first start of 1.0.1 also checks the Auditor configuration and, with Admin enabled, the Admin configuration before the conversion, but only as files and as JSON, as the quickstart lists. The roles of 1.0.0 refuse such a configuration when they start, except an Auditor configuration that 1.0.0 treated as absent, such as a dangling symbolic link; 1.0.1 refuses it already before the conversion, so the state is not converted. Everything else that the roles need is checked only by the roles after the conversion, for example the values of `tenant` and `catalog` such as a value with a NUL character or an unknown catalog, the Auditor store and, when the Admin configuration lists devices, the complete Admin configuration. When a role refuses such a configuration as the role starts, the instance is already converted to 1.0.1 and does not start until its configuration is corrected or the backup is restored. Such a start writes no `instance_start` audit record and no later start records the upgrade; the quickstart describes the only indirect evidence that remains, which needs audit history kept from before the upgrade.

Syslog receivers and tools that parsed each NetOps message as one JSON audit record now receive part envelopes with base64 data. Reassemble a record with `netops audit reassemble` from a copy of the part archive before you process it as a whole record.

Device connections with a stored password use only SSH password authentication. A device whose SSH server offers keyboard-interactive but not password authentication, which 1.0.0 reached with the same password, is now refused, and NetOps reports it as a refused credential. Enable password authentication on such a device or use a key.

## What you get

- One multi-architecture image for `linux/amd64` and `linux/arm64`, pinned by digest in the release `env.example`.
- One MCP endpoint over Streamable HTTP, always HTTPS, protected by a bearer token. The instance creates its own certificate authority with name constraints and renews its short-lived server certificate automatically.
- Every request and response is written to the audit before it is executed or delivered. If the audit cannot be written, the operation is refused (`audit_unavailable`) and an unknown Admin write is never retried automatically. The audit can go to a TLS syslog receiver (recommended) or to a local, size-limited log.
- The roles run as separate processes under their own user IDs with no Linux capabilities, on a read-only root filesystem, with CPU, memory and process limits. A short start-up bootstrap uses the few capabilities listed in `compose.yaml` to prepare protected state and then drops all of them.
- Refused, failed or uncertain operations are MCP errors (`isError`) with their full result content.
- The instance CA is valid for 730 days and is rotated explicitly with `netops ca rotate`; an interrupted local audit write is recovered with `netops audit recover`. Both run while the instance is stopped and are recorded in the audit.

## Requirements

Linux with Docker Engine, as root or in rootless mode, and the Compose plugin: Ubuntu, Debian or Fedora Server on amd64 or arm64, or Raspberry Pi OS 64-bit on arm64, natively or in a Linux virtual machine. Docker Desktop is not supported as the runtime. macOS and Windows are supported only as MCP client hosts. MCP clients connect over the network from any system.

- The server name in `.env` must be a DNS name that clients resolve; IP addresses are refused because common MCP clients do not accept IP names under a constrained CA. A local DNS entry or a hosts-file entry on each client is enough.
- On Fedora and other SELinux hosts, enable SELinux support in the Docker daemon (`"selinux-enabled": true`); the quickstart shows how to verify it.
- Syslog audit needs a TLS syslog receiver that stores the dedicated part archive with a message size limit of at least 2048 bytes, such as the default; storage by rsyslog 8.2504 and 8.2512 with the gtls or the ossl driver and by syslog-ng 4.12 is verified on arm64 and amd64, with each receiver running in a container.

## Known limitations

- The separate Helper SSH proxy to a runner host supports both keyboard-interactive and password authentication. When a server offers both methods, one connection with an incorrect password can cause two failed authentication attempts, which may count under the runner account's lockout policy.
- Authenticated requests with bodies above 64 KiB or uncertain body framing are processed one at a time across roles, so they can queue behind another large request. Other authenticated requests can use the remaining slots within the shared limit of 16.
- The 60-second deadline covers only the receipt of the request body: a client that does not read a large response keeps its operation slot until the response is sent, so such clients can occupy the shared limit of 16.
- 1.0.1 upgrades only NetOps 1.0.0; it does not upgrade or migrate 0.x installations or data.
- The roles are isolated as processes and files inside one container, not against the host administrator or the container runtime.
- An incomplete local audit write blocks further operations until `netops audit recover` runs while the instance is stopped. A full syslog queue blocks new operations, and an interrupted send can deliver records to the receiver more than once.
- The opt-in FortiOS `managed_switch_stacking` and `managed_switch_poe` queries have no positive result on stacking- or PoE-capable hardware. Virtual device images do not establish physical hardware behavior.
- The process-profile acceptance check uses a nominal 50 ms sampling interval and can miss processes that start and exit between observations. A previously unknown process that exits after its first observation but before its second may be attributed to a Docker exec runtime helper, up to four such cases per sample. This requires its recorded identity and parent PID, an older pinned `runc exec` parent tied to the same container (the shim's cgroup, UID 0, host PID namespace and reference-matching executable bytes), confirmation that the parent was alive after the child's first observation, and fresh confirmation that the child is absent. This proof is weaker: the child is not observed alive a second time, and its own executable and PID namespace need not have been observed. Missing required evidence, any recorded contradiction or a fifth such case fails the check.
- When the converting first start of 1.0.1 stops after the conversion, for example because a role refuses its configuration or the start is interrupted, no audit record names the upgrade. The only indirect evidence is the version in the last 1.0.0 records and in the next `instance_start` of 1.0.1, and only with audit history kept from before the upgrade; see [Refused first start](https://github.com/radek-cerny-soukr/netops/blob/v1.0.1/docs/quickstart-1.0.md#refused-first-start).
- The SHA-256 of a syslog record detects damaged or incomplete part archives. It does not prove the authenticity of data that an attacker controlled before the record was complete.
- Audit events suppressed before NetOps sends them cannot be detected from the receiver archive.

Details: [verified support](https://github.com/radek-cerny-soukr/netops/blob/v1.0.1/docs/verified-support.md) and [security](https://github.com/radek-cerny-soukr/netops/blob/v1.0.1/SECURITY.md).

## Install

Follow [the quickstart](https://github.com/radek-cerny-soukr/netops/blob/v1.0.1/docs/quickstart-1.0.md). In short: download `compose.yaml`, `env.example`, `netops-1.0.1-manifest.json`, `netops-1.0.1-SHA256SUMS` and `netops-1.0.1-SHA256SUMS.sigstore.json` from this release, verify them, set the bind address, port and server name, then run `init` and start the service.

Device enrollment is an explicit operator step described in [Helper configuration](https://github.com/radek-cerny-soukr/netops/blob/v1.0.1/docs/helper-configuration.md). An inventory written for 0.x needs the 1.0 Helper section and the English device roles `perimeter`, `internal` and `lab`.

## Verify this release

```sh
cosign verify-blob --bundle netops-1.0.1-SHA256SUMS.sigstore.json \
  --certificate-identity 325383355+radek-cerny-soukr@users.noreply.github.com \
  --certificate-oidc-issuer https://github.com/login/oauth netops-1.0.1-SHA256SUMS
sha256sum -c --ignore-missing netops-1.0.1-SHA256SUMS
```

The checksum list covers the release manifest, which records the image index and per-architecture digests, the SBOMs, the vulnerability scans and their assessments, and the acceptance reports of every tested platform. `env.example` already pins the image by that index digest. A download is verified only after both commands succeed.

## Security

Every release candidate is built once in GitHub Actions and the same digests are tested, accepted and published without a rebuild. Each architecture is scanned; a fixable High or Critical finding blocks the release and every other finding, of any severity, ships with a written assessment (`netops-1.0.1-vulnerability-assessments.json`). SBOMs cover the application, its Python dependencies and the operating-system packages. The container maps to the CIS Docker Benchmark v1.6.0 as described in [docs/security/cis-docker-benchmark.md](https://github.com/radek-cerny-soukr/netops/blob/v1.0.1/docs/security/cis-docker-benchmark.md).
