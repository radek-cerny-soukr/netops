### Cross-cutting

- Untested OS versions warn instead of refusing. Admin no longer refuses a change only because the firmware is not among the tested versions of its profile; the former family rule (any FortiOS 7.6.x or ExtremeXOS 33.7.x build) is removed, and only the listed builds count as tested. The plan, preview, result, status and `admin doctor` carry `firmware_support` (`status`, `tested_versions`, `message`), the start audit record stores `firmware_tested` and a notification adds a warning; an untested status is part of `plan_sha256`, so the person approves the warning with the plan. The FortiOS schema-transaction workflow still requires its exact build. Helper reads and diagnostics of FortiOS and FortiADC and `config_read` of ExtremeXOS (also images without a patch level), Cisco IOS, IOS XE, NX-OS and Arista EOS return their data with the same `firmware_support` and a `firmware_untested` warning. The Auditor FortiADC catalog evaluates its rules on another FortiADC version or build and reports it with the info rule `fortiadc.scope.untested-version`; another product stays out of scope. Device identity, account rights, argument validation, device capabilities and write safeguards are still checked; on FortiOS 8.0.1 and later, the webhook safeguard refuses configuration profile changes to tables without a REST inverse (`safeguard_no_rest_inverse`), while DHCP reservations now have one. The warning was seen live with `triage_flow` on the FG-60F and `config_read` on IOSvL2 and EXOS-VM 33.6.1.14, and in further live reads with a narrowed list of tested versions; the Auditor rule is covered by automated tests only.
- Fortinet SSH: Helper, Admin and the Auditor collection open one held OpenSSH session per FortiOS or FortiADC operation and account (Admin: one for the write account and one for the check account) and never scan the host key. The public key comes from the new optional device field `host_key` (`<type> <base64>`, matching `host_key_fingerprint`), which FortiOS and FortiADC devices now need; a missing key (`missing Fortinet public host key; add host_key at enrollment`), a malformed key or a fingerprint mismatch is refused with its own error before the SSH connection is opened and before any credential is sent (a role can read its own vault earlier). OpenSSH failures before login are reported as `auth`, `host_key`, `negotiation` or `disconnected`. After a lost Helper diagnostic session, one fresh pinned session restores the device-side filter or option and checks the cleanup; a lost FortiADC write is returned by `admin recover` with a fresh session. Verified live on the FG-60F (Admin enrollment, apply, undo, a lost write session and `admin recover`) and on VM220 (Helper and Admin), with no key scan.
- Approval hashes: as in 1.0.11, an apply whose fresh plan differs from the approved one is refused with `plan_changed` before any write, with the approved (`expected`) and the fresh (`actual`) `plan_sha256` in `reason_details` for ordinary apply; MCP undo and the initial ticketed save check return only `expected`, while the later pre-write save recheck can return the code alone. Every operational clear and save, profile batches and Ruckus changes apply only with the approved `plan_sha256` (`--expect-plan-sha256`, MCP `expected_plan_sha256`) and are refused without it (`plan_changed` or a specific `*_preview_required` code); for single configuration changes this depends on the table and the impact (for example FortiOS firewall policy, NAT, DHCP reservation, DNS entry, Phase 2 and FortiSwitch ports, FortiADC certificate replacement, ACL tables, or `endpoint_impact` on ExtremeXOS, NX-OS and Junos).
- Profile batches: on NX-OS, EOS, Junos, FortiOS, IOS and IOS XE, `table=batch`, `op=update`, `key=batch` plans 2 to 32 profile changes against each preceding predicted configuration with one approval hash, writes them under one device safeguard and returns every step with its result; a failed step starts the return of the whole batch (NX-OS timed configuration return, EOS session commit timer, Junos `commit confirmed`, IOS archive revert timer, FortiOS automation stitch with the inverse of every step in reverse order); Admin verifies the return and ends `unknown` or `revert-failed` when it cannot confirm the starting state. A confirmed batch can be undone in reverse step order. A FortiOS batch holds addresses, address groups and at most one firewall policy and needs the CLI-script safeguard, so it is refused on FortiOS 8.0.1 and later (webhook safeguard). Verified live on d-nxos, the three cEOS, vJunos, IOSvL2/IOSv, IOL XE/IOL-L2 XE and the FG-60F.
- Admin MCP undo and unblock: the new tools `admin_undo`, `admin_unblock_preview` and `admin_unblock` are off (`mcp_undo_disabled`) unless the Admin configuration sets `mcp_undo`. `admin_undo` needs the hash of the last `admin_undo_preview` this server issued for the device, once and within 600 seconds while the journal of the device is unchanged. `admin_unblock_preview` reads the device through both accounts and offers `unblock_sha256` only when the change is fully on the device; a device in the state before, a leftover safeguard, a changed account list, an unfinished or `revert-failed` operation, a schema transaction or a profile batch stays with the operator commands `admin recover` and `admin unblock`. Verified live on the FG-60F; `revert-failed` and schema transactions are covered by automated tests only.
- Private encrypted backups: the operator commands `admin backup` (FortiOS global backup over REST with a pinned certificate), `admin backup-eos`, `admin backup-nxos`, `admin backup-xe` and `admin backup-xe-status`, `admin backup-ios` and `admin backup-ios-status`, `admin backup-exos`, `admin backup-junos` (optionally saving the rescue configuration), the unseal commands `admin backup-unseal --platform fortios|eos|nxos|ios|xe`, `admin backup-exos-unseal` and `admin backup-junos-unseal`, `admin backup-nxos --status`, and `admin restore-junos`. Confirmed exports write AES-GCM files with `NETOPS_BACKUP_KEY` into a private directory on the backup host, keep the last 7 per target by default and require the `plan_sha256` of their preview; the status commands authenticate a local archive and unseal extracts it to a private file. `restore-junos` needs its own approved preview, keeps an encrypted copy of the current configuration and uses `load override` under `commit confirmed`. These commands run outside enrollment and the change journal. The contents never pass through MCP. Verified live on the lab devices; `restore-junos` on vJunos.
- Helper configuration: `config_read` keeps an approved baseline across restarts and new processes and compares later reads with it (verified live on IOSv, IOSvL2 and the X440) and keeps a local history of redacted snapshots (`recent_snapshots`); `config_diff` also compares running and startup configuration on IOS, IOS XE, NX-OS and EOS; FortiADC full reads can be kept as encrypted archives (`NETOPS_FORTIADC_BACKUP_KEY_FILE` in `compose.yaml`).
- Helper counters: pass the `counter_baseline` of a complete `interface_errors` read as `baseline` of the next read to get per-port deltas and the interval; a reset or wrap lists the affected counters in `counter_reset_or_wrap` and sets their deltas to `null`. Zero deltas were verified live on the X435, X440, IOSv and IOSvL2; nonzero deltas, resets, wraps and the managed FortiSwitch are covered by automated tests only.
- Inventory intent check: the new operator command `netops check-intent PLAN --inventory FILE --endpoint URL --ca FILE --token-file FILE` reads the expected LAG members, VLAN membership and PoE power interval of the inventory plan `helper.intent.PLAN` through the public Helper endpoint and exits with 0 (`pass`), 1 (`fail`) or 2 (`incomplete`). It is a one-time run; schedule it outside NetOps. With `--notify` and a webhook in `NETOPS_DISCORD_WEBHOOK`, an overall `fail` makes one delivery attempt to Discord, and `notification` reports its result. Verified live through the public HTTPS MCP endpoint on d-exos, d-exos-b, the X440 and the IT case, and through the SSH transport of Helper on IOSvL2, with delivery switched off; the Discord delivery is covered by automated tests with a fake HTTP server only.
- `locate_endpoint` finds a host by name as well (DHCP lease → ARP → FDB) and follows a wireless client to its access point and the switch port of that access point; it reports an incomplete chain instead of guessing. Verified live on the IT case, d-exos, d-exos-b and the X440.
- Classic IOS: when Admin verifies that its own revert timer restored the managed object and finds the original `banner exec` missing, Admin ends with `unknown` and `exec_banner_lost`, blocks the device and writes nothing more; restore the banner by hand, unblock the device and repeat the operation or enrollment. The enrollment self-test ends the same way and issues no enrollment. Verified live on IOSvL2 with the banner removed on purpose after the device return; the original loss of the banner could not be reproduced live.
- The qualification and CI engine tests now give the test tmpfs `/pytmp` 2 GiB instead of 512 MiB, because the Admin suite ended with `ENOSPC` in 512 MiB; the qualification documentation and the minimum requirements state it.

## Security

The security-related changes of 1.0.12 keep every new write of the standard Admin path behind the existing preview, `plan_sha256`, enrollment, journal, audit and readback controls, with check-account readback where the operation uses it; whether apply requires the approved `plan_sha256` depends on the operation (always for clear, save and profile batches). Backup exports (including `backup-junos --rescue`) and `restore-junos` each require an approved preview and run outside enrollment and the journal. Status and unseal authenticate the local archive. Irreversible operations (operational clear, save, port bounce, PoE cycle, session clear, DHCP lease release, IPsec tunnel recovery, FortiADC certificate import, Catalyst 9800 client disconnect) name their target and scope in the preview and have no undo; a scoped clear can remove several entries or sessions. FortiOS and FortiADC connections trust only the public host key stored with the device and never scan it. An untested OS version is reported to the person and bound into `plan_sha256`; it no longer blocks a change, while identity, rights, device capabilities and safeguards are still checked. The Admin MCP undo and unblock tools are off unless the configuration sets `mcp_undo`. Configuration backups are AES-GCM files outside MCP; device output in Helper results stays redacted. These notes do not assert the result of the review or scan of the 1.0.12 release candidate.

## Upgrade from 1.0.11

Follow [Upgrade from the previous release](../docs/quickstart-1.0.md#upgrade-from-the-previous-release):

1. Check the 1.0.11 instance, stop it and create its backup and state manifest.
2. Download and verify the 1.0.12 release files. Prepare a separate instance directory and a new Compose project with the same server name and port, and download the 1.0.12 image.
3. Restore the backup into an empty target volume and compare it with the source manifest before the first start. Keep the original instance and backup.
4. Start the new instance. The first start converts only the recorded product version from 1.0.11 to 1.0.12 under the instance lock and writes an `instance_start` audit record with `upgrade` from 1.0.11 to 1.0.12. A second start skips conversion. CA, keys, token, role data and connection details are unchanged.

Do not run `init` on the restored state. Only 1.0.11 is accepted as the previous release; upgrade 1.0.10 to 1.0.11 first.

For rollback, stop 1.0.12, preserve its audit records written after the backup, and start the unchanged 1.0.11 instance; see [Rollback](../docs/quickstart-1.0.md#rollback).

What changes for operators:

- Enrollments made with 1.0.11 are not valid in 1.0.12: an enrollment is bound to the enrollment protocol and to the SHA-256 of every Admin profile file, and 1.0.12 adds 158 profile files and changes 19, so every Admin device needs `admin enroll` again after the upgrade; until then Admin refuses its changes with `enrollment_required`.
- FortiOS and FortiADC: add `host_key` (the OpenSSH public key from a trusted known_hosts entry, matching `host_key_fingerprint`) to the device in the Helper inventory and the Admin configuration, and for FortiOS also in the Auditor collection inventory (the Auditor collects FortiADC as an export, not over SSH); NetOps no longer scans the key, and without `host_key` the operation stops.
- Admin: FortiOS firewall policy, DHCP reservation and DNS entry changes and ExtremeXOS port changes with `endpoint_impact` now need the approved `plan_sha256`; add `--expect-plan-sha256` (MCP `expected_plan_sha256`) to scripts that apply them. A preview made with 1.0.11 on a FortiOS 7.6.x or ExtremeXOS 33.7.x build that is not listed in the profile is untested now and its hash differs; run a new preview.

## Known limitations

- Live verification used the lab devices named above; depending on the change it ran through the public MCP path, the operator command line or the Admin runtime against an independent CLI read. PoE with a powered client, optics (DOM) outside ExtremeXOS, FortiExtender, FortiADC HA pairs, Catalyst 9800, hardware QFP, physical PFC/TCAM, configured VXLAN/EVPN, ExtremeXOS stacks and Juniper SRX are covered by automated tests on captured or documented outputs only. FortiGate optics, central log reads and the switch survey/device card are not part of 1.0.12.
- Lab-specific gaps: Admin changes on FortiOS 8.0.x were not run live; the other Admin apply and unattended safeguard-expiry scenarios of FortiOS address types, address groups, DHCP reservations, DNS entries and policy move and staged creation (through Admin ran one DNS A record, a disabled policy create and delete, and one address, group and policy batch), ExtremeXOS MLAG writes, the global jumbo size, stack ports, VLAN membership of a LAG and a packet test of an attached ACL, the IOS, IOS XE, NX-OS and Junos ND clear, positive changes of the NX-OS vPC domain, keepalive and peer link, the EOS BGP neighbor configuration, MLAG peer changes and a successful save, Junos BGP configuration and soft refresh, the Ruckus compensation after a failed write and `admin recover`, and the Discord delivery of `netops check-intent` are covered by automated tests only.
- The limitations listed in the [1.0.11 release notes](notes-1.0.11.md#known-limitations) still apply, except where the platform sections above extend the scope; for example, Juniper SRX now has Admin profiles (covered by automated tests only).
