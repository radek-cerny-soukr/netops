# Auditor configuration inside NetOps

Configure the stopped instance with `netops configure auditor`. JSON requires `tenant` and `catalog` (an available Auditor catalog key); `inventory` and `vault` are an optional pair. Use `catalog: "fortiadc"` to query stored audits of FortiADC exports. Collection uses the platform of each inventory entry. The instance catalog selects the default catalog for MCP rule lookups. The adapter owns the private store and role environment. Selecting another tenant/catalog preserves imported data. The Auditor reads its device credentials only from this private vault. For FortiOS collection enroll a `super_admin` administrator, which can also write, and restrict it with `trusthost` to the collector; a read-only profile hides other accounts' entries without saying so ([account model](../../../docs/account-model.md#auditor), [known limitations](../../../README.md#known-limitations)).

Use the [current operator workflow](../../../docs/quickstart-1.0.md#auditor-operator-workflows), [inventory](inventory.md), [shared vault schema](../../netops-core/docs/vault.md) and [collector boundaries](channels.md). MCP exposes read-only store/catalog queries, described with their accepted argument values in [Auditor tools](tools.md); it does not collect configurations or contact devices. An invalid tool argument, such as an unknown `severity` or `group_by` value, is refused with the generic `Role operation failed; no automatic retry` without naming the argument. No standalone MCP process or separate package is installed in NetOps 1.0.

The registry includes `fortios`, `exos`, `fortiadc`, `cisco-ios`, `cisco-nxos`, `arista-eos`
and `juniper-junos`. A platform becomes selectable when its catalog and checks are installed.
A collection for a platform with unavailable rules fails before connecting or recording an audit.
