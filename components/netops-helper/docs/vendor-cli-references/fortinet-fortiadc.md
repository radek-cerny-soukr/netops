# Fortinet FortiADC CLI references

## Review baseline and limits

- Vendor: Fortinet.
- Product and document title: FortiADC 7.6.7 CLI Reference.
- Reviewed version: FortiADC 7.6.7.
- Verification date: 2026-10-27.
- Catalog module: `src/netops_helper/query_catalog/fortiadc.py`.
- Contract of the identity gate and of the first query: `docs/fortiadc-f1-contract.md` in the repository.

The exact machine-checked templates and per-query source links are in the [generated query catalog](../query-catalog.md); the source-ID records are in [`query-sources.json`](../query-sources.json).

These references establish the vendor-documented command syntax and its purpose. They are not proof that a particular appliance, firmware build, administrator profile or virtual image permits the command. The vendor page shows an example output taken from FortiADC 7.4.1; the synthetic fixtures of the tests make no claim about complete status formatting. A sanitized measured status through the actual transport is still outstanding. The ten later queries rest on the example outputs of their vendor pages; one measurement of one virtual machine (see Limitations) supports them but is not a statement about other builds or hardware.

The returned data is sensitive operational evidence. The status output can expose the serial number, hostname, HA mode and firmware and signature database versions; the later queries can expose the VM UUID and license state (`vm_license`), interface names and traffic counters, routes and next hops (`routing_table`), neighbor addresses (`arp_table`) virtual and real server identifiers (`slb_load`), the availability and traffic counters of one named virtual server (`slb_vs_stat`), the WAF signature database version and licence state (`waf_signature_status`), client, virtual-server and real-server addresses, ports and names of active sessions and persistence entries (`slb_sessions`, `persistence_sessions`), IP addresses blocked by the WAF (`waf_block_ip`), driver, firmware and counters of a network interface (`nic_detail`), log file names (`log_list_traffic`, `log_list_attack`) and the serial number and support contracts (`autoupdate_contract`). It remains untrusted device output even when the command is read-only.

## Accepted queries

The table is the conservative whitelist of the profile: thirty-three queries. In the measurement of 2026-10-30 on FortiADC-KVM 7.6.7 build0676, `routing_table` (`get router info routing-table all`) and six other CLI reads (`vm_license`, `interface_state`, `interface_counters`, `arp_table`, `slb_load`, `slb_vs_stat`) were refused with `Command fail. Return code is -284 (CLI parsing error.)` in the three tested access profiles without `is-system-admin yes` (seven, six and two commands respectively; the attempts also included read-write on `system` or `load-balance` where tried), while `system_status`, `system_performance`, `firewall_timeouts` and `waf_signature_status` were allowed. With a system-administrator account (`is-system-admin yes`, as the built-in `admin`), `vm_license`, `interface_state`, `interface_counters` and `arp_table` returned their output through the exec channel; `routing_table` was not refused with `-284` there but answered `get vty failed` and `Command fail. Return code is -1 ((null))`, and `slb_load` and `slb_vs_stat` returned one empty line. These three queries therefore use a query-scoped terminal session; its measured output is described under Limitations. Enroll an account for the existing bounded diagnostic reads as `account_role: "admin-bounded"` with `role_boundary: "catalogue"`; this remains an administrator on the device, not a device-read-only account, see [account boundaries](../read-only-accounts.md). `interface_state`, `nic_detail`, `slb_vs_stat`, `tls_handshake_stats` and `tls_session_reuse` have parameters. The `interface_state` and `nic_detail` values must be listed in the `interfaces` inventory of the target. The `vdom` and `virtual_server` values of `slb_vs_stat` must be listed in the `adc_vdoms` and `adc_virtual_servers` inventories; the Helper accepts letters, digits and `_ . -`, starting with a letter or digit, at most 35 characters (a Helper constraint, not a vendor limit). The TLS statistics queries accept only `virtual_server`, from `adc_virtual_servers` with the same name constraint; `virtual-server` is a fixed command keyword, not a caller-supplied datasource. No other caller value reaches the command line. `normal` is not a bounded-output promise; `high-volume` marks queries whose output size depends on the number of routes, neighbors, servers, sessions, blocked addresses, log files or processors.

Primary sources: [FortiADC 7.6.7 CLI Reference](https://docs.fortinet.com/document/fortiadc/7.6.7/cli-reference) and its page [get system status](https://docs.fortinet.com/document/fortiadc/7.6.7/cli-reference/379949/get-system-status). The pages of the twenty-nine later queries are listed with their source IDs in the provenance table below; `log_list_traffic` and `log_list_attack` share one page.

What the other queries show, as documented on their pages: `system_performance` the CPU and memory usage, system load and uptime; `vm_license` the UUID, license file validity, allowed versus used CPU, RAM and disk, and the registration status of a FortiADC-VM; `interface_state` the record of one named interface; `interface_counters` the receive and transmit counters of all interfaces; `routing_table` the whole routing table with route codes; `arp_table` the neighbor table; `firewall_timeouts` the global firewall timeout values; `slb_load` the real servers of each virtual server with id, status and weight; `slb_vs_stat` the availability, connections, requests, round-trip times and throughput of one named virtual server and, because the optional real-server argument of the vendor command is not used, all members of its real-server pool with their health-check state and time of the last change (so the number of rows depends on the pool, hence high-volume); `waf_signature_status` the WAF signature database version, release date and signature count; `cpu_info` the CPU records of the appliance; `slb_sessions` and `persistence_sessions` the session and persistence tables of the load balancer; `nic_detail` the driver and statistics of one named port; `waf_block_ip` the IP addresses blocked by the WAF; `log_list_traffic` and `log_list_attack` the stored traffic and attack log files; `autoupdate_contract` the FortiGuard service contracts of the appliance. `diagnose hardware get sysinfo cpu` and `diagnose hardware get deviceinfo nic-detail` are keywords of shared pages, and `execute log list-type tlog` and `alog` are two arguments of one page. The pages of `interface_state` and `arp_table` are shared with their parent commands. `routing_table` uses the `all` keyword on the documented `get router info routing-table` page; the `kernel-*` keywords are not exposed.

Of the nine newly listed fixed queries, the three BGP/OSPF reads have installed measurements of explicit inactive or disabled routing states; the other six remain source-qualified without installed output qualification, except that `traffic_group_status` has recorded empty output in active-passive (both roles) and standalone mode. They help review the system clock, log-file inventory, LLDP topology, BGP/OSPF peer state, HA nodes, traffic-group node assignment, and LLB policy details. In particular, the brief traffic-group command does not return floating IP addresses, and the log-file list does not report filesystem capacity.

The page documents the syntax `get system status` and an example whose `Version:` line reads `FortiADC-VM v7.4.1,build0310,231030 (GA.F)`. The hardware field starting `FortiADC-` is what the platform identity check in `netops_core.platforms.require_identity` relies on.

## Excluded families

- Every `config` command and every `execute` command except the eight exact read views of the table (`execute waf block-ip list`, `execute log list-type tlog`, `execute log list-type alog`, `execute autoupdate contract`, no-argument `execute date`, `execute log list-type all`, and the two TLS statistics `show virtual-server {virtual_server}` templates): the profile is read-only; the date-setting form of `execute date` and other modifying forms, including `execute waf block-ip add`/`delete`, `execute log delete`, `display`, `rename` and an `execute autoupdate` update stay refused.
- Configuration display and backup (`show`, `show full-configuration`, backup and export): the configuration boundary of Phase 1 holds for this platform too.
- Debug and packet-capture families, log content and support-bundle retrieval, shells and file display. Of the `diagnose` family only the twelve commands of the table are accepted by the Helper, which does not establish that a restricted profile may run them (see the first paragraph of this section); the other `diagnose hardware` and `diagnose server-load-balance` sub-commands stay refused; `diagnose netlink neighbor add`, `delete` and `flush`, `neighbor6`, `diagnose netlink interface list` without an interface name and the `kernel-*` variants of `get router info routing-table` stay refused.
- Arbitrary CLI: raw command text is never accepted as a query name.

## Object configuration views

Use config_read with platform="fortiadc", redaction="full" and section set to
"load-balance virtual-server NAME", "load-balance pool NAME",
"system health-check NAME", "security waf profile NAME" or
"system certificate local_cert_group NAME". These opt-in views use
the existing config_access read permission and the semantic configuration
redactor, including removal of health-check passwords and secret keys; they are
not ssh_read queries. Each executes the corresponding fixed show command.
Object names use the Helper's existing 1–35 character FortiADC object grammar.
The returned configuration is section-only, with unknown fields reported rather
than exposed. The fixed show command forms and output shapes for these five views
are awaiting live qualification on a FortiADC. The client-SSL-profile GET view is described below. The certificate-group view preserves member default selection,
local certificate names and intermediate CA group references; it does not fetch
the referenced certificate or private-key material. Its schema is documented in
the FortiADC 7.6.7 CLI Reference, page 352203 (config system certificate local_cert_group).


### Named TLS profile GET

config_read section="load-balance client-ssl-profile NAME" uses the exact fixed
get load-balance client-ssl-profile NAME command. Official 7.6.7 CLI Reference
pages 774093 (client-ssl-profile) and 148570 (get) describe its fields and display
semantics. A single read of an existing profile returned 18 colon fields;
all 18 are already classified among the 37 public TLS fields in the existing
7.6.7 configuration policy. This establishes this measured output shape, not all
profiles or firmware versions. End-to-end Helper qualification remains pending.

The returned normalized_from_get=true representation uses a synthetic config/edit/set
wrapper around the displayed values. The typed requested name binds the command
and cache selector; it is not an independently returned object identity. TLS/cipher
settings and certificate/CA references remain visible under the existing semantic
policy, while credentials and unclassified values remain hidden. This does not
claim raw configuration faithfulness or fetch referenced certificate/key material.

## Environment findings: HA setup on FortiADC-VM 7.6.7

NetOps does not configure FortiADC HA; the Helper only reads `ha_status` and the HA views of the table. These findings come from preparing an HA pair of two FortiADC-KVM 7.6.7 build0676 VMs on 2026-11-01 and 2026-11-02 with a separate tool, and they matter to anyone who builds such a pair before reading it with NetOps. They are one observation on one hypervisor and firmware.

- HA management trusted hosts: the 7.6.7 CLI Reference page `config system ha` shows `ip-network` in the syntax of `config mgmt-trust-ip-list`, while the parameter table of the same page names `ip-netmask`. The parser refuses the syntax form: `set ip-network <address>/<prefix>` ends with `Parsing error at 'ip-network'` and `Command fail. Return code is -284 (CLI parsing error.)`. Use `set ip-netmask <address>/<prefix>` in CIDR form.
- Login prompt: in an interactive terminal session the first prompt after login, `<hostname> # `, arrives without a trailing newline, like the prompt after each command (see Limitations). A client that reads line by line waits until its timeout; read up to the prompt instead.
- Network interfaces added to a running VM: FortiADC does not see a virtual NIC added while it runs. `show full-configuration system interface` keeps listing only the earlier ports, so `set hbdev` or `set datadev` with the new port has no interface to bind. The ports appear only after `execute reboot` (the CLI asks `Do you want to continue? (y/n)`); the restart adds an `edit portN` block for each new port to `config system interface` and leaves the other configuration sections unchanged. A configuration hash taken before the restart therefore no longer matches; take the baseline after the restart.
- HA management IP on port1: `set mgmt-ip` with the address that port1 already holds is refused with return code -59, also with a /32 mask. It is accepted when the same batch first removes the interface address (`config system interface`, `edit port1`, `unset ip`, `next`, `end`) and then sets `config system ha` with `set mgmt-status enable`, `set mgmt-interface port1`, `set mgmt-ip <port1 address>/<prefix>`, `set mgmt-ip-allowaccess https ping ssh`, `set mgmt-trust-ip enable` and the `config mgmt-trust-ip-list` entries. The node then stays reachable on the same address. The reverse order restores it: `set mgmt-status disable` in `config system ha`, then `set ip <address>/<prefix>` on port1.
- `set local-node-id`: the CLI Reference marks it as not used in active-passive mode; in standalone mode the parser refuses it with -284. Leave it unset for an active-passive pair.
- Persistence pickup: the CLI Reference names `http-persistence-pickup`, which the parser refuses with -284. The Administration Guide 7.6.7 (active-passive configuration) names `l7-persistence-pickup`, which is accepted together with `l4-persistence-pickup` and `l4-session-pickup`.
- Mode change: after `end` of a `config system ha` batch that sets `mode active-passive` or `mode standalone`, no prompt arrives for at least 30 seconds and the connection stays open. Read the result back on a new connection (`get system ha`, `show system ha`) instead of waiting for the prompt.
- Pair state: with these settings (`group-id`, `hbdev port4`, `datadev port5`, `priority` and `config-priority` lower on the intended primary, `override enable`) the pair formed: the primary reported `Mode: active-passive`, `State: Primary`, `Peer Count: 1` and the peer as `Secondary`, `In Sync`.
- NetOps reads after the pair formed: NetOps connects to each node on its HA management IP. The FortiADC 7.6.7 Administration Guide (HA synchronization exceptions, pp. 192-193) says the Configuration Source pushes the configuration, and administrator accounts are not among the listed exceptions, so they are synchronized from the Configuration Source. Verified on 2026-11-02 in one pair: with the Configuration Source's synchronized credentials configured for both nodes, `ha_status`, the configuration read and `system_status` succeeded on the primary (the Configuration Source) and on the secondary; `vm_license` succeeded on the primary. Configure NetOps with the Configuration Source's synchronized credentials for every node of the pair; which node is the Configuration Source decides this, not the current role. If the nodes had different credentials before the pair formed, the secondary's own credentials are expected to stop working once the configuration is synchronized; this was not tested. `traffic_group_status` (both nodes) and `slb_load` (primary) were refused with the engine error `the diagnostic session prompt cannot be verified`: in the pair the CLI prompt carried the HA role prefix (`(P) FortiADC-KVM # `, after `end` `(I) FortiADC-KVM # `), which the terminal session of this engine version did not accept (see Limitations). The refusals of the earlier pair attempt were recorded without this detail and their cause is not determined. `vm_license` and `slb_load` on the secondary were not run. Repeated on 2026-11-02 in a second pair with an engine version whose terminal session accepts the HA role prefix: `ha_status`, the configuration read (section `all`), `system_status`, `vm_license` and `slb_load` succeeded on both nodes, in the first roles and after the forced failover; `traffic_group_status` returned no output on both nodes (that engine version refused it with error code `empty`, `The device returned no output for this query; no result was read`; see Traffic groups).
- Traffic groups: Traffic groups are used in Active-Active-VRRP (FortiADC 7.6.7 Administration Guide, Traffic Group, p. 246). The guide does not say what the traffic-group status prints in standalone or active-passive. In the active-passive pair of 2026-11-02 `traffic_group_status` returned no output on both nodes in the first roles, after the failover and after the return, and the configuration read showed an empty `config system traffic-group` in each of these phases. `ssh_read` returns this empty output as a successful read (`ok: true`, empty output); the readings above were taken with an engine version that still refused it with error code `empty`.
- Forced failover, verified on 2026-11-02 in one active-passive pair: `execute ha force failover-standby set` on the primary asks `Do you want to continue? (y/n)`; after `y` it prints `HA failover-standby is set.` and `execute ha force failover-standby status` prints `HA failover-standby is set.`. The prompt right after the answer still carried `(P)`; on the next connection the node showed `(S) <hostname> # ` and the peer `(P) <hostname> # `, and `ha_status` reported the first node `Secondary` and the peer `Primary`, in sync, peer count 1. `execute ha force failover-standby unset` on the same node printed `HA failover-standby is unset.` without a question; the prompt of that answer still showed `(S)`, the next `status` printed `HA failover-standby is unset.` with prompt `(P)`, and `ha_status` reported the first roles again (primary and secondary, in sync). `execute ha force standby` is documented for HA VRRP mode only and was not run.
- Traffic through the pair during the failover and the return, measured on 2026-11-02 with one failover and one return: the pair had `l7-persistence-pickup`, `l4-persistence-pickup` and `l4-session-pickup` enabled under `config system ha`; short HTTP requests had no failure (452 of 452 during the failover, 453 of 453 during the return, both backends answered); the long-lived TCP connection (SMTP, one `NOOP` every 0.2 s) to the virtual server `LAB_VS_SMTP` (profile `LB_PROF_TCP`; no `type` line in the LAB_VS_SMTP configuration) recorded 3 errors and 3 reconnects in each run; in the failover run the probe started at 08:30:44.343Z and the first error came at 08:31:16.595Z, at most 1.6 s after the answer of the device recorded at 08:31:15Z (`HA failover-standby is set.` and the prompt; whole seconds); the time of sending `y` was not recorded more precisely; in the return run the probe started at 08:40:30.438Z, the answer of the device to `unset` (`HA failover-standby is unset.` and the prompt) was recorded at 08:41:00Z (whole seconds) and the first error came at 08:41:02.697Z; the last recorded error is the truncated reply `421 4.7.0 ... Error: too`; the times of the later errors and the reply at the first interruption were not recorded. The long connection did not survive the window in either run (`survived` false, 4 connections); whether the failover interrupted it is not determined. The FortiADC 7.6.7 Administration Guide (p. 188) says that with Layer 4 Connection Synchronization enabled the TCP session table is synchronized, and if subsequent traffic for the connection is distributed through a different cluster node because of failover, the TCP sessions can resume without interruption. NetOps reads the HA configuration, including the `*-pickup` settings, with the configuration read (section `all`), and does not change it.

## Limitations

- Identity is established from the hardware field of one `Version:` record: `FortiADC-` selects this profile and other products are refused before the query is sent. `ssh_read` implements this gate as described in the section `Transport wiring of ssh_read` of the F1 contract; its source tests use synthetic responses and still need a matching and a mismatched response from a real device through the real transport.
- `engine._CLI_REFUSALS` has a dedicated FortiADC full-line failure pattern (contract section `CLI refusal classification of fortiadc`). A capture of FortiADC 7.6.7 build0676 CLI answers contains five standalone `Command fail. Return code is -284 (CLI parsing error.)` lines. Only that code/description is observed; other signed numeric codes and nonempty single-line descriptions are a structural inference, not additional device measurements. The official CLI pages cited above do not document this message. Refused identity probes remain `product_identity`; a matching refusal after verified identity is `device_cli_error` and is not cached.
- The refusal regression is completed: the observed `-284` fixture failed before the fix and passes after it, and the earlier tests remain green.
- The SSH transport is the exec channel. A FortiADC VM (`FortiADC-KVM v7.6.7`) was measured on 2026-10-26 with a separate tool: the exec form without a terminal (`-T`) is accepted with exit status 0 and the answer is framed like an interactive shell. The first line begins `<hostname> # ` followed by `Version: ...`, and the output ends with the line `<hostname> # ` without a newline. The Helper removes both prompts in `netops_core.prompt` (contract section F1-WIRE-PROMPT) before it checks the identity. This is one observation on one VM and firmware; the source tests use a synthetic host name and no captured bytes, and this observation alone does not establish Helper refusal handling.
- `routing_table`, `slb_load` and `slb_vs_stat` use an interactive terminal session instead (`transport` `pty` in the result): the identity probe stays on the exec channel, then the Helper opens a terminal, verifies the `<hostname> # ` prompt, sends the one catalogue command and reads up to the next prompt; the same refusal classifier applies. On 2026-10-30, on FortiADC-KVM v7.6.7 build0676 with an administrator account, the exec channel answered `get router info routing-table all` with `get vty failed` and `Command fail. Return code is -1 ((null))`, and `diagnose server-load-balance slb_load` and `diagnose server-load-balance vs_stat` with one empty line. On the same day a separate tool, not the Helper, sent each of the three commands once in an interactive terminal session and read up to the prompt: `get router info routing-table all` returned the IPv4 table with `S>* 0.0.0.0/0 [10/0] via 198.51.100.1, port1` and the connected routes `192.0.2.0/24` (port2), `203.0.113.0/24` (port3), `169.254.0.0/16` (haport0) and `198.51.100.0/24` (port1), with the addresses rewritten to documentation ranges; `diagnose server-load-balance slb_load` listed four virtual servers of vdom `root`, each with two real-server pool members shown as `status 1, weight 0`; `diagnose server-load-balance vs_stat vdom root vs <virtual server>` reported `availability:HEALTHY` and both members of its pool with `hc_state: UP` (on a second connection; the first was reset before the command was sent). The installed Helper terminal path was measured on FortiADC-KVM 7.6.7 build 0676: `routing_table` returned 379 bytes of IPv4 routes, `slb_load` returned 447 bytes of virtual-server and member data, and `slb_vs_stat` returned 632 bytes of virtual-server health and statistics. Each capture completed at the prompt with the installed source parity and audit checked. This is one observation on one VM and firmware.
- In an HA cluster FortiADC puts the node role in front of the hostname in the terminal prompt: `(P) FADC # ` and `(S) FADC # ` (FortiADC 7.6.7 CLI Reference, `execute ha force failover-standby`, PDF page 639) and `(M) FAD1 # ` (FortiADC 7.6.7 Administration Guide, `diagnose debug ha`, PDF pages 205-206); the Fortinet pages do not document `(I)`, which a FortiADC-KVM v7.6.7 build0676 VM printed as `(I) <hostname> # ` after `end` on both nodes of a two-VM pair on 2026-11-02. For FortiADC only, the terminal-session paths accept an optional prefix `(P) `, `(S) `, `(M) ` or `(I) ` (also in a configuration context such as `(ha)`); any other prefix or a prefix without the following space is refused as an unverified prompt, and other platforms are unchanged.
- DoS block-count reads (`dos_access_limit`, `dos_conn_limit`, `dos_req_limit`) need the system administrator account and are enrolled only as `admin-bounded` with `role_boundary: "catalogue"`. On 2026-10-31, on FortiADC-KVM v7.6.7 build0676, an account whose access profile grants read on system, load-balance, log, link-load-balance, global-load-balance and security (no system administrator) sent `execute dos get dos-access-limit <virtual server>` and received `Parsing error at 'dos'. err=1` and `Command fail. Return code is -284 (CLI parsing error.)`; the same command string was accepted from the administrator account. The command syntax matches the cited reference page, and the access-control table of the FortiADC 7.6.7 CLI reference assigns `execute dos` to no access-profile area. This is a documented limitation for read-only accounts; NetOps does not widen a read-only account to run these commands.
- Cost and permissions: `system_status` is the identity probe and takes one SSH connection; every other query takes one more connection for its own command. The account needs the right to run `get system status` and the command of each query it uses; a restricted profile with every access-profile area `read` and `is-system-admin no` is refused `diagnose server-load-balance` (`slb_vs_stat`, `slb_load`) with `-284`, while the built-in `admin` (`super_admin_prof`) reads both (measured 2026-10-31 on FortiADC-KVM 7.6.7 build0676, see `read-only-accounts.md`, section FortiADC). The Helper spaces successive SSH-family connection starts to one FortiADC target by at least five seconds; this applies per connection, not per complete query. This is conservative local pacing in response to observed connection bursts, not a documented Fortinet limit.
- Measurement of the later queries: the reference runs of 2026-10-30 on one VM, FortiADC-KVM v7.6.7 build0676 (two batches, run with an administrator account), executed the ten commands of the table (`slb_vs_stat` with the difference described in the next item), with `diagnose netlink interface list port1` for `interface_state`; it is one observation on one VM and firmware. `diagnose netlink interface list port9`, a nonexistent interface, returned no output besides the prompt; the Helper accepts only interface names from the target's inventory. A command with an extra argument (`diagnose server-load-balance slb_load extra`) ended with `Command fail. Return code is -284 (CLI parsing error.)`, the message of the refusal classifier above.
- Measurement of `waf_signature_status` and `slb_vs_stat`: the second batch of the reference runs executed `get security waf-signature-status`, which returned the lines `Version`, `Engine Version`, `Signature Number`, `Release Date`, `License Status` and `License Expire Date`. For `slb_vs_stat` the run executed `diagnose server-load-balance vs_stat vdom root vs <virtual server> rs <real server>`, that is with the optional real-server argument that the Helper template omits; the virtual server was in the state `DEAD`, the output began with `vdom name is root` and `virtual-server: <name>, availability:DEAD`, listed the counters Client RTT, Concurrent Connections, Inbound Throughput, Outbound Throughput, Requests, Server RTT and APP Response, and ended with `real-server-pool: <pool>`; no real-server rows were printed. The template without the real-server argument, on a virtual server that is not in the state `DEAD`, was measured only through a terminal session, see the item on `routing_table`, `slb_load` and `slb_vs_stat` above.
- Measurement of `cpu_info`, `slb_sessions`, `persistence_sessions`, `nic_detail`, `waf_block_ip`, `log_list_traffic`, `log_list_attack`, `autoupdate_contract`: a third read-only reference batch of 2026-10-30 on the same VM, run with an administrator account, executed the eight commands of the table with `port2` for `nic_detail`; every command ended with exit status 0. `diagnose hardware get sysinfo cpu` returned four `processor` records in the Linux cpuinfo format. `diagnose server-load-balance session list` returned a header of twelve columns and 307 session rows under test load. `diagnose server-load-balance persistence list` and `execute waf block-ip list` returned only their header lines (no persistence entry and no blocked address existed), so the format of their records rests on the vendor page. `diagnose hardware get deviceinfo nic-detail port2` returned the driver, version and bus blocks, the link settings and the receive and transmit counters. `execute log list-type tlog` and `alog` listed 16 and 8 log files with a numeric value whose unit the output does not name, and the time of the last change. `execute autoupdate contract` returned the serial number, the contracted services with their dates and the support level and type descriptions.
- Both TLS statistics queries have been verified through an installed Helper on FortiADC-KVM 7.6.7 build0676 with the fixed `show virtual-server NAME` syntax. The verification covered one enrolled virtual server; successful and failed client handshakes were observed, and the server-side counters were zero. The handshake view returns client-side success/failure and SSL record counters plus server-side counters; the reuse view returns session-ID cache and combined session/ticket reuse counters. The Helper returns the device counters without parsing them into a new metric. A cumulative counter snapshot does not establish that a new handshake or test connection succeeded. Each query uses the existing bounded PTY read, identity gate, query/name enrollment, refusal classifier, audit, redaction and cache. No generic datasource or clearing command is available.

The BGP summary, BGP neighbor and OSPF neighbor reads also require a PTY on the measured FortiADC-KVM 7.6.7 build 0676. The same commands that failed through exec returned complete terminal results: no active BGP instance and OSPF routing not enabled. These observations qualify the transport and the inactive state; they do not demonstrate established routing sessions.

Installed Helper measurements on 2026-10-30 (source `315f8f0`, one FortiADC-KVM 7.6.7 build0676, administrator credential enrolled as `admin-bounded`/`catalogue`) exercised the three routing reads and five bounded diagnostics. BGP summary and neighbors returned an explicit inactive-instance message; OSPF neighbors returned an explicit routing-not-enabled message. These qualify the read transport and reported inactive state, not established routing sessions. Ping to the enrolled gateway returned five replies from five fixed packets. DNS returned a CNAME and three IPv4 addresses. The enrolled HTTP `/health` endpoint returned status 200 and `ok backend-a`; a single enrolled `HC_HTTP_APP` check returned UP/status 200 and one success. Traceroute returned three unresponsive hops before its 60-second deadline and Ctrl-C: `complete=false`, `deadline_reached=true`. This is partial diagnostic output and does not establish a route or target reachability. All five diagnostics preserve bounded output and the declared result metadata; a successful tool invocation does not mean a healthy network result.
