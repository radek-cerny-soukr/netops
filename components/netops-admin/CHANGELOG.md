# Changelog

## 0.2.6 - 2026-10-06

- Pin netops-core 0.2.7 and netops-auditor 0.2.10; align first-operation instructions with the exact installation versions and validate these documentation pins.
- Create /opt/netops-admin with the installing user as its owner. Stop each unpack, checksum and installation step on failure in an ordinary shell.
- Use local umask 022 during venv and pip creation and verify the installed askpass program before the first operation. Add whole-block positive and negative installation regressions.

## 0.2.5 - 2026-10-06

- Stop archive installation on download, signature or checksum failure; check internal source manifests after verified extraction.

- Update locked PyJWT to 2.15.0 to reject deeply nested JWT payloads with DecodeError.

- Restrict measured visibility conditions to their declared global or VDOM contexts; an unknown context refuses the change.

- Integrate calibrated FortiOS schema transactions with apply, preview, doctor, enrollment, undo and recovery. Keep the exact library and calibration pinned; share the audit, independent readback, timed safeguard, notification and journal with profile requests. Bind calibrated generated UUIDs after their first readback and refuse identity replacement.
- Add admin_schema_apply and admin_schema_preview MCP tools for batches of up to 32 operations. Every operation consumes a budget unit and unmeasured operations remain refused.

- Count every suboperation against transaction budgets, with old journal records counting as one change; malformed journal weights are refused.

- Refuse FortiOS automation placeholders in planned changes and timed inverses so variable substitution cannot alter rollback data.

- Add pinned offline schema transaction planning and verification, with rollback calibration, nested owner contexts, reference checks and reverse dependency order. The offline plan stays non-executable; live execution requires a separate configured binding and enrollment.

- Broken input is answered with a documented exit code and its reasons, never a traceback or a hang; `tests/test_malformed_inputs.py` feeds the configuration and every file it names, the port policy, the request, the plan, FortiOS and ExtremeXOS snapshots, every file and directory of the state directory, the answers of a device to the write and the check account, every argument of every command, every parameter of the MCP tools and the inputs of `scripts/export_status.py` the same broken shapes as the auditor's matrix. It caught and this release fixes:
  - The request, snapshot, plan and policy files (16 MiB), the configuration (1 MiB), the journal files (16 MiB), the export status and the ntfy topic file (64 KiB) are read without blocking, only as regular files and no further than their limit: a pipe in place of any of them blocked the command for good, `/dev/zero` ended in `MemoryError` and a NUL character in a path in a `ValueError` traceback. The audit log is opened without blocking and must be a regular file; a pipe there blocked `apply` and `doctor`.
  - A JSON document nested too deeply (request, plan, policy, configuration, journal, export status) ended in a `RecursionError` traceback; it is now `<name> is nested too deeply`. A key repeated within one JSON object, which the parser resolved by keeping the last value (a second `op` of a request replaced the first), is refused in every JSON input as `<name> repeats a key within one JSON object`; a journal file with one cannot be read and an export status with one blocks. A string with an unpaired surrogate escape is refused as well.
  - A state directory or journal directory the tool cannot use - a file, a pipe, a device or a link loop in its place, or a parent that is a file - is `the state directory cannot be used: <reason>` instead of a `FileExistsError`, `NotADirectoryError` or `OSError` traceback, a lock file that is a pipe, a directory or a symbolic link is refused instead of blocking, and a block, baseline or enrollment file that is a directory no longer ends `unblock` in a traceback.
  - A journal record whose fields have the wrong type - a `plan`, `steps` or `safeguard` that is not an object or a list, an epoch that is not a number, a text the audit log cannot carry, a `change_id` other than its file name - is a state file that cannot be read, where `status`, `undo`, `recover`, `notify-retry`, `unblock` and `preview` ended in a `TypeError`, `KeyError` or `AttributeError` traceback. The plan that `undo` and `recover` use passes the checks of `verify --plan`; a block file must name a device, a reason and a change identifier, a baseline an account fingerprint.
  - MCP: an unconfigured server, a state directory or a journal file that cannot be read is a tool error or a `rejected` result instead of `Error calling tool ...` with a traceback in the server log, and a refusal repeats at most 64 characters of a device name or file name.
  - `unblock` and `notify-retry` check that the audit log can be written before they change the journal, as `apply` does.
  - `scripts/export_status.py`: an answer of `syslog-ng-ctl` that is not UTF-8 or carries a count of more than 18 digits, a `.pending-since` file that is a pipe, a directory or holds `-inf`, and an output path the system refuses ended in a traceback, a hang or a status with `Infinity`, which the admin could not read; each is now exit code `1` with one line, or the pending time starts again. Only ASCII digits count as a queue length, and the destination name must match as a whole.
- Pin `netops-auditor==0.2.9` and `netops-core==0.2.6`.
- Changed behaviour: the audit gate takes the state of every rule from the auditor (`rule_status`) and confirms only a complete evaluation. Every rule outside the management catalogue, the management rules in `required_rules` and those the table needs must be `evaluated`; another management rule that is not evaluated no longer blocks. Before the change an incomplete evaluation refuses the request with `the auditor evaluation is not complete: mandatory rules not evaluated: ...`; after the change the confirmation stops with the new non-blocking reason `audit incomplete` and the step `audit_incomplete`, where 0.2.4 reported `audit unavailable` or refused with `the auditor could not evaluate the snapshot before the change (PolicyError)`. A `vlan` change on an ExtremeXOS switch whose membership lines the auditor cannot expand now goes ahead (see `docs/execution.md`).
- ExtremeXOS: a `configure vlan <name> add ports all` or a port range across slots no longer refuses a `vlan-membership` or `ports` change when the snapshot carries the port list in `configure vr <name> add|delete ports`; the planner expands it as the auditor does. Without that list the change is refused as before with `VLAN membership cannot be evaluated from this snapshot`.
- FortiOS: a dump cut inside a block or a quoted value is `snapshot incomplete` wherever it is cut. Before the change the request is refused with `snapshot is cut off: ...` without blocking the device; after the change the reason `snapshot incomplete` blocks it, where 0.2.4 ended with `postcheck unavailable` and no block.
- FortiOS: a comment that ends with a backslash (`set comment "C:\\temp\\"`, issue #1) is read, its inverse and the safeguard script escape it, and the safeguard return restores it; the fake FortiGate of the tests now escapes quotes and backslashes in its output as FortiOS does.
- Changed behaviour: a request may carry `"` and `\` in a FortiOS text value (`comment` of an address or an address group, `description` of a DHCP reservation); the renderer writes both escaped inside the quoted value, so `undo` of an operation that changed or deleted such a comment requests it back. Before, the request was refused with `attribute comment may hold printable ASCII only, without quotes or backslashes`, also for `undo`, and only the safeguard restored such a comment. A control character or a character outside ASCII is still refused (`attribute comment may hold printable ASCII only`), and ExtremeXOS text values still refuse `"` and `\` with the earlier message, because the ExtremeXOS CLI has no escape for them. `docs/planning.md` describes the rule.
- Changed behaviour: `create` compares the new key with the object names and with the values that can name an object, no longer with secrets and free text: on FortiOS not with attributes whose name contains `password`, `passwd`, `passphrase`, `pwd`, `secret`, `psk`, `key`, `community`, `token`, `comment` or `description`, nor with `name` of `system snmp community`; on ExtremeXOS not with commands of `snmp` or `snmpv3`, the word after `community`, `encrypted`, `password` or `shared-secret`, nor the text after `description`, `description-string`, `display-string`, `sysName`, `sysContact` or `sysLocation`. `delete` and `update` find references the same way. Every other value still counts, so a new object still cannot take a name that an existing or dangling reference resolves to. A `delete` of a referenced object is refused with `object '<key>' is referenced in the configuration`, without the section, entry, attribute or line. A `preview` with the result `rejected` counts in `rejections_per_hour` like a refused `apply`, under the same lock; a refusal by an exhausted budget is still not counted. Before, `preview` and `apply` answered whether a guessed key equalled a plaintext SNMP community, a secret or a comment anywhere in the configuration, `delete` named where the value was, and refused previews were not counted, so guesses were unlimited. An ExtremeXOS VLAN can now take the name of a port display string, and a FortiOS address the text of a comment. `docs/planning.md` lists the compared values, `docs/execution.md` what remains.
- Tests: synthetic secrets in the device snapshots (FortiOS administrator, user, IPsec, certificate, RADIUS, TACACS+, Wi-Fi and SNMP secrets; ExtremeXOS account, RADIUS, TACACS and SNMP secrets), in the vault and in the free text are run through the commands and the failure paths of the command line and of MCP and searched for in every output, the journal, the audit log and the notifications received by a local HTTP server, also in hexadecimal, URL-encoded and base64 form. None was found; no code changed. `docs/execution.md` describes where each piece of data goes, what the notification carries, and, as a known limit, that a refused `create` confirms a guessed key equal to a value in the configuration such as a plaintext SNMP community.
- The reason of a change that was not confirmed because the snapshot after the change was refused names the cause: `snapshot incomplete` (no `#config-version` header, no section of the table, no ExtremeXOS `vlan` module), `snapshot scope unsupported` (a FortiOS dump wrapped in `config global` or `config vdom`, or a header with VDOMs enabled), `snapshot unreadable` (does not parse, not UTF-8, too large), `snapshot firmware mismatch`, or `postcheck rejected` for any other refusal of the comparison. `administrator table` remains only for the account check: another account list, changed account entries, or an administrator table that cannot be read. Before, every one of these gave `administrator table` in the journal record, its `postcheck_failed` step, the audit log, the notification and the block. Blocking is unchanged: all of these reasons block the device as before, and the account check before a change still blocks with `administrator table`.
- The MCP server announces itself in `initialize` as `serverInfo` `{"name": "netops-admin", "version": "0.2.5"}`, the package name and version. Before, it sent `{"name": "NetOps Admin", "version": "4.0.5"}`, the version of FastMCP.
- Changed behaviour: `netops-admin recover` exits with `6` when an operation it settled left the device blocked, instead of `0`.
- The results and reasons that block a device are defined once (`netops_admin.blocking`) and used by the journal, the notification and the command line.
- Changed behaviour: `netops-admin apply` and `netops-admin undo` exit with the new code `6` when the result is `confirmed` with a reason that blocks the device (`not persisted`, `foreign change during save`, `saved configuration unverified`). Before, they exited with `0` as for a clean confirmation, so a script saw success although the device refused every further change. `confirmed` without a blocking reason still exits with `0`, other results with `4`. The MCP answer is unchanged and carries `result` and `reason`.
- Take the last snapshot of the confirmation while the safeguard is still installed. A change by someone else between the checks after the change and the confirmation is now returned by the safeguard: `reverted`, reason `foreign change`, device blocked, as `docs/execution.md` describes. Before, the admin removed the safeguard first, left the planned change unsaved on the device and reported `unknown` with the reason `safeguard fired during confirmation` and no differences. An unreadable last snapshot now waits for the safeguard and verifies the return, reason `final check unavailable`.
- After the removal of the safeguard, take one more snapshot. When it differs from the prediction the admin does not save, reports `unknown` with the reason `foreign change after the safeguard was removed` and the differences, and blocks the device. The reason `safeguard fired during confirmation` remains only for a snapshot that shows the object in its previous state and the rest unchanged.
- On ExtremeXOS, take a snapshot after `save configuration`. A change by someone else stored by the save gives `confirmed` with the reason `foreign change during save` and the differences; an unreadable snapshot gives `confirmed` with the reason `saved configuration unverified`. Both block the device and the notification says so. The save itself cannot be tied to a checked snapshot; `docs/execution.md` describes the remaining window.
- `scripts/export_status.py` takes `--audit-file`, the absolute path of the audit log the syslog-ng destination reads, and records it in the status as `audit_file`. A status that names another file than `audit_file` of the configuration no longer acknowledges `audit_delivery` and blocks the export: enrollment and new changes are refused with the reason `the export status covers another audit file`, and `doctor` reports it. Before, an instance whose `export_status_file` pointed at the status of another instance's audit log reported `acknowledged` for events no shipper read. A status without `audit_file` is accepted as before; `doctor` notes that it does not name the audit file. Documentation: `audit_delivery` stays `pending` until `status` (command line or `admin_status`) reads the operation, and that read writes the journal record and a `delivery` event.
- Enable the FortiOS profiles `firewall addrgrp` and `system dhcp server/reserved-address` on 8.0.0 build0167, after the one-shot automation stitch was measured there with the same commands as on 7.6.7 build3704: member additions and removals, reservation create, update and delete; a reservation recreated by the inverse keeps its ID. Other FortiOS 8.0 builds stay refused for both tables.
- ExtremeXOS `vlan-membership` and `ports`: before planning, the write account reads `show ports no-refresh` and the plan keeps the listed ports as `ports`. While the configuration holds no `configure vlan default delete ports all`, a listed port without another native VLAN is untagged in `Default`, so a port that was never configured can be planned (0.2.4 refused it with `object '<n>' does not exist`) and the inverse of a native move returns it to `Default`; the planner, `verify`, the safeguard return, `recover` and the audit use that membership, and the `delete ports all` line counts as membership. A port the switch does not list is refused with `port <n> is not reported by the switch`, for a display string too. A port in a link aggregation is refused with `VLAN membership changes on link aggregation ports are unsupported` also when it has no VLAN line (before: `object '<n>' does not exist`). Offline `plan` takes the list with `--ports`. Plans without `ports`, such as those in a 0.2.4 journal, are read as before. The EXOS profiles are unchanged. The port list and the refusal of an unlisted port were run on the EXOS-VM image and on the X440-G2, and changes of never-configured ports on factory EXOS-VM images.
- ExtremeXOS: the explicit form of `Default` that a switch prints after its first membership change also counts as membership when it holds `configure vr VR-Default delete ports <ports>` or `configure vr VR-Default add ports <ports>` naming exactly the listed ports, and `configure sys-recovery-level switch reset`, the default the switch prints after the first change of a port, is left out of the comparison of every table. Before, a factory EXOS-VM image returned the first membership change of a never-configured port as a foreign change and blocked the device. Another recovery level and a VR port line with other ports are still compared.
- ExtremeXOS display string on a never-configured port: with the port list of the plan the rest of the configuration is compared through the VLAN membership model, the port itself included, because the display string alone makes a factory switch print the explicit `Default`; and the audit of the `ports` table holds the implicit `Default` of the listed ports, as the audit of `vlan-membership` did. Before, such a display string was refused by the audit with `exos.management.port-native` when the policy listed the port, and otherwise returned as a foreign change with the device blocked. Plans without a port list compare the lines as before.
- Documentation: `docs/installation.md` says that an upgrade which changes a profile file, as 0.2.5 does, needs a new enrollment of every device, and that the exporter should run with `--audit-file`; `docs/execution.md`, `docs/review-020.md` and the repository's verified support record the measurement of the address group and DHCP reservation profiles on FortiOS 8.0.0 build0167.
- Measured on 29 September 2026 with an earlier state of this version, which still pinned `netops-auditor` 0.2.8 and `netops-core` 0.2.5, on FortiOS 8.0.0 build0167 (FortiGate 60F: address group and DHCP reservation writes, `undo`, returns by the stitch, a change by someone else before and after the removal of the safeguard), on ExtremeXOS 33.6.1.14 (EXOS-VM) and 33.7.1.6 (X440-G2 hardware: changes by someone else in the confirmation windows with the exit codes `4` and `6`, the port list), with `recover` after a killed process on the EXOS-VM image and with the exporter started with `--audit-file`; an archive built from that state, installed by its own guide, then ran on the EXOS-VM image with the exit code `6` of `recover` and `undo`, and a failed save is covered by tests only. See [verified support](../../docs/verified-support.md#admin-025-validation-29-september-2026). On 2 October 2026 the source of this version with `netops-auditor` 0.2.9 and `netops-core` 0.2.6 ran on FortiOS 8.0.0 build0167 and ExtremeXOS 33.6.1.14, among it `undo` and the safeguard return of a FortiOS comment with quotes and a trailing backslash, a lost safeguard removal, protected references and the refusals of `preview`, and `doctor` on a factory EXOS-VM image; see [verified support](../../docs/verified-support.md#candidate-check-of-the-release-sources-2-october-2026). A failed save is still covered by tests only.
- Documentation: the upload to PyPI is a separate manual step and is postponed. `docs/installation.md` names the versions on PyPI on 1 October 2026 and installs 0.2.5 only from the release archives, each verified with its release `SHA256SUMS` and Sigstore bundle (`cosign verify-blob` with the maintainer's certificate identity, the same as for `netops-helper`); the README and the release guide no longer say that `pip install netops-admin` installs this version. `docs/execution.md` says that auditor 0.2.9 leaves the same secret and free-text attributes out of `address-unused` as the planner.
- The version gate also checks that `CHANGELOG.md` opens with the only heading of the version in `pyproject.toml`.
- The wait for a safeguard to fire is bounded by the longest allowed `safeguard_seconds` (900) plus 20 s of grace and 60 s of slack, 980 s in all. Before, it gave up after 600 s, so a device configured with a safeguard of about 600 s or more ended `unknown` and was blocked while the safeguard later returned the change; every allowed value now ends with the verified result.
- Changed behaviour: an object that refers to a name listed under `protected` of the device, before or after the change, is not changed at all: every create, update or delete of it is refused before any mutation, also a change of another member or of a description. A reference is a member of an address group (`member`), a tagged or native VLAN of a port (`vlan-membership` `tagged` and `untagged`; for a display string in `ports` the VLAN membership of the port in the snapshot, the implicit `Default` of the listed ports included) and, on ExtremeXOS, a port that a VLAN holds (`vlan`). Names are compared without letter case and across the tables of `protected`; the built-in protected names of the profiles (`all`, `none`, `Default`, `Mgmt`) count only when they are listed. When a name is protected and the VLAN membership of the snapshot cannot be evaluated, a change of a port or of a VLAN is refused. Before, only the key was compared, so a protected address could be added to or removed from a group and a port of a protected VLAN could be changed, although `docs/installation.md` promised protection of the objects that refer to the protected names; `docs/installation.md` and `docs/planning.md` describe the references.
- Documentation: `docs/execution.md` says how an ExtremeXOS membership line with `all`, a port range across slots or no `tagged`/`untagged`, an unterminated UPM profile, and a FortiOS snapshot with a `config global` block or a truncated one stop an operation: refused before any mutation, or after the change not confirmed and returned by the safeguard. Tests cover each case with the auditor of this tree, whose rule states the audit gate reads (see the entry on `rule_status` above).
- Changed behaviour: `netops-admin apply` and `netops-admin preview` refuse a request whose `device` field names another device than `--device`, before the device is contacted. Before, the field was ignored and the request ran on the device of `--device`. The MCP tools pass the same `device` for both and are unchanged.
- The count of refused requests (`rejections_per_hour`) is updated under a lock. Before, concurrent processes lost refusals: with 4 processes of 100 refusals each, fewer than 400 were counted.
- Every journal file is written through its own temporary file, and the write probe of the journal uses its own file name. Before, all writers of one file shared `.<name>.tmp`, opened with truncation: concurrent writers failed with `FileNotFoundError` on a temporary file another process had already renamed and could leave a mixed file, and two operations on different devices could refuse each other with `the journal cannot be written durably: No such file or directory`.
- An unreadable `rejections.json` (not JSON, not a list of times) refuses every request with `the count of refused requests (rejections.json) cannot be read; a person must check it`, and a request refused for another reason keeps its reason. Before, the decoding error escaped `apply` and `preview` instead of a refusal, and a JSON object was read as an empty count.
- Test: an ExtremeXOS display string with a space, in a request to the renderer or taken from the snapshot for the inverse, is refused.
- `netops-admin verify` refuses a plan whose values have the wrong type (for example a number as `key`, a list as `table`, an unknown `op` or `platform`, a text as the predicted state before the change) with `plan holds a value of the wrong type` and the exit code `3`. Before, such a plan ended in a Python traceback with the exit code `1`, the code of a snapshot that does not match.
- Changed behaviour: `notify.timeout_seconds` must be a number from 1 to 60. Before, any value `float()` accepted was taken, also a negative, zero, infinite or NaN timeout or a text such as `"10"`, and a value it did not accept ended in a traceback; a timeout outside the range made every notification fail.
- `recover` settles an operation interrupted before its safeguard was planned without contacting the device, and when the device cannot be reached it records the step `recovery_access_failed` and settles the operation as `unknown` with the reason `interrupted; device unreachable`, which blocks the device. Before, the error of the connection escaped `recover` and the operation stayed `running` without a record.
- `enroll` removes the previous enrollment of the device only right before the probe is written: after the probe has been planned, has passed the checks `apply` runs before a change and the notification of the self-test was delivered. Before, it removed a valid enrollment first, so an invalid `--probe` or any refusal before the write left the device without enrollment and refused every change.
- `unblock` of a device that is not blocked keeps the fingerprint of the administrator accounts; notifications are still waived as before. Before, it returned `false` but removed the fingerprint without an audit event, so the next operation took the current accounts as the new reference.
- `preview` of a request whose `request_id` was already used for a different request returns `rejected` with `request_id was already used for a different request`, the reason `apply` gives. Before, it returned `known-request` and said that `apply` would return the earlier operation.
- An unreadable state file (an operation, a request, a block, an account fingerprint or an enrollment that is not UTF-8 JSON, not a JSON object, cannot be opened or lacks one of its identifiers) refuses `apply`, `preview`, `recover`, `status`, `unblock` and `notify-retry` with `the state file <name> cannot be read; a person must check it`, and `doctor` reports it as `refused`, an unreadable enrollment included. A known `request_id` whose operation file is missing is refused the same way and names that file. Before, the decoding error or a `KeyError` escaped these commands, `apply` returned nothing for a missing operation file while `preview` reported `known-request`, and an unreadable account fingerprint blocked the device as a changed administrator table. A `rejections.json` that cannot be opened now refuses like one that cannot be decoded; before, the `OSError` escaped `apply` and `preview`.
- `scripts/export_status.py` writes the status and its `.pending-since` file each through its own temporary file, created exclusively, and removes it when the write fails. Before, every run used `.<name>.tmp`, opened with truncation: concurrent runs failed on a temporary file another run had already renamed, and a symbolic link placed at that name was followed by the root timer; `.pending-since` was written in place.

## 0.1.0 - internal milestone (not published)

Initial internal implementation.

- `netops-admin plan` and `netops-admin verify`: a request validated against a table profile and a snapshot, commands, inverse and predicted state; comparison of a later snapshot with the prediction.
- Profiles: FortiOS 8.0.0 build0167 `firewall address` and ExtremeXOS 33.7.1.6 `vlan`, each with create, update and delete, enabled only on firmware where the rollback was measured on a device. Snapshots are parsed with the netops-auditor parsers.
- `netops-admin apply` behind an on-device safeguard: a one-shot automation stitch on FortiOS, a Universal Port Manager profile and one-shot timer on ExtremeXOS. Journal synced before the first mutation, device lock, `request_id` deduplication, account checks before and after a change, device block after an unknown result, a failed return, a foreign change, an unexpected account or a change that could not be saved.
- Before a confirmation, a read-only check account reads the object and the auditor rules are evaluated on the new snapshot; both are also required to work before the change. A new finding of severity high or medium, an evaluation that does not complete, or a check account that sees another state stops the confirmation and lets the safeguard return the change.
- A new change on a device waits until the notification of its previous operation is delivered; `unblock` can waive it after a check of the channel.
- Other administrator sessions on the device are counted and recorded in the journal, the audit log and the notification.
- Optional `check_address` lets the check account use another management address.
- ExtremeXOS profile `ports`: update of the port display string, measured rollback in both directions.
- A fingerprint of the account entries is kept after each operation and compared before the next one and after the change; `unblock` resets it.
- On ExtremeXOS: refusal when the switch holds unsaved changes, firmware check, `save configuration` after a confirmation or a verified return.
- Commands for a person: `status`, `recover`, `notify-retry`, `unblock` and `undo`, which returns a confirmed operation as a new operation behind a new safeguard and refuses when the object changed since.
- MCP server with two tools, `admin_apply` and `admin_status`; it finishes a running operation when the client disconnects. `fastmcp` is an optional dependency pinned in `requirements-mcp.txt`.
- Limits set by the administrator: changes per device per hour, changes per day, refused requests per hour, plan size and journal capacity, besides the request size and text lengths.
- Audit log with a closed event schema and no free text; export limits read from a shipper status file (`scripts/export_status.py` for syslog-ng); ntfy notification recorded separately from the result.
- Component gate: import allowlist per module, no programs started from the package, version agreement of `pyproject.toml`, package and SBOM, and a content scan of every released file.
